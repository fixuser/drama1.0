# 12 充值、一次性VIP与提现

## 1. 业务目标与范围

本章覆盖通用币充值、一次性VIP卡、支付订单/回调/对账，以及通用币提现审核和出款。

目标1.0保留：

- 固定通用币套餐与任意金额充值；
- 一次性VIP卡购买、激活/排队、到期、剧集解锁、历史账务及合法返佣；
- 支付渠道、订单、回调、支付回查和财务对账；
- 提现申请、冻结、审核、出款、回调、失败退回与记录。

明确排除：所有充值赠送（`giveaway`、双倍、匹配、活动赠送）、VIP自动续订/订阅回调/转移/连续订阅任务、VIP邀请活动。历史订单保留原始实付、赠送和状态用于审计。

## 2. 入口与角色

- 用户端：`/payments`、`/payments/pay/:id`、`/orders`、`/cards`、`/withdrawal`、`/withdrawal/record`、`/withdrawal/details/:no`。
- 财务端：充值订单、VIP订单、套餐、渠道、提现审核/批量导出/自动出款、异常订单与统计。
- 外部角色：充值支付商、App Store/Google、出款支付商、Sumsub KYC。
- 系统任务：支付回查、VIP到期、返佣解冻、提现异步队列、回调与对账监控。

## 3. 订单模型与状态

`Order` 包含订单号、用户、商品类型、引用商品、支付方式、单价、数量、实付、优惠、第三方单号和状态。商品包括任务、剧集、VIP、通用币套餐和任意通用币；本章只描述充值与一次性VIP。

订单状态包含未支付、已完成、已取消、退款/退款中、支付失败、`PAYMENT_AUTO`、转移等。目标1.0：

- 新订单只使用一次性支付状态；`PAYMENT_AUTO` 和转移仅用于历史兼容查询。
- `UNPAID→FINISHED` 只能由可信支付确认或受控人工补单完成。
- 终态回调幂等，不能从完成回退为未支付，也不能重复入账/返佣。

## 4. 充值

### 4.1 固定套餐

当前 `PointPack` 有原始通用币 `Amount`、售价/折扣价和 `Giveaway`。支付完成时现状入账 `Amount + Giveaway`。

**目标1.0：**

- 新订单只入账套餐明确购买数量 `Amount`；`Giveaway` 必须为0且不参与显示、入账、任务或返佣。
- 历史完成订单保留当时 `Giveaway` 字段和实际入账审计，不能改写为0。
- 套餐上下架、价格、币量和支付渠道按规则版本保存到订单快照。

### 4.2 任意金额充值

- 服务端读取币/美元及美元/IDR汇率，按用户输入的通用币数量计算支付金额。
- 渠道返回可用状态、币种、最小/最大IDR金额和手续费（如有）。
- 金额必须大于0、精度受限并在渠道范围内；汇率快照写订单。
- 不允许通过 `quantity_decimal` 负数、超精度或客户端总额改变入账。

### 4.3 充值主流程

1. 用户选择套餐/数量和渠道。
2. 服务端读取商品、渠道和汇率，生成唯一 `UNPAID` 订单。
3. 调用支付商创建支付意图/链接，保存第三方单号和请求摘要。
4. 支付商回调经签名验证后锁定订单、重查金额/币种/商户号。
5. 同一事务或可靠本地事件中将订单完成、增加通用币、写充值流水、生成合法返佣/任务事件。
6. 回调丢失时，`reconcileDepositOrdersCron` 每5分钟回查近6小时至3分钟前的未支付订单。
7. 对账比较支付商成功金额、订单实付、钱包入账和返佣。

提供方现状包含 EZ、Stripe、InTheBag、Monetapay、Haipay、JayaPay、FuturePay、Unispay、Apple和Google等；目标只启用已签约且配置完整的渠道，未使用实现应关闭路由。

## 5. 一次性VIP卡

### 5.1 商品与购买

`Plan` 配置名称、周期、价格和权益；订单数量必须为1。当前首次30日卡在非Apple/Google支付下有固定1单位优惠价，并支持月卡优惠券。

**待确认：**首次1单位价格和VIP优惠券是否被视为活动。目标建议所有新订单完全使用后台商品当前有效价格，不执行隐式首购促销；若业务要保留，应作为明确、可审计的商品价版本，而不是代码分支。

### 5.2 权益状态

`UserPlan` 至少区分排队、有效、过期、退款、转移等状态：

1. 支付完成创建权益；无当前有效权益则立即生效，有有效权益则按规则排队顺延。
2. 播放侧仅接受当前有效且未过期权益。
3. 每分钟 `checkUserPlanExpire` 处理到期和下一张卡激活。
4. 退款撤销相应权益并处理未解冻返佣；历史账务保留。
5. 目标不允许新自动续订、`PAYMENT_AUTO`入账、订阅回调、`TransferUserPlan`或连续订阅任务。
6. 已经成功扣款的历史自动续订权益继续履约至现有到期日，但不创建下一期扣款。

### 5.3 返佣

一次性VIP购买可按合法基础返佣参数向直接/间接上级产生冻结返佣；使用消费/赠送资产的例外规则需明确。VIP邀请活动额外奖励全部排除。

## 6. 支付异常与回滚

- 创建支付意图失败：订单保持未支付/支付失败，不入账。
- 回调金额、币种、商户或签名不匹配：拒绝并告警，不能仅信第三方“成功”状态。
- 订单已完成的重复回调：返回成功确认但不重复入账。
- 入账事务失败：订单不能成为不可补偿的完成状态；通过outbox/补偿任务重试。
- 取消未支付订单：释放锁定优惠券；当前订单创建与锁VIP优惠券不在同一事务，需修正。
- 退款：以反向流水冲销可退资产，冻结/撤销未结返佣；余额不足进入欠款/人工流程，不能删除原流水。

## 7. 提现前置与金额规则

### 7.1 前置条件

1. 银行卡属于本人且银行/钱包渠道启用；
2. 用户KYC为 `APPROVED`；
3. 用户绑定OTP时必须校验；
4. 配置要求人脸时，存在当日通过/已提交的提现人脸记录；
5. 用户正常且通用币可用余额足够；
6. 提现金额、手续费、汇率和到账金额由服务端重算。

### 7.2 P0 金额校验缺失

`CreateWithdrawal` 当前：

- 对 `ApplyCoinsAmount` 和 `ApplyAmount` 调用 `decimal.NewFromString` 后忽略解析错误；
- `minWithdrawalAmount`、`maxWithdrawalAmount` 的赋值代码全部被注释，因此保持0，后续上下限判断不执行；
- 未在余额校验前显式要求申请币数大于0；
- 余额判断仅为 `AvailablePoint < applyCoinsAmount`，随后执行 `available -= amount`、`frozen += amount`。

负数或非法输入的实际影响必须立即在隔离环境验证；按运算路径可能导致可用余额增加、冻结余额减少或异常提现单。此项为P0，修复前应在网关/服务端临时拒绝非正数并监控异常申请。

目标校验顺序：解析成功 → `amount>0` → 精度/单笔限额 → 日/周限额 → 余额 → 手续费后净额>0 → 渠道IDR限额 → 客户端展示金额一致性。

### 7.3 手续费与到账

当前每周从周日开始统计有效提现次数：首笔使用 `FirstWithdrawFeeRate`，其余使用 `SecondWithdrawFeeRate`，并取最低手续费：

`手续费币 = max(申请币 × 费率 ÷100, 最低手续费币)`

`IDR到账 = (申请币 - 手续费币) × 币兑USD汇率 × USD兑IDR汇率`

结果截断5位后与客户端传入到账金额比较。目标需明确周起点和业务时区，并以订单保存的汇率/费率快照为准；客户端金额只是防错，不是事实源。

## 8. 提现状态机与资产变化

现有状态包括待审核、拒绝、处理中、已到账、失败、审核通过、批量通过/到账/失败。

```text
创建 -> AWAIT_REVIEW（可用币减少，提现冻结增加）
AWAIT_REVIEW -> PROCESSING/APPROVE/BATCH_APPROVE（冻结不变）
PROCESSING/APPROVE -> ALREADY_RECEIVED（冻结扣除，写提现与手续费流水）
任一允许非终态 -> REJECTED/FAIL/BATCH_FAIL（冻结扣除，可用币原路退回）
```

管理服务 `handleWithdrawal` 对终态使用条件更新，仅允许从非终态迁移；受影响行数为0时跳过后续处理，具备终态幂等基础。账户、冻结流水、提现单和机器人券提现标志在同一事务更新。

目标要求成功只扣冻结一次，失败/拒绝只退回一次；手续费在成功时确认，失败不收。所有人工状态变更记录审核人、原因、IP和批次。

## 9. 审核、出款与对账

- 旧单笔 `ModifyWithdrawal` 已固定禁用；当前使用批量审核和 `AutoWithdraw`。
- 自动出款把单据发布到 `withdrawal:auto`，消费者按提现ID加分布式锁并调用选定支付商。
- 支持 Haipay、Jaya、FuturePay、Unispay 等银行/钱包映射和渠道金额限制。
- 当前银行卡无手机号时使用固定 `1235210602`；Haipay通知URL硬编码 `https://shortpro.app/...`，均应配置化并拒绝伪造用户数据。
- 部分外部请求失败路径只记录并返回，提现可能停留待审核/处理中；目标需要可重试队列、查询任务和超时告警。
- 支付商回调必须验签、按第三方单号/本地单号幂等映射，并只允许合法状态迁移。
- 每日/每批对账：申请币、冻结、成功币、手续费、IDR出款、支付商状态和退款必须守恒。

## 12. 验收场景

1. 固定套餐和任意金额充值按原始购买币量入账，`giveaway`始终为0；重复/乱序回调只入账一次。
2. 支付金额/币种/签名不匹配不入账；回调丢失可由回查恢复，订单、钱包和返佣对账一致。
3. 一次性VIP购买、排队、激活、到期和退款正确；关闭自动续订后不再创建下一期订单。
4. 已付费存量自动续订权益履约到期，历史 `PAYMENT_AUTO` 可审计但不产生新扣款/任务/邀请奖励。
5. 提现对空、非法、零、负数、超精度、低于/高于限额、余额不足均服务端拒绝且资产不变。
6. 正常提现创建后可用减少等于冻结增加；成功只扣冻结一次，失败/拒绝完整退回。
7. 首笔/后续手续费、最低费、业务周和汇率边界逐项核对，净到账必须大于0且符合渠道限额。
8. 出款重复点击、队列重投、支付商重复回调和终态乱序不产生重复出款或重复退款。
9. 所有充值赠送、VIP邀请及自动续订任务/通知/统计均不再产生新数据。
