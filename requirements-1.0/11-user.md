# 11 用户

## 1. 业务目标、角色与入口

用户模块负责账号注册登录、邀请关系、安全设置、实名/KYC、银行卡、账号状态和注销，是所有资产与业务权限的主体。

用户端入口：`/login`、`/register`、`/user`、`/security/*`、`/settings/*`、`/certifications/*`、`/bankCards/*`。管理端负责用户检索、状态、KYC/银行卡审计、团队关系及安全操作。

## 2. 用户类型与状态

现有类型包括普通用户、管理员、合伙人、业务员、子账号、审核账号和测试/泡沫账号。用户端登录只允许普通、审核和泡沫类型，后台角色通过独立权限体系登录。

| 状态 | 目标行为 |
| --- | --- |
| `NORMAL` | 可按权限使用保留功能 |
| `DISABLED` | 禁止登录和新资金动作，历史数据可审计 |
| `TERMINATED` | 已注销，不能恢复登录；个人标识匿名化，账务/KYC按合规保留 |
| 团队禁用/支持团队禁用 | 登录或团队能力受限；目标需区分“禁止登录”与“仅禁团队” |

当前登录把 `IsTeamDisabled`、`IsTipsTeamDisabled` 与账号禁用一起拒绝登录。业务需确认团队处罚是否应阻断整个账号。

## 3. 注册

### 3.1 主流程

1. 用户以邮箱或手机号获取并提交注册验证码。
2. 邮箱统一小写，校验禁用后缀；密码拒绝纯数字并满足最小长度/强度。
3. 服务端校验验证码、邮箱/手机号唯一。
4. 如有邀请码，区分粉丝码 `F...` 和分销码，校验邀请人正常及邀请权限，生成邀请链。
5. 事务内创建用户、渠道事件和邀请日志。
6. 默认用户类型为普通；历史 `TipsLevel_VIP` 只表示支持等级L1。
7. 生成登录令牌并推进注册任务。

### 3.2 目标1.0

- 注册核心事务不得同步执行活动资格、活动赠送或活动邀请计数；相关现状钩子全部关闭。
- 邀请关系采用统一领域函数，注册、后绑定和机器人券自动绑定使用同一校验。
- 邮箱/手机号在数据库层有规范化唯一约束，避免并发重复。
- 密码规则由配置/安全策略定义，不仅依赖“是否可转为整数”。
- 新用户默认是否可邀请使用语义清晰的 `invite_enabled`；当前字段和注释方向相反。

## 4. 登录与会话

### 4.1 现状

1. 第一步按邮箱/手机号查询并校验密码、用户状态和类型。
2. 首次登录国家与本次IP国家不同会把 `IpStatus` 标为异常，但仍继续生成令牌。
3. 代码先判断用户是否绑定OTP，随后固定 `isOpt=false`（变量拼写如此），实际关闭登录OTP第二步。
4. 无OTP流程写登录日志并生成token；第二步逻辑仍保留但通常不会被要求。
5. 忘记密码成功后清除用户token。

### 4.2 目标规则

- OTP开关按安全配置和用户绑定状态生效，不能用代码常量关闭。
- 登录token区分“密码已验证”和“OTP已验证”，未完成第二步不能访问业务接口。
- 异常IP应触发风险策略（额外验证、通知或限制高风险资金动作），不是只写标记。
- 退出、改密、注销和管理员禁用后撤销所有会话。
- 登录日志包含用户、设备、IP/国家、结果和失败原因，但不记录密码/OTP/token明文。

## 5. 安全设置

### 5.1 当前能力

- 设置/修改登录密码和支付密码；初次设置支付密码通过 `UpdateUser`，后续通过安全token。
- 邮箱、手机号变更通过验证码和安全中心token。
- 生成/绑定/修改OTP。
- 忘记密码通过邮箱/手机号验证码重置。

### 5.2 P0 全局超级密码

`models.User.CheckPassword` 和 `CheckPayPassword` 都读取 `super.password`，任意非管理员用户在输入该值时可通过登录密码或支付密码校验。

- **代码路径已确认。**生产环境是否配置、谁知悉以及使用日志需立即核查。
- **目标1.0：**彻底移除用户登录/支付路径的全局绕过；管理员协助只能通过有审批、短时、单用户、不可用于支付的重置流程。
- 如已配置，立即轮换/清空并审计登录、支持、剧集购买、提现等使用支付密码的历史异常。

### 5.3 其他已确认问题

- `ChangeUser` 设置/变更邮箱的分支明确没有唯一性检查。
- OTP设置分支在 `user.CheckOtp(req.Value)` 返回真时反而报“OTP错误”，判断方向疑似反转。
- 登录OTP被硬编码关闭。

上述均需在隔离环境复现；邮箱唯一性和OTP错误优先级为P0/P1（取决于生产数据库约束与实际入口）。

## 6. 邀请关系

系统同时存在 `InviterFans`（粉丝链）、`InviterUserIds`（分销/CPS链）、粉丝码和创建时邀请码。

目标规则：

1. 一个用户的直接粉丝上级只允许绑定一次，除明确的合规迁移流程外不可修改。
2. 邀请链最长深度和每种返佣使用哪条链明确记录。
3. 禁止形成自邀请和环；绑定时在事务内检查。
4. `IsInviterFansDisabled` 当前字段注释为“是否拥有邀请权限”，但多处以 `!field` 判为禁止；需数据字典确认后重命名迁移。
5. 注册、`BindFansCode`、机器人券自动绑定不能分别实现不同方向的权限判断。
6. 邀请关系变更不追溯修改历史返佣，所有结算保存当时来源链快照。

## 7. KYC与提现人脸验证

### 7.1 首次实名

- 当前H5使用 Sumsub；服务端按用户是否已 `APPROVED` 选择首次身份验证或人脸验证级别。
- Sumsub `applicantReviewed` 回调读取申请人证件/姓名，映射为 `Verification` 和用户 `VerifiedStatus`。
- `GREEN` 视为通过；部分 reject label 解释为“人脸通过但实名信息不符”。
- 首次流程更新用户和Verification；重复回调不改已通过实名状态。

### 7.2 提现人脸

- 从提现入口初始化时创建 `WithdrawFaceCheck(WAITING)`。
- 回调更新当日最近一条等待记录为人脸通过、姓名不符或人脸拒绝。
- 服务端开关 `withdrawal.face_check_required` 启用时，创建提现要求当日 `FACE_PASSED` 或 `SUBMITTED`。
- H5提现页的人脸状态前置判断有被注释路径，不能依赖前端；服务端校验必须保留。

### 7.3 目标要求

- 验证供应商回调签名、时间戳和事件幂等；原始敏感响应加密/脱敏保存。
- 回调按供应商事件ID和申请人ID匹配，不只查“当天最近一条等待记录”。
- KYC状态和提现单使用的验证记录建立明确关联。
- Zoloz/手工实名等旧路径若不再使用应关闭入口但保留历史审计。
- Sumsub回调中的活动触发全部移除。

## 8. 银行卡

1. 仅实名通过用户可新增银行卡。
2. 当前持卡人姓名必须精确等于 `FirstName + 空格 + LastName`；大小写、多空格、单名制和姓名顺序可能导致误拒绝。
3. 卡号在全局查询中不得重复；银行卡绑定用户，列表排除软删除项。
4. 提现前还要验证该银行/钱包渠道当前启用。

目标建议使用规范化姓名比对或供应商账户名验证，保留原始姓名和匹配结果；卡号加密保存、展示仅后四位，搜索使用不可逆索引。

## 9. 账号注销

现状注销将邮箱/手机号追加匿名后缀、状态改为 `TERMINATED` 并解绑第三方账号；财务、KYC、订单、流水和邀请历史仍保留。

目标注销前检查：未完成提现、有效持仓、冻结资产、有效一次性VIP和争议订单。无法即时注销时进入关闭中并说明原因。完成后撤销token、推送token和第三方授权，禁止新登录；审计所需数据按保留期限脱敏保存。

## 10. 接口、模型、缓存和证据

主要接口：

- 登录注册：`/v1/users/login/step1`、注册、登出、忘记密码、验证码
- 用户资料：`/v1/users/get`、`/v1/users/update`、`/v1/users/change`、`/v1/users/delete`
- 安全：安全token、OTP生成/绑定、支付设置
- 邀请：邀请列表、绑定粉丝码、邀请链接
- KYC：`/v1/sumsub/initialize`、Sumsub回调、实名查询、提现人脸状态
- 银行卡：`/v1/user/bank/create`、`list`、`modify`、`/v1/user/withdraw/bank/list`

核心模型：`User`、`LoginLog`、`InviteLog`、`Verification`、`WithdrawFaceCheck`、`BankCard`、第三方绑定。

核心证据：

- `splay/services/user/user.go`、`security.go`、`otp.go`、`tips.go`、`sumsub.go`
- `splay/models/user.go`
- `splay/apis/userpb/user.proto`、`splay/apis/basepb/model.proto`
- `h5/src/pages/Login/`、`Register/`、`Security/`、`Certifications/`、`BankCards/`
- `admin/src/pages/Users/`

## 11. 问题、疑问与建议

| 级别 | 类型 | 内容 |
| --- | --- | --- |
| P0 | 已确认 | 全局 `super.password` 同时绕过登录与支付密码 |
| P0/P1 | 已确认/需验证影响 | 变更邮箱不做唯一性检查；需确认数据库约束能否兜底 |
| P1 | 已确认 | 登录OTP被固定关闭，设置OTP判断方向疑似反转 |
| P1 | 已确认 | 邀请权限字段命名与多处判断/注释方向冲突 |
| P1 | 需验证 | 邀请链数组在部分路径可能混用 `InviterFans` 与 `InviterUserIds`，空粉丝码路径有解引用风险 |
| P1 | 待确认 | 团队禁用是否应禁止整个账号登录；姓名匹配规则和单名用户如何处理 |
| P1 | 建议 | 将身份认证、登录风控、邀请绑定拆成明确领域服务并增加不可变安全审计 |

## 12. 验收场景

1. 邮箱/手机号并发注册和变更均保持唯一，验证码不可重放。
2. 普通密码、错误密码、绑定OTP、异常IP、禁用/注销状态的登录结果符合规则。
3. 任意全局配置值不能绕过用户登录或支付密码；安全重置有单用户审批审计。
4. 注册、后绑定和机器人券绑定在自邀请、环、禁用邀请人、已绑定用户场景一致。
5. Sumsub成功、拒绝、姓名不符、重复/乱序回调均得到幂等状态；提现使用正确验证记录。
6. 银行卡仅实名用户可绑，归属和渠道正确，敏感信息脱敏。
7. 注销前置条件、token撤销、第三方解绑和历史账务保留均可验证。
8. 注册、KYC和邀请流程不再生成任何活动资格、赠送或活动任务进度。
