# 01 系统架构与工程边界

> 状态：2.0 实施约束。本篇定义进程、领域、数据库、事务、异步任务和运维边界；各领域文档不得放宽这些约束。

## 1. 目标与验收标准

2.0 不在 1.0 `splay` 上继续堆功能，而是以空 PostgreSQL Schema 重建可以被证明正确的后端。架构目标是：

1. 一个业务动作中的用户、资产、订单、持仓、关系、等级脏标、任务事实和审计记录，只要属于同一业务结果，就在 `database.default` 的一个本地事务中同成同败。
2. 业务包不能绕过事务直接写表；所有写原语只接受已开启的 `Tx`，不接受裸 `DB`。
3. 主从路由是可观测的静态决策：`default` 承担全部写入和强一致读，`slave` 只承担允许延迟的命名查询。
4. 事务内没有 Redis、HTTP、RPC、对象存储、短信、邮件或支付商请求，数据库锁时间不受外部网络抖动影响。
5. 不建通用 Outbox。可从数据库事实重建的异步工作，以领域表中的 `status` / `dirty_at` / `next_run_at` 为持久待办，Redis 信号只缩短延迟。
6. 同一命令重放、同一渠道回调重推、多 worker 并发抢任务，都不能导致重复入账、重复发奖或重复迁移状态。
7. 四个进程能够在空库上按顺序部署，业务进程不自动建表，应用代码不包含历史迁移、双写或割接分支。

## 2. 核心决策

| 主题 | 2.0 决策 |
| --- | --- |
| 部署单元 | `apid`、`mand`、`workerd`、`migrate` 四个独立二进制 |
| 业务真源 | PostgreSQL `database.default` |
| 主从 | `default` 写 + 强一致读；`slave` 弱一致读 |
| 事务边界 | 顶层 Use Case 一次 `RunInTx`，内部写原语共享同一 `Tx` |
| 隔离级别 | PostgreSQL `READ COMMITTED` |
| 并发正确性 | 条件更新 + 唯一约束 + 必要处 `FOR UPDATE` + 固定锁序 |
| 跨边界事件 | 提交后最小信号，消费者回查数据库 |
| 可靠异步 | 领域状态/脏标 + `default` sweep，不依赖 Redis 保正确 |
| Outbox | 不建表、不设全局开关、不用于同库领域写 |
| 错误契约 | 锁定 Forge `v0.4.1`；Service 将 Domain error 映射为 `errkit`，Transport 统一编解码 |
| 外部 callback | 原始 HTTP + 固定字面量路由 + raw-body 验签 + 内部 typed command；不建 callback Proto |
| 外部消息 | Forge `message` 只作 SMS/Email transport；事务外发送，primary 状态/lease/sweep/retry 保正确 |
| Schema | 只有 `migrations/default/`；`slave` 不有独立 Schema |
| 时间 | 业务时区固定 `Asia/Jakarta`，周一为每周起点 |

## 3. 进程拓扑与职责

### 3.1 进程清单

| 进程 | 入口 | 责任 | 不得承担 |
| --- | --- | --- | --- |
| `apid` | 公开 gRPC + HTTP Gateway + 供应商原始 callback HTTP | APP 登录、用户、短剧、资产、订单、持仓、任务等在线 Use Case | 管理权限、定时扫描、全量导出、Schema 变更 |
| `mand` | 管理 gRPC + HTTP Gateway | 后台登录、RBAC、数据范围、配置发布、审核、人工纠偏、运维查询 | APP 令牌、业务 cron、自动迁移 Schema |
| `workerd` | 无公开业务 API，仅健康/运维端点 | 领域 sweep、收益 rollup、对账、到期结算、等级重算、外部投递 | 承载用户同步请求、拥有不可重入的单实例假设 |
| `migrate` | CLI | 对 `database.default` 执行 `init/up/status`，开发环境可 `down` | 启动服务、连 Redis、对 `slave` 执行迁移 |

### 3.2 进程组装规则

- 每个进程只组装自己需要的 Provider。`apid` / `mand` 不启动 cron 和队列消费，`workerd` 不注册公开业务路由。
- `apid`、`mand`、`workerd` 在任何 Forge Provider 启动前各自调用一次 `ConfigureErrorContract`，全量注册 `errkit` Encoder/Decoder、code name 及 gRPC/HTTP 映射；注册是进程级不可变启动步骤，禁止在请求期间修改。
- 进程之间不通过 Go 全局单例相互调用；它们通过共享的数据事实协作。
- 同一领域逻辑可被 `apid`、`mand`、`workerd` 共用，但业务决策必须位于 Use Case / Domain，不放在进程组装包。
- 四个进程的构建版本、Schema 最小/最大兼容版本和配置版本都进健康信息，不兼容时启动失败。

## 4. 分层、领域与依赖方向

### 4.1 分层

| 层 | 内容 | 允许依赖 | 禁止 |
| --- | --- | --- | --- |
| Transport | Proto/HTTP 绑定、参数转换、身份提取、`errkit` 编解码 | Use Case、API 类型、Forge `errkit` | SQL、领域状态机、跨表写 |
| Use Case | 一个可验收的用户/管理/作业动作，持有事务边界 | Domain、Repository 接口、Unit of Work | 直接拼散落 SQL、调用另一个 RPC 来完成同库写 |
| Domain | 状态机、金额变动意图、等级/任务/资格纯规则、sentinel/typed error | 领域类型 | API 生成物、Forge/`errkit`、数据库连接、Redis、网络客户端 |
| Repository | 按领域意图命名的读写原语 | Domain、Bun/PostgreSQL | 发送消息、开启嵌套事务、跨领域编排 |
| Infrastructure | DB/Redis/支付/短信/邮件/存储实现、日志和指标 | 第三方库 | 业务资格和金额规则 |

### 4.2 领域所有权

| 领域 | 所有的核心事实 | 向外提供的写意图 |
| --- | --- | --- |
| Identity/User | `users`、凭据、登录标识、KYC、银行卡 | 注册、身份变更、安全状态变更 |
| Relation/Level | `users.parent_id`、`users.inviter_ids`、`referral_edges`、`user_levels` | 绑定上级、置脏、重算并记录等级变化 |
| Asset | `user_assets`、`asset_ledgers`、`asset_freezes` | 入账、出账、冻结、解冻、结算冻结、冻结收益 |
| Order/Payment | 充值单、提现单、一次性 VIP 单、支付回调事实 | 建单、合法迁移、产生资产变动意图 |
| Drama/Holding | 短剧、剧集、解锁事实、`Playlet Backing`/机器人持仓、收益事实 | 解锁、参与/购买、日结、到期 |
| Task/Voucher | 任务定义、用户进度、领取记录、`Robot Activation Voucher` | 记录可验证进度、领取、占用/核销券 |
| Config/Stats/Audit | 配置版本、收益 rollup、作业记录、操作审计 | 发布配置、推进水位、记录审计 |

跨领域业务由顶层 Use Case 编排。例如“解锁剧集”由同一 Use Case 在一个事务中调用资产扣款原语和剧集解锁原语；Drama 不通过 RPC 调用 Asset Service，Asset 也不理解剧集规则。

### 4.3 Forge 错误契约

`github.com/toolbelts/forge` 首发锁定 `v0.4.1`，`errkit` 只出现在 Service/Transport 边界：

1. Domain 和 Repository 返回可判定的 sentinel/typed error 并保留 cause，不 import Forge、Proto 或 gRPC。
2. Service 使用一个受测 mapping registry 将领域/基础设施错误转为 `errkit.Error`；需保留内部 cause 时用 wrap，对外 message 只允许稳定安全摘要。
3. Transport 通过应用 `api/common/v2/error.proto` 实现 Encoder/Decoder，并为每个非零业务码注册 code name、gRPC code 与 HTTP status。`request_id` 来自 header/metadata；字段错误和重试细节由 Proto detail 表达，不假定 `errkit` 自动生成。
4. 未包装的 SQL、供应商或内部错误一律映射为安全 `INTERNAL`；原错误只进入脱敏日志。callback 对外依供应商协议返回 ACK，不套通用 errkit JSON。
5. CI 遍历 Proto 错误目录和 mapping registry：缺 code name、Encoder/Decoder、gRPC/HTTP 映射或安全 message 的任一码都不得合并。

## 5. 数据库实例与主从路由

### 5.1 配置契约

- `database.default` 必填，使用可读写业务角色，承担全部 DML、事务、锁、幂等检查和读己之写。
- `database.slave` 可选。本地和单库环境未配置时，在组装层一次性别名到 `default`；业务代码不自行判空或切换。
- 生产 `slave` 使用独立 PostgreSQL 只读角色，只授予必要 Schema 的 `SELECT`，并设置会话默认只读。启动时校验连接目标、时区、只读设置和角色权限；不满足时生产进程启动失败。
- 两个 DSN 即使指向同一物理主库，也是两个连接池。`default` 事务中经 `slave` 或裸 `default DB` 发出的语句不属于该事务。
- 只有 `migrations/default/`。复制库通过 PostgreSQL 复制获取 Schema，`migrate slave ...` 在连库前就拒绝。

### 5.2 查询路由矩阵

| 查询 | 路由 | 原因 |
| --- | --- | --- |
| 事务内的任何读 | 当前 `Tx` | 共享未提交写入、锁和事务快照 |
| 余额、冻结、限额、券状态、订单状态、幂等结果 | `default` | 结果决定后续写入，不能读到旧值 |
| 登录、权限、数据范围、安全状态 | `default` | 安全决策失效不能容忍复制延迟 |
| 刚刚发布的配置和写后回读 | `default` | 读己之写 |
| 短剧内容列表、已封账历史、后台列表 | 命名 `...FromReplica` 查询 | 允许短暂陈旧，减载主库 |
| 报表、导出、对账候选集、全量扫描 | 命名 Replica 查询，最终 claim/复核走 `default` | 大扫描与最终一致性分开 |
| worker 抢占、清理 `dirty_at`、推进 `next_run_at` | `default` 事务 | 从库不能参与状态迁移 |

仅查询 Repository 可以持有 Replica Reader，方法名必须表达弱一致语义，如 `List...FromReplica`、`Scan...CandidatesFromReplica`。Use Case 不接受“是否走从库”的布尔参数。

## 6. 事务模型

### 6.1 顶层 Use Case 的固定流程

1. 解析身份、校验请求形状和非数据库前置条件。
2. 生成或提取幂等键，准备不可变的业务时间 `now`。
3. 只在 `database.default` 上开启一次事务。
4. 事务内重新读取所有决定写入的状态，需串行化时加锁；事务外的预检只是快速失败，不是正确性依据。
5. 按预先声明的锁序调用各领域写原语，写入业务事实、资产流水、派生脏标和审计。
6. 返回错误即整体回滚；只有事务提交成功才生成对外成功结果。
7. 提交后再删除/失效缓存、发 Redis 信号、触发外部投递。这些操作不能改写已提交的业务结果。

### 6.2 接口约束

| 接口 | 约束 |
| --- | --- |
| Unit of Work | 只在 `default` 上创建 `Tx`，统一 commit/rollback/panic 恢复和事务指标 |
| Command Repository / 写原语 | 参数必须是 `Tx`；传裸 `DB` 不能通过编译 |
| Query Repository | 分为 Primary Query 和显式命名的 Replica Query，不在方法内动态选库 |
| Domain Rule | 纯计算，不持有 `DB`、`Tx`、Redis 或网络客户端 |
| Post-commit Effect | 只接收已持久化对象的 ID/版本，不传可被当成事实的可变业务载荷 |

禁止将 `Tx` 暗藏在 `context.Context` 后默认回落到 DB，禁止领域方法内再次 `RunInTx`，禁止在事务内调用另一个 Service/RPC 完成同库写。

### 6.3 隔离级别与锁序

2.0 默认使用 `READ COMMITTED`。不用全局 `SERIALIZABLE` 买单，而是对具体竞态建模：

- 扣减余额、冻结、核销券和状态迁移使用带旧状态/下界的条件 `UPDATE`，影响 0 行翻译为明确业务错误。
- 重复注册、重复解锁、重复领取、重复回调使用唯一约束托底，“先查再写”只用于优化错误文案。
- 限额、销量、订单终态、持仓结算等需要串行化的聚合行使用 `FOR UPDATE`。
- 多行锁始终先排序再获取。资产行按 `(user_id, asset_type)`，关系/等级行按 `user_id`，批量单据按主键升序。
- 跨领域默认锁等级唯一固定为：命令幂等/外部事件防重行（如有）→ 本次会写资产流水时的统计发布根共享锁（封账/口径切换取排他锁）→ `finance_business_days` 共享 fence → 业务聚合根（订单/产品/券/持仓/结算）→ 注销根预锁 → 提现安全事实 → 既有冻结明细（仅终结时）→ 本次会参与业务裁决的用户、关系、资格和聚合行（统一按 `user_id`）→ 资产行（按 `(user_id, asset_type)`）→ 资产后的可重建统计投影（`income_calc_dirty/user_income_stats`，按 calc/user）→ 只追加的业务子事实、流水和审计。`user_levels` 等裁决聚合必须在取得任一资产锁之前一次收齐并加锁；收益投影不得参与余额、资格、额度或状态判断，任何路径都不得先锁它再回头锁资产。
- 纯资产调整没有业务聚合根时，若会写 `asset_ledgers` 也必须在命令防重后先取得 rank 40 `rollup_roots('income') FOR SHARE`、再取得 rank 50 day fence，随后才可直接进入资产层；绝不能从资产开始再补锁 fence。一旦取得较低层级的锁，后续不得再取得更高层级的锁。特例必须在 Use Case 内写明，并提供与购买、结算、退款/补偿的双向并发用例。
- 事务内不做无界扫描，不上传文件，不等待外部返回，不执行不可控的用户回调。

“业务聚合根按 type/id”必须实现为共享的 `BusinessRootLockKey(rank,type_code,normalized_id)`，按该三元组字典序比较，不能由各领域按表名临时排序，也不能直接比较异构表恰好相同的数值 ID。首发 rank/type_code 固定如下；同一 type_code 内按主键升序，复合主键先规范化成稳定二进制 key。新增表若可能与其他领域同事务锁定，必须先通过 ADR/注册表分配唯一 type_code、更新静态锁序测试，未登记不得调用写仓储：

| rank | 根类型 | 首发 type_code 顺序 |
| ---: | --- | --- |
| 20 | 百分位发布 head | 10=`income_percentile_heads`；创建/发布某月时把同 calc/window 的前驱与当前 head 按 `(calc_version_id,window_type,as_of_month_end)` 升序锁定，只有稳定 ID/proof 查询可用 MVCC 不加锁 |
| 30 | 普通用户人口发布根 | 10=`user_population_roots`；注册在分配 `registration_seq` 前持 SHARE 到提交，月度百分位捕获 cutoff 时短暂持 UPDATE |
| 35 | 等级规则运行根 | 10=`level_rule_runtime_roots`；注册、关系绑定及所有会改变等级输入的写持 SHARE 并要求 CLEAN，规则 rollout 持 UPDATE 切 barrier/serving 版本 |
| 40 | 统计发布根 | 10=`rollup_roots`；所有 `asset_ledgers` writer 先取 `income` 行 SHARE，日封账协调/发布/恢复和计算版本激活取 UPDATE |
| 50 | 账务日 fence | 10=`finance_business_days`；仅会写 `asset_ledgers` 的事务取得 `FOR SHARE`，日封账取得 `FOR UPDATE` |
| 90 | 异步任务来源流根 | 10=`task_source_consumption_roots`；按 `(source_domain,source_kind,shard_id)` 规范 key 排序，异步来源 writer 在业务根前锁单 shard 分配连续 seq，period barrier 按同序短锁固定 64 shard upper |
| 100 | 外部 attempt / 高风险审批 | 10=`payment_attempts`，20=`payout_attempts`，30=`admin_action_approvals`，40=`ad_verification_attempts`，50=`play_credential_issuances` |
| 200 | 目录/供给根 | 10=`playlets`，20=`episodes`，30=`playlet_revisions`，40=`episode_revisions`，50=`playlet_backing_offers`，60=`robot_products`，70=`robot_voucher_rules`，80=`robot_voucher_codes`，85=`user_robot_vouchers`，90=`deposit_product_series`，100=`deposit_products`，110=`vip_product_series`，120=`vip_products`，130=`payment_channels` |
| 300 | 用户业务单/持仓根 | 10=`deposit_orders`，20=`vip_orders`，30=`episode_purchase_orders`，40=`withdrawals`，50=`playlet_backings`，60=`robot_holdings`，70=`asset_exchanges` |
| 350 | 商品维度用户限额根 | 10=`user_robot_product_stats`；仅现金机器人购买触碰，固定在商品/既有 holding 之后、来源结算与期间根之前，按 `(robot_product_id,user_id)` 排序 |
| 400 | 来源结算/冲正根 | 10=`team_rebate_settlements`，20=`playlet_backing_settlements`，30=`robot_holding_settlements`，40=`playlet_backing_terminations`，50=`robot_holding_cancellations`，60=`partner_pool_facts`，70=`finance_recovery_case_roots`；案件是 root 的受控子事实 |
| 500 | 期间聚合根 | 5=`partner_calendar_roots`，10=`partner_months`，15=`partner_month_generations`，20=`partner_month_shards`，30=`partner_monthly_qualifications`，40=`partner_settlements`，45=`partner_adjustment_user_roots`，50=`partner_settlement_adjustments`，55=`partner_pool_reversal_dispositions`，60=`partner_adjustment_applications`，65=`partner_adjustment_heads`，70=`partner_closure_adjustment_dispositions` |
| 600 | 注销根 | 10=`account_closures` |
| 700 | 既有冻结明细 | 10=`asset_freezes`；仅终结时锁定，按规范 freeze ID 排序 |

命令/供应商事件防重事实始终在 rank 50 之前，既有 `asset_freezes` 固定在 rank 700。仅允许在较高 rank 锁后 INSERT 一个事务提交前对外不可见、且不会通过既有唯一键等待另一事务的全新子事实；一旦要读取、更新或命中既有行，仍必须按注册 rank 预收集并加锁。closure、退款、出款、返佣释放等多根流程必须记录实际 `(rank,type_code,normalized_id)` 锁轨迹，CI 断言全程单调。

百分位创建/发布遵循 rank 20 → rank 30：先预收集同 window 的前驱和当前 head，按月份升序锁齐，再以 UPDATE 短暂取得人口 root、捕获 upper 后立即结束协调事务。不得先锁人口 root 再回头锁 head，也不得先锁当前月再反锁前驱；批量窗口按 `window_type` 枚举值排序。构建 worker 后续只锁单个 publication/派生分片，不持人口 root。

任何会为一个或多个用户新增、释放、减少注销 blocker 的用例都必须使用共享的两阶段 closure gate，不能直接把“锁 closure 再锁 user”封成一个会越过中间层的 helper：

1. 在 rank 500 及以前的来源/期间根锁齐后调用 `PrelockUserClosures(tx,user_ids)`。它预读并按 closure ID 锁全部未完成 `account_closures`，记录哪些用户当时没有 closure，返回不可伪造的 gate token；此时不得提前锁 user。
2. 调用方继续按全局顺序锁本次需要终结的既有 `asset_freezes`；不涉及冻结时本步骤为空。提现没有专用人脸中间层。
3. 调用 `LockUsersAndValidateClosureGate(tx,token,source_metadata)`，按 `UserStateLockKey` 锁齐 users/资格/任务等用户层行，并在 user 锁保护下复查第一阶段“无 closure”的用户仍无新行、既有 closure 未换代，再返回逐用户结构化裁决。`source_metadata` 必须区分命令主体/业务所有者与可选第三方受益人：主体不满足规则时可使命令失败；第三方 CLOSED/CLOSING 不能否决已经成立的付款人履约或退款，只返回 `DENY_NEW_BENEFIT/EXTERNAL_RECOVERY_ONLY`，调用方不得锁其资产，而是在同事务写唯一未授予审计或 Finance recovery。ACTIVE 接受新可选业务；CLOSING 只接受 cutoff 前已登记来源的终结/领取/纠错或显式清退动作并同事务推进 `next_check_at`；CLOSED 禁止新钱包/权益。

两个阶段之间不得做业务状态迁移或资产写入，gate token 绑定事务、排序后的 user 集、closure 版本和来源摘要，不能跨事务复用。所有相关写仓储都断言有效 token；这样退款、返佣释放、提现终态既能保持 `closure -> freeze -> user`，也不会出现 user→closure 反向路径。

进入“用户/关系/资格/聚合”层后再使用共享 `UserStateLockKey(type_code,user_id,normalized_id)` 全序：10=`users`，20=`user_credentials`，30=`otp_bindings`，40=`security_challenges`，45=`session_families`，50=`user_sessions`，60=`session_issuances`，70=`kyc_cases`，80=`bank_accounts`，90=`user_relation_stats`，100=`user_levels`，110=`user_limit_usages`，120=`user_tasks`，125=`user_vip_stats`，130=`vip_entitlements`。先比较 type_code，再比较 `user_id/id`，因此多用户流程先锁完所有 `users`，再进入下一类；禁止 refresh 先锁 session/family 再回头锁 user，也禁止 closure/改密在 user 后扫描并追加无界历史行。安全终态只锁当前 auth version 下有硬上限的 family/issuance 根，历史行由索引 EXISTS 或 keyset 清理。KYC、绑卡和提现统一遵守 users→全部 current/candidate KYC（ID 序）→bank→limit，禁止 case/provider 回调反向锁 user。新增同层可变表必须分配唯一 code；只追加新行沿用“提交前不可见且不等待既有唯一键”的窄例外。

资产之后的可重建投影使用独立 `ProjectionLockKey(type_code,calc_version_id,user_id)`：10=`income_calc_dirty`，20=`user_income_stats`。writer、dirty worker、重建和对账凡同事务命中两者都必须先锁完 type 10 再锁 type 20，且各 type 内按 `(calc_version_id,user_id)`；禁止 stats→dirty 回头锁。该层不能参与任何资金/资格裁决。

## 7. 幂等契约

### 7.1 命令幂等

- 所有资产变动必须提供全局唯一 `idem_key`；`asset_ledgers.idem_key` 唯一约束是最终防线。
- 其他需要返回原结果的命令使用 `command_deduplications`，唯一键为 `(actor_type, actor_scope, rpc_name, idempotency_key)`，保存可空审计列 `actor_id`、`request_hash`、结果引用和完成时间。`actor_scope` 必须非空：已认证主体使用 `USER:<id>`/`ADMIN:<id>`，匿名注册使用服务端密钥 HMAC 后的规范化登录身份，不能让 `NULL actor_id` 参与唯一性。
- 同键同请求重放返回原结果；同键不同 `request_hash` 返回冲突，不覆盖旧结果。
- 有自然业务唯一键的表（如用户剧集解锁、任务领取、单据渠道号）同时保留数据库唯一约束，不只依赖通用幂等表。

### 7.2 回调与 worker 幂等

- 支付回调以 `provider + provider_transaction_id + action` 构成幂等键，订单状态条件迁移与资产流水在同一事务。
- worker 不相信 Redis payload 中的状态或金额，只使用 ID 回查 `default`；转移使用旧状态条件和业务唯一键。
- worker 在写入成功前崩溃，状态仍是可扫描的待办；写入成功后崩溃，重试由状态条件/唯一键变为空转。

## 8. 异步模型：无通用 Outbox

### 8.1 明确不做的事

2.0 不创建 `outbox_events`、`event_outbox` 或通用消息表，也不提供“开启/关闭 Outbox”的环境开关。原因是：

- 核心领域表在同一 PostgreSQL 库，本地事务已经能够原子更新；拆成消息反而把强一致降为最终一致。
- 通用 Outbox 会引入第二套状态、重试、清理和监控，却不能自动解决外部系统的 exactly-once。
- 当前需要异步的工作都可以从具体领域状态重建，领域状态比通用消息更能解释“还欠什么”。

未来只有当“必须投递给数据库之外、无法从业务表重建、且丢失不可接受”三个条件同时成立时，才单独立 ADR 设计窄用途 Outbox，明确唯一事件类型、消费者、保留期、重试与对账；不得恢复成全领域通用消息表。本次 Schema 不预留空表。

### 8.2 三类后续动作

| 类型 | 例子 | 持久方式 | Redis 作用 |
| --- | --- | --- | --- |
| 同库核心结果 | 扣款+持仓+流水，回调入账+订单终态 | 同一 `default` 事务直接写 | 不参与正确性 |
| 可重建派生工作 | 等级重算、统计 rollup、到期释放、缓存失效 | `dirty_at`、水位、`status/next_run_at` | 事务提交后发 ID 信号加速 |
| 外部投递 | SMS、Email、通知、支付下单 | 领域投递表的 `PENDING/next_run_at/attempt_count` | 可用作即时唤醒，丢失后 primary sweep 仍会执行 |

### 8.3 领域待办状态机

不建通用任务 payload 表，领域表保存自己的待办。两种标准形状如下：

1. **脏标型**：`CLEAN → DIRTY → CLEAN`。写业务事实的同一事务用 `dirty_at = COALESCE(dirty_at, now())` 保留最早未处理时间。worker 记录 `started_at`，只在 `dirty_at <= started_at` 时清除，不会把计算期间的新变动一起清掉。`user_levels.dirty_at` 使用该形状。
2. **任务状态型**：`PENDING → PROCESSING → SUCCEEDED`；可重试错误进入 `RETRY_WAIT`，到 `next_run_at` 后回到 `PENDING`；参数/权限/外部账号等不可自动恢复错误进入 `BLOCKED`，只能经管理权限修复后重开。

worker 从 `default` 用小批量 `FOR UPDATE SKIP LOCKED` 抢占，每批、每用户或每业务单独立事务。任务不依赖“workerd 只有一个副本”的部署假设。

### 8.4 Forge `message` 投递边界

- 首发统一锁定 Forge `v0.4.1`，只使用 `message` 作 SMS/Email transport adapter；不实现 WhatsApp 渠道。Twilio、BytePlus、Aliyun 可使用内置 SMS sender；Kirim 若纳入则在 Infrastructure 实现受限的自定义 `message.SmsSender`。Email 使用 Forge 的 SMTP/SendGrid sender 与启动期编译模板；sender 凭据由项目 Infrastructure Provider 从 secret 注入，不要求把密钥写进数组式 YAML。
- Forge `v0.4.1` 的 `message.Manager` 会在多个兼容 sender 间自动 fallback，失败日志和返回错误还可能包含完整收件人。2.0 因此由应用 `DeliveryProviderRegistry` 先确定唯一 provider，每个运行时 Manager 实例只装配一个 sender；不能把多供应商 fallback 当作重试策略。调用时隔离 Forge 内部 recipient-bearing 日志（例如注入禁用 logger 的 context），适配器只输出脱敏目标和归一化错误码，禁止记录或向上透传 Forge 原始错误字符串。
- challenge/delivery 在 primary 保存 `status/lease_owner/lease_until/lease_generation/next_run_at/attempt_count/delivery_dedupe_key`；worker 先短事务 claim，事务外调用 Forge，再以新短事务 CAS finalize。该 key 只负责应用级防重，Forge 不保证把它传给供应商。
- Forge 返回 nil 只把本地状态推进为 `PROVIDER_ACCEPTED`，不写 `DELIVERED`；只有供应商可验回执才能形成更强送达事实。已证明未被供应商接受的临时失败才进入 `RETRY_WAIT`；网络超时、响应丢失或调用后未 finalize 的过期 `SENDING` 在没有供应商幂等/查询证据时条件转为终态 `UNKNOWN`，保留原 `delivery_dedupe_key` 但禁止自动重发或换 sender。验证码若实际到达仍可在 challenge 到期前验证；未到达则由用户在冷却期后显式创建新 challenge。
- 验证码/reset token 的生成、摘要、尝试上限、过期、一次消费和短期密文销毁仍由安全领域负责；Forge 不是业务真源、队列或送达对账系统。
- 日志、trace、metrics 和错误元数据只记录脱敏手机号/邮箱、channel、sender 代号与 `delivery_dedupe_key` hash，禁止记录完整收件人、OTP、模板敏感参数或凭据。

## 10. API 和管理能力边界

### 10.1 `apid`

- Transport 只负责从令牌取 `user_id`、校验 Proto 和转换结果；用户不能从请求体指定他人 `user_id`。
- 金额、价格、费率、等级门槛和可购数量以服务端事务内事实为准，客户端值只能作为期望值做冲突检查。
- 所有第三方 callback 使用预注册的 provider/kind 固定字面量 HTTP 路由，先限制 content type/体积并保留 raw body 与需要的 headers，按该路由绑定算法验签，再解析为内部 typed command 进入幂等 Use Case。外部协议不经 gRPC-Gateway/Proto 解码，响应使用 provider-required ACK。
- 固定路由映射 provider 和事件种类；请求 query/body 不能选择验签算法。全部 Gateway 路由也禁止路径参数：GET 标识放 query，POST 命令标识放 Proto body，action 使用固定后缀。

### 10.2 `mand`

- 每个管理方法声明独立权限点，列表和详情同时套数据范围；看得到不等于改得了。
- 改状态、调资产、发布配置、重跑作业、解除 `BLOCKED` 分别使用更细权限，不共用一个“管理员”开关。
- 管理写 Use Case 在同一事务写业务变更和 `admin_audit_logs`。审计写失败时管理操作整体回滚；不允许“先改成功再尽量记录”。

### 10.3 `workerd` 与 `migrate`

- `workerd` 健康端点只暴露存活、就绪、最后一次作业和待办延迟，不提供绕过 `mand` RBAC 的手工执行 HTTP 口。
- 手工重跑、重开阻塞任务和缓存清理经 `mand` 发起，写 `admin_audit_logs`，由 `workerd` 从持久状态执行。
- `migrate` 使用独立数据库角色，不复用在线业务角色；生产 `down` 失败关闭。

## 11. 缓存与作业原则

- 缓存是派生数据，不是资格、余额、订单状态或幂等性的真源。
- 缓存写入/失效只发生在事务提交后。删除优先于在写路径重建缓存，防止并发写将旧值再次回填。
- Redis Pub/Sub 可用于多副本缓存失效和领域唤醒；信号丢失分别由 TTL 和 primary sweep 恢复。
- cron 不使用“当前时间精确等于某时刻”的条件；使用 `<= now()` 范围条件、部分索引、水位和追赶循环。
- 所有作业可重入，能在停机后追赶，能在多 worker 下安全并行，且每批有数量、耗时、水位和失败原因。

## 12. 权限与安全

1. APP 令牌、管理令牌和 worker/migrate 身份分开，不能跨端使用。
2. `default`、`slave`、`migrate` 使用不同 DB 角色；应用日志不输出 DSN 密码、令牌、支付密钥、完整手机号/邮箱和 PII。
3. 管理数据范围以 `user_id` 及关系链判定，不将 `F<code>` 或 `2*user_id+1` 当作内部关系键。
4. 所有人工资产纠偏都是新的可审计反向/调整流水，不直接改历史流水或删除事实。
5. 系统时间、配置秘密和签名算法集中治理，业务包不自行读环境变量或复制安全配置。
6. 提现不做专用人脸检查，仍要求基础 KYC APPROVED 和已验证银行卡。TOTP 从未成功确认时为 `NEVER_BOUND`（仅有未确认 PENDING/EXPIRED 也在此分支）并可跳过；ACTIVE 必须在业务事务中锁定 binding、验证 code 并原子推进 `last_accepted_step`；曾确认但当前 REVOKED（含 reset）须重绑或完成受控恢复，禁止降级绕过。

## 13. 可观测性

### 13.1 指标

- API：按进程/方法的 QPS、p50/p95/p99、错误码、限流和 panic。
- 数据库：`default/slave` 分开的连接池使用率、等待时间、慢 SQL、锁等待、死锁、事务时长、回滚数和复制延迟。
- 幂等：幂等命中、同键不同请求冲突、唯一约束冲突和回调重放次数。
- 异步：各领域 pending/dirty 数、最老待办年龄、claim 数、重试数、`BLOCKED` 数、sweep 补回数和 Redis 信号失败数。
- 缓存：L1/L2 命中率、回源耗时、单飞合并数、失效广播失败和主动清理数。

### 13.2 日志与追踪

每个在线请求、供应商 callback 和作业批次带 `request_id/trace_id`。事务日志至少包含 Use Case、事务耗时、重试/回滚类型，不输出流水全量 `extras`、原始 callback body、完整收件人和未脱敏请求体。

## 14. 失败模式与恢复

| 失败 | 预期行为 | 恢复/告警 |
| --- | --- | --- |
| 事务中任意一步失败 | 所有同库写回滚，不发提交后信号 | 返回稳定业务错误，记回滚原因 |
| 提交成功后进程立即退出 | 业务事实仍正确，可能少一个 Redis 信号 | primary sweep 根据持久待办补回 |
| Redis 不可用 | 核心 DB 事务继续；登录/限流等必须 Redis 的能力明确失败 | 待办延迟指标上升，sweep 继续运行 |
| `slave` 落后 | 强一致路径无影响；弱一致列表可短暂陈旧 | 复制延迟告警，超阈值停用重报表/导出 |
| `slave` 不可用 | 交互式轻查询可经限流和熔断后一次回落 `default`；重查询不回落 | 记录 fallback 指标，优先保护主库 |
| worker 中途退出 | 未完成的 `dirty_at/status/next_run_at` 仍可见 | 锁/租约超时后由其他 worker 或 sweep 接管 |
| 外部投递长期失败 | 按领域策略退避，最终进 `BLOCKED`，不回滚已成功业务 | 告警+管理端查看/修复/重开 |
| 主库不可用 | 写请求和强一致读失败关闭 | 由数据库基础设施晋升主库，应用不自主选主 |

## 15. 测试与验收用例

### 15.1 事务与并发

1. 在资产扣减成功后人为让持仓/订单/关系/审计写失败，断言余额、流水和所有业务表都没有变化。
2. 跨领域写在测试中记录同一数据库事务标识；任意原语改用裸 DB 时测试/静态门禁失败。
3. 并发扣款、并发冻结、并发领取和重复回调不产生负余额或重复事实。
4. A→B 与 B→A 或相反用户集合的批量资产变动并发执行，固定锁序下无死锁，总额守恒。
5. 事务内发 Redis/HTTP/RPC 或使用 `.db/.slave` 执行查询/DML 被 AST 门禁阻断。

### 15.2 主从与异步

1. 使用生产同等的 slave 角色连接，`SELECT` 成功，`INSERT/UPDATE/DELETE/RunInTx` 写入失败；代码扫描不存在 `slave` DML。
2. 模拟 slave 延迟，余额、限额、登录权限、等级重算和写后回读仍返回 primary 真值；内容/后台列表允许旧值。
3. 业务事务回滚时不发信号；提交后才发。人为丢弃所有 Redis 信号，sweep 仍能从 `dirty_at/status/next_run_at` 完成全部待办。
4. 两个 workerd 同时扫描同一批待办，`SKIP LOCKED`+状态条件使每个业务结果只生效一次。
5. 缓存失效广播丢失后，TTL 到期能回源，期间不影响资产和资格写入。
6. SMS/Email 在 claim 提交后、Forge 调用前后和 finalize 前各杀进程；成功只到 `PROVIDER_ACCEPTED`，明确未接受才可用原 `delivery_dedupe_key` 重试，不确定结果由 sweep 收敛到 `UNKNOWN` 且不换 sender/自动重发。日志不含完整手机号、邮箱、OTP 或模板敏感参数。

### 15.3 启动与 Schema

1. `migrate default init && migrate default up` 能在空库创建全部 Schema，`status` 无未知迁移。
2. `migrate slave up`、未知数据库名和未知 action 在连库前失败。
3. 故意配错时区、让 default 只读或让生产 slave 可写，进程就绪检查失败。
4. 代码库不存在 1.0 历史数据迁移、双写、新旧表切换和运行时自动建表路径。
5. 错误目录逐码证明 `errkit` code name、Encoder/Decoder、gRPC/HTTP 映射全部存在；裸 SQL/供应商错误只对外输出安全 INTERNAL，Domain 依赖图无 Forge。
6. 枚举 Gateway/OpenAPI 路由，无动态路径参数且无 callback Proto descriptor；每个外部 callback 只能通过其固定字面量路由、raw-body 验签和 provider ACK 契约。
