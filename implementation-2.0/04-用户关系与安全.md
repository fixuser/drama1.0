# 04 用户关系与安全

> 本章是 Drama 2.0 空库实现规范。关系标识只使用 `user_id`；不生成、不接收、不保存、不展示 F 码，也不提供 F 码兼容、历史回填或迁移保底。

## 1. 目标与边界

本章覆盖两个边界：身份与安全域负责用户、认证、KYC、银行卡、注销和后台 RBAC；关系域负责建立一次性邀请关系、提供用户侧五层团队查询、提供后台完整数据范围，并为等级与返佣提供稳定且可审计的拓扑。两者共享 `users.id`，但账号状态、团队能力、关系拓扑和后台授权分别建模，不能用一个字段互相代替。

目标：

1. `users.id` 就是所有领域统一使用的 `user_id`，不再保留另一套内部用户编号。
2. `parent_id + inviter_ids bigint[]` 是完整关系唯一真源；直属上级排在数组首位，链不因五层业务口径截断。
3. `referral_edges` 是唯一的用户侧团队查询投影，只保存第 1～5 层，能够按祖先、层级稳定分页。
4. 注册绑定和一次性后绑定复用同一个领域命令、校验顺序和事务实现。
5. 后绑定只允许“当前无上级且无任何直接下级”的普通用户执行；成功后关系永久不可修改。
6. 账号状态、邀请能力、团队能力分别表达，禁止再用反向布尔字段或用户 ID 前缀推断权限。
7. 关系建立、边表投影和审计在 default/primary 的一个数据库事务内完成；slave 不参与写事务。
8. 注册、登录、OTP、密码、会话、KYC、银行卡和注销均有显式状态机、幂等边界和不可变审计；密码、OTP、令牌、证件和完整卡号不以明文落库或进入日志。
9. 普通用户与后台主体分表、分 token issuer/audience；后台每个动作同时校验稳定权限点、数据范围和近期 MFA，不存在超级密码或全局绕过码。
10. KYC 和银行卡核名供应商调用永远在数据库事务之外；本地意图、回调事件和状态推进依靠 primary 状态 + 唯一键收敛。2.0 不建立每笔提现专用人脸检查。
11. 注销先把账号置为限制新动作的 `CLOSING`，等持仓、冻结、在途提现等阻塞项清零后才进入终态；不物理删除关系、资金或审计事实。

不在本章范围内：

- F 码、粉丝码、特殊粉丝码别名及旧分享链接兼容；
- `inviter_fans`、`inviter_user_ids` 两套旧链并存；
- 改绑、解绑、搬树、合并账号和历史关系迁移；
- 活动邀请、邀请次数奖励、VIP 邀请及任何活动副作用；
- 用关系链直接计算已发生交易的返佣。历史返佣只认结算时保存的关系快照。
- 短信、邮件、KYC 和银行供应商内部实现，以及提现业务状态机；本章只定义调用边界、身份事实和安全前置。
- 历史凭据导入、旧会话延续、旧 KYC/银行卡回填和旧账号注销迁移；2.0 从空库开始。

## 2. 对象、术语与不变量

### 2.1 核心对象

| 对象 | 含义 | 唯一真源 |
| --- | --- | --- |
| 用户 `User` | 身份、账号状态和关系头信息 | `users` |
| 完整祖先链 | 当前用户从直属上级到根节点的所有用户 ID | `users.inviter_ids` |
| 直接关系 | 当前用户与直属上级的一条边 | `users.parent_id` |
| 五层团队投影 | 面向等级、团队列表、返佣的祖先到后代边 | `referral_edges` |
| 关系审计 | 谁在何时以何种入口完成绑定以及绑定结果 | `referral_audits` |
| 邀请能力 | 用户能否成为新关系的上级 | `users.invite_enabled` |
| 团队能力 | 用户能否使用团队展示、等级和返佣能力 | `users.team_enabled` |

“后台全链”和“用户五层”是两个不同口径：

- 后台 `RELATION_SUBTREE` 范围包含根本人及其全部后代，统一谓词为 `users.id = $scope_root_user_id OR users.inviter_ids @> ARRAY[$scope_root_user_id]`，没有五层限制；管理员 ID 只用于认证和审计，角色权限决定“能做什么”，范围根用户 ID 只决定“能看谁”。
- 用户团队、等级和返佣只使用 `referral_edges WHERE ancestor_user_id = $user_id AND depth BETWEEN 1 AND 5`。
- 禁止用 `inviter_ids[1:5]` 替代边表热查询，也禁止用 `referral_edges` 推导后台完整数据范围。

### 2.2 强制不变量

1. 无上级用户满足 `parent_id IS NULL AND inviter_ids = '{}'`。
2. 有上级用户满足 `parent_id = inviter_ids[1]`。
3. 若用户 `u` 的上级为 `p`，则 `u.inviter_ids = [p.id] || p.inviter_ids`。
4. `inviter_ids` 内全部为正数、顺序不重复，且不包含用户自己的 ID。
5. 所有祖先必须真实存在；用户物理删除被禁止，注销只改变账号状态。
6. 一名用户最多产生一条成功关系审计；绑定成功后没有 `UNBIND` 或 `REBIND` 状态。
7. `referral_edges` 完全由普通用户的 `inviter_ids` 前五项派生，不能由接口单独增删。
8. 对每个普通用户 `u` 和 `u.inviter_ids[i]`，当 `1 <= i <= 5` 时恰有一条 `(ancestor_user_id, depth=i, descendant_user_id=u.id)`。
9. 关系拓扑不随账号禁用、注销、`invite_enabled` 或 `team_enabled` 改变；这些状态只影响新绑定或业务资格。
10. 用户类型在创建后不可改。后台操作集由 RBAC 决定，不能通过改用户类型或关系链临时提权。
11. 所有关系字段和 API 字段都是 `user_id` 语义；任何 `F...` 输入直接返回参数错误，不做猜测性转换。
12. 完整链不按五层业务口径截断；平台硬上限 `RELATION_PATH_MAX_DEPTH=128`，已发布关系策略必须满足 `1<=max_relation_depth<=128`。若新链超过规则上限或平台硬上限，整次绑定拒绝，绝不写入截断链。

## 3. 状态机

### 3.1 用户关系状态

```text
注册时携带 parent_user_id ─────────────────────> BOUND
注册时无上级 ──> UNBOUND_EMPTY
                    ├─ 登录后一次性 bind ─────> BOUND
                    └─ 成为他人的上级 ────────> ROOT_WITH_CHILDREN

BOUND / ROOT_WITH_CHILDREN ──> 对“给自己绑定上级”均为终态
```

状态由事实字段推导，不额外保存可漂移的 `relation_status`：

- `UNBOUND_EMPTY`：`parent_id IS NULL`、`inviter_ids` 为空且无直接下级，仍可执行一次后绑定。
- `ROOT_WITH_CHILDREN`：自身无上级但至少有一个直接下级；拓扑保持根节点，永久失去后绑定资格。
- `BOUND`：`parent_id IS NOT NULL` 且存在唯一 `referral_audits` 记录。

账号被禁用或注销后仍是 `BOUND`，不得借状态变化清空或重挂关系。绑定请求失败不产生中间状态，不允许写入半条链。

### 3.2 邀请和团队能力状态

```text
ENABLED <──管理员审计命令──> DISABLED
```

`invite_enabled=false` 仅禁止该用户成为新上级；`team_enabled=false` 仅禁止其新增团队权益和用户侧团队能力。两者都不等价于账号登录禁用，不改变既有拓扑。能力恢复后仍沿用原关系。

## 4. 数据表、约束与索引

### 4.1 `users` 的关系字段

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `bigint` | 主键，即业务 `user_id`；必须为正数 |
| `type` | `smallint` | 显式用户类型；禁止从 ID 数字特征推断 |
| `registration_seq/registered_at` | `bigint null/timestamptz` | NORMAL 主体两者必填，sequence 由数据库单调序列分配、partial unique 且不可更新；非 NORMAL 主体 sequence 必须为空。回滚 gap 合法但永不复用 |
| `status` | `smallint` | 账号状态，与关系能力分离 |
| `auth_version` | `bigint` | 非负且只增；密码重置、账号禁用、注销完成或全局撤销时只更新这一行并原子加一，token/family/session/issuance 必须携带快照并在 primary 比较，实现 O(1) 全局撤销 |
| `closure_generation` | `bigint` | `NOT NULL DEFAULT 0` 且只增；每次账号 `ACTIVE -> CLOSING` 与 closure 创建同事务加一，后续失败/清理均不回退，播放授权以该值作为唯一规范注销代次 |
| `play_credential_sweep_generation/cursor/dirty_at/next_run_at` | `bigint/bigint/timestamptz null/timestamptz null` | auth/status/review grant 变化时同一用户行把 sweep generation 加一、cursor 归零并置 dirty/next-run；只驱动播放凭证有界卫生清扫，不参与即时失效判断 |
| `play_credential_sweep_claim_owner/claim_until/claim_generation/claim_due_at` | `text null/timestamptz null/bigint/timestamptz generated` | owner/until 成对，generation 非负且每次领取/根失效递增；due 为 `COALESCE(until,'-infinity')`，供可接管 root partial index 与旧 owner fencing |
| `parent_id` | `bigint null` | 直属上级，外键 `users(id) ON DELETE RESTRICT` |
| `inviter_ids` | `bigint[]` | `NOT NULL DEFAULT '{}'`，直属在前的完整祖先链 |
| `relation_depth/relation_path_key` | `smallint/bytea` | depth 等于祖先数；path 以 root→self 的每段 8 字节无符号大端 user ID 规范编码，非空且可由 inviter_ids+id 重建。它只是 B-tree 子树范围/等级待办索引键，不是第二关系真源 |
| `invite_enabled` | `boolean` | `NOT NULL DEFAULT true`，正向语义 |
| `team_enabled` | `boolean` | `NOT NULL DEFAULT true`，正向语义 |
| `relation_bound_at` | `timestamptz null` | 成功绑定时间；无上级时为空 |
| `closed_at` | `timestamptz null` | 仅账号终态 `CLOSED` 非空；注销不删除用户行 |
| `version` | `bigint` | 任一用户当前事实变化时加一，供乐观锁和诊断 |
| `created_at/updated_at` | `timestamptz` | 审计时间 |

数据库约束：

- `CHECK (id > 0)`。
- `CHECK ((parent_id IS NULL AND cardinality(inviter_ids)=0) OR (parent_id IS NOT NULL AND cardinality(inviter_ids)>0 AND parent_id=inviter_ids[1]))`。
- `CHECK (array_position(inviter_ids, id) IS NULL)`。
- `CHECK ((parent_id IS NULL) = (relation_bound_at IS NULL))`。
- `CHECK (relation_depth=cardinality(inviter_ids) AND relation_depth BETWEEN 0 AND 128 AND octet_length(relation_path_key)=8*(relation_depth+1) AND octet_length(relation_path_key)<=1032)`；数据库不可变函数复核 path 末段为自身 ID。`1032=8*(128+1)`，把索引键宽度控制在 PostgreSQL 默认 8KB page 的普通 B-tree 安全范围内；迁移、Go 常量与规则发布器必须同源。
- `parent_id` 建 B-tree 索引，支撑直属列表和后绑定“无下级”检查。
- `inviter_ids` 建整列 GIN 索引，只支撑后台完整数据范围与审计查询；不建立 `[1:5]` 数组切片表达式索引。

PostgreSQL 数组无法用普通外键保证每个元素存在，也不适合用复杂 CHECK 检查去重。领域命令必须在事务内验证候选上级的既有链；一致性作业再独立检查“元素存在、无重复、前缀正确”。发现异常只告警并阻断新写，不静默截断或修正。

`relation_path_key = encode_path(reverse(inviter_ids) || id)`，编码和 `path_prefix_upper` 由 migration 安装的不可变数据库函数与 Go golden vector 共同校验；固定宽度使一个用户的全部后代在 B-tree 上形成连续半开区间。注册与合法后绑定同事务写 path；后绑定要求该用户没有任何下级，因而不需要批量改写后代。业务关系、返佣深度仍只认 parent/inviter/edges，禁止从 path 反推或修改拓扑。

`max_relation_depth`、允许成为上级的显式用户类型及后绑定二次认证要求来自 primary 中当前生效的 `rule_versions(domain=REFERRAL)` 及一对一 `referral_rule_settings`；后者使用类型化列保存最大链深、允许上级类型集合、后绑定近期认证级别和循环检查上限，不藏任意 JSON。发布器和数据库约束都强制 `1<=max_relation_depth<=RELATION_PATH_MAX_DEPTH(128)`，规则不能扩大平台硬上限。没有生效版本时绑定失败关闭，不使用代码默认值。关系规则版本只约束新命令，不重写既有不可变拓扑。

### 4.2 `referral_edges`

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `ancestor_user_id` | `bigint` | 外键 `users(id) ON DELETE RESTRICT` |
| `descendant_user_id` | `bigint` | 外键 `users(id) ON DELETE RESTRICT` |
| `depth` | `smallint` | `CHECK (depth BETWEEN 1 AND 5)` |
| `created_at` | `timestamptz` | 与关系建立事务同一时刻写入 |

键与索引：

- 主键：`(ancestor_user_id, depth, descendant_user_id)`，同时满足总览约定的三列唯一性，支撑祖先下按层级顺序分页。
- 反向唯一约束：`UNIQUE(descendant_user_id, depth)`，既支撑校验、返佣取上级和诊断，也从数据库层禁止同一后代同一层出现两个祖先。
- `CHECK (ancestor_user_id <> descendant_user_id)`。

边表只为 `type=NORMAL` 的后代建边；祖先可为规则明确允许且已开启邀请能力的显式类型，深度仍按完整链中的真实位置计算。任何可成为祖先的主体都必须先有 `user_relation_stats` 行；授予邀请能力与初始化该行同事务，缺行时注册/绑定失败关闭。用户侧团队接口只向具备团队能力的普通用户开放，等级模块仍只为参与等级体系的普通用户建立 `user_levels`。

边表是派生投影，不保存业务状态、等级、金额或权限。插入使用主键幂等，但主键冲突只代表“同一条边已存在”；反向唯一冲突代表链不一致，必须让整笔关系事务回滚，不能掩盖或择一保留。

### 4.3 `referral_audits`

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `bigint identity` | 主键 |
| `user_id` | `bigint` | 被绑定用户，`UNIQUE`，保证一生最多成功绑定一次 |
| `before_parent_user_id` | `bigint null` | 一次性绑定前恒为空 |
| `after_parent_user_id` | `bigint` | 成功后的直属上级 |
| `before_inviter_ids` | `bigint[]` | 一次性绑定前恒为空数组 |
| `after_inviter_ids` | `bigint[]` | 成功后完整链快照 |
| `source` | `smallint` | `REGISTER` 或 `POST_BIND` |
| `actor_user_id` | `bigint` | `NOT NULL`；后绑定为本人，注册为新创建用户 |
| `deduplication_id` | `bigint` | 指向公共 `command_deduplications`，`UNIQUE` |
| `request_id` | `varchar(64)` | 链路追踪，不作为业务幂等依据 |
| `ip_hash/device_hash` | `bytea null` | 风控审计，仅保存不可逆摘要 |
| `created_at` | `timestamptz` | 成功提交时间 |

唯一约束：

- `UNIQUE(user_id)`。
- `UNIQUE(deduplication_id)`；`command_deduplications` 以 `(actor_type, actor_scope, rpc_name, idempotency_key)` 唯一并保存 request hash 和结果引用。注册的 scope 是规范化登录身份的服务端 HMAC，不保存明文身份，也不依赖尚不存在的 `user_id`。

该表只允许 INSERT 和 SELECT，应用角色没有 UPDATE/DELETE 权限。失败请求写结构化安全日志和指标，不写成功审计表。

`user_relation_stats` 是关系域自己的同步派生热表：每个 NORMAL 用户及每个被允许作为祖先的其他显式类型各一行，保存 `user_id`、`direct_normal_member_count`、`five_level_normal_member_count`、`version`、`updated_at`。注册/后绑定时，直属上级的 direct normal 加一、前五层全部祖先的 five-level normal 加一，并与用户关系、边和审计同事务提交；计数可从 NORMAL 后代的 `referral_edges` 重建并每日对账。非 NORMAL 祖先只获得关系展示统计，不创建 `user_levels`、返佣资格或普通用户五层权益；API 必须按主体 capability/权限区分。普通成员计数不写入 `user_levels`，避免纯关系展示变更扩大等级热行写入。

## 5. API

所有新接口只提供 v2 语义，不代理旧字段。

### 5.1 用户接口

| RPC / HTTP | 请求要点 | 响应要点 | 一致性 |
| --- | --- | --- | --- |
| `Register` / `POST /v2/auth/register` | 可选 `inviter_user_id`；请求头 `Idempotency-Key` | 新 `user_id`、直属上级 ID | primary 事务结果 |
| `BindParent` / `POST /v2/me/referral/bind-parent` | `parent_user_id`、`Idempotency-Key` | `parent_user_id`、`bound_at` | primary 强一致 |
| `GetReferralSummary` / `GET /v2/me/referral/summary` | 无 | 直属上级、能力状态、直属和五层人数；不暴露完整祖先链 | primary 强一致 |
| `ListDirectMembers` / `GET /v2/me/referral/direct-members` | `offset`、`limit`、可选状态筛选 | 直属成员，含 `offset/limit/total` | slave，返回 `as_of` |
| `ListTeamMembers` / `GET /v2/me/referral/team-members` | `depth=1..5`、`offset`、`limit`、可选状态筛选 | 五层内成员及真实 `depth`，含 `total` | slave，返回 `as_of` |

接口字段为数值型 `user_id`；若网关按 Proto JSON 将 `int64` 编码为十进制字符串，仍只接受纯十进制正整数。`F3`、`fans_code`、`inviter_fans_code` 和模糊的 `inviter_id` 字段均不存在。

分享链接只携带十进制 `inviter_user_id=<users.id>`；服务端不生成可逆编码、校验位别名或第二套分享码。注册完成后页面展示的仍是同一个 `user_id`。

分页遵循全局 `offset + limit + total` 规范，固定排序为 `(depth, descendant_user_id)`，限制最大 `offset/limit` 并监控深分页；`total` 与 items 使用同一过滤口径。响应不返回成员完整祖先链、邮箱、手机号、KYC 或资产信息。

### 5.2 后台接口

| 接口 | 用途 |
| --- | --- |
| `GetReferralGraph` / `GET /v2/admin/users/referral?user_id=...` | 查看直属上级和完整祖先链；selector 位于 query |
| `GetRelationAudit` / `GET /v2/admin/users/referral/audit?user_id=...` | 查看关系成功审计；selector 位于 query |
| `GET /v2/admin/users?ancestor_user_id=...` | 按完整链查询操作人数据范围内的用户 |
| `UpdateInviteCapability` / `POST /v2/admin/users/invite-capability` | `user_id` 放 Proto body；启停邀请能力，要求 `referral.capability.write`、原因和幂等键 |
| `UpdateTeamCapability` / `POST /v2/admin/users/team-capability` | `user_id` 放 Proto body；启停团队能力，要求 `referral.capability.write`、原因和幂等键 |
| `GetRelationInvariantReport` / `GET /v2/admin/relationship/invariants` | 使用 `referral.invariant.read` 查看一致性作业结果和异常样本 |

没有后台改绑接口。关系纠错不通过线上通用 API 实现；2.0 空库若产生关系不变量错误，应先止写、定位代码缺陷并由单独审批方案处理。

## 6. 主流程

### 6.1 注册时绑定

1. 校验注册命令和幂等键；创建或读取该命令的既有结果。
2. 若没有 `inviter_user_id`，创建无上级用户，`parent_id=NULL`、`inviter_ids={}`，不写边和关系成功审计。
3. 若携带上级，按 user ID 升序锁定已存在的上级行；校验账号状态、显式类型、`invite_enabled` 和链不变量。
4. 生成 `new_chain = [parent.id] || parent.inviter_ids`；验证正数、无重复、没有新用户 ID，且不超过已发布 `max_relation_depth`；不做任何截断。
5. 创建用户并写 `parent_id`、完整 `inviter_ids`、`relation_depth`、root→self `relation_path_key` 和 `relation_bound_at`；注册顶层 Use Case 同时初始化两种资产账户。
6. 若新用户是普通用户，按 `new_chain` 前五项批量插入 `referral_edges`，创建本人的零值 `user_relation_stats`，并原子增加直属/五层祖先的关系计数。
7. 写唯一 `referral_audits(source=REGISTER)`；初始化等级判定聚合由等级模块在同一事务执行。
8. 提交后返回事务内结果。通知、埋点或缓存删除失败不得反向修改已提交关系。

### 6.2 一次性后绑定

1. 只允许已登录普通用户给自己绑定，完成必要的近期登录或 OTP 二次确认并通过限流。业务事务按命令防重后先持 rank35 等级 runtime root SHARE 并要求 CLEAN；若当前用户仍有 level dirty/queue，事务外先有界刷新，锁内仍不 clean 则返回 retryable，禁止在待办使用旧 path 时改关系。
2. 按 `user_id` 升序锁定“当前用户”和“候选上级”；所有创建子关系的路径也必须锁候选上级，因此能与并发后绑定互斥。
3. 在锁内重新检查当前用户：`parent_id IS NULL`、`inviter_ids={}`、不存在 `users.parent_id=current_user_id`、不存在 `referral_audits`。
4. 校验候选上级存在、可邀请、不是自己；候选链不含当前用户、自身满足完整链不变量，拼接后不超过 `max_relation_depth`。
5. 生成完整链和新 root→self path，原子更新当前用户的 parent/inviter/depth/path，插入前五层边，写唯一审计，并增加直属/五层祖先的 `user_relation_stats`。由于锁内再次证明该用户没有任何下级，只改这一条 path，不存在搬树或批量更新 queue。
6. 调用等级模块对新增团队成员关系做原子增量和 dirty 标记；当前新成员未达到等级资格时不得凭空增加合格人数。
7. 事务提交。相同幂等键重试返回第一次结果；任一前置条件变化则整个命令失败且无写入。

“无下级”检查不能只在事务外查询。并发的“甲绑定上级”和“乙把甲设为上级”都会竞争甲的用户行锁，后拿锁的一方在锁内重查后失败，从而避免甲的既有子链需要搬树。

### 6.3 用户五层查询

1. 鉴权确认请求人为本人且 `team_enabled=true`。
2. `GetReferralSummary` 固定读取 primary 中的用户关系、能力状态及关系域 `user_relation_stats`，不允许客户端选择数据源，也不在每次首页请求执行大团队 COUNT。
3. 成员列表查询 `referral_edges` 的主键前缀，显式限制 `depth BETWEEN 1 AND 5`。
4. 与最小化用户公开资料、等级摘要连接；账号状态过滤由接口口径明确，不删除边。
5. 返回 `as_of`、`offset/limit/total` 和分页结果。slave 延迟只影响展示新鲜度，不能用于绑定资格或资金判定。

### 6.4 后台完整数据范围

1. RBAC 先判断操作人是否具有目标动作权限。
2. 同时具备目标权限点和显式 `GLOBAL` 数据范围的管理员可查看全站；`RELATION_SUBTREE` 使用统一的 `users.id = $scope_root_user_id OR users.inviter_ids @> ARRAY[$scope_root_user_id]`，明确包含范围根本人。
3. 查询条件由数据访问层统一注入，业务 handler 不得手写或省略范围条件。
4. 任何写操作在 primary 再次校验目标用户仍在范围内，禁止以 slave 的旧链授权。

## 7. 事务边界与并发规则

### 7.1 必须同一 primary 事务完成

- 注册用户、登录身份、COMMON/EXPERIENCE 两条资产行、关系字段、五层边、关系审计、`user_levels` 初始化；
- 后绑定的用户关系字段、五层边、关系审计、`user_relation_stats` 人数增量、等级判定聚合和 dirty 标记；
- 邀请/团队能力变更及其安全审计；
- 因用户资格状态变化产生的等级合格人数增减。

事务内任一写入失败全部回滚。关系正确性不依赖 outbox、消息队列、Redis 锁或 slave；这些组件只能用于提交后的通知和加速。

### 7.2 锁顺序

1. 收集需要写或用于互斥的用户 ID。
2. 去重后按 `user_id` 升序 `SELECT ... FOR UPDATE`。
3. 锁内重读全部前置条件。
4. 先写唯一真源 `users`，再写派生边和审计，最后调用等级聚合。

禁止先持有 Redis 锁再等待数据库锁，也禁止一个入口锁“子后父”、另一个入口锁“父后子”。数据库唯一约束是最终并发防线。

### 7.3 primary/slave 约束

- 绑定、授权、等级、返佣和后台写范围校验只读 primary。
- 团队列表、关系展示和非安全报表可读 slave，并必须带 `as_of` 或数据延迟提示。
- 写请求成功响应直接使用事务内对象，不提交后立即去 slave 回读。
- slave 不可用时，非关键列表可降级到 primary 的限流查询；不得用缓存猜测授权结果。

## 8. 幂等键

| 命令 | 幂等键 | 数据库防线 | 重试语义 |
| --- | --- | --- | --- |
| 注册 | 客户端 `Idempotency-Key` + 注册身份 | 注册命令唯一键、登录身份唯一键 | 相同载荷返回原用户；不同载荷冲突 |
| 后绑定 | `actor_user_id + Idempotency-Key` | 公共命令唯一键、`referral_audits.user_id UNIQUE` | 相同上级返回原结果；不同上级返回冲突 |
| 写边 | `(ancestor_user_id, depth, descendant_user_id)` | `referral_edges` 主键 | 同一派生边 `DO NOTHING`，其他差异报不变量错误 |
| 邀请能力变更 | `operator_admin_id + Idempotency-Key` | 安全命令唯一键 | 返回第一次变更结果 |
| 团队能力变更 | `operator_admin_id + Idempotency-Key` | 安全命令唯一键 | 返回第一次变更结果 |

幂等键至少保留到业务审计保留期结束。服务端必须保存请求语义摘要；同一个键携带不同 `parent_user_id` 或不同目标状态时返回 `IDEMPOTENCY_CONFLICT`，不能把第二次请求当成功。

## 9. 失败模式与处理

| 失败模式 | 对外结果 | 内部动作 |
| --- | --- | --- |
| 上级不存在或 ID 非正数 | `INVALID_PARENT` | 无写入，记录原因指标 |
| 输入包含 F 码或非十进制值 | `INVALID_USER_ID` | 直接拒绝，不转换 |
| 自邀请或候选链包含自己 | `RELATION_CYCLE` | 回滚并触发高优先级安全日志 |
| 上级账号/邀请能力不可用 | `PARENT_NOT_ELIGIBLE` | 无写入 |
| 当前用户已有上级 | `RELATION_ALREADY_BOUND` | 若幂等键命中则返回原结果，否则冲突 |
| 当前用户已有直接下级 | `RELATION_HAS_CHILDREN` | 禁止后绑定，不搬树 |
| 并发绑定冲突 | 一个成功，其余返回已绑定/有下级 | 依靠行锁和唯一约束收敛 |
| 候选完整链有重复、断链或自引用 | `RELATION_INVARIANT_BROKEN` | 阻断绑定并告警，禁止截断继续 |
| 新完整链超过 `max_relation_depth` | `RELATION_DEPTH_LIMIT` | 无写入；返回配置上限，禁止截断 |
| 边或审计写入失败 | 通用可重试错误 | 整个事务回滚 |
| slave 延迟 | 列表暂时不含新成员 | 返回 `as_of`；安全和资金路径改读 primary |
| 缓存删除失败 | 绑定仍成功 | 缓存短 TTL/版本校验，记录异步重试 |
| 上级后来注销或团队禁用 | 关系不变 | 新权益按消费者资格规则处理，历史快照不变 |

## 10. 缓存与作业

### 10.1 缓存

- 关系绑定和权限校验不使用缓存作为真源。
- 可缓存团队 summary 和公开成员卡片，键至少包含 `user_id`、查询深度、过滤口径和 `user_levels.version`。
- 绑定提交后尽力删除相关用户的团队缓存；缓存必须有短 TTL，删除失败不能形成长期错误。
- 完整祖先链不放入面向用户的通用缓存，也不写入前端 token。
- 后台范围查询不缓存“允许访问用户 ID 全集”，避免权限或状态变化后继续放行。

### 10.2 作业

| 作业 | 数据源 | 行为 |
| --- | --- | --- |
| `relationship_invariant_check` | primary 或一致性副本 | 检查 parent/head、重复、自引用、断链和链前缀 |
| `referral_edge_diff` | `users.inviter_ids` 对 `referral_edges` | 检查前五层缺边/多边，输出样本和总数 |
| `relationship_depth_report` | `users.inviter_ids` | 监控深度分布和异常突增，不截断数据 |
| `team_cache_refresh` | slave | 只做展示预热，可丢弃、可重跑 |

一致性作业默认只报告，不自动重写唯一真源。缺失的派生边可以在审批后从 `inviter_ids` 幂等重建；多余边先查明写路径缺陷再删除。作业必须记录游标、扫描量、差异量、耗时和最后成功时间。

## 11. 权限与安全

1. 普通用户只能查看自己的直属上级、五层团队和本人绑定审计摘要，不能传任意祖先 ID 查询他人团队。
2. 后绑定只能本人执行，不提供客服代绑；需要近期登录或 OTP，按账号、IP、设备限流。
3. `invite_enabled`、`team_enabled` 只能由独立后台权限修改，必须填写原因并写不可变安全审计。
4. 后台“操作权限”和“数据范围”分别校验：RBAC 允许动作，完整链限制对象；任一不满足即拒绝。
5. 用户侧接口不返回 `inviter_ids`，防止一次泄露完整组织关系。
6. 日志只记录必要 user ID、结果码和 request ID；邮箱、手机号、token、OTP、设备原值不进入关系日志。
7. 应用数据库角色无权直接 UPDATE `parent_id`、`inviter_ids` 或 DELETE 关系审计；只能经关系领域仓储执行受控语句。
8. 所有关系创建入口锁候选上级，防止“正在后绑定的用户”同时获得第一个下级。
9. 账号注销不物理删除用户和关系。展示层按隐私规则匿名化资料，账务与关系审计继续引用稳定 user ID。

## 12. 指标、日志与告警

关键指标：

- `relation_bind_total{source,result,reason}`；
- `relation_bind_tx_seconds{source}` 和数据库锁等待时间；
- `relation_bind_conflict_total{already_bound,has_children,cycle,idempotency}`；
- `relation_depth` 直方图及最大值；
- 距 `max_relation_depth` 还剩 10% 以内的用户数和超限拒绝数；
- `referral_edge_insert_total`、`referral_edge_diff_total{missing,extra}`；
- `relationship_invariant_error_total{kind}`；
- 团队列表 P50/P95/P99、扫描行数、返回行数和超时率；
- 后台完整范围查询 P95、GIN 候选行数和拒绝次数；
- slave lag、强制切 primary 次数、团队缓存命中率；
- 邀请/团队能力变更次数及操作者分布。

告警门槛：

- 任意自引用、循环、断链或 parent/head 不一致立即告警；
- `referral_edge_diff_total > 0` 持续两个检查周期告警；
- 绑定事务 P99、锁等待或死锁超过基线告警；
- 单账号/IP 的失败绑定突增触发风控；
- 后台范围查询未注入范围条件应由测试和运行时断言直接失败，而不是只记日志。

## 13. 验收用例

### 13.1 关系正确性

1. 无上级注册后 `parent_id=NULL`、`inviter_ids={}`、无边、无成功绑定审计。
2. A 邀请 B、B 邀请 C 后，C 的链严格为 `[B,A]`，边为 `(B,1,C)`、`(A,2,C)`。
3. 建立超过五层的链时 `inviter_ids` 保存全部祖先，边表只保存最近五层且深度准确。
4. parent/head、前缀、无重复、无自引用和边表差异检查全部为零。
5. 后台通过第六层及更深祖先仍能看到目标用户；用户团队接口看不到第六层。
6. 代理/业务员作为上级时不靠 ID 前缀识别，完整链保留，普通后代边的深度不跳级。
7. 新链恰好等于 `max_relation_depth` 可提交，超过一层整单拒绝，用户行、边和审计均无部分写入。

### 13.2 后绑定与并发

1. 无上级且无下级的普通用户后绑定成功一次；第二次使用新幂等键返回已绑定。
2. 相同幂等键、相同上级重试返回同一结果；相同键、不同上级返回幂等冲突。
3. 已有直接或间接下级的用户不能后绑定；检查在锁内执行。
4. 两个请求同时给同一用户绑定不同上级，只有一个提交。
5. “用户绑定上级”和“另一个用户把该用户设为上级”并发时，只有满足最终不变量的一方成功。
6. 注册、后绑定分别与邀请能力禁用并发，结果由行锁后的最新状态决定。
7. 事务在写用户、边、审计、等级聚合任一步注入故障，数据库均无部分结果。

### 13.3 安全与 API

1. `F3`、带空格字母、负数、零、溢出和不存在 ID 全部被拒绝，且无兼容解析日志分支。
2. 用户不能查询任意他人的完整链或团队；后台无 RBAC 或不在完整链范围内均被拒绝。
3. 邀请禁用不阻断登录，团队禁用不清空关系；账号禁用后不能成为新上级。
4. 写请求提交后即返回正确上级，不受 slave 延迟影响；随后 slave 列表可通过 `as_of` 表达延迟。
5. 团队接口所有查询计划使用 `referral_edges` 主键前缀，无 `inviter_ids[1:5]`、字符串匹配或全表扫描。
6. 后台完整范围查询使用整列 GIN，未出现五层截断。

### 13.4 性能基线

以生产目标规模和最深链构造压测数据，至少验证：

- 绑定事务只写 1 个用户、最多 5 条边、1 条审计及有限等级聚合行；写放大不随后代数增长。
- 五层成员列表按固定索引顺序分页；在允许的最大 offset 内 P95 达标，深分页达到全局上限时明确拒绝。
- 后绑定“无下级”检查命中 `users(parent_id)` 索引。
- 后台完整范围查询和用户五层查询分别命中预期索引，执行计划无数组切片表达式扫描。

## 14. 用户、认证与安全实施规范

### 14.1 目标、对象与不变量

安全域的目标不是把所有字段堆回 `users`，而是把身份、资料、认证因子、会话、合规审核、收款账户、注销和后台授权拆成边界清晰的事实。热路径只锁必要行，敏感信息只在明确用例中解密，任何外围供应商不可决定本地最终状态。

| 对象 | 真源 | 说明 |
| --- | --- | --- |
| 用户账号 | `users` | 普通用户主体、账号状态、关系头和通用版本 |
| 展示资料 | `user_profiles` | 昵称、头像、语言、区域等非认证资料 |
| 用户凭据 | `user_credentials` | 规范化登录标识、登录/支付密码 hash 和验证状态 |
| 会话族根 | `session_families` | 每次登录建立一个 refresh family；保存状态、当前 generation、账号版本快照和有界活动 slot |
| 用户会话 | `user_sessions` | family 内单次 refresh 摘要、认证级别、generation 快照、轮换链与到期历史 |
| 会话签发结果 | `session_issuances` | 登录/refresh 单次逻辑签发的短期加密响应，用于提交成功但响应丢失后的精确重放 |
| 登录审计 | `login_audits` | 登录尝试、结果和脱敏风险信号，只追加 |
| 用户安全审计 | `user_security_audits` | 改密、OTP、会话族撤销、KYC/卡/注销决定的稳定事件，只追加 |
| OTP 与二次认证 | `otp_bindings`、`security_challenges` | 加密后的长期因子与有次数/时限的短时挑战 |
| KYC | `kyc_cases`、`kyc_provider_events` | 本地审核状态和供应商幂等事件；提现复用基础 KYC，不另建每笔人脸检查 |
| 银行卡 | `bank_accounts` | 加密账号、掩码、规范化户名、供应商核名及人工复核 |
| 注销 | `account_closures` | 请求、阻塞项快照、重检水位和完成事实 |
| 后台主体与授权 | `admin_users`、`admin_roles`、`admin_permissions` 及关联表 | 与普通用户分离的身份、MFA、权限点和数据范围 |

强制不变量：

1. 普通用户只由 `users.id` 标识；后台主体只由 `admin_users.id` 标识。两类 token 使用不同 issuer、audience 和签名用途，ID 数字偶然相同也不是同一主体。
2. `users.status` 只表达 `ACTIVE/DISABLED/CLOSING/CLOSED`。`DISABLED` 和 `CLOSED` 禁止登录；`CLOSING` 仅允许登录后读取资料、查询注销和执行明确登记的 blocker 处置，不允许充值、Playlet Backing、Robot Purchase、绑定关系、普通新增银行卡或普通业务提现。若进入 CLOSING 后既有清退卡失效，只允许带 `purpose=ACCOUNT_CLOSURE` 的窄补卡/核名流程，不能用于恢复其他业务。
3. `invite_enabled/team_enabled` 与账号状态正交。团队禁用不等于登录禁用，账号恢复也不自动恢复被单独禁用的团队能力。
4. 登录标识先按种类确定性规范化，再由数据库唯一约束兜底；客户端收到的登录失败不能区分“账号不存在”“密码错误”或“后台账号走错入口”。
5. 登录密码和支付密码只保存带算法参数的单向 hash；OTP secret、证件、完整银行账号和户名原值使用字段级信封加密并保存密钥版本；长期会话/挑战表中的 refresh、重置码和短信码只保存摘要。唯一例外是 `session_issuances` 为响应丢失恢复保存短 TTL、设备/nonce 强绑定的 token pair 密文，到期 crypto-shred，不能用于普通认证查询。
6. 不存在超级密码、万能 OTP、管理员代输用户密码、配置开关绕过密码/MFA，或仅在测试环境之外可启用的同类分支。测试替身只能通过依赖注入存在，生产组装无法加载固定验证码。
7. Access Token 是短时声明，不是会话真源。受保护请求在 primary 校验账号状态、`users.auth_version`、`session_families.status/generation` 和当前 `user_sessions` 快照；任一版本不等立即拒绝。全局撤销只增加一行 `users.auth_version`，不得同步扫描或 UPDATE 全部 family/session/issuance；单 family 撤销只条件推进该 family 的 generation/status。Refresh Token 每次使用都轮换，旧 token 重放触发 family 根撤销。
8. 同一用户、同一 OTP 类型最多一个 ACTIVE 绑定；相同 TOTP time step 只能成功一次。二次认证只提升当前会话的 `auth_level/mfa_verified_at`，不能永久写一个“已验证”布尔值绕过以后检查。
9. 同一用户同一时刻最多一个进行中的 KYC case。只有本地状态机接受且验签成功的唯一供应商事件或有权限的人工复核，才能把 KYC 推进为 `APPROVED/REJECTED`。
10. 可用于新提现的银行卡必须属于当前用户、状态为 `VERIFIED`，且开户名通过版本化规范化后与已批准 KYC 姓名一致并完成供应商核名；不确定结果必须进入人工复核，不能按成功处理。
11. 注销不物理删除用户、关系、资产、持仓、订单、结算或审计。`CLOSED` 前必须在 primary 重新确认持仓、可用/冻结资产、ACTIVE 冻结、在途提现和其他已登记阻塞项均满足关闭策略。
12. 外部 KYC、银行卡核名、短信和邮件调用不进入数据库事务；Redis、供应商响应和 slave 均不是真源。短信与邮件统一使用 Forge `message` 作为发送适配层，WhatsApp 完全不进入 2.0。
13. 任何可能新建、增加、释放或清除注销 blocker 的写路径都必须在全局业务根之后、资产之前锁目标 `users` 行，并在锁内按来源类型检查 ACTIVE/CLOSING 许可。CLOSED 后禁止产生新的钱包权益；历史事实纠错只能形成独立外部应付/追偿，不能重新打开账号或直接写其钱包。

### 14.2 状态机

#### 14.2.1 账号、会话与 OTP

```text
账号：ACTIVE <──管理员有审计地启停──> DISABLED
       ACTIVE ──用户请求注销────────> CLOSING ──阻塞清零并复核──> CLOSED
       CLOSED 为终态；CLOSING 不复用 DISABLED，也不清空关系

会话族：ACTIVE(generation=n) ──family 撤销/复用检测──> REVOKED(generation=n+1)
         ACTIVE ──超过 family 有效期───────────────> EXPIRED

会话：ACTIVE ──刷新轮换────────────> ROTATED
       ACTIVE ──单 family 登出/清理归一──> REVOKED
       ACTIVE ──超过时间──────────────> EXPIRED
       任一状态 ──auth_version 不等────> 逻辑无效（无需改行）

OTP：PENDING ──正确码确认──> ACTIVE ──受控重置──> REVOKED
     PENDING ──超时/次数用尽────────────> EXPIRED
```

密码修改、密码重置、OTP 重置、账号禁用和注销完成都在锁住 `users` 后只把 `auth_version` 加一；若会影响播放凭证，同时在同一行推进 `play_credential_sweep_generation`、cursor 归零并置 dirty。提交瞬间，所有旧 version 的 token/family/session/播放 issuance 即逻辑失效，复杂度 O(1)。旧行的状态归一、密文销毁和归档由 generation fenced 的有界 keyset 作业异步完成，不是撤销正确性的前置。支付密码是额外的资金操作因子，不是账号登录凭据，也不能替代规则要求的 Authenticator/TOTP 或 KYC。

#### 14.2.2 KYC

```text
INITIALIZED -> PROVIDER_PENDING -> APPROVED
                              ├-> REJECTED
                              ├-> MANUAL_REVIEW -> APPROVED / REJECTED
                              └-> EXPIRED
```

`APPROVED` KYC 是当前用户唯一有效实名事实；重新核验必须创建新 case，并由明确规则决定旧批准在新 case 完成前是否仍有效。未知供应商状态保持 `PROVIDER_PENDING` 并安排回查，不猜成成功或失败。普通提现与注销清退提现都直接复用该基础 KYC 事实和 VERIFIED 银行卡，不创建提现专用人脸意图、状态、供应商事件或一次性消费记录；删除的只是每笔提现专用人脸步骤，不代表取消基础 KYC。

#### 14.2.3 银行卡

```text
PENDING_VERIFICATION -> VERIFIED -> DISABLED
                    ├-> REJECTED
                    └-> MANUAL_REVIEW -> VERIFIED / REJECTED
```

供应商明确姓名/账号不匹配进入 `REJECTED`；超时保持待核验并重试；供应商返回模糊匹配、别名或无法判定时进入 `MANUAL_REVIEW`。已核验账号、银行和户名不可原地覆盖；`UpdateBankAccount` 若改变这些事实，创建新的待核验记录，旧记录仅在新记录核验成功后由同一用户命令禁用。

#### 14.2.4 注销

```text
REQUESTED -> WAITING_BLOCKERS <──发现新阻塞── READY
                 └──全部清零───────────────> READY -> COMPLETED
```

`account_closures` 状态推进与 `users.status` 配套：创建请求时用户变为 `CLOSING`；`COMPLETED` 与 `users.status=CLOSED`、凭据禁用和 `users.auth_version+1` 的逻辑全局撤销在同一事务发生。事务不等待、枚举或锁定会话历史；`blockers_snapshot` 只用于解释，完成资格每次都从 primary 事实重新计算。

### 14.3 数据表、关键字段、约束与索引

除只追加审计外，下列可变表均具有 `created_at/updated_at/version`；状态迁移使用带旧状态和 `version` 的条件更新。

#### 14.3.1 资料、凭据、会话与审计

`user_profiles`：

- `user_id bigint` 主键、外键 `users(id) ON DELETE RESTRICT`；
- `display_name/avatar_object_key/language/region/timezone`，展示字段有长度、字符集和内容安全校验；
- 不保存 KYC 姓名、证件、密码、关系链或资产聚合，避免普通资料读扩大敏感面。

`user_credentials`：

| 字段 | 约束/说明 |
| --- | --- |
| `id/user_id` | identity 主键；用户外键 `RESTRICT` |
| `kind` | `EMAIL_PASSWORD/MOBILE_PASSWORD/PAY_PASSWORD`；未知值失败关闭 |
| `normalized_identifier` | 登录种类必填；支付密码行为空 |
| `secret_hash/hash_policy_version` | PHC/自描述 hash 与生成策略版本；永不保存明文 |
| `identifier_verified_at/secret_changed_at/disabled_at` | 验证、换密、禁用审计时间 |

唯一约束为登录种类的 `(kind, normalized_identifier)`、以及 `(user_id, kind)`。邮箱执行 Unicode/IDNA 与域名小写规范化，手机号转 E.164；规范化函数带固定测试向量。支付密码不得和登录密码共用 hash 行，也不存在空 hash 即跳过校验的路径。

`session_families` 是 refresh family 的可变根，保存 `id uuid/user_id/auth_version_snapshot/slot_no/status=ACTIVE|REVOKED|EXPIRED/generation/expires_at/revoked_at/revoke_reason/created_at/updated_at/version`；`user_id/auth_version_snapshot/slot_no/status/generation` 均 NOT NULL。`generation >= 1` 且只增；每次 refresh 在同一事务把 generation 加一并创建该 generation 的唯一 session，复用检测/单设备登出则把根条件转 REVOKED 并再加一。首发固定且数据库可证明的上限为：同一用户、同一 `auth_version_snapshot` 最多 16 个 ACTIVE family。实现为 `slot_no smallint NOT NULL CHECK (slot_no BETWEEN 1 AND 16)` 与 partial unique `(user_id,auth_version_snapshot,slot_no) WHERE status='ACTIVE'`；新登录持 user 锁后先在这至多 16 行内条件终结已到期 family，再选择空 slot，满额返回 `ACTIVE_SESSION_FAMILY_LIMIT_REACHED`，不得静默挤掉其他设备。另建 `(user_id,created_at,id)` 支撑历史 keyset。旧 auth version 的 ACTIVE 字样不代表仍有效，校验必须同时满足快照等于 `users.auth_version`，异步清理再归一为 REVOKED。

`user_sessions`：

- `id uuid` 主键，`user_id`、`family_id` 外键，保存 `auth_version_snapshot/family_generation`；`UNIQUE(family_id,family_generation)` 保证每个 generation 只有一个逻辑 session；
- `refresh_token_hash bytea UNIQUE`、`auth_level`、`mfa_verified_at`；
- `issued_at/access_expires_at/refresh_expires_at/last_seen_at/status=ACTIVE|ROTATED|REVOKED|EXPIRED/rotated_to_session_id/revoked_at/revoke_reason`；
- `(family_id,family_generation)` 和 `(user_id,created_at,id)` 支撑当前定位与历史 keyset 清理；历史 ROTATED/REVOKED/EXPIRED 行不参与账号全局撤销事务。

`session_issuances` 是安全域自己的短期结果表，不是 Outbox：保存 `id/kind=LOGIN|REFRESH/user_id/family_id/auth_version_snapshot/family_generation/live_slot/challenge_id nullable/predecessor_session_id nullable/replacement_session_id/request_nonce/request_context_hash/device_key_thumbprint/access_token_ciphertext/refresh_token_ciphertext/key_version/response_hash/expires_at/destroyed_at/created_at`；`user_id/family_id/auth_version_snapshot/family_generation/live_slot` 均 NOT NULL。LOGIN 使用 `(challenge_id,request_nonce)` 唯一，REFRESH 使用 `(predecessor_session_id,request_nonce)` 唯一，`replacement_session_id` 全局唯一；CHECK 保证两种 kind 只填写对应来源，`(user_id,created_at,id)` 支撑 keyset 清理。

同一用户、同一 `auth_version_snapshot` 最多 32 条未销毁 issuance：`live_slot smallint NOT NULL CHECK (live_slot BETWEEN 1 AND 32)`，partial unique `(user_id,auth_version_snapshot,live_slot) WHERE destroyed_at IS NULL`。签发事务在 user/family 锁后只检查这至多 32 行，先 crypto-shred 已过期行再选择空 slot；仍满额返回 `LIVE_SESSION_ISSUANCE_LIMIT_REACHED`，且不得消费登录 challenge 或轮换旧 session。密文仅允许认证服务在相同 nonce、规范化请求 hash、设备持有证明、当前 `users.auth_version` 和 ACTIVE family generation 全部匹配时解密；任一版本已失效只返回重新登录语义，不回放旧 token。TTL 到期立即 crypto-shred，元数据随后按 keyset 游标物理清理；日志、审计、普通后台和通用查询均不可读取。

Access Token 不以明文长期落库，token 内的 `subject/session_id/family_id/family_generation/auth_version/auth_level/issued_at/expires_at` 必须与 primary 用户、family 和 session 行相容。refresh/access 原文只属于一次逻辑签发；同一请求因响应丢失的重试可在短 TTL 内从 `session_issuances` 返回完全相同的 token pair，绝不生成第二对。

`login_audits` 为只追加表，保存 `id/user_id nullable/identifier_hash/entrypoint/result/reason_code/session_id nullable/ip_hash/device_hash/risk_flags/created_at`。索引 `(user_id, created_at DESC, id DESC)` 和 `(identifier_hash, created_at DESC)`；不保存登录标识原文、密码、验证码、token、User-Agent 全文或可逆设备指纹。

`user_security_audits` 为自助与系统安全动作的统一追加式审计，保存 `id/user_id/actor_type(USER/SYSTEM/ADMIN)/actor_id nullable/event_type/target_type/target_id/result/reason_code/request_id/session_id nullable/ip_hash/device_hash/before_hash/after_hash/created_at`。管理员 actor 引用 `admin_users.id`，不能塞进 `user_id`；表中只存稳定类型和脱敏 hash，不保存密码、OTP、token、证件、卡号或任意请求 body。索引 `(user_id,created_at DESC,id DESC)` 和 `(target_type,target_id,id)`，应用角色无 UPDATE/DELETE 权限。

#### 14.3.2 OTP 与安全挑战

`otp_bindings` 保存 `id/user_id/kind/status=PENDING|ACTIVE|REVOKED|EXPIRED/secret_ciphertext/key_version/confirmed_at/last_accepted_step/revoked_at/revocation_reason/reset_by_admin_id/version`。建立 `UNIQUE(id,user_id)` 供提现审计快照复合引用，以及 partial unique `(user_id, kind) WHERE status='ACTIVE'`；`last_accepted_step` 在验证成功事务内用条件更新推进，防止同一步重放。管理员重置要求独立权限、近期 MFA、理由和工单，只能写 `REVOKED + revocation_reason=ADMIN_RESET`，不能读取 secret，也不另造 RESET 状态。

提现所称 OTP 固定指 Authenticator/TOTP，不是短信验证码。提现安全状态由绑定历史派生，不另存可漂移布尔值：没有任何 `confirmed_at IS NOT NULL` 历史为 `NEVER_BOUND`，仅有未确认的 PENDING/EXPIRED 记录仍属于该分支，创建普通或注销清退提现时可不提交 `otp_code`；存在 `ACTIVE` binding 时请求必须提交 `otp_code`；至少一条历史 binding 曾确认但当前没有 ACTIVE（包括管理员 reset 后的 REVOKED）为 `REBIND_REQUIRED`，必须重新绑定或完成受控恢复，不能降级成 `NEVER_BOUND` 绕过验证。提现事务在创建业务单和冻结之前锁 ACTIVE binding、验证 TOTP，并以条件更新原子推进 `last_accepted_step`；同一步并发只允许一次成功。若同一幂等请求已提交成功，则先返回原提现结果，不重新消费 OTP。原始 `otp_code` 不写数据库、请求审计或日志。

`security_challenges` 保存：

- `id uuid`、`user_id nullable`、`purpose`（登录 MFA、OTP 绑定、改密、支付密码、重置密码、绑卡、后绑定、注销等）；
- `challenge_digest/context_hash/delivery_target_hash` 用于验证/查重，绝不保存明文验证码或 reset token；
- 短期 `delivery_target_ciphertext/delivery_secret_ciphertext/delivery_key_version`、`delivery_channel=SMS|EMAIL/template_code/locale/delivery_dedupe_key/delivery_status=PENDING/SENDING/RETRY_WAIT/PROVIDER_ACCEPTED/UNKNOWN/DEAD/lease_owner/lease_until/lease_generation`，只供该 challenge 的可恢复投递；
- `status=PENDING/VERIFIED/CONSUMED/EXPIRED/LOCKED/CANCELED`、`attempt_count/max_attempts/expires_at/verified_at/consumed_at`；
- `session_id nullable`、`next_run_at/last_error_code/version`，支撑外部验证码发送与恢复。

索引 `(status, expires_at)` 和待发送 partial `(delivery_status,next_run_at,lease_until,id) WHERE status='PENDING' AND delivery_status IN ('PENDING','SENDING','RETRY_WAIT')`；应用级 `delivery_dedupe_key` 唯一且同一 challenge 重试复用。供应商接受请求或挑战终结后立即清空/crypto-shred 两个 ciphertext，验证仍只使用 digest；ciphertext 的 TTL 不得晚于 `expires_at`，普通应用/日志/管理 API 无解密权限。挑战绑定 purpose、主体、会话和规范化请求 hash；短信/邮件 challenge 不能替代提现要求的 Authenticator/TOTP。

Forge `message` 只承担 SMS 与 Email 的发送适配，不能承担 challenge 状态、lease、sweep、重试、一次消费或送达真值。worker 在 primary 短事务领取 challenge 后提交，事务外调用 Forge，再用新短事务条件写回；Forge 返回成功只写 `PROVIDER_ACCEPTED`，表示供应商接受请求，不表示终端已经 `DELIVERED`。Forge 当前不返回统一 provider message ID，也不提供跨供应商幂等保证，因此 `delivery_dedupe_key` 只是应用级防重依据，不会自动传给供应商。只有 provider profile 能证明请求未被接受的临时失败才进入 `RETRY_WAIT`；网络超时、响应丢失或调用后未 finalize 的过期 `SENDING` 在没有供应商幂等/查询证据时由 sweep 条件转 `UNKNOWN`，禁止自动重发或换 sender。UNKNOWN challenge 若消息实际到达仍可在到期前验证；未到达时用户冷却期后显式创建新 challenge，并使旧 challenge 按规则取消或到期。应用先按 channel/region/template profile 选定唯一 provider，再调用只装配该单一 sender 的 Forge Manager，禁止触发 `v0.4.1` 内建的跨 sender fallback。SMS 可直接使用 Forge 内置 sender，Kirim 通过项目内实现 `message.SmsSender` 接入；Email 使用 Forge email sender 能力。WhatsApp 不建立 channel 枚举、配置、模板或 fallback。调用 context 必须隔离 Forge 内部可能包含完整收件人的日志；适配器不得向日志、数据库或上层错误透传 Forge 原始错误字符串，只记录脱敏目标和归一化错误码，并通过敏感字段扫描门禁。

#### 14.3.3 KYC 与供应商事件

`kyc_cases` 保存 `id/user_id/attempt_no/provider/provider_case_id/status/is_current`，以及加密的法定姓名/证件引用、`legal_name_normalized_hash/name_normalization_version`、供应商结果码、人工审核人/理由、`submitted_at/decided_at/expires_at/next_run_at/attempt_count/last_error_code/version`。

- `UNIQUE(provider, provider_case_id)`；
- `UNIQUE(user_id, attempt_no)`；
- partial unique `(user_id) WHERE status IN ('INITIALIZED','PROVIDER_PENDING','MANUAL_REVIEW')`；
- partial unique `(user_id) WHERE status='APPROVED' AND is_current=true`；批准新 case 的事务先锁用户、撤销旧 current 标记，再设新 current；
- partial 索引 `(next_run_at,id)` 覆盖需要建单/回查的进行中状态。

姓名规范化结果使用带密钥 hash 做等值比较；需要展示时只解密最小字段并留审计。KYC 文档使用受控对象存储 key，上传 key 必须绑定当前 user ID、用途、内容类型和过期时间，数据库不保存公开 URL。

`kyc_provider_events` 是正式的身份供应商事件表，不另建泛化 `provider_events`。字段含 `provider/provider_event_id/kyc_case_id/provider_case_id/event_type/payload_hash/signature_key_version/mapped_status/process_result/error_code/received_at/processed_at`，`UNIQUE(provider, provider_event_id)`。只保存通过签名、时限和来源校验后的脱敏摘要；原始敏感 body 按合规策略加密短期留存或不留存，绝不进入普通日志。`kyc_case_id` 是唯一目标类型。

#### 14.3.4 银行卡

`bank_accounts` 关键字段：

| 字段 | 约束/说明 |
| --- | --- |
| `id/user_id` | identity 主键；用户外键 `RESTRICT` |
| `bank_code/bank_directory_rule_version_id` | 来自当时已发布 `BANK_DIRECTORY` 版本，不接受自由文本或隐式复用渠道 code |
| `account_number_ciphertext/key_version` | 完整账号加密保存，仅出款快照授权路径可解密 |

| `holder_name_ciphertext/holder_name_normalized_hash` | 原值加密；规范化 hash 与 KYC 快照比较 |
| `name_normalization_version/kyc_case_id/kyc_name_hash_snapshot` | 固化当时规范化规则和批准实名 |
| `status/provider/provider_reference/provider_result_code` | 核名状态和脱敏供应商结果 |
| `provider_request_key/next_run_at/attempt_count/last_error_code` | 稳定核名请求键、回查时间和重试摘要；同一卡重试不换 key |

同用户同银行同账号的进行中或可用记录由 partial unique `(user_id, bank_code, account_number_hash) WHERE status IN ('PENDING_VERIFICATION','MANUAL_REVIEW','VERIFIED')` 防重；`provider_request_key NOT NULL UNIQUE`，lease owner/until 必须成对，终态清空 lease。索引 `(user_id,status,id DESC)` 支撑自助列表，`(status,next_run_at,verification_lease_until,id) WHERE status='PENDING_VERIFICATION'` 支撑 primary 回查。姓名规范化固定执行 Unicode NFKC、首尾去空白、连续空白折叠、locale-aware 大小写折叠和已发布标点/称谓规则，并保存版本。应用先与 KYC 姓名 hash 精确比较，再调用供应商核名；任何模糊匹配都不能只凭 `strings.EqualFold` 自动通过。

`bank_directory_entries` 归属 `rule_versions(domain=BANK_DIRECTORY)`，保存稳定 `bank_code/display_name/country/fiat_currency/allow_withdrawal/allow_account_closure/status`，唯一 `(rule_version_id,bank_code)`；`provider_bank_code_mappings` 显式保存目录项到 `payment_channel_id/provider_bank_code` 的映射并联合唯一。发布 hash 覆盖两表；下架只阻止新绑卡/新提现，不改旧提现快照。`ListSupportedBanks` 按 purpose/币种返回当前 PUBLISHED 版本和可用 code，创建卡必须在 primary 重验版本/entry/mapping。

#### 14.3.5 注销

`account_closures` 除下述字段外还必须包含 `last_withdrawal_seq bigint NOT NULL DEFAULT 0`，非负且只增；每次 ACCOUNT_CLOSURE 提现创建都在已锁 closure 行上分配连续序号。`withdrawals(closure_id) WHERE purpose='ACCOUNT_CLOSURE' AND status IN ('AWAIT_REVIEW','APPROVED','PAYING','FAIL_CONFIRMING')` 的 partial unique 保证同一 closure 至多一笔非终态清退，历史终态批次不影响下一批。

`account_closures` 保存 `id/user_id/status/requested_at/ready_at/completed_at/blockers_snapshot/blocker_hash/next_check_at/attempt_count/last_error_code/deduplication_id/lease_owner/lease_until/lease_generation/version`，并为大量历史负合伙人调整保存 `partner_adjustment_scan_after_seq/partner_adjustment_scan_upper_seq/partner_adjustment_scanned_seq`。`lease_generation` 非负且每次成功认领加一；owner/until 必须成对为空或非空，只有 `REQUESTED/WAITING_BLOCKERS/READY` 可持有租约，COMPLETED 必须清空。三个 seq 非负且 `scanned<=after<=upper`。每个扫描批次在新事务中先锁 rank 500 `partner_adjustment_user_roots(user_id)`、后锁 rank 600 closure，并同时匹配预读的 `(closure_id,version,lease_owner,lease_generation,lease_until,scan_after,scan_upper)` 及 `lease_until>clock_timestamp()`；再按 `(user_id,approval_seq)` 最多 N 条推进 after 和 version。到 upper 时，只有 root `last_approval_seq=upper` 才令 `scanned=upper`；若增大则把新 upper 纳入下一窗口。租约过期后旧 owner 即使先抢到两行也影响 0 行，不能推进游标、续租或置 READY。MANUAL 审批和 SOURCE_REVERSAL 创建都在同一 per-user root 锁内分配 approval_seq，因此不存在先分配旧时间/ID、后提交到游标之前的漏扫窗口。partial unique `(user_id) WHERE status <> 'COMPLETED'`，待检查索引 `(next_check_at,lease_until,id) WHERE status IN ('REQUESTED','WAITING_BLOCKERS','READY')`。

同一行另有与完成裁决解耦的可空 `security_cleanup_status=PENDING|RUNNING|DONE/security_cleanup_next_run_at/security_cleanup_lease_owner/security_cleanup_lease_until/security_cleanup_generation`，以及三组类型化 keyset 游标 `family_cleanup_after_created_at/family_cleanup_after_id`、`session_cleanup_after_created_at/session_cleanup_after_id`、`issuance_cleanup_after_created_at/issuance_cleanup_after_id`。COMPLETED 前 cleanup 状态/游标必须全空，COMPLETED 后状态必填；游标时间与 ID 必须成对，owner/until 也必须成对且 generation 单调。cleanup 领取使用 partial 索引 `(security_cleanup_next_run_at,security_cleanup_lease_until,id) WHERE status='COMPLETED' AND security_cleanup_status IN ('PENDING','RUNNING')`。注销完成只把 cleanup 置 PENDING，不把历史清理纳入 CLOSED 条件；每个清理事务先锁这一 closure/cursor 根，除此之外只触碰一种历史表且最多 200 行，再同事务推进对应 `(created_at,id)` 游标。禁止一个事务扫描或锁定该用户全部历史。

`account_closure_dispositions` 保存 `id/closure_id/user_id/asset_type=EXPERIENCE/kind=FORFEIT/amount/rule_version_id/consent_version/deduplication_id/asset_ledger_id/created_at`。金额必须为正；`deduplication_id` 和 `asset_ledger_id` 唯一；规则版本必须与同意文案版本同属当时已发布的 ACCOUNT_CLOSURE 版本。它是用户近期 MFA 后明确放弃不可提现体验资产的不可变事实，使用 `ApplyMutations(EXPENSE)`，不能由 worker 自动生成、不能处置 COMMON，也不能以注销为名把资产转给其他用户。

`account_closure_common_dispositions` 只处理“余额为正但当前已发布、固定最多 32 个且支持 ACCOUNT_CLOSURE 的渠道，在零手续费/已发布清退规则下仍因最小法币单位、渠道下限或舍入得到不可支付结果”的 COMMON dust。字段为 `id/disposition_no/closure_id/user_id/amount/channel_eligibility_snapshot_hash/rule_version_id/consent_version/deduplication_id/asset_ledger_id/finance_recovery_case_id/created_at`；`disposition_no`、dedup、ledger、case 分别唯一，金额必须等于事务锁内全部可用 COMMON，snapshot hash 必须等于该规则版本的完整 channel set hash。同一 closure 可因后续既有来源再次入账而产生多次处置，每次使用新命令对应的服务端 ULID disposition_no，不能覆盖旧行。它不是放弃：用户近期 MFA 下明示同意后，同一事务以 `ACCOUNT_CLOSURE_COMMON_DUST_TO_PAYABLE` 调用 `ApplyMutations(EXPENSE)` 把钱包归零，并创建等额 `direction=PAYABLE/reason=ACCOUNT_CLOSURE_COMMON_DUST/value_basis=ASSET/asset_type=COMMON` 的 Finance case。case 解决只能走外部收付证据，不能 waive PAYABLE；OPEN PAYABLE 已完整承接钱包价值，不再是 closure blocker，账号关闭也不删除其主体/案件。

这里的“不可支付”按“无法形成任何合法正批次”判定，而不是要求一个批次覆盖全部余额：余额超过单笔/渠道/DAY/WEEK 上限时必须串行分批或等下一窗口，绝不能误判为 dust。清退批次固定为 `min(available_common,单笔上限,渠道上限,DAY剩余额度,WEEK剩余额度)`；同一 closure 仅一笔非终态，前批终结后继续下一批。只有锁定并复验当前规则版本完整的 1..32 channel slot 集、对应渠道状态与集合 hash，且每个槽算出的合法批次都为 0（下限、最小单位或舍入导致）时，才允许把全部剩余 COMMON 转 PAYABLE。

`account_closure_rule_settings` 与 `rule_versions(domain=ACCOUNT_CLOSURE)` 一对一，使用类型化列保存 COMMON 清退的最低额/手续费例外、dust 外部应付同意文案版本、允许的银行卡状态、所需近期认证级别、EXPERIENCE 放弃同意文案版本、阻塞重检周期，以及生成的 `closure_channel_count/closure_channel_set_hash`。`account_closure_channel_slots` 以 `(rule_version_id,slot_no)` 唯一，slot 只能 1..32，另以 `(rule_version_id,payment_channel_id,fiat_currency)` 唯一；每行固定渠道及所引用的不可变渠道规则版本。发布事务持规则 domain root，写完整 slot 集并由延迟约束触发器验证 `count BETWEEN 1 AND ACCOUNT_CLOSURE_CHANNEL_MAX=32`、slot 连续、无重复、全部可用且 canonical hash 与 settings 完全一致，随后整体封存。注销/清退/放弃/应付转移事实都保存规则版本和关键数值快照。发布校验必须枚举该有界集合中每个清退币种/渠道的最小单位：正常 withdrawal 能覆盖则使用提现；否则必须启用上述 PAYABLE dust 路径，禁止发布一套让正余额既不能提现又不能合法转应付的规则。

阻塞项由代码中的穷举 `ClosureBlockerProvider` 注册表统一登记，新增任何“可增加/释放 COMMON、产生 EXPERIENCE、占用资产或保留法律状态”的业务状态时，CI 必须要求同步实现 provider；不能由各接口临时拼查询。首发至少覆盖：非终态 Playlet Backing/Robot Purchase 持仓及待日结/返本、ASSIGNED 未核销 Robot Activation Voucher、ACTIVE/QUEUED 一次性 VIP 权益及其非终态退款、待释放团队返佣、用户已归属但尚未 CLAIMED 的合伙人来源/正 adjustment/selected settlement、尚未终结且仍有负余额的 adjustment、closure 请求前已有来源事实但尚未领取的任务奖励、剧集退款 finality=ELIGIBLE 且未到 `refund_eligible_until` 或存在 REQUESTED 请求、Playlet Backing/Robot Purchase 退款补偿、任一非零 COMMON/EXPERIENCE 可用或冻结额、ACTIVE `asset_freezes`、可能失败释放的在途提现、非终态充值退款/出款，以及仍处迟付风险窗且未取得“确认未收款”最终证据的充值或一次性 VIP COLLECT（即使本地订单/attempt 已 EXPIRED/FAILED）和 legal hold。剧集 NOT_ELIGIBLE/REJECTED/EXPIRED/REFUNDED 不再阻塞。合伙人 provider 必须 root-aware：月根 OPEN/CALCULATING 时只用 0 代/来源判断未来权益，SEALED/CLAIMABLE 时只看 `selected_calculation_version` 的正代，旧 0 代和失败代永不成为 blocker；零额 selected settlement 允许无 ledger 领取为 CLAIMED。负 adjustment 的 blocker 真值仅为“已 APPROVED、无首个已发布 head且原额<0”，或“最新 selected head `remaining_after<0`”，PENDING_APPROVAL 由独立审批 blocker 表达，REJECTED/最新 head=0 明确不阻塞。负 adjustment 一旦由唯一 disposition 全额 POSTED 或转全额 RECEIVABLE，就不再是未来月份 blocker；正数和已形成的 claimable 权益仍必须正常领取/清退。`blockers_snapshot` 使用固定 blocker code、饱和数量（`0..20/>20`）与至多 20 个对象 ID 摘要，不保存任意 `extras`，也不能替代完成时实时查询。

注册表还有一项写侧契约：每个 provider 同时登记会改变该 blocker 的命令/worker 及其 CLOSING 策略。cutoff 后创建的可选新订单、持仓、任务来源、充值或人工赠款必须锁 `users` 并只接受 ACTIVE；请求前已经持久化的来源可以在 CLOSING 继续终结、释放或领取，但必须锁同一 user、验证来源早于 cutoff，并把 closure `next_check_at` 提前。任何未锁 user 的 blocker 写入口、仅检查缓存状态的入口或“先插来源后检查账号”的入口都不能通过 CI。

COMMON 优先通过带 `purpose=ACCOUNT_CLOSURE` 的串行有界清退提现归零：每批取余额、单笔/渠道上限和 DAY/WEEK 剩余额度的最小正数，同一 closure 仅一笔非终态；额度用尽则等下一窗口继续。只有事务内锁定当前规则完整且最多 32 条的 channel slot 集、对应渠道状态根并复验 set hash，证明每个槽都连一个合法正批次也无法支付时，用户才可用上述 dust disposition 把钱包价值等额转为外部 PAYABLE，绝不没收 COMMON。EXPERIENCE 可先按已发布规则兑换，或由用户明确调用上述放弃命令归零，绝不隐式兑换/删除。以 `account_closures.requested_at` 为 cutoff：此前已存在的任务来源事实、合伙人 pool/allocation/正 adjustment 即使当时还处 OPEN/CALCULATING/SEALED，等待期间变成 CLAIMABLE 后也允许通过清退白名单领取并立即转成 COMMON blocker；负 adjustment 则由 06 章专用 disposition sweep 终结。若相关月为 CALCULATING，sweep 至多等待该 current generation 发布为 SEALED/CLAIMABLE 后读取最新 head；若月为 OPEN，则在锁住月根、证明 current generation 未 staging 后可先写 disposition，使以后 staging 必须排除。它对全部剩余负额只允许一次全额 COMMON 扣回，余额不足则一分不扣并建立全额 RECEIVABLE Finance case；禁止部分扣回、无限跨月等待或用未来收入抵到未知日期。cutoff 后不接受该 CLOSING 用户的新任务来源或新可选业务。不得因状态从 OPEN 进入 CALCULATING/SEALED 而短暂漏阻塞，也不得关闭后丢弃既得权益。失败提现释放、充值迟付、退款回补、冻结返佣释放和持仓后续结算等所有未来入账都会重新置 closure `next_check_at`，完成检查必须从 primary 重算。

`account_closures` 必须显式建立 `UNIQUE(id,user_id)`。所有同时保存 closure_id 与 user_id 的子事实（两类 asset disposition、closure withdrawal/exchange、机器人券处置、合伙人 adjustment disposition、任务补偿）都以 `(closure_id,user_id)` 完全同序 composite FK 回该键；单列 closure/user 外键或应用 CHECK 不能代替，迁移测试必须用 A 用户子事实指向 B 用户 closure 的反例验证拒绝。

#### 14.3.6 后台主体与 RBAC

`admin_users` 独立保存 `id/login_identifier_normalized UNIQUE/password_hash/hash_policy_version/password_changed_at/otp_secret_ciphertext/otp_key_version/otp_bound_at/status/session_version/data_scope_type/data_scope_root_user_id/failed_login_count/locked_until/last_login_at/version`。状态为 `INVITED/ACTIVE/DISABLED`；没有已设置密码和 MFA 的主体不能进入 ACTIVE。`admin_invites` 保存单次 token hash、admin、用途 `INITIAL_ACTIVATION|CREDENTIAL_RECOVERY`、过期/消费时间并分别唯一；`admin_login_challenges` 保存 PASSWORD_OK 后的短期 MFA challenge、尝试次数与消费状态；`admin_sessions` 保存独立 family/session、refresh hash、generation、过期/撤销和设备摘要，活动会话有硬上限。`admin_auth_issuances` 保存 `kind=INVITE_ACCEPT|LOGIN|REFRESH`、invite/challenge/predecessor session 三选一、`request_nonce/request_hash/device_proof_hash`、replacement session/activation context、短 TTL 加密响应、过期/销毁时间；三种 kind 分别按 `(invite_id,request_nonce)`、`(challenge_id,request_nonce)`、`(predecessor_session_id,request_nonce)` 唯一，replacement session 亦唯一。`GLOBAL` scope 要求 root 为空，`RELATION_SUBTREE` 要求 root 指向真实 `users(id)`。后台 token 不复用 `user_sessions` 或 public token issuer，短时 token 携带 `admin_id/admin_session_id/session_version/mfa_at`，每次高风险命令在 primary 校验。

`admin_roles` 保存 `id/code UNIQUE/name/status/version`；`admin_permissions` 以稳定 `code` 为主键并保存领域、风险级别和说明，权限点只能新增或停用，不能改名复用。首发至少登记 02 章的 `user.read`、`user.status.write`、`kyc.read`、`kyc.review`、`bank.review`、`referral.read`、`referral.audit.read`，以及后台主体/RBAC 的独立读写权限。

`admin_user_roles(admin_user_id,role_id)` 和 `admin_role_permissions(role_id,permission_code)` 使用联合主键、外键 `RESTRICT`。数据范围独立保存在 `admin_users`；`RELATION_SUBTREE` 与 6.4 的完整链范围组合。GLOBAL 是显式、高风险、可审计授权，不是绕过权限点的“超级管理员”分支。

创建后台主体、授予/回收角色、修改角色权限、重置后台 MFA/密码和改变状态都写 `admin_audit_logs`，保存操作者、稳定权限点、理由、工单和脱敏前后快照。`CreateAdminUser` 只创建 INVITED 主体和一次性邀请；匿名 `AcceptAdminInvitation` 校验 token 后设置首个密码、建立待确认 MFA secret，`ConfirmAdminMfaActivation` 消费同一激活上下文并原子绑定 MFA、令主体 ACTIVE 和递增 session version。ACTIVE 管理员使用 `StartAdminLogin` 校验密码并创建 MFA challenge，`CompleteAdminLogin` 仅在 OTP 成功后签发独立 access/refresh；`RefreshAdminSession/LogoutAdminSession` 使用 family generation 和 refresh rotation。Accept、CompleteLogin 和 Refresh 在提交 issuance/session 后、返回响应前崩溃时，相同 nonce/request hash/device proof 在短 TTL 内解密返回完全相同结果，不建第二个 context/session，也不把原 refresh 误判为盗用；不同 nonce/设备重放已轮换 refresh 才撤销 family。密文销毁后只返回重新激活/登录的稳定错误，不能重发凭据。`ResetAdminMfa/ResetAdminCredential` 必须由另一名有权限管理员发起：撤销全部会话、递增 session version、置回 INVITED 并签发 recovery invite，不存在绕过 MFA 的临时 ACTIVE。数据库种子只创建最小 bootstrap 主体/角色，由部署时一次性本机命令从 secret manager 生成短期激活链接；bootstrap 凭据/token 不写仓库、日志、镜像或迁移 SQL。

### 14.5 主流程与事务边界

本节所有认证、改密、OTP、注销和 KYC/银行卡写事务统一使用 01 章 `UserStateLockKey(type_code,user_id,id)`：预查询只用于收集 ID，不携带裁决；事务内依次锁所有相关 `users → user_credentials → otp_bindings → security_challenges → session_families → user_sessions → session_issuances → kyc_cases → bank_accounts → relation/level/risk/limit/task/VIP` 并重验。`session_families` 使用预留 `type_code=45`，位于 challenge 40 与 session 50 之间，其余既有 code 不平移。找 token/family/session/challenge/case/card 可以先无锁定位 `user_id` 和候选 ID，但不得把定位查询升级为 family/session/case/card-first 行锁；同一类型多行按 ID 升序，集合扩大则回滚扩集重试。只有当前 auth version 的至多 16 个 family、至多 32 个未销毁 issuance 和业务裁决所需的当前 KYC/银行卡事实进入安全热事务，历史只走 keyset 作业。

#### 14.5.1 注册、登录与会话轮换

注册在事务外完成标识规范化、密码策略校验和 hash，随后由顶层 Use Case 开一个 primary 事务，严格按“写/命中 `command_deduplications` → rank 30 `user_population_roots('normal_users') FOR SHARE` → rank 35 `level_rule_runtime_roots('TEAM_LEVEL') FOR SHARE` 并要求 CLEAN → rank 40 `rollup_roots('income') FOR SHARE`”取得 barrier。锁内第一件事检查 cutover：若为 QUIESCING，立即返回可重试 `INCOME_CUTOVER_RETRY` 并整体回滚，尚未分配 `registration_seq`、写 user/资产/关系/等级或任何业务事实；不得绕过 COMMON writer屏障。NORMAL 才分配 sequence并写 `users`、资料/凭据、COMMON/EXPERIENCE 两资产行、可选关系/边/审计及首次 L1。若有非终态 candidate，同事务为新 COMMON 零账户 upsert `ACCOUNT_CREATED,first=latest=0`；BUILDING/CATCHING_UP 禁止写 activation leaf，PROVING 后才写当前代 USER_ACCOUNT leaf并 bump shard mutation，VALIDATED 因变化退回 PROVING。不能提交后补或写未来代 leaf。人口 SHARE 不串行注册；sequence gap合法不可复用。百分位 population UPDATE 捕获 upper 后新注册只得更大 seq。任一步失败整体回滚；注册不发送外部请求。

`StartLogin` 对存在和不存在的标识执行一致的规范化、限流并返回不泄露账号存在性的挑战。`CompleteLogin` 必须携带客户端随机 `completion_nonce` 和设备持有证明；对存在、缺凭据和不存在三条路径都执行恒定代价的密码比较，在事务外完成 CPU 密集 hash/MFA 计算并生成待签发 token pair/密文。短 primary 事务按 user→credential→challenge→当前 version family slots→session→issuance 顺序重查状态/版本：先终结已到期 family、选择 slot 并插入全新 `session_families(generation=1)`，再插入第一条 session；进入 issuance 层后清理已过期密文、选择 live slot 并插入 LOGIN issuance，最后才消费 challenge、写 `login_audits`。family 或 issuance 无空 slot 时整笔回滚，因此 challenge 未消费、临时插入的 family/session 不可见。提交后响应丢失时，同 challenge/nonce/request hash/device proof 的重试按 user→family→session→issuance 校验当前 auth/family generation 并返回原 token pair，不再次消费挑战或创建 session。不同 nonce 不能复用已消费 challenge；TTL 已销毁或版本已失效时返回 `SESSION_ISSUANCE_EXPIRED` 并要求重新登录，不伪造成功。

`RefreshSession` 必须携带新的 `rotation_nonce` 和同一设备密钥的持有证明。服务先用旧 refresh hash 无锁定位 user/family/session：若它仍是 family 当前 generation，则在事务外生成 replacement token pair/密文，在一个 primary 事务严格按 user→family→旧 session→既有 issuance（如有）加锁，校验账号 ACTIVE/CLOSING 白名单、`users.auth_version`、family ACTIVE/generation、到期和设备绑定。新 generation session 可在 family/session 层先作为提交前不可见的新子行插入；进入 issuance 层后才清理过期密文并申请 live slot，成功则插入唯一 REFRESH issuance、推进 family generation、把旧 session 转 ROTATED，任一步失败均回滚新 session 且不轮换旧 token。若旧 session 已 ROTATED，仍按 user→family→session→issuance 查询 `(predecessor_session_id,rotation_nonce)`：nonce、请求 hash、device proof、auth version 和 issuance 所属 generation 全匹配且密文未过期时返回原 replacement，不增加 generation/session；密文已销毁时返回 `SESSION_ISSUANCE_EXPIRED`。不同 nonce、请求上下文或设备证明再次使用旧 token 才视为复用，条件推进同一 family `status=REVOKED,generation=generation+1`，不扫描历史 session。`Logout` 先锁 user 再锁 family，条件撤销 family 根；重复调用返回同一终态。

改密/重置在事务外生成新 hash；primary 事务按 user→credential→challenge 顺序消费挑战、更新目标 credential、把 `users.auth_version` 原子加一并写安全审计。提交即使全部旧 token/family/session/issuance 失效，事务不得预收集或更新该用户会话历史；过期状态归一与密文销毁由有界作业完成。任何代码都只能调用同一密码校验器，不存在 `super.password` 分支。

#### 14.5.2 OTP 绑定和近期认证

1. `StartOtpBinding` 校验当前会话和近期登录，在本地生成 secret、加密后创建 PENDING binding/challenge；同键同载荷重试返回同一待绑定对象和同一受控 secret 响应，不生成第二把密钥，其他接口永不解密返回。
2. `ConfirmOtpBinding` 在事务外计算 TOTP 候选 step，在 primary 事务按 user→binding→challenge→session 锁定，校验次数、有效期、未绑定和 step 大于 `last_accepted_step`，再把 binding 置 ACTIVE、消费 challenge、提升当前 session 认证级别。
3. 后续高风险命令校验 `mfa_verified_at >= now-policy.recent_window`、purpose 和 session；验证成功时原子推进 `last_accepted_step`，相同验证码不能并发成功两次。
4. 管理员 OTP 重置只吊销旧 binding、增加 `auth_version` 完成 O(1) 逻辑全局撤销；不扫描 session 历史。用户必须重新绑定，客服不能读取或替用户设置密钥。
5. `CreateWithdrawal` 与 `CreateClosureWithdrawal` 使用同一提现 OTP 原语：先命中已提交的命令幂等结果；没有结果时在用户层锁定 binding 历史。`NEVER_BOUND` 可继续，ACTIVE 必须校验请求中的 `otp_code` 并条件推进 `last_accepted_step`，`REBIND_REQUIRED` 直接拒绝并引导重新绑定/受控恢复。OTP 验证、提现单、限额预占和冻结属于同一 default 事务；任一步失败都不推进 step。

#### 14.5.3 KYC 供应商

`InitializeKyc` 先在 primary 短事务锁 user，再按 ID 锁当前 `is_current=true` case 与唯一进行中候选 case，重验账号状态后创建/读取唯一 INITIALIZED case 和命令幂等结果并提交；不存在 case-first 路径。worker 或请求编排器随后在事务外调用供应商，再开新事务按 user→当前/目标 cases（ID 升序）条件写入 `provider_case_id/status/next_run_at`。超时保持可回查状态，重试使用稳定 merchant/case key，不新建随机供应商单。

裸 HTTP adapter 先在事务外对原始 body 验签和解析，并只无锁定位 KYC case 与 user。合法事件在一个 primary 事务内先插入/读取 `kyc_provider_events` 防重，随后必须锁 user，再一次查询并按 ID 锁“原 current、目标候选”全部 case，重验集合、账号/purpose、provider、case、事件时间和允许边后才推进；APPROVED 切换在同一组锁内先撤旧 current、再设新 current。重复同事件返回原处理结果；相反终态只记冲突并告警，不覆盖已批准事实。adapter 返回供应商专属 ACK，内部不暴露 callback Proto。

人工 `ReviewKyc` 在命令防重/审批事实后无锁定位 user 与候选 ID，正式事务固定 user→原 current/目标候选 cases（全部按 ID）→追加 `admin_audit_logs`；锁内重查状态、权限、范围、近期 MFA、理由和工单，再执行同一 current 切换原语。禁止 `SELECT ... FOR UPDATE` case 后再找/锁 user；预读集合变化时整体回滚重试。

#### 14.5.4 银行卡核名与人工复核

1. 创建/替换的事务外校验只生成候选；正式裁决固定锁 user→当前 KYC→涉及的 bank rows（ID 升序）→已登记 risk/limit 聚合，锁内要求用户 ACTIVE、KYC APPROVED 和近期二次认证，再完成账号/户名规范化、加密和 hash 重验。
2. 同一 primary 事务写命令幂等、`bank_accounts(PENDING_VERIFICATION)`、稳定 `provider_request_key` 和当时 KYC case/name hash 快照，提交后才调用核名供应商。
3. 外部结果事务先无锁定位 user/KYC/bank，随后仍按 user→KYC→bank→risk/limit 锁定：明确一致时条件转 VERIFIED；明确不一致转 REJECTED；模糊结果转 MANUAL_REVIEW；网络未知保持 PENDING 并设置 `next_run_at` 回查。禁止 worker 先锁 bank 再补 user/KYC。
4. `ReviewBankAccount` 在命令防重/审批事实后固定锁 user→引用的 KYC case→目标 bank→涉及的 risk/limit 聚合，校验 `bank.review`、数据范围、近期后台 MFA、理由和工单，写决定及 `admin_audit_logs` 同事务提交；目标或 KYC 引用变化即回滚扩集，不存在 card→KYC/user 路径。
5. 变更银行/账号/户名创建新行重走核名，不能 UPDATE 已验证敏感事实；禁用只阻止新提现，既有提现继续使用创建时不可变收款快照。

#### 14.5.5 注销等待与完成

`RequestAccountClosure` 要求近期 MFA 和幂等键。事务外完整 blocker/“未来资产能力”查询只用于 fast-fail 和生成候选 ID，不具有裁决效力。正式 primary 事务写防重后先确保并锁 rank 500 `partner_adjustment_user_roots(user_id)`，再锁 `users`，重查仍为 ACTIVE；`requested_at=clock_timestamp()` 只在两者都锁定后取得，并把当时 `last_approval_seq` 同时写成 scan upper，after/scanned 从 0 开始。随后用注册表的索引 EXISTS/有硬扫描上限的饱和聚合在锁内重跑完整能力判断；provider 此处只读，不在 user 之后补锁低 rank 业务根，也不为展示精确总数扫描全部历史。由于所有 blocker 写路径也必须持同一 user 锁，锁取得前已提交的新来源对本事务可见，锁后尚未提交的来源只能等待并在看到 CLOSING 后拒绝或按既有来源白名单终结。只要当前有 COMMON，或任何既有未终结事实未来可能增加/释放 COMMON（包括失败提现释放、购买退款、冻结返佣释放、持仓结算/返本、合伙人/任务领取），就必须已有 KYC APPROVED、可用 VERIFIED 银行卡，且 Authenticator/TOTP 状态能按 `NEVER_BOUND/ACTIVE/REBIND_REQUIRED` 规则完成清退；REBIND_REQUIRED 缺少恢复路径时保持 ACTIVE 并返回具体可操作原因，NEVER_BOUND 本身不构成 blocker。锁内通过后才创建 `account_closures(REQUESTED)`、把用户置 CLOSING 并写 `user_security_audits`；不清空关系、不释放冻结、不取消提现、不删持仓。

请求事务锁内通过后，创建 `account_closures(REQUESTED)`、`users.status ACTIVE -> CLOSING`、`users.closure_generation += 1`、`play_credential_sweep_generation += 1/cursor=0/dirty_at=now()` 和安全审计必须同事务提交。`closure_generation` 是播放授权即时失效的唯一规范注销代次；禁止用 `account_closures.lease_generation`、closure 行 ID 或通用 `users.version` 代替，任何失败回滚都不能只推进其中一项。

CLOSING 只允许查询和白名单收尾命令：已有持仓/订单/提现继续由原状态机终结；允许 `InitializeKyc(purpose=ACCOUNT_CLOSURE)`、`GetClosureWithdrawalQuote`、`CreateClosureWithdrawal`、`CreateClosureCommonDustDisposition`、EXPERIENCE 兑换/放弃、`DisposeClosureRobotActivationVoucher`，以及领取 closure cutoff 前已经由来源事实归属、但可在等待期才从 OPEN/CALCULATING/SEALED/未完成转为 CLAIMABLE 的任务/合伙人权益；还允许仅在 KYC/原 VERIFIED 卡失效时的 closure-purpose 重新核验/补卡。该重新 KYC 只能恢复清退资格，不恢复充值、Playlet Backing、Robot Purchase 或普通提现。`CreateClosureWithdrawal` 只能把服务端按当时余额、单笔/渠道上限及 DAY/WEEK 剩余额度算出的最大合法批次汇往 VERIFIED 清退卡，使用 `withdrawals.purpose=ACCOUNT_CLOSURE`、关联 `closure_id/closure_withdrawal_seq`；同一 closure 最多一笔非终态，前单终结后才可继续下一批。单笔下限和手续费按已发布注销清退规则处理，额度为 0 时等下一窗口，不能把大额余额误当 dust。ACTIVE Authenticator/TOTP 仍必须按提现事务规则校验；曾绑定后被 reset/revoke 的用户必须先重绑或受控恢复，不因 CLOSING 降级。`CreateClosureCommonDustDisposition` 请求固定含 `expected_available_common/consent_version/Idempotency-Key`；正式事务按命令防重→income root/day fence→当前 ACCOUNT_CLOSURE rule root→完整且最多 32 条 channel slot/对应渠道状态根（按 slot/channel ID）→以服务端 disposition_no 规范化的 Finance recovery root→closure→user→COMMON asset 加锁，锁内重算并复验 slot count/连续性/`closure_channel_set_hash`、近期 MFA、同意版本、余额与“完整有界集合内所有清退渠道均无法形成任何合法正批次”判据，再把 disposition、等额 EXPENSE ledger、PAYABLE case、closure 唤醒和审计同事务提交；集合不完整/hash 漂移、任一渠道可形成正批次、余额为零/改变、CLOSED 或 consent 漂移都失败且不扣款。该资金事务锁行上限不随历史渠道数增长。`ForfeitClosureExperience` 由用户明确确认后把指定或全部可用 EXPERIENCE 记为 disposition 与 `EXPENSE` 流水；正式锁序是命令防重→income/day→closure→user→EXPERIENCE asset。EXPERIENCE→COMMON 兑换也必须用 05 章的 closure→user→limit→asset 顺序并标记 ACCOUNT_CLOSURE。ASSIGNED Robot Activation Voucher 由专用 sweep 按 code/mapping→closure→user 原子 VOID并写 `robot_voucher_dispositions`，不处置任何资产。系统绝不隐式兑换或放弃资产。收尾动作可能随既有事实继续产生的新收入重复执行，直至全部事实归零。

closure worker 只在 primary 用短事务执行精确认领：候选查询必须带 `status IN ('REQUESTED','WAITING_BLOCKERS','READY') AND next_check_at <= now() AND (lease_until IS NULL OR lease_until <= now()) FOR UPDATE SKIP LOCKED`；随后的条件 UPDATE 重复同一状态、时间和租约谓词，写唯一 `lease_owner`、`lease_until` 并令 `lease_generation=lease_generation+1`，影响 0 行即放弃，随后立即提交。worker 用返回的 owner/generation 令牌调用完整 blocker registry；首发固定 `K=20`，每个 provider 只能执行命中 partial/index-only 索引的 `EXISTS`、读取已维护的有界聚合根，或用 `LIMIT K+1` 得到“0/1…K/>K”的饱和计数，并返回固定 code/饱和 count 与至多 K 个示例 ID。禁止对无硬界历史执行精确 `COUNT(*)`。发现任一 blocker 就用只触碰 closure 的短事务写回 WAITING_BLOCKERS/快照并释放租约，不得为了说明原因锁定或加载该用户全部订单、attempt、持仓、freeze、结算或权益历史。

只有 registry 零 blocker 才进入 READY 完成事务。正式事务不锁任何终态业务或安全历史，按 01 章 rank 锁“预检时仍非终态且确实参与完成裁决的低 rank 根（正常应为空）→ `partner_adjustment_user_roots` → account_closure → user → 固定种类 credentials（至多三个）→ 当前 auth version 的 ACTIVE family（至多 16）→ 各 family 当前 generation session（至多 16）→ 当前 version 未销毁 issuance（至多 32）→ 完成裁决确需的 current/candidate KYC（至多两条）→ 两种 user_assets”，各类型内按 ID。它不锁 ROTATED/REVOKED/EXPIRED family/session、已销毁 issuance、旧 KYC/卡或终态订单/attempt/持仓历史。完成上述有界锁集后重新运行相同的索引化 registry，并重验 `lease_owner/lease_generation`、`lease_until > clock_timestamp()`、状态、两种余额，以及 `partner_adjustment_user_roots.last_approval_seq = partner_adjustment_scanned_seq = partner_adjustment_scan_upper_seq`；所有 blocker 写入口也必须先经过同一 user gate，因此未提交 writer 只能在 closure 之后取得 user 并看到 CLOSED 后回滚，已提交事实则必被锁内复检看到。若复检出现预收集外的低 rank 根或 freeze 事实，不在 closure/user 后补锁，整体回滚并写回 WAITING_BLOCKERS；绝不扩成“锁该用户全部历史”。

仍无阻塞时同一事务原子写 `account_closures=COMPLETED`、`users=CLOSED/closed_at/auth_version+1`、禁用固定种类凭据、清空完成租约、把 `security_cleanup_status` 置 PENDING/三组游标置初值并追加安全审计。`auth_version+1` 在提交点已 O(1) 使全部旧 token/family/session/issuance 失效；CLOSED 正确性不依赖物理 UPDATE 这些行。`account_closure_security_cleanup` 随后用三个独立 `(created_at,id)` 游标运行；每个短事务固定 closure/cursor→一种历史表，历史行最多 200 条：先 crypto-shred issuance，再归一/归档 session，最后在没有子行引用后归一/归档 family；物理删除也保持子表先于父表，不在同一事务反向混锁。崩溃从已提交游标续跑，DONE 只表示清理结束，不改变已完成注销。旧 closure owner/代次的迟到结果均被条件更新拒绝；外部供应商通知和隐私清理同样在提交后按自身状态重试，不进入完成事务。

### 14.6 幂等键、失败模式与恢复

所有命令仍使用公共 `(actor_type,actor_scope,rpc_name,idempotency_key)`，在业务事务内写 `command_deduplications`；已认证 scope 来自主体 ID，匿名注册 scope 来自规范化登录身份的服务端 HMAC，任何 scope 都非空：

| 命令/事件 | 稳定键与数据库防线 |
| --- | --- |
| 注册 | 客户端幂等键；规范化登录标识唯一 |
| OTP 绑定、改密、支付密码、绑卡、注销 | 当前主体 + RPC + 幂等键；challenge purpose/context hash |
| 提现 Authenticator/TOTP | 已提交命令结果优先；ACTIVE binding 以 `last_accepted_step` 条件推进，NEVER_BOUND 可跳过，历史 reset/revoke 必须先恢复 |
| 注销 COMMON 清退/EXPERIENCE 放弃 | closure + RPC + 幂等键；提现 purpose/closure 唯一语义，disposition dedupe/ledger 唯一 |
| refresh | `user_sessions.refresh_token_hash`、`(family_id,family_generation)` 唯一；family 根 generation 条件推进防重放 |
| KYC 建单 | 用户 + attempt/命令键；`(provider,provider_case_id)` 唯一 |
| KYC 回调 | `(provider,provider_event_id)` 唯一；固定裸 HTTP adapter 验签后进入内部命令 |
| 银行卡 | 命令键 + 同用户账号指纹 partial unique |
| 后台审核/授权 | admin + RPC + 幂等键；目标状态/角色集合进入 request hash |

| 失败模式 | 处理 |
| --- | --- |
| 用户不存在、密码错误、入口类型错误 | 相同 `INVALID_CREDENTIALS` 和近似耗时；只在脱敏审计区分原因 |
| 密码 hash 损坏/算法未知 | 失败关闭、告警、走受控重置；不降级明文比较 |
| refresh 并发或旧 token 重放 | 同一 predecessor + nonce/request hash/device proof/auth version/family generation 的并发是同一逻辑轮换，均返回同一 issuance；不同 nonce、上下文或设备的旧 token 复用只条件撤销 family 根，不扫描 session |
| 活动 family 或 live issuance 达硬上限 | 分别返回稳定限额错误；不得消费 challenge、推进 family generation 或轮换 session，清理到期 issuance 后可重试 |
| OTP 错误/并发重放 | 原子增加次数或推进 step；超限锁 challenge，不泄露 secret |
| Redis/Forge message/短信或邮件供应商不可用 | challenge 内加密投递材料、应用级 `delivery_dedupe_key` 和状态保留；primary sweep 只重试已证明未接受的失败，不确定调用转 `UNKNOWN` 且不自动重发；UNKNOWN 时 API 不宣称发送成功，但用户若实际收到仍可按 challenge digest/status 在到期前验证；过期后 crypto-shred 并要求新建挑战 |
| 登录/refresh 提交后响应丢失 | 相同 nonce、请求 hash 和设备证明在短 TTL 内从 `session_issuances` 返回原 token pair；不建第二个 session、不误判 refresh 复用 |
| 已轮换 refresh 用不同 nonce/设备重放 | 撤销整个 family 并告警；与原请求相同但 issuance 已销毁时只要求重新登录，不误伤 family |
| KYC/核名超时 | 保持进行中/UNKNOWN 语义，按稳定 provider key 回查，不随机重发 |
| 提现 ACTIVE OTP 缺失、错误或同 step 重放 | 在建单/冻结前拒绝；事务失败不推进 `last_accepted_step`，已成功同幂等请求优先返回原结果 |
| 回调重复、乱序或未知状态 | 唯一事件返回原结果；仅允许状态边推进，未知保持 pending 并告警 |
| 银行户名模糊 | 进入 MANUAL_REVIEW；未复核前不能用于提现 |
| 注销仍有持仓/冻结/在途提现 | 保持 CLOSING/WAITING_BLOCKERS，返回分类 blocker；禁止强制删事实 |
| CLOSING 等待期间 KYC 失效/撤销 | 只开放 purpose=ACCOUNT_CLOSURE 的重新 KYC 和补卡；恢复清退能力但不恢复普通业务 |
| 注销有 COMMON/EXPERIENCE 余额 | 只允许清退提现、显式兑换或用户确认的 EXPERIENCE 放弃；任一步与流水/处置事实同事务 |
| CLOSING 后清退卡失效 | 只开放 `purpose=ACCOUNT_CLOSURE` 的补卡/核名；新卡仅用于 closure 清退，不恢复充值、购买或普通提现 |
| 管理员权限或数据范围中途撤销 | 每次写在 primary 重查；未提交则整体拒绝，已提交审计不回滚 |

核心认证、KYC、银行卡、注销和 RBAC 不写通用 outbox。可恢复工作依赖对象自身 `status + next_run_at + attempt_count` 与 primary sweep；challenge 的短期密文只是其自身不可缺的投递状态，不是任意事件 payload，过期即销毁。提交后 Forge SMS/Email 发送可失败，不改变本地安全事实；WhatsApp 不在配置和恢复矩阵内。

### 14.7 缓存、作业、权限与可观测性

缓存规则：

- 密码/OTP/refresh、账号状态、会话撤销、近期认证、KYC/银行卡资格、注销阻塞和后台权限最终判断不从缓存或 slave 完成。
- 可缓存 `GetMe` 的非敏感 profile 与掩码银行列表，键包含 `user/version`，短 TTL；提交后尽力失效。
- 后台权限与数据范围的最终授权每个 RPC 都在 primary 通过 `admin_users -> admin_user_roles -> admin_role_permissions/admin_permissions` 重查；首发不缓存“允许”结果，也不依赖 Redis 失效或未定义的关联版本。只可缓存权限 code 的无主体静态说明用于展示，不能参与 allow/deny，因此撤权事务提交后的下一命令立即生效。

| 作业 | 行为 |
| --- | --- |
| `security_challenge_expire` | primary 批量终结过期/超限挑战 |
| `session_expire_cleanup` | 按 `(created_at,id)` keyset、每事务最多 200 行，把过期或 auth version 已失效的 family/session 状态归一；不参与 token 的实时撤销判断 |
| `session_issuance_crypto_shred` | 按 keyset 每事务最多 200 行，到期或 auth version 已失效即清空 token 密文并标 destroyed；随后按安全保留期物理删除元数据 |
| `kyc_provider_reconcile` | 回查超时/未知 KYC case，使用稳定 provider key |
| `bank_verification_reconcile` | 回查 PENDING 核名并升级人工队列 |
| `account_closure_sweep` | primary `SKIP LOCKED` 重算阻塞并完成可关闭账号 |
| `account_closure_security_cleanup` | CLOSED 后按 closure 三组游标分表小批量清理 family/session/issuance 历史；失败只重试清理，不回退 CLOSED |
| `rbac_invariant_check` | 检查未知权限、孤儿 grant、无 MFA ACTIVE 管理员和非法 scope |

权限与隐私：

1. 普通用户所有自助主体来自 token；银行/KYC 详情必须先按 user ID 限定，不能先按对象 ID 查询后再“补鉴权”。
2. 后台授权同时满足 issuer/audience、ACTIVE admin、近期 MFA、稳定 permission、角色 grant、数据范围和目标状态；任何未知权限/范围失败关闭。
3. KYC 列表、KYC 明文详情、KYC 审核、银行卡审核、账号状态修改、后台主体管理和角色授权分别使用权限点；“能看”不推出“能改”。
4. 完整银行卡只允许出款适配器对已创建提现快照解密；普通后台详情仍返回掩码。KYC 文档使用短时签名 URL，生成和下载均审计。
5. 所有密码、OTP、token、完整卡号、证件和供应商原始敏感 body 加入结构化日志 denylist 与测试；管理员也不能通过通用审计 API取回。

关键指标与告警：

- `auth_attempt_total{entrypoint,result,reason}`、登录/密码 hash P50/P95/P99、枚举防护耗时差；
- `session_refresh_total{result}`、refresh reuse、会话族撤销数、family/issuance 硬上限拒绝数、stale history/cleanup lag、primary 版本校验失败数；
- `otp_challenge_total{purpose,result}`、重放/超限/重置次数；
- `kyc_case_total{provider,status}`、provider 延迟、pending age、重复/乱序/签名失败事件；
- `bank_verification_total{provider,result}`、manual queue age、KYC 姓名不一致数；
- `account_closure_total{status,blocker}`、最长等待、READY 回退、完成失败数；
- 注销 COMMON 清退金额/失败原因、EXPERIENCE 显式放弃金额，以及清退提现 OTP 缺失/错误/重放/须重绑次数；
- `admin_authz_denied_total{permission,reason}`、GLOBAL scope 授权变更、高风险命令缺 MFA 次数；
- 敏感字段日志扫描命中、解密调用量、KMS 错误和未登记权限点均立即告警。

### 14.8 安全验收用例

1. 相同账号存在/不存在、普通/后台入口错误和密码错误的响应码、文案类别与耗时分布无法稳定枚举；登录路径不存在超级密码或固定 OTP。
2. 注册在用户、profile、credential、双资产、关系边、等级或审计任一步故障时完全回滚；同键重试只产生一个 user ID。
3. 密码/支付密码只出现为 hash；OTP/卡号/证件为密文，长期 refresh/reset/code 只存摘要；仅 `session_issuances` 可有短 TTL token 密文，权限、设备/nonce 绑定和到期 crypto-shred 全部验证。日志敏感字段扫描为零。
4. 两个完全相同 nonce/request hash/device proof 的 refresh 并发只把 family generation 推进一次、创建一条 replacement session/issuance，两个调用都返回相同 token pair；旧 refresh 换 nonce、上下文或设备再用只撤销一个 family 根。创建第 17 个当前-version ACTIVE family、或第 33 条未销毁 issuance 必须在任何 challenge/session 状态变化前稳定拒绝；并发 100 次也不能突破数据库 slot 约束。
5. 预置百万条 ROTATED/REVOKED session 历史后执行改密、禁用与 closure 完成，主事务锁行数和耗时不随历史量增长，均只凭 `users.auth_version+1` 让旧 access/refresh 立即不可用。refresh、logout、OTP、KYC/银行卡与 closure 正反并发 10 分钟，锁轨迹按 `users→...→family→session→issuance→KYC→bank→risk/limit` 单调；故意注入 session→user、case→user 或 bank→KYC/user 实现必须被断言捕获。
6. blocker 注册表对失败提现释放、各类退款回补、冻结返佣释放、持仓日结/返本、合伙人/任务领取逐项有 provider；新增可入账状态但未注册或其写路径未锁 user/未登记 CLOSING 策略时 CI 失败。暂停注销请求的事务外预检后并发提交一项新来源：若新来源先持 user 并提交，注销锁内复检必须看到它并在缺 KYC/VERIFIED 卡时保持 ACTIVE；若注销先持 user 转 CLOSING，新可选来源必须失败且无半状态。两种次序都不能让旧预检结果决定状态。
7. CLOSING 可在满足 KYC、清退卡和提现 OTP 规则后反复清退后续 COMMON；清退卡失效时只能走 closure-purpose 补卡。普通绑卡、普通提现、充值、Playlet Backing、Robot Purchase 和新任务来源仍拒绝，最终不存在不可操作的资金 blocker。
8. OTP 同一步并发提交只有一次成功；绑定未确认、过期、错误超限、管理员吊销后均不能提升认证级别。提现分别覆盖 NEVER_BOUND 可跳过、ACTIVE 请求缺少/错误 `otp_code` 拒绝、同 step 并发仅一笔成功、曾绑定后 reset/revoke 必须重绑或受控恢复；普通和 closure withdrawal 规则完全相同，失败事务不推进 step，同幂等成功重放不再验新码。
9. 团队禁用用户仍能登录并使用非团队功能；账号 DISABLED 不能登录；CLOSING 只能执行已登记的收尾/查询动作。
10. KYC 供应商超时、重复、乱序、未知状态、错 case、错用户和验签失败都不误推进；回调与 `ReviewKyc` 的实际锁轨迹均为 event/command→user→原 current/目标 cases（ID 升序），与 closure 并发无 case→user 死锁；人工审核缺权限/MFA/理由时失败。
11. 银行卡姓名规范化覆盖大小写、Unicode、空白、标点和 locale 测试；精确匹配 + 供应商成功才自动 VERIFIED，模糊结果进入人工复核。核名回写、`ReviewBankAccount` 及提现用户层轨迹固定为 user→OTP binding→KYC→bank→risk/limit，故意注入 card-first 或 binding-first 实现必须失败。
12. 银行账号/户名变更创建新记录而非覆盖；禁用后不能用于新提现，既有提现的收款快照不变；用户和普通后台 API 永不返回完整卡号。
13. 注销存在有效持仓、非零资产、ACTIVE 冻结或在途提现时保持 WAITING_BLOCKERS；CLOSING 仍可把全部 COMMON 经 closure withdrawal 清退，并可在近期 MFA/明确同意后用 disposition + EXPENSE 原子放弃 EXPERIENCE。等待期间让 KYC/银行卡失效，只能用 ACCOUNT_CLOSURE 重新核验/补卡恢复清退，普通业务仍关闭。模拟既有持仓后续再次入账，重复清退后最终可达零余额；阻塞全部终结后 CLOSED、凭据禁用和 `auth_version+1` 同事务完成。即使历史安全清理暂停/崩溃，账号仍保持 CLOSED 且旧 token 不可用；恢复后每批不超过 200 行并从游标收敛，关系和审计仍可追溯。
14. 角色无权限、权限无范围、范围不含目标、token audience 错误、MFA 过期和权限中途回收均拒绝；GLOBAL scope 也不能绕过 permission。
15. 模拟 Redis、slave、Forge message、短信/邮件、KYC/核名供应商故障，核心事实无越权成功；primary sweep 令 pending 工作最终收敛：明确未接受可重试，不确定消息调用转 UNKNOWN 且不重复发送。Forge 返回成功只推进 `PROVIDER_ACCEPTED`，断言无代码把它解释成 DELIVERED；手机号/邮箱日志扫描为零，WhatsApp 配置与枚举为零。

## 16. 实施顺序与完成定义

1. 先定义 user/admin 主体、账号/会话/KYC/银行卡/注销状态、正向能力枚举、稳定权限点和统一错误码。
2. 创建 `users/user_profiles/user_credentials/session_families/user_sessions/session_issuances/login_audits`，实现标识规范化、密码 hash、枚举防护、16/32 slot 硬上限、可恢复的一次逻辑 token 签发、family generation 轮换与 `auth_version` O(1) 全局撤销。
3. 创建 `otp_bindings/security_challenges`，实现绑定、近期认证、重放防护、改密/重置与限流审计。
4. 创建 KYC/供应商事件和裸 HTTP provider adapter，先完成原始 body 验签、渠道 ACK、超时、重复、乱序与未知状态测试；不创建 callback Proto 或提现人脸表。
5. 创建 `bank_accounts`，落地姓名规范化测试向量、核名意图/回查、人工复核和只返回掩码的 API。
6. 创建 `account_closures` 和 blocker registry；接入持仓、资产冻结、充值/提现与结算终态，完成 primary sweep。
7. 创建后台主体、角色、权限和关联表；注册权限注解、完整链数据范围、近期 MFA、双人复核及审计。
8. 创建 `users` 关系字段、约束、整列 GIN、`referral_edges` 和不可变关系审计表。
9. 实现唯一 `BindParent` 领域命令及按 user ID 排序的锁助手；注册和后绑定接入同一命令，并接入等级聚合初始化/增量。
10. 实现用户五层仓储和后台全链范围仓储，禁止 handler 拼接关系或授权 SQL。
11. 上线安全/关系一致性作业、边表 diff、供应商回查、注销 sweep、指标、敏感日志扫描和告警。
12. 通过本章全部状态、并发、故障注入、IDOR/MFA、供应商、权限和执行计划验收后，身份安全与关系域才可开放真实用户和资金入口。

完成定义：仓库中不存在超级密码、固定验证码、明文安全 secret、F 码领域类型或兼容分支；所有认证因子、会话、KYC、银行卡、注销和后台授权都有唯一真源、状态机、幂等与审计；外部调用不持有数据库事务；所有关系写入只有一个入口；任意已提交用户要么完全无上级，要么用户行、前五层边和唯一审计同时存在；后台全链与用户五层的查询代码、索引和权限测试彼此独立。
