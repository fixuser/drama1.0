# 07 短剧内容与参与（Playlet Backing）

## 1. 目标与范围

本域提供短剧发现、剧集授权与购买、收藏/历史、短剧参与（Playlet Backing）及收益、弹幕审核和 Banner 投放。内容消费与 Backing 共用短剧主数据，但权益、资产和结算是不同业务对象。

本域不包含 AI 聊天、版权包/二创、活动电影票、支持值、普通短剧支持券、双倍券或活动加成。

## 2. 核心对象与不变量

| 对象 | 作用 | 不变量 |
| --- | --- | --- |
| 短剧/剧集/受众规则 | 可发布内容、价格及语言/区域/平台/应用版本定向 | 剧集必须属于短剧；请求环境必须命中同一版受众规则；下架后不能新购或签发播放凭证 |
| 剧集权益 | 证明指定用户可播指定剧集 | 同一时刻 `(user_id, episode_id)` 最多一条 ACTIVE；退款只转 REVOKED，来源历史可追溯 |
| VIP 权益 | 在有效期内解锁允许的付费剧集 | 只来自已支付一次性 VIP 订单 |
| 广告解锁权益 | 一次已验证广告完成永久解锁一集 | 用户/剧集唯一；广告事件唯一 |
| 广告验证 attempt | 先于供应商网络调用落库的可恢复意图 | 网络不在事务内；只有结果事务确认账号 ACTIVE 才发永久权益 |
| 剧集购买单 | 记录定价、双资产实付、权益和退款 | COMMON 部分才是购买返佣基数；订单、扣款、权益和冻结返佣同事务 |
| 授权/凭证/观看历史/播放事件 | 分别表达判断、可撤销短凭证、续播状态和真实播放事实 | 凭证绑定用户、短剧、剧集四个访问代次；签发、客户端报进度和 heat 均不等于真实播放 |
| Playlet Backing Offer | 一期助力额度、份额、周期、收益规则 | 发布后规则不可原地修改 |
| Playlet Backing | 用户用 COMMON 形成的收益合约 | 同用户/offer 周期唯一；任务状态不影响收益 |
| Backing 日结算 | 直接收益和五层返佣的来源 | 同 Backing/业务日只结算一次；合伙人池只在创建 Backing 成功时创建一次 |
| 弹幕/举报/私有屏蔽/作者限制 | 剧集时间点内容和用户、管理治理闭环 | 敏感命中仅本人可见并待审；用户屏蔽不改变全局状态，管理限制不删除历史事实 |
| Banner/revision | 服务端版本化投放和安全跳转 | 时间区间、点击生效时间、定向、priority 和数量上限由服务端执行；已发布版本不可原地修改 |

## 3. 状态机

### 3.1 内容

```text
DRAFT --发布检查--> PUBLISHED --手动下架/到期--> OFFLINE
  ^                       |                         |
  +------修改草稿---------+                         +--归档--> ARCHIVED
```

- 只有 `PUBLISHED` 且命中语言、区域、平台、规范化 `app_build` 区间和发布时间的内容可发现、购买和新鉴权。`platform + app_build` 是同一请求内固定的客户端环境；缺失、非法或平台不匹配按公开接口契约返回稳定不可见原因，不降级为“所有版本可见”。
- 已发布内容修改产生新 revision；视频引用、价格和可见规则必须经过重新发布。
- 下架不删除已有权益、收藏、历史或结算事实。

### 3.2 播放权益

服务端统一调用 `AuthorizeEpisode(user, episode, client_context, as_of)`，其中 `client_context` 至少包含规范化 `language/region/platform/app_build`，并按以下顺序给出稳定原因：

1. 内容/剧集是否存在、关联正确、已发布且对请求环境可见；
2. 是否免费集或价格为零；
3. 是否有指定剧集购买权益；
4. 是否有有效一次性 VIP 权益；
5. 是否有广告永久解锁权益；
6. 是否存在当前有效、范围明确的受控审核授权 `REVIEW_POLICY`。

列表页的 `unlocked` 和最终播放鉴权必须使用同一函数。审核访问不是隐藏的“审核账号永久放行”：它必须命中不可变的审核策略版本和一条当前 `ACTIVE`、未过期、用户/内容范围/客户端环境均匹配的 `content_review_grants`；撤销或到期后下一次重放、start、heartbeat、origin 取片立即拒绝。审核策略不能给普通用户生成购买、广告或其他永久权益。

### 3.3 广告验证与播放凭证

```text
广告 attempt：PENDING --租约认领--> VERIFYING --验证成功且账号 ACTIVE--> ENTITLED
                    ^          |--可重试失败--> RETRYABLE --到期--> EXPIRED
                    |          |--无效证据------> REJECTED
                    +----------+--账号非 ACTIVE---> IGNORED_ACCOUNT_STATE

播放 issuance：PENDING_PROVIDER --结果事务复验通过--> ACTIVE --超时--> EXPIRED
                                      |                         +--撤销--> REVOKE_PENDING --> REVOKED
                                      |--供应商失败----> PROVIDER_FAILED
                                      +--代次已变化-----> REVOKE_PENDING
```

`IGNORED_ACCOUNT_STATE/REJECTED/EXPIRED/PROVIDER_FAILED/REVOKED` 都是稳定终态；`RETRYABLE/REVOKE_PENDING` 依赖业务表的 `next_run_at`、租约代次和 primary sweep，不依赖 Outbox。账号进入 CLOSING 后不新建永久解锁或 ACTIVE 播放凭证；已返回的凭证因用户或内容访问代次不匹配而在网关/origin 立即失效，数据库状态的有界清扫和供应商撤销只负责卫生回收，绝不是即时失效前提。

### 3.4 Playlet Backing

```text
ACTIVE --到期日结算完成--> MATURED
ACTIVE --经审批提前终止--> TERMINATED
```

创建成功即为 `ACTIVE`。offer 下架只阻止新 Backing，既有 Backing 按创建时快照履约。提前终止仅允许 ACTIVE 且 offer 发布快照显式启用，必须使用下面固定补偿矩阵；管理命令不能提交任意金额或直接改 `ends_at`。

### 3.5 弹幕与 Banner

```text
弹幕：PUBLIC
      SELF_VISIBLE_REVIEW --审核通过--> PUBLIC
      PUBLIC/SELF_VISIBLE_REVIEW --审核拒绝或隐藏--> HIDDEN
      HIDDEN --复核恢复--> PUBLIC

作者发言资格：ACTIVE --管理员限制--> RESTRICTED --复核恢复/到期--> ACTIVE

Banner：DRAFT --发布--> PUBLISHED --撤回/到期--> OFFLINE
```

作者限制的 `hide_existing=true` 通过查询时 join 隐藏该作者既有弹幕，不批量 UPDATE 正文；恢复限制后，未被单条管理隐藏的弹幕可重新展示，而用户自己的 block 永不被管理恢复删除。Banner 的“未开始/投放中/已结束”和是否可点击分别由当前 PUBLISHED revision 的 `[effective_from,effective_to)` 与 `clickable_from` 派生，不依赖客户端时钟。

## 4. 数据表、约束与索引

### 4.1 内容与权益

核心表见 [03-数据模型总览.md](03-数据模型总览.md)：`playlets`、`playlet_revisions`、`playlet_localizations`、`content_audience_rules`、`content_review_policy_versions`、`content_review_grants`、`playlet_groups`、`playlet_group_items`、`episodes`、`episode_revisions`、`episode_localizations`、`episode_purchase_orders`、`episode_refund_requests`、`episode_entitlements`、`vip_entitlements`、`ad_verification_attempts`、`ad_provider_events`、`ad_unlock_entitlements`、`favorites`、`play_authorization_requests`、`play_authorization_audits`、`play_credential_issuances`、`watch_histories`、`play_events`、`video_provider_events`。

关键约束：

- `playlet_revisions(playlet_id,revision_no)`、`episode_revisions(episode_id,revision_no)` 分别唯一。`playlet_localizations(playlet_revision_id,language)`、`episode_localizations(episode_revision_id,language)` 随各自 revision 发布并进入 content hash；PUBLISHED 后一并禁止 UPDATE，修正创建下一 revision 及新本地化行。revision 保存发布时可见策略/素材 hash，以及每集视频引用和显式价格；聚合根的 `current_revision_id` 只在发布事务中切换并写审计，旧订单、凭证和播放始终能通过外键回放当时标题/字幕/视频/价格。
- `content_audience_rules` 归属一个 playlet/episode revision，保存 `language_key/region_key/platform/min_app_build/max_app_build nullable`；前三个 matcher 键全部 NOT NULL，未限定语言/区域使用数据库保留哨兵 `ANY`，客户端输入永远不能规范化成该哨兵。build 区间左闭右开且 `min < max`，同 revision/三个规范键的区间用 exclusion constraint 禁止重叠；发布校验和延迟约束触发器拒绝同 revision/platform 在任一维混用 `ANY` 与具体值，因此不需要隐式优先级。发布事务把规范化受众集合纳入 content hash；搜索、列表、购买预检、最终授权和凭证 finalize 共用同一 `ContentAudienceMatcher`，不得各写一套版本比较。Banner audience 使用完全相同的规范化、禁混和区间协议。
- `episodes(playlet_id, episode_no)` 与 `episodes(id,playlet_id)` 分别唯一；`episode_revisions.price_amount >= 0`。任何同时保存 `episode_id/playlet_id` 的授权审计、issuance、session 或 provider event 都用同列序 `(episode_id,playlet_id)` composite FK 引用 `episodes(id,playlet_id)`；对象与 revision 也使用 03 章规定的 composite FK，不能拼接不同短剧的剧集或版本。
- `content_review_policy_versions` 是发布后不可变的审核访问规则，保存稳定 policy code/version、允许的用户类型、内容范围、客户端 matcher、有效期、状态和 `content_hash`；`content_review_grants` 保存 `user_id/policy_version_id/status=ACTIVE|REVOKED|EXPIRED/valid_from/valid_until/scope_hash/granted_by_admin_id/revoked_by_admin_id`。同一用户/策略版本/范围唯一，`valid_until>valid_from`；grant 建立、撤销和到期收敛都写管理审计并推进该用户凭证清扫根。它只是一项每次都要复验的临时授权，不创建 `episode_entitlements`。
- 三类清扫根使用同构字段：账号根为 `users.play_credential_sweep_generation/cursor/dirty_at/next_run_at/claim_owner/claim_until/claim_generation/claim_due_at`，内容根为 `playlets|episodes.credential_sweep_generation/cursor/dirty_at/next_run_at/claim_owner/claim_until/claim_generation/claim_due_at`。generation/cursor/claim_generation 非负；owner/until 同空同非空；`claim_due_at` 是 `COALESCE(claim_until,'-infinity')` 的生成列；dirty 为空时 cursor、next-run、claim token 全部归零/置空，dirty 非空时 next-run 必填。对应账号/内容访问语义或 review grant 变化时，同一根行把 sweep generation 加一、cursor 归零、dirty/next-run 置 DB now、清 owner/until并递增 claim generation，使旧 worker 失效；这些字段只驱动卫生清扫，不能替代 `auth_version/closure_generation/access_generation` 和当前权益/审核策略的即时鉴权。
- `episode_purchase_orders` 保存 `order_no/user_id/episode_id/episode_revision_id/quoted_amount/paid_experience/paid_common/status=SUCCEEDED|REFUNDED/refund_finality=NOT_ELIGIBLE|ELIGIBLE|REQUESTED|REFUNDED|REJECTED|EXPIRED/refund_rule_version_id/refund_window_seconds_snapshot/refund_eligible_until/deduplication_id`、两种扣款流水、权益引用、退款事实与时间；`episode_revision_id` 必须属于同一 episode 且为下单时 PUBLISHED revision。购买事务使用数据库 `purchased_at` 和已发布类型化退款规则计算不可变截止时间：窗口为 0 时直接 NOT_ELIGIBLE，正窗口时 `refund_eligible_until=purchased_at+window` 且初始 ELIGIBLE。`order_no`、公共幂等引用唯一，成功购买按 `(user_id, episode_id)` 唯一。
- `episode_refund_requests` 保存 `request_no/order_id/user_id/refund_rule_version_id/refund_eligible_until/status=REQUESTED|SUCCEEDED|REJECTED|EXPIRED/requested_at/source_persisted_at/reason/evidence_hash/request_deduplication_id/decision_id/decided_at/refund_tx_id nullable`。每个 order 至多一行；request_no、dedup、非空 decision/refund tx 分别唯一。`source_persisted_at` 由数据库复制 `requested_at`，请求只允许 order=SUCCEEDED、finality=ELIGIBLE 且数据库 now `< refund_eligible_until`，同事务复制订单不可变规则/截止时间并把 order finality 转 REQUESTED。审批不是可提交的中间状态：APPROVE 决定必须在同一原子退款事务直接执行 `REQUESTED -> SUCCEEDED`；REJECTED/EXPIRED 是无资金效果终态并同步 order finality。`(order_id,user_id,refund_rule_version_id,refund_eligible_until)` composite FK 防止串单或伪造窗口。
- `episode_purchase_orders` 建 closure 热索引 `(user_id,refund_eligible_until,id) WHERE status='SUCCEEDED' AND refund_finality='ELIGIBLE'`，`episode_refund_requests(user_id,id) WHERE status='REQUESTED'` 覆盖待裁决责任。到窗 worker 只按该索引有界领取并条件执行 ELIGIBLE→EXPIRED；到窗与请求并发只能一方命中。NOT_ELIGIBLE/REJECTED/EXPIRED/REFUNDED 不再具有未来退款责任。
- `episode_entitlements` 保存 `status=ACTIVE/REVOKED`、`source_type/source_id`、COMMON/EXPERIENCE 实付快照和规则版本；partial unique `(user_id, episode_id) WHERE status='ACTIVE'`，订单来源唯一。退款保留 REVOKED 行，之后按当前规则重新购买可创建新 ACTIVE 行。
- `ad_verification_attempts` 保存 `attempt_no NOT NULL UNIQUE/deduplication_id/provider/verification_key/user_id/episode_id/request_digest/provider_material_ciphertext/key_version/status/next_run_at/attempt_count/lease_owner/lease_until/lease_generation/provider_event_id/entitlement_id/last_error_code/expires_at/created_at/updated_at`。非空命令幂等引用唯一，`(provider,verification_key)` 唯一；加密材料仅供服务端核验重试，终态或到期立即 crypto-shred。租约 owner/until 必须成对，generation 只增；状态与租约的每次 UPDATE 都匹配旧状态、owner 和 generation。
- `ad_provider_events(provider, provider_event_id)` 唯一，保存验签/服务端查询结果、attempt、用户、剧集、事件时间和原始负载摘要；只有 VERIFIED 事件可关联 `ad_unlock_entitlements`，验证成功但账号非 ACTIVE 也保留事件并把 attempt 终结为 `IGNORED_ACCOUNT_STATE`，绝不创建权益。
- `ad_unlock_entitlements(user_id, episode_id)` 唯一，并引用唯一 VERIFIED provider event。
- `play_authorization_requests` 是 DENIED 与 AUTHORIZED 共用的命令防重根，保存 `user_id/request_id/request_hash/correlation_id/status=DENIED|PENDING_PROVIDER|ACTIVE|FAILED|REVOKE_PENDING|REVOKED/decision_audit_id/issuance_id nullable/created_at/updated_at`；`(user_id,request_id)`、`correlation_id`、非空 issuance 分别唯一，并额外建立完全同序 `UNIQUE(user_id,request_id,correlation_id)` 作为子表 composite FK 目标。同键同 hash 返回这条根所指原决定/结果，同键异义冲突；客户端不能仅凭 correlation 读取。
- `play_authorization_audits` 每行不可变，保存 `correlation_id/event_kind=DECISION|ISSUANCE_RESULT|REVOCATION_RESULT/user_id/playlet_id/episode_id/episode_revision_id/decision_audit_id nullable/result/reason_code/request_id/request_hash/request_digest/client_language_key/client_region_key/client_platform/client_app_build/matched_audience_rule_id/audience_revision_hash/client_context_hash/access_basis_type/access_basis_id/review_policy_version_id nullable/review_grant_id nullable/auth_version/closure_generation/playlet_access_generation/episode_access_generation/credential_digest/provider_reference/created_at`。规范 client/matcher 字段让 worker 从数据库重放。DECISION 只允许 AUTHORIZED/DENIED；ISSUANCE_RESULT 只允许 ISSUED/PROVIDER_FAILED/REJECTED_STATE，REVOCATION_RESULT 只允许 REVOKED/REVOKE_FAILED 且引用已成功 issuance。三种 event kind 各最多一行，避免 ISSUED 占位后无处记录撤销；稳定 reason 精确解释状态。它仅用于审计，不进入真实播放统计。
- `play_credential_issuances` 保存 `issuance_no/provider_request_key/correlation_id/decision_audit_id/user_id/playlet_id/episode_id/episode_revision_id/request_id/request_hash`、与 DECISION 相同的规范 client/matcher 字段、basis/review引用、四代次、凭证密文、状态和租约。`user_id/request_id/correlation_id` 全部 NOT NULL，并按完全同列序 composite FK 回 `play_authorization_requests(user_id,request_id,correlation_id)`；AUTHORIZED 才可一对一创建 issuance，DENIED 必须无 issuance，不能把两个合法 request/correlation 拼成第三条关系。access basis 固化 FREE/PURCHASE/VIP/AD/REVIEW_POLICY，仅作审计且每次仍复验。`provider_request_key=issuance_no`，lease完整 fencing，首发 TTL 最多5分钟；客户端只获需在 origin 复验的包装短凭证。
- `closure_generation` 的唯一真源是 `users.closure_generation`：注册初始为 0，每次 `RequestAccountClosure` 把账号从 ACTIVE 置 CLOSING 时与 closure 创建同事务加一，永不回退或复用。DECISION、issuance、播放 session 都复制该值；授权/finalize/start/heartbeat/origin 逐次比较用户当前值。禁止使用 closure worker 的 `lease_generation`、closure ID 或 `users.version` 推导该代次。
- `video_provider_events(provider, provider_event_id)` 唯一；`play_events` 必须引用已验证 start/heartbeat/CDN/provider 事实或服务端签发且仍有效的播放会话，不得由“凭证已签发”直接生成。
- 服务端会话型 `play_events` 保存不可枚举 `session_id UNIQUE`、`authorization_audit_id/issuance_id`、用户/短剧/剧集/revision、与 issuance 相同的规范 client context/matcher hash、access basis/review policy/grant 快照、四个访问代次快照、`started_at/last_heartbeat_at/last_sequence/verified_duration`；start、每次 heartbeat 和 origin 后续取片都重验用户与内容当前状态、四代次，并调用同一 `RevalidatePlaybackAccess` 从 primary 验证当前 FREE/PURCHASE/VIP/AD/REVIEW_POLICY 事实。VIP 路径先有界 `EnsureVipEntitlementCurrent`；购买退款、VIP 到期/撤销、广告权益失效或 review grant/策略失效即使没有提升内容代次，也必须立即拒绝旧 issuance/session。heartbeat 以 `WHERE last_sequence < :sequence` 条件推进，重复或倒序为 no-op 并保留指标。provider/CDN 模式则引用唯一 `video_provider_events`，两种证据类型显式枚举，不能混用客户端进度。
- `watch_histories(user_id, playlet_id)` 唯一；旧客户端事件时间不得覆盖较新进度。
- 列表索引包含状态、语言/区域/平台、应用 build 区间、发布时间和稳定 ID；内容下架后缓存版本递增。

### 4.2 Backing 与收益

`playlet_backing_offers` 至少保存 `playlet_id`、`period_no`、`capacity`、`sold_amount`、`amount_mode(FIXED/MINIMUM)`、`unit_amount`、`starts_at/ends_at`、结构化 `default_daily_rate/income_scale/income_rounding_mode`、活跃值系数、规则版本和状态；首发同一 offer 周期不允许日率 override，若未来引入必须另建不可变结构化表并应用同一发布校验。受控终止使用类型化 `termination_enabled/termination_refund_rate/termination_fee_rate/termination_rounding/settled_income_policy`。首发只允许 `settled_income_policy=KEEP`，比例在 `[0,1]`；发布时除校验终止净额不可能为负、FIXED 金额或 MINIMUM 下限的 5% 合伙人池舍入后严格为正外，还必须要求 `default_daily_rate>0` 且 `round(unit_amount*default_daily_rate,income_scale,income_rounding_mode)>0`。因此任何最小合法助力额都能产生正额日收益，不存在零额日结路径。

`playlet_backings` 保存 `backing_no NOT NULL UNIQUE`、用户、offer、实际 COMMON 扣款、名义本金/活跃值快照、`yield_base_amount/default_daily_rate/income_scale/income_rounding_mode` 固化快照、Jakarta 半开计息区间 `[starts_on,ends_on)`、状态、幂等键、`settlement_cursor_date` 和 `next_run_at`。cursor 初始为 starts_on，只能在同事务写完该日唯一结算后精确加一天，不能跳日；唯一键另有 `(user_id, backing_offer_id)`。

`playlet_backing_terminations` 每个 backing 最多一行，保存终止业务号、`user_id`、offer/终止规则版本、`gross_compensation_common/fee_common/net_compensation_common`、已结收益 KEEP 快照、未结业务日数、可空且唯一 `compensation_ledger_id`、非空且 CHECK 固定为 COMMON 的 `compensation_asset_type`、partner pool reversal、审批/工单、幂等和时间。金额 CHECK 固定为：

```text
gross = round(actual_common_amount * termination_refund_rate_snapshot)
fee   = round(gross * termination_fee_rate_snapshot)
net   = gross - fee >= 0
```

CHECK 固定 `net > 0` 当且仅当 `compensation_ledger_id IS NOT NULL`，`net=0` 时 ledger 必须为空。实际子列 `(compensation_ledger_id,user_id,compensation_asset_type)` exact composite FK 回资产流水父键；FK 在 ledger 为空时按可选引用跳过，非空时由固定资产列证明 COMMON。延迟触发器再验证 kind=INCOME、金额=net、biz/ref 为本 termination，幂等键 `playlet_backing:terminate:compensate:<backing_no>`；已到账日收益及其团队返佣保留，未到业务日不再产生收益，活跃值全额移除，原 cash source 的 partner pool 按 06 章唯一 REVERSAL 冲正。终止补偿替代任何未来本金/收益主张，不另做隐藏返本。

`playlet_backing_settlements` 保存 `backing_id/user_id/business_date`、`yield_base_amount_snapshot/daily_rate_snapshot/income_scale_snapshot/rounding_mode_snapshot`、`direct_income`、`status=POSTED`、非空且 CHECK 固定 COMMON 的 `asset_type`、非空唯一 `asset_ledger_id`、规则版本和重试字段。`(backing_id,business_date)` 唯一；CHECK 按固化协议重算 `direct_income=round(yield_base_amount_snapshot*daily_rate_snapshot,...)>0`。实际 `(asset_ledger_id,user_id,asset_type)` composite FK 回 `asset_ledgers(id,user_id,asset_type)`，延迟触发器验证 kind=INCOME、金额、backing/biz ref 和稳定幂等键；零金额 ledger 或“只推进 cursor 不入账”的 settlement 均不可提交。

团队返佣使用 `team_rebate_settlements`，合伙人池来源使用 `partner_pool_facts`。剧集购买返佣引用 `episode_purchase_orders`，Backing 日返佣引用 `playlet_backing_settlements`；合伙人池则以 `source_kind=CASH_PLAYLET_BACKING, source_fact_id=playlet_backings.id` 在 Backing 创建成功时只创建一次。来源用户、受益用户、层级、结算时等级/比例、规则版本必须完整保存。

`finance_recovery_cases` 在本领域仅承接“原受益返佣已 RELEASED，但第三方账号 CLOSED 或锁内可用额不足，退款冲正不能安全完成钱包全额扣回”的窄场景；`reason_code` 分别固定为 `CLOSED_ACCOUNT/INSUFFICIENT_AVAILABLE`，不得部分扣回后再建差额案。来源组件、主体和方向唯一，金额为正；终态解决必须创建一对一、外部凭据自然键全局唯一的 `finance_external_settlements`，WAIVED 只允许 RECEIVABLE，PAYABLE 只能凭完整外部付款证据 RESOLVED。这是 Finance 应收/应付业务案件而非消息投递；字段、状态、管理 API、权限和锁序以 [05-资产冻结与事务.md](05-资产冻结与事务.md) §12.1、[06-等级团队与返佣.md](06-等级团队与返佣.md) §5.4.1 和 [02-API与鉴权规范.md](02-API与鉴权规范.md) §8 为唯一契约，解决/应收豁免不重开账号、不 UPDATE 原 GRANT/REVERSAL、不补写钱包流水。

`benefit_forfeiture_audits` 仅表达“新来源计算时第三方不合格或已 CLOSING/CLOSED，因而当时未建立受益权”，不能用于没收已归属金额。它保存 `source_type/source_id/source_component/calculation_mode/beneficiary_user_id/account_status/relation_depth/rule_version_id/previous_effective_rate_before/previous_effective_rate_after/entitlement_rate/candidate_diff/not_granted_amount/reason_code/calculation_trace_hash/created_at`；自然键唯一。DIFFERENTIAL 中跳过者必须满足 `previous_effective_rate_after=previous_effective_rate_before` 且 `not_granted_amount=0`，只记录候选比例；更远的合格 ACTIVE 祖先从最近一次实际生效比例继续计算。FLAT 的直属/间接槽位互相独立，未授予时 `not_granted_amount=round(base_amount*entitlement_rate)>0` 且绝不转给其他层。这样报表不会把同一差额同时统计为“被没收”和后续祖先的正常收入。

容量用条件更新保护：`sold_amount + amount <= capacity`，以影响行数决定成功，不使用缓存计数判定。

### 4.3 弹幕与 Banner

- `barrages`：`episode_id/user_id/play_at_ms/content/language/moderation_status/sensitive_rule_version/global_hide_reason/created_at`；发送语言必填，缺失时由服务端按“请求语言 → 当前内容实际语言 → 系统默认语言”确定并回显；索引 `(episode_id,language,moderation_status,play_at_ms,id)`。
- `barrage_reports`：`(barrage_id,reporter_user_id)` 唯一，保存原因、`private_hide_scope=NONE|BARRAGE|AUTHOR` 和审核终态；禁止举报本人。选择私有隐藏时，report 与对应 block 在同一事务提交。
- `barrage_blocks`：保存 `user_id/target_type=BARRAGE|AUTHOR/blocked_barrage_id nullable/blocked_user_id nullable/created_at`，CHECK 保证恰有一个 target；分别以 `(user_id,blocked_barrage_id)`、`(user_id,blocked_user_id)` 建非空唯一索引。它只影响本人查询，不改变弹幕全局状态，管理恢复也不删除。
- `barrage_author_restrictions`：作者、状态 `ACTIVE/REVOKED/EXPIRED`、`hide_existing`、原因、开始/结束、管理员与审计引用；同作者最多一个 ACTIVE。ACTIVE 阻止新建弹幕，`hide_existing` 在查询时生效而不批量改行；恢复/到期只推进限制事实。
- `sensitive_words` 按发布版本和 `language` 保存词条；精确语言无规则时使用系统默认语言规则并在弹幕保存实际匹配版本，绝不静默跳过检测。
- `banners` 是稳定聚合根，保存 `status/current_revision_id/version`；`banner_revisions` 保存不可变 `revision_no/placement/effective_from/effective_to/clickable_from/priority/max_items_group/media/alt_text/jump_type/jump_target/content_hash`，已发布版本不 UPDATE。`clickable_from` 承接 1.0 `clicked_at` 的“允许点击时间”语义，必须为空或位于合理投放窗口内。
- `banner_audience_rules` 归属 revision，保存语言/区域/平台与左闭右开的 `min_app_build/max_app_build`；发布校验、列表和点击复验共用匹配器。`banner_revisions(banner_id,revision_no)` 唯一；root 的 current revision 只在发布事务切换并递增版本。
- `banner_events` 保存 revision、事件类型 `IMPRESSION/CLICK`、服务端事件时间和客户端去重键；CLICK 只有在 primary 复验 revision 仍为当前 PUBLISHED、投放有效且已到 `clickable_from` 后才落库。真实曝光/点击不影响投放资格，不向用户展示未经定义的虚拟 CTR。

## 6. 主流程与事务边界

本章任何可能产生资产流水的购买、退款、Backing、日结或终止事务，都在 command/provider event 防重之后、取得任一内容/订单/Backing/返佣业务根之前，先调用 `AcquireIncomeWriteFences`，依次取得 income root SHARE 与当前 `business_date` 的 OPEN day fence。来源/期间根收齐后、用户层之前必须对购买者、来源用户和候选收益人先 `PrelockUserClosures`，再锁既有 freeze，最后 `LockUsersAndValidateClosureGate`；无 freeze 时两阶段相邻。新购买/Backing 及新受益资格只接受 ACTIVE；CLOSING 只终结 cutoff 前来源并唤醒 blocker，CLOSED 不生成钱包/权益。下列锁序表中的“day fence”均是 root→day 组合的简写；资产原语不得懒获取。

凡本次会读取真实等级快照、做 DIFFERENTIAL/合伙人资格裁决，或改变活跃值/等级输入，rank 35 `level_rule_runtime_roots` 必须排在 income root/day 之前。会按等级付款的剧集购买、Backing 创建和 Backing 日结先在业务事务外对有硬上限的候选集合执行 06 章 `EnsureLevelFresh`；排水 Tx 不持内容、订单、Backing、月份、day 或资产锁。真正业务 Tx 复验 runtime root CLEAN、queue `LIMIT 1` 与 fresh token，变化即回滚重试。Backing 创建对“本次来源”固定使用 active delta 写入前的 fresh 等级/资格快照，随后才增加活跃值并标 dirty，所以该份 Backing 不能用自身业绩抬高自己的返佣/池分配；新指标从下一来源起生效。退款只消费历史快照，无需等待 rollout；终止/到期虽不按新等级付款，仍先取 rank 35 CLEAN guard 再减少指标。

closure gate 必须携带 `role=PAYER|SOURCE_OWNER|THIRD_PARTY_BENEFICIARY`并返回逐用户裁决，不得把“任一候选用户非 ACTIVE”翻译为整个来源失败。付款人/来源所有人仍按业务要求失败关闭；新返佣候选人的不合格/CLOSING/CLOSED 用户不建 GRANT/freeze/钱包流水。DIFFERENTIAL 为其写零金额跳过 forfeiture 且不推进 previous；FLAT 只有规则舍入后金额正才写正额 forfeiture，ZERO_DIFF/ZERO_ROUNDED 只留在 calculation audit。退款冲正命中已 CLOSED 或余额不足第三方时，不调用会失败的钱包扣回，以原受益组件自然键写唯一 `finance_recovery_cases(direction=RECEIVABLE)`，并让返佣 REVERSAL 终态为 EXTERNAL_RECOVERY；它们与付款人退款终态同成败，第三方状态或余额绝不能卡住主事务。

### 6.1 购买剧集

1. 在 primary 读取已发布剧集和价格版本；已有权益或成功订单则按幂等语义返回。对前两层返佣候选完成有界 `EnsureLevelFresh`，即使 FLAT 金额与等级无关，也保证 settlement 保存的真实等级快照可审计。
2. 顶层 Use Case 开启一个 default 事务，先锁命令防重行和 rank 35 runtime root，再取得 income root/day fence，然后锁剧集/既有购买根；再读取前两层关系并一次收齐购买者、受益人及所需等级/资格行，以及本次真实来源可能推进的任务定义、规则和唯一 `user_tasks`；在用户层前完成 closure 预锁，再按 `user_id` 锁定并复验 fresh token，得到付款人与第三方候选人的分角色裁决，任务按 ID 固定顺序锁定。
3. 在取得任何资产锁前完成规则、权益、返佣资格、关系和任务实例快照校验；随后只把购买者 `EXPERIENCE/COMMON` 与裁决为 ACTIVE/可接受既有来源的受益人 COMMON 账户合并按 `(user_id, asset_type)` 排序锁定；CLOSING/CLOSED 新受益候选人不进入资产锁集。
4. 在锁内再次校验权益；先扣足可用 `EXPERIENCE`，不足部分扣 `COMMON`。返佣基数严格等于 `paid_common`，按 [06-等级团队与返佣.md](06-等级团队与返佣.md) 的 `EPISODE_PURCHASE` 两层 FLAT 规则先计算每槽位金额：正额 ACTIVE 才调用 `OpenFreeze(INCOME_FROZEN)`，正额非 ACTIVE 写自然键唯一的 `benefit_forfeiture_audits`，ZERO_DIFF/ZERO_ROUNDED 只写 calculation audit。
5. 同事务写 `episode_purchase_orders`、两种扣款流水、`episode_entitlements`、全部 GRANT/freeze、任务进度和审计。
6. 任一写失败全部回滚。返回提交后的余额、订单和永久权益。

`idempotency_key` 的语义包含剧集、规则版本和购买意图；同键改剧集或金额视为冲突。并发重复购买依靠权益唯一键与账户锁只扣一次。

批准退款命令在不持有用户/资产锁时先从 primary 预收集唯一 REQUESTED 退款、订单全部原返佣 GRANT、其既有 freeze、权益、当前 closure 和追偿参与者 ID；正式事务按“退款请求/订单 → 全部原 GRANT（按 ID）→ 每条原 GRANT 的 recovery root → 付款人关闭后的 refund PAYABLE roots → `PrelockUserClosures` → 全部既有 freeze（按 ID）→ `LockUsersAndValidateClosureGate`/权益/追偿聚合 → 全部资产”一次锁齐并重验集合。潜在 recovery root 无论最终是否建案都在 rank 400 预锁，禁止余额判断后反向补锁。锁内出现未预收集的新 GRANT/freeze/closure 时整体回滚、扩集重试。

付款人 ACTIVE 正常退款；CLOSING 只在 request 的 `source_persisted_at<=closure.requested_at` 时按既有来源白名单退款，并将返还余额作为 blocker、唤醒 closure；cutoff 后请求拒绝。按 blocker 契约，普通流程不会带着 ELIGIBLE/REQUESTED 责任完成 CLOSED；若防御性处理发现付款人已 CLOSED，则绝不重开钱包，而把每个正 `paid_common/paid_experience` 组件各创建一条 `EPISODE_REFUND_AFTER_ACCOUNT_CLOSED`、PAYABLE/ASSET 的 Finance case，保存原订单金额和 request 证据，退款请求与订单仍可终结。随后将权益转不可用，并为每条原 GRANT 创建唯一 REVERSAL。未释放返佣用 `SettleFreeze` 终结，原 GRANT 转 CANCELED、REVERSAL 终态固定为 CANCELED_FROZEN；已释放且钱包可写、余额充足时扣回一次并把 REVERSAL 终态置 POSTED；账号 CLOSED 或余额不足时不做部分钱包扣回，对应 REVERSAL 指向同事务在预锁 root 下创建/命中的唯一 `finance_recovery_cases` 并终态 EXTERNAL_RECOVERY，原 GRANT 保持 RELEASED。退款请求 SUCCEEDED、订单/退款 finality REFUNDED、权益、付款人退款流水或 PAYABLE、全部返佣结果及 recovery case 同事务，重复或乱序命令只能得到原终态；之后案件 RESOLVED 或 RECEIVABLE 的 WAIVED 只终结 case，不改写返佣或钱包，PAYABLE 不可 waive。

### 6.2 播放凭证

1. `AuthorizeEpisode` 要求稳定 `request_id`；服务端以令牌 user、playlet/episode、规范 context和操作生成 request hash。正式事务先 insert/lock `play_authorization_requests(user_id,request_id)`：同 hash 返回原根所指决定/issuance/短期结果，不同 hash冲突。首次请求再锁内容→closure→user并重跑授权。无权时同事务追加 DENIED DECISION、把 request root终结 DENIED且 issuance保持空；有权时追加 AUTHORIZED DECISION，保存规范 context/matcher/basis/四代次，创建唯一 PENDING_PROVIDER issuance、把 request root指向它并授予初始 lease。于是 DENIED 响应丢失也不会生成第二 correlation/DECISION；事务回滚绝不调用供应商。
2. DECISION/issuance 提交后，只有持有该 owner/generation 的 worker 才用稳定 `provider_request_key=issuance_no` 在事务外调用视频供应商。调用前崩溃由租约过期 sweep 以同 key 接管，超时只能查询/重试，不生成新凭证意图。
3. 供应商返回后开新 primary 结果事务，先锁 provider 结果防重键与 issuance，并要求 `status=PENDING_PROVIDER`、owner/generation 与发起调用的 token 完全一致；再按全局顺序锁 playlet/episode/revision → `PrelockUserClosures` → user。在同一锁内只从 issuance/DECISION 读取原始规范 client context，重跑 `ContentAudienceMatcher` 并同时重验：用户仍 ACTIVE，用户与内容四个代次均与 DECISION 相同，内容仍 PUBLISHED 且 matcher 仍得到同一 rule/revision/context hash，FREE 或当前 PURCHASE/VIP/AD 权益仍成立，或当前 REVIEW_POLICY grant 仍 ACTIVE、未过期且策略版本/用户/内容/环境仍匹配，凭证未过期。worker 不接受调用方补传 context。全部成立才条件转 `PENDING_PROVIDER -> ACTIVE`、清 lease、短期加密保存包装凭证并追加 ISSUED audit；任一不成立则转 `REVOKE_PENDING`、清 lease并写稳定 `REJECTED_STATE + reason_code`，绝不返回凭证。供应商失败只由当前 token 转 `PROVIDER_FAILED`。旧 owner 或旧 generation 的迟到结果影响 0 行，不得写审计终态。
4. 只有结果事务提交后才可向客户端返回凭证；提交失败不返回。响应丢失时客户端以同一 `request_id` 重放，服务端经 `(user_id,request_id)` 找回 correlation，锁 issuance，并使用持久化 context 重验当前 ACTIVE、全部代次和 `RevalidatePlaybackAccess` 后才解密原短期结果；不同请求不能只凭可猜 correlation 取回。finalize 提交与 HTTP 响应间发生注销、改密、内容策略、权益或 review grant 变化也不会产生可用窗口：网关/origin 每次兑换包装凭证都从 primary 权威行验证 issuance=ACTIVE、user/content 状态、四个 generation 与当前 basis 事实一致；Redis/CDN 缓存不能替代该检查。
5. `StartPlaybackSession` 消费该短凭证并绑定 user/episode/episode_revision/DECISION/issuance、access basis 及四代次；`HeartbeatPlaybackSession` 和 origin 每次后续取片同样从 primary 校验账号/内容状态、四代次、当前权益、未过期会话、单调序号、合理时间增量和防重键。只有通过该策略的 start/heartbeat，或经精确字面量路由进入视频裸 HTTP Adapter、以限长 raw body 验签后映射且 `provider_event_id` 唯一、仍满足四代次及当前权益门禁的事件，才能创建/推进真实 `play_events`。客户端 `UpdateWatchProgress` 只维护续播位置，不作为真实播放或收益输入。
6. 主动撤销单个 issuance 时可直接条件转 `REVOKE_PENDING`。账号访问语义/review grant 变化时推进 `users.play_credential_sweep_*`，短剧/剧集访问语义变化时推进对应内容根的 `credential_sweep_*`；同一根事务只增加访问代次（适用时）与 sweep generation、把 cursor 归零并设置 dirty/next-run、清旧 claim，禁止扫描、锁定或批量更新任何 issuance，因此根状态事务为 O(1)。从该提交起网关/origin 因代次或当前 basis 复验失败立即拒绝。

   根领取与根内清扫使用两级有界协议。`PLAY_CREDENTIAL_ROOT_CLAIM_BATCH_MAX=100`、`PLAY_CREDENTIAL_SWEEP_BATCH_MAX=500` 都与 SQL `LIMIT` 绑定且不能由运营配置放大：

   - claim 短事务只锁一种 root 表，候选满足 `dirty_at IS NOT NULL AND next_run_at<=now() AND claim_due_at<=now()`，按 `(next_run_at,claim_due_at,id) FOR UPDATE SKIP LOCKED LIMIT 100`，条件更新 owner/until、令 claim generation 加一并立即提交；三种 root 轮询领取，崩溃后租约自然可接管。
   - worker 在事务外按该根和 cursor 预读最多 500 个 issuance ID；正式事务先按 ID 锁 issuance，再按全局顺序锁 playlet/episode、closure/user，最后校验 root 的 `sweep_generation/claim_owner/claim_generation/claim_until` 均与 token 匹配。只把旧代或当前 basis 已失效的 ACTIVE/PENDING_PROVIDER 条件转 `REVOKE_PENDING`，同一 token CAS 推进 cursor；状态改变、集合扩大或 token 变化就回滚/扩集，旧 owner 影响 0 行。
   - 读到尾时以同一四元 token CAS 清 dirty/next-run/owner/until并把 cursor 归零；失败则保存稳定错误、退避 next-run并释放 claim。不能先锁 root 再回锁 rank 更低的 issuance。REVOKE_PENDING 的 provider revoke 另用 issuance 自身短 claim，网络在事务外使用稳定 key，结果事务匹配 owner/generation 后转 REVOKED、同步 request root并追加唯一 REVOCATION_RESULT，或退避；ISSUANCE_RESULT 的 ISSUED 行不被覆盖。凭证/会话短时有效，迟到/重放按唯一键收敛。

外部视频调用绝不位于资产或权益事务内。

### 6.3 创建 Playlet Backing

1. 服务端读取已发布 backing offer 和版本，校验时间、固定/最小份额、用户状态、Backings 数和余额；预收集本人及前五层候选并在业务事务外完成固定预算 `EnsureLevelFresh`。
2. 事务内先锁命令防重行和 rank 35 runtime root，再依次取得 income root/day fence，随后锁 backing offer/既有 Backing 根；从 primary 预读关系/版本与受益集合后，调用 `EnsurePartnerMonth` 取得收益月 OPEN 共享 fence，并按全局 rank ensure/锁齐本人及祖先的 `partner_monthly_qualifications`、全部候选受益人的 `partner_settlements`。这些期间根全部完成后，才一次收齐本人、祖先等级/资格以及本次真实来源可能推进的任务定义/规则/实例 ID，按 `UserStateLockKey` 加锁。锁内重验关系、fresh token 与任务版本，固化来源发生前等级/资格快照，再条件占用 offer 容量；集合扩大必须回滚扩集，禁止 user/asset 后补锁月份根。
3. 随后锁 `(user_id, COMMON)` 账户并使用 `ApplyMutations` 扣 COMMON；创建 `playlet_backings` 和资产流水。
4. 按规则快照增加个人活跃值，并通过 `referral_edges` 原子更新最多五层聚合、设置等级 dirty。
5. 以本次实际 COMMON 助力额为 `pool_base_amount`，只写步骤 2 已持锁的月份对象，在同一事务创建唯一 `partner_pool_facts(CASH_PLAYLET_BACKING, backing_id)`，按当时规则计算一次 5% 基础池和分配；写任务进度与审计后提交。

只有 COMMON 一种支付路径。不存在支持值、普通支持券或“公共尾部再次扣款”的第二段逻辑。

### 6.4 每日 Backing 结算

worker 只在 primary 领取到期工作，按 `backing_id` 小批量 `FOR UPDATE SKIP LOCKED`：

1. 领取事务提交后只把锁内 `settlement_cursor_date` 作为本批业务日；若 cursor 已到 ends_on 则转终结分支，禁止调用方/墙钟选择更晚日期跳过缺口。预收集五层候选并在不持有 holding/day/month 锁时完成 `EnsureLevelFresh`；真正结算事务按 rank 35→income root→day fence→Backing 顺序进入，检查 `(backing_id, business_date)` 唯一事实、要求 `business_date=settlement_cursor_date<ends_on` 并复验 fresh token；
2. 用 Backing 行固化的 base/rate/scale/mode 计算严格正直接收益；若重算结果不正，视为 `RULE_INVARIANT_BROKEN`，整笔不写 settlement/ledger、不推进 cursor 并触发 P0 告警。只有正额 POSTED settlement 才按结算时 fresh 等级、五层边和版本比例计算团队差额返佣；不得再创建或增加合伙人池；
3. 一个顶层事务写日结算、所有受益人的 COMMON 入账流水、返佣快照、持仓累计和审计，并把 cursor 精确推进一天；失败整体重试；
4. 到期只停止生成新应结日。仅当锁内 `settlement_cursor_date=ends_on`，且规范索引证明 `[starts_on,ends_on)` 每日恰有一条成功结算、无缺口时，后续有界终结事务才将持仓转为 `MATURED`，按规则减少活跃值并更新五层聚合；worker 停机跨多日后必须逐日追平，不能只结末日。

任务是否完成不参与步骤 1–4。Redis 信号丢失时，`next_run_at/status` 扫描仍能恢复。

经审批提前终止时，顶层 Use Case 只接受 backing_no/原因/工单/幂等与匹配审批，不接受金额。事务在防重后先取 rank 35 CLEAN guard，再取 income root/day fence，随后锁 ACTIVE Backing 事实并读取该行内已固化的不可变 offer/终止规则快照，不再回锁 rank 更低的 offer 行；随后锁原 partner pool GRANT，再按 rank 锁原月份 month/本人及祖先 qualification/受益 settlement。若需要后续 OPEN 月 adjustment，必须也在进入用户层前 Ensure 并锁该月根及相关 adjustment/application；最后才锁用户状态和所需资产。按上述公式创建唯一 termination，`net>0` 时入账补偿，移除活跃值、停止未来日结并把 Backing 转 TERMINATED，同时创建唯一 pool REVERSAL。原月份仍 OPEN 时按原快照对称冲减；已封账时在后续 OPEN 月创建确定性 SOURCE_REVERSAL 负调整。已结日收益/团队返佣 KEEP。终止、资产补偿、活跃值、REVERSAL/adjustment 和审计任一失败全部回滚；MATURED/TERMINATED 重放以外的调用拒绝。

### 6.5 广告、弹幕与 Banner

- 广告/视频供应商回调只进入 02 章登记的精确字面量裸 HTTP Adapter：先限制 content type 与 raw body 大小、保留原始字节并完成签名/时间窗校验，再解析并映射为内部 typed command；禁止先经 Gateway JSON→Proto 解码。Adapter 调用领域 Use Case 后返回供应商要求的专属 ACK，不返回通用 errkit JSON。`VerifyAdCompletion` 同样只先做本地格式、限流和可快速完成的签名校验；在任何供应商网络调用之前，必须用短 primary 事务写入/命中唯一 `ad_verification_attempts(PENDING)`。事务只保存脱敏 digest、可重试所需的短期加密材料和稳定 provider key，不发权益。
- 在第二个短事务按 `status/next_run_at/lease_until` 条件认领 attempt 为 VERIFYING 并立即提交；之后才在事务外向供应商验证。超时/进程崩溃由租约过期以原 verification key 重查，不新建 attempt。
- 验证结果在新 primary 事务中按统一顺序收敛：attempt/唯一 provider event 防重根 → episode/revision → `PrelockUserClosures` → `LockUsersAndValidateClosureGate`。事务同时匹配 attempt 的 owner/generation，校验 provider 结果属于同用户/剧集且内容仍可用；只有 user=ACTIVE 才可写唯一 `ad_provider_events(VERIFIED)`、创建/命中 `ad_unlock_entitlements(user_id,episode_id)` 并转 ENTITLED。CLOSING/CLOSED 则仍保留已验结果审计，但 attempt 转 `IGNORED_ACCOUNT_STATE` 且不发永久权益。客户端声明或 provider token 本身从不是权益事实。
- 弹幕创建先确定并保存实际语言，校验作者无 ACTIVE restriction；事务写正文和任务进度，命中该语言或默认回落敏感词时状态为 `SELF_VISIBLE_REVIEW`。任务只因真实成功发送事实推进。列表在同一 SQL 中应用全局审核、作者 restriction、单条/作者私有 block 和语言回落，`COUNT(*) OVER()` 或等价同口径查询产生过滤后 total。
- 举报禁止举报本人；`private_hide_scope=BARRAGE|AUTHOR` 时，举报事实与相应唯一 block 同一事务提交。管理员隐藏/恢复单条只推进全局 moderation，限制/恢复作者只推进 `barrage_author_restrictions`；两者均不删除任何用户 block。
- Banner 编辑创建 DRAFT revision；发布事务校验素材、`effective_from < effective_to`、`clickable_from`、placement 上限、定向 build 区间和安全跳转，锁 root + expected version 后把新 revision 置为 current、递增 root version 并写审计；提交后失效对应 placement/环境缓存。`ListBanners` 以服务端时间过滤并稳定按 `priority DESC,banner_id` 截取配置上限；`RecordBannerClick` 在 primary 重新复验当前 revision 和点击资格，不可点击时返回稳定原因且不写 CLICK。

## 8. 失败模式

| 失败 | 处理 |
| --- | --- |
| 内容在购买并发下架 | 事务内版本/状态重查失败，不扣资产 |
| EXPERIENCE 足但 COMMON 补差不足 | 两种资产都不扣，权益不创建 |
| 最后一份 Backing 容量竞争 | 条件更新只有一个成功，失败方完整回滚 |
| 日收益配置缺失或固化快照重算不正 | 返回 `RULE_INVARIANT_BROKEN`，不写 settlement/ledger、不推进 cursor；P0 告警，禁止按 0 静默结算 |
| 团队关系/等级 dirty | 在 primary 刷新强一致资格；不使用 slave 旧值 |
| 剧集退款与返佣释放乱序 | 两路均先锁 GRANT 再锁 freeze，订单终态和唯一 REVERSAL 收敛；只释放或追偿一次且不得死锁 |
| 退款遇到 CLOSED 或余额不足第三方 | 不做不安全的钱包扣回；REVERSAL 终态 EXTERNAL_RECOVERY 并引用同事务唯一 Finance receivable case，付款人退款照常收敛 |
| 视频供应商失败/结果提交失败 | 不计真实播放也不返凭证；稳定 provider request/correlation 可查询重放 |
| 视频供应商旧 owner 迟到 | finalize 必须匹配 issuance owner/generation；影响 0 行，由当前 lease owner 以同 provider key 查询收敛 |
| 凭证 finalize 与注销/改密/内容变化并发 | user/content 锁和四个 generation 决定结果；不匹配转 REVOKE_PENDING 且不返回，已返回短凭证在网关/origin 复验时立即失效，无全量 UPDATE |
| 广告核验成功后账号已非 ACTIVE | 保留 provider event，attempt 转 IGNORED_ACCOUNT_STATE，不建永久权益 |
| 广告/视频回调重复或伪造 | attempt/所属 provider 事件唯一；验签/服务端核验失败不发权益、不计播放 |
| 敏感词服务异常 | 采用已发布本地规则；规则不可用时收紧为待审，不公开 |
| Banner 缓存过期后点击 | 点击命令在 primary 复验 current revision、投放窗口和 clickable_from；不合格不落事件并返回稳定原因 |
| Redis 缓存/信号丢失 | 数据库事实不受影响；版本/TTL 和 sweep 恢复 |

## 9. 缓存与作业

- 内容目录、分组、本地化和 Banner 可缓存，键包含发布版本、语言、区域、平台和规范化 app build bucket；管理发布后主动失效，TTL 兜底。
- 最终播放授权、余额、Backing 资格和容量不直接信任缓存。
- 作业包括剧集退款 ELIGIBLE 到窗过期/REQUESTED SLA 扫描、Backing 日结算/到期、购买返佣释放、Finance case SLA 提醒、广告 attempt 租约过期重试与加密材料销毁、按根 generation/keyset 有界清扫播放凭证、凭证过期/供应商撤销、播放地址健康检查、结算失败重试、真实播放 rollup、弹幕审核队列和 Banner 投放状态刷新。
- 所有作业记录 `job_runs`，基于业务表 `status/next_run_at` 扫描；没有通用 Outbox。

## 10. 指标与告警

- 内容：授权成功率/拒绝原因、广告 attempt 各状态/最老待办/租约失效数、供应商凭证延迟、ACTIVE/REVOKE_PENDING 凭证数、用户/内容代次拒绝数、各根清扫 backlog/cursor 延迟、单批最大行数、仅授权未播放数、列表与鉴权不一致数、真实播放与 heat 分布。
- 购买：成功率、重复命中、混合扣款比例、退款 ELIGIBLE/REQUESTED 数、最老请求年龄、到窗过期延迟、批准/拒绝 SLA、冻结返佣/释放/冲正/追偿、CLOSED 受益人 Finance case/未建受益审计数、回滚数和未配价格数。
- Backing：容量竞争、日结算延迟/吞吐/重试、直接收益与返佣金额、每来源 pool fact 数和活跃值差异。
- 弹幕：发送、语言回落、敏感命中、作者限制、单条/作者 block、待审时长、举报处理 SLA 和可见 total 差异。
- Banner：服务端有效条数、不可点击原因、app build 过滤、缓存/revision 版本、非法跳转发布拦截、真实曝光/点击。

以下必须告警：权益已创建但无对应扣款（免费/广告/VIP 来源除外）、结算与资产流水不一致、内容下架仍签发凭证、待审弹幕公开、Backing 被任务阻断收益、排除类型写入。

## 11. 验收用例

1. 语言/区域/平台/app build 左闭右开边界/发布时间和稳定分页正确；缺失翻译按目标语言 → 默认语言 → 占位回落；搜索、列表、购买和最终鉴权使用同一受众匹配结果。
2. 免费、购买、VIP、广告和无权益五种情形下，剧集列表与最终鉴权结果完全一致。
3. 广告完成只为指定剧集生成一次永久权益；伪造客户端完成、重复回调和错误剧集均失败，provider event 与权益可双向追溯。
4. 100 次并发购买同一集只创建一个订单/权益并扣款一次；EXPERIENCE 优先、COMMON 补差，返佣只以 COMMON 为基数，任一订单/权益/任务/freeze/流水写失败全部回滚。
5. 同一用户并发剧集购买/创建 Backing 与任务奖励领取时，购买/Backing 在资产前锁任务、领取保持任务→资产，持续压测无死锁；任务进度和资金仍同事务。
6. 剧集返佣只到前两层且先冻结；到期只释放一次，退款前/后分别验证取消冻结和已释放追偿，重复乱序退款不产生第二次资产效果。退款与同批 release worker 正反并发时两路严格 GRANT→freeze，连续 10 分钟无死锁。
7. Backing 只能扣 COMMON；固定/最小份额、容量、Backings 数和同周期唯一性在并发下成立。
8. Backing offer 以最小合法 `unit_amount` 验证 default rate 后日收益舍入为正；边界下方、rate=0 或舍入为 0 的版本不能发布。故意破坏已固化快照使运行时结果不正时，必须 `RULE_INVARIANT_BROKEN`、cursor 原地不动且无 settlement/ledger/返佣。每个现金 Backing 成功时只生成一条 `pool_amount=pool_base_amount*5%` 的 pool fact；连续 N 日日结仍只有一条，正额日结直接收益/五层返佣及到期活跃值回退可重放且无重复，任务未完成不影响结算。
9. 签发凭证、客户端续播进度和 heat 均不计真实播放；只有有效 start/heartbeat/provider event 去重后计入，迟到事件不回退进度。
10. 下架阻止新购/新 Backing/新凭证，既有 Backing 按快照继续履约。
11. 弹幕保存实际发送语言，缺失语言按规定回落；敏感弹幕仅本人可见且进入审核。本人举报被拒绝；举报选择隐藏单条/作者时与 block 同事务，过滤后 total 与 items 一致。管理员限制作者后不能新发且按 `hide_existing` 查询生效，恢复全局弹幕或作者资格不删除用户 block。
12. Banner revision 在 `effective_from/effective_to/clickable_from` 各边界按服务端时间给出稳定 `clickable/non_clickable_reason`，priority 与 placement 上限稳定，语言/区域/平台/app build 定向正确；危险 URL 和非法时间无法发布，点击时 primary 复验，发布/撤回后缓存立即失效。
13. 财务/运营报表只使用真实播放和真实金额，heat 永远不进入结算。
14. `TerminatePlayletBacking` 对 ACTIVE 按 offer 快照公式唯一补偿，MATURED/已 TERMINATED/规则未启用拒绝；与日结/到期并发由 backing 行锁收敛。逐写点故障时 termination、COMMON、活跃值、pool REVERSAL/adjustment、状态和审计全部回滚；已结收益保留、终止后无新日收益。
15. 在广告网络调用前杀进程、调用后结果事务前杀进程，以及丢弃所有 Redis 信号；同一 attempt 均由 primary sweep 以原 provider key 收敛，只有一条 event/权益。核验期间并发 ACTIVE→CLOSING/CLOSED，结果只能为 IGNORED_ACCOUNT_STATE，永久权益为零。
16. 播放 DECISION 提交后、provider 返回后、finalize 提交与响应之间三个点分别并发注销/改密、短剧下架、剧集 revision/可见策略变化；凭证要么不返回，要么因用户/内容状态或四个 generation 不匹配而无法在网关兑换。创建 issuance 后令初始 worker 超时、由 sweep 接管，再让旧 owner 迟到返回，只有当前 owner/generation 可写一次结果；拒绝审计准确区分账号、内容、代次、权益和过期。已建立 session 后中途提升 playlet/episode generation，下一 heartbeat/origin 取片必须失败。状态变化事务只锁/更新一个根和 O(1) 清扫水位、触碰 issuance 行数为 0；百万旧 issuance 以每批不超过 `PLAY_CREDENTIAL_SWEEP_BATCH_MAX=500` 的 keyset 事务收敛，旧 generation worker 不能越过新 generation cursor。provider revoke 失败只留 REVOKE_PENDING 待办。
17. 购买成功前把一个两层返佣候选人转 CLOSING/CLOSED，付款人订单/权益仍成功。分别构造该 FLAT 槽位舍入后正额和舍入为零：正额不建 GRANT/freeze、只建精确 not_granted 的 forfeiture；零额只在 calculation audit 为 ZERO_ROUNDED，不能建零额 forfeiture，二者都不得转给另一层。冻结未释放时退款只得到 CANCELED GRANT、`REVERSAL(CANCELED_FROZEN)` 和一次冻结最终扣除，不进入 confirmed reversal。返佣已释放后分别制造余额不足和第三方 CLOSED 再退款：两种情况付款人退款/权益撤销与唯一 Finance recovery case 同事务提交，不部分扣回，原 GRANT 保持 RELEASED、REVERSAL=EXTERNAL_RECOVERY，CLOSED 用户钱包/version 不变。换幂等键或回调乱序不会多建案/多退款；case 后续 RESOLVED 或 RECEIVABLE 的 WAIVED 也不改返佣/钱包，PAYABLE waive 必须拒绝。
18. 已有 ACTIVE issuance 和播放 session 时调用 `RequestAccountClosure`：同一提交必须令用户 CLOSING、`closure_generation` 恰加一并设置清扫 dirty；提交后首次网关兑换、heartbeat 和 origin 取片都因代次失配立即失败，即使 sweep/provider revoke 尚未运行。回滚注销事务时状态与两种 generation 均不变；closure worker lease 变化不得影响授权代次。
