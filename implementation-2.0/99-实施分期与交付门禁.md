# 99 实施分期与交付门禁

## 1. 目标与发布策略

2.0 按 P0–P7 依赖顺序实现，每期都交付可运行、可测试、可回滚的垂直基础；不得在资产底座未通过时提前开发资金业务。最终发布是空库新系统发布，只包含新 Schema 和部署步骤，不包含 1.0 数据迁移、双写、旧 API 代理或旧系统割接。

总原则：

- 上一期出口是下一期入口；硬门禁失败不能用功能开关绕过。
- 领域实现必须同时交付 Proto、Schema、Use Case、权限、指标、对账和测试。
- 回滚只停止新入口、回滚应用/配置并安全完成已提交事实；不得删除或重写财务数据。
- 所有比例、金额、周期和资格通过已发布规则版本上线，不使用临时代码常量。

## 3. P0 工程骨架

### 3.1 交付物

- `apid`、`mand`、`workerd`、`migrate` 四类进程及健康检查、优雅停机和统一构建。
- `api/public/<domain>/v2`、`api/admin/<domain>/v2`、`api/common/v2` 的 Proto 生成、Gateway、OpenAPI 和 lint/breaking CI；不建 `api/callback` Proto。
- `database.default`、`database.slave`、PostgreSQL 只读角色；Redis 和外部供应商配置接口。
- 显式 Tx 接口、顶层事务 runner、主从命名仓储和禁止事务内网络调用的静态规则。
- 锁定 Forge `v0.4.1`；建立 Domain sentinel/typed error → Service `errkit` → Transport Proto/gRPC/HTTP 编解码，进程启动前注册 Encoder/Decoder、code name 及全部 gRPC/HTTP 映射，Domain 无 Forge 依赖。
- 建立固定字面量 callback HTTP adapter：限长 raw body/headers 验签、映射内部 typed command、返回 provider ACK；Gateway/OpenAPI 无路径参数。
- Forge `message` 只作事务外 SMS/Email transport；应用 registry 预选 provider，每个 Manager 只装配一个 sender，禁用自动跨供应商 fallback，并隔离 Forge recipient-bearing 日志/原始错误；primary challenge/delivery 保存 lease/sweep/retry 和应用级 `delivery_dedupe_key`，成功只到 `PROVIDER_ACCEPTED`，无可靠证据的不确定调用收敛为 `UNKNOWN` 且不自动重发；WhatsApp 不进入 2.0，手机号/邮箱必须脱敏。
- 统一日志、trace、metrics、BusinessClock、金额解析器、权限注解和审计基础。
- `migrate` 创建平台/RBAC/幂等/规则版本基础表；迁移兼容版本检查。

### 3.2 验收出口

1. 空 PostgreSQL 一条发布命令完成迁移，四进程可启动并通过 readiness。
2. slave 生产角色所有写和 `FOR UPDATE` 失败；命名查询仓储路由测试通过。
3. 示例 Use Case 证明一次 default 事务、回滚和提交后钩子边界。
4. Proto/OpenAPI/权限/错误码 CI 通过：每个错误码的 errkit 全映射完整，裸错误不泄漏，路由无动态路径参数/callback Proto，日志敏感字段测试通过。
5. SMS/Email 发送在事务外且崩溃可由 primary sweep 收敛，成功仅 `PROVIDER_ACCEPTED`；明确未接受才可重试，超时/响应丢失/调用后未 finalize 在无可靠证据时转 `UNKNOWN` 且不自动重发；单 Manager 单 sender、Forge 原始 recipient 日志隔离和应用侧脱敏测试通过，WhatsApp 残留为零。
6. Redis 不可用时核心 health 与数据库事实路径仍按策略运行。

### 3.3 回滚

回滚进程版本或配置版本；若迁移只做 expand 可保留未使用表。不得自动执行破坏性 down。P0 无业务流量。

## 4. P1 用户与关系

### 4.1 交付物

- 注册、登录、refresh/logout、密码/支付密码、OTP、近期认证和安全审计；`users.auth_version` + 有界 `session_families` 实现 O(1) 全局撤销，`session_issuances` 保证登录/轮换提交后响应丢失可按同 nonce/设备返回原结果。
- 本期先实现注册的命令防重→`user_population_roots` SHARE→`level_rule_runtime_roots` SHARE/CLEAN、不可变 `registration_seq`、关系与首次等级部分；人口根为 P7 月末 cutoff，等级根阻断规则原地 rollout。income root、双资产和完整注册组合在 P2 一次接通，本期不伪造零资产用户或 candidate activation。
- 用户资料、账号状态、KYC 供应商事件、银行目录/核名/人工复核、`user_security_audits`，以及注销请求/CLOSING/阻塞注册表；不建提现专用人脸能力，资金处置后移。
- 后台主体、MFA、RBAC、读写权限拆分和数据范围。
- `users.parent_id`、`inviter_ids bigint[]`、五层 `referral_edges`、`user_relation_stats`、关系审计和一次性后绑定。
- 为注册硬依赖前移最小等级底座：`user_levels`、完整首发 TEAM_LEVEL 结构化规则和无数据库 evaluator；这里只用于全零首次计算和契约测试，活跃值、增量聚合、worker/返佣仍在 P3。
- 注册关系事务和 L0→首次 L1 计算行；这里只验收到资产前的内部切片，注册外部入口在 P2 接入 income root 与双资产初始化前保持关闭。

### 4.2 验收出口

内部注册切片、无上级、合法后绑定、自邀、循环、禁用上级、并发绑定和已有下级晚绑定全覆盖；边表可从祖先链重建，`user_relation_stats` 可从边表重算，全零等级 evaluator 稳定得到 L1。普通用户并发注册的 `registration_seq` 唯一单调，均取得 population root SHARE 且彼此不因该根串行；本期锁轨迹止于 dedupe→rank30→rank35。超级密码、F 码、字符串关系和活动钩子扫描为零。认证、IDOR、MFA、脱敏、只追加安全审计及注销请求→CLOSING→WAITING_BLOCKERS/READY 的 blocker 注册测试通过；本期不宣称完整注册成功、COMMON 清退或 EXPERIENCE 资产处置完成。

### 4.3 回滚

停止注册/关系绑定入口，保留已创建用户和不可变审计；回滚应用后不得修改已绑定关系。供应商回调可继续记录并由恢复版本处理。

## 5. P2 资产硬门禁

### 5.1 交付物

- `rollup_roots`、最小 `rollup_versions/income_calc_policy_segments`、`finance_business_days` 与 `income` bootstrap，以及 `user_assets`、`asset_ledgers`、`asset_freezes`、`asset_exchanges`、`asset_adjustments`、`finance_recovery_cases`、通用 `user_limit_usages`、结构化兑换/纠错规则和对账批次迁移；`asset_ledgers.business_date` 在本期即以 Jakarta generated column + FK 落地，不等 P7。幂等 `InitializeFinanceBootstrap` 在一个事务固定 `finance_launch_date/first_earning_month`，创建首个 ACTIVE calc 的完整 EVENT_TIME segment、唯一 launch-1 genesis anchor 与 launch day OPEN 行；P7 扩展 dirty/publication/proof，不替换这些根和合同。
- 注册 Use Case 接通 canonical dedupe→rank30→rank35→rank40 顺序，并在同一事务预建 COMMON/EXPERIENCE 两行；P7 candidate 尚不存在时 activation hook 确定性 no-op。至此注册链路才具备对外开放条件。
- `ApplyMutations`、`OpenFreeze`、`ReleaseFreeze`、`SettleFreeze`，仅接收 Tx。
- 本期交付 `EnsureFinanceBusinessDay/AcquireFinanceDayFence(tx,occurred_at)`；所有流水写入先持 OPEN 业务日共享 fence，资产原语断言 fence 已由顶层取得，禁止在业务根之后补锁。P2 并发门禁已覆盖 OPEN、日期映射、旧日拒写和锁序；P7 只在此底座上增加封账/rollup。
- 六种操作、体验资产显式兑换/冲正、全局固定锁顺序、幂等冲突、条件更新、统一金额精度和审计。
- `ForfeitClosureExperience` 的 disposition + EXPENSE 原子处置；不包含 COMMON 清退提现。
- 钱包/流水/冻结查询和受双人复核的管理补偿入口。
- 逐用户/资产账户—流水—冻结对账、差异告警和并发压测工具。

### 5.2 硬出口

必须完整通过 [98-测试与性能验收.md](98-测试与性能验收.md) 第 3、4 节，包括 100 用户、10,000 次并发随机变动：无负余额、无重复入账、无死锁、逐资产守恒。任一业务失败的资产/流水/冻结/审计全部回滚。bootstrap 另须通过 [98](98-测试与性能验收.md) §9.4 的 genesis 硬门禁：只能一条、列形状完全匹配、禁止任何 ledger/publication/shard 引用，launch day 资产写可取得 OPEN fence；重复执行只返回同一 contract hash。

P2 未签字前，P3 可开发纯等级函数，但 P4/P5 不得合入任何真实资金写入。

### 5.3 回滚

关闭所有资产命令，仅保留 primary 钱包/审计读取和对账。绝不回滚已提交流水或清空账户；缺陷通过受审计的反向流水修复。

## 6. P3 等级、团队与返佣

### 6.1 交付物

- 在 P1 最小等级底座上完成活跃值不可变流水、`user_levels` 全量聚合、顺序 L0–L7 规则运营能力。
- 扩展并冻结无数据库依赖 evaluator 的全阈值/差额响应契约。
- 持仓、活跃值和关系变化对最多五层祖先的同事务增量更新和 dirty 标记。
- `users.relation_path_key`、`level_recalc_queue`、每波最多本人+五层的 primary worker、强一致 path-range 有界排水/fresh token，以及单份 materialization 的等级规则 rollout maintenance barrier、重建/对账工具。
- 统一 `team_rebate_settlements` 引擎：五层 DIFFERENTIAL 可用返佣、两层 FLAT 冻结返佣、到期释放、退款 REVERSAL/追偿和等级/关系/规则快照。
- 基础 5% 合伙人池、月度资格、原子领取、来源唯一 REVERSAL，以及 MANUAL 双人审批/SOURCE_REVERSAL 确定性跨月抵扣；月结使用稳定 hash 空间、`partner_month_sources/adjustment_heads`、固定 N 多事务游标和独立验证阶段，发布事务只锁有界 shard 证明。

### 6.2 验收出口

- 所有等级阈值上下最小单位、升降级、最高等级、版本切换和并发不丢更新通过；深链/百万 dirty 后代仍按 path B-tree 每次只读 N、每波最多锁 6 用户，超同步预算失败关闭但 worker 最终收敛。规则 rollout 全程阻断混合等级读写，前后 qualified 门槛变化的计数 delta 与 proof 正确后才恢复 serving。
- 团队热查询在 `V2-PERF-1` p95 < 200ms；等级 worker 持续至少 500 次/秒。
- 合伙人系数 30/50/70/100%、收益月和并发领取唯一正确；相邻月份并发封账必须由前驱证明串行，单 shard 热点来源仍按固定 N 续跑，任何事务不随来源数增长。
- 返佣引擎用四类 typed source fixtures 完成 source matrix、冻结释放/退款冲正、余额不足追偿和 adjustment 不覆盖历史；本期不伪造尚未存在的剧集/VIP 业务表集成。
- 等级变化不发活动奖励、不更新任务；历史返佣不因后续等级变化而改写。

### 6.3 回滚

暂停异步重算和新返佣入口；保留 dirty，恢复版本从 primary 继续 sweep。若新规则有问题，发布经过审核的前一规则新版本，不回写已结算快照。

## 7. P4 短剧与机器人

### 7.1 交付物

- 短剧/分组/剧集/本地化/字幕的草稿、发布、下架和缓存版本。
- 单一 `AuthorizeEpisode`、`episode_purchase_orders`/权益、`episode_refund_requests` 与 eligibility/finality 窗口、到期 sweep、可恢复 `ad_verification_attempts`、广告供应商事件与永久权益、收藏、历史、授权审计和可验证真实播放事件；外部播放凭证绑定用户/短剧/剧集四个访问代次、短 TTL，并以 O(1) 根提代次即时失效、有界 keyset 清扫历史。
- 剧集 EXPERIENCE 优先 + COMMON 补差 + COMMON 部分两层冻结返佣事务。
- COMMON `Playlet Backing`、容量、活跃值、参与成功时唯一 5% pool fact、逐日直接收益/返佣和到期。
- 机器人商品、售价/本金快照、`user_robot_product_stats` O(1) 现金限购根、持仓、等级暂停、逐日收益、返本。
- `Robot Purchase` 时唯一 5% pool fact；`Robot Activation Voucher` 规则/批次/券码/分发/核销、`robot_qualification_consumptions`、零本金、零团队返佣和跨现金/券首持仓并发保护；券只分发给 ACTIVE 用户，ASSIGNED 未用券纳入关户处置。
- 为 P4/P5 同事务来源接入先交付最小任务事实表和 `RecordTaskProgress(tx, verifiedSource)` 内部原语；任务列表、领取和管理发布入口仍保持关闭，P6 再补完整产品能力。

### 7.2 验收出口

内容列表与最终授权完全一致；凭证签发/续播/heat 不冒充真实播放；剧集并发购买只扣一次且 `EPISODE_PURCHASE` 真实来源集成、冻结返佣释放/冲正通过。`Playlet Backing`/`Robot Purchase` 容量、取消/终止和结算守恒，每个现金来源只入池一次；跨现金/券首持仓唯一；任务未完成不阻断收益；券不返本不返佣。Redis 丢信号后所有到期工作由 sweep 恢复。支持值、普通短剧支持券、FlashSale 和订阅类型扫描为零。

### 7.3 回滚

下架新商品/Backing offer 并关闭新购；已提交权益继续可读，既有持仓由上一稳定 worker 按快照履约。不能通过删除持仓或改结束时间回滚。

## 8. P5 支付与提现

### 8.1 交付物

- 支付渠道、充值商品、原额充值订单、每单每 kind 唯一支付尝试、迟付 finality、回调/回查和渠道对账。
- 一次性 VIP 显式价商品、订单、排队/有效/到期权益、`user_vip_stats` 容量预占与每用户 64 条非终态硬上限、两层 COMMON 冻结返佣、唯一退款 attempt、`REFUND_NOT_ACCEPTED` 可重试终态和退款 REVERSAL；无自动续订。
- 发布稳定任务 `PURCHASE_ONE_TIME_VIP <- ONE_TIME_VIP_ENTITLEMENT_CREATED`，并与 VIP 订单、权益和冻结返佣同事务；不创建 `SUB_VIP`。
- 提现不建专用人脸检查；DAY/WEEK reservation、KYC/已验证银行卡前置，TOTP 从未成功确认可跳过、ACTIVE 必验且防 step 重放、曾确认但当前 REVOKED（含 reset）须重绑或受控恢复；COMMON 冻结、审核、最多 8 个 payout attempt、受控渠道切换、`payout_failure_resolutions`、失败释放、成功扣除及 canonical/duplicate/late disposition 对账。
- `purpose=ACCOUNT_CLOSURE` 注销清退提现；CLOSING 只允许服务端按余额、单笔/渠道上限和 DAY/WEEK 剩余额度计算的最大合法批次串行清退，不开放普通提现或隐式 EXPERIENCE 处置。
- 外部调用事务外执行，`status/next_run_at` primary sweep；权威相反终态必须落类型化 Finance case/source reversal/payout disposition，P0 人工告警只负责调查和受控外部结算，不替代确定性账务状态机。
- 管理端审核/出款权限分离；命中已发布金额/风险阈值的动作强制异人复核。

### 8.2 验收出口

支付 callback 重复/乱序/错误金额、raw-body 验签/provider ACK、请求超时回查、原额入账和退款后“原 credit + 唯一 settle”、VIP 并发权益、`ONE_TIME_VIP_PURCHASE` 真实来源冻结返佣及中性任务原子履约通过。提现非法金额、条件 TOTP 缺失/错误/重放在冻结前拒绝，提现人脸表/API/锁/callback target 扫描为零；注销 COMMON 全链清退与 P2 EXPERIENCE disposition 联合可达，账户—冻结—流水—渠道账单对账零差异。

### 8.3 回滚

关闭新建充值/VIP/提现入口；保留已提交订单状态查询、回调验真、回查和在途提现 worker。不得因版本回滚忽略供应商已成功事实或释放未知状态冻结。

## 9. P6 任务与运营

### 9.1 交付物

- 在 P4 最小任务内核上完成白名单任务定义/版本、真实进度事件、周期实例、原子领取、自然来源唯一的 `task_compensations`、公共查询和管理发布；异步来源固定 64 个 `task_source_consumption_roots`、连续 `task_source_seq` 和 `task_period_source_barriers`，周期过期必须等 grace + 全分片 consumed upper，并重跑所有来源事务故障注入。
- 弹幕发送、敏感词本人可见待审、举报/审核/屏蔽闭环。
- Banner 服务端投放、priority、数量限制、安全跳转、缓存失效和真实事件。
- 配置草稿/复核/发布/回滚、未生效尾版本 `ReplaceScheduledRuleVersion` 原子替换、作业诊断、审计检索和站内通知投递；SMS/Email 经 Forge `message` 事务外发送，primary delivery/lease/sweep/retry 可收敛，只把 transport 成功记为 `PROVIDER_ACCEPTED`，无可靠证据的不确定调用记 `UNKNOWN` 且不自动重发。
- Finance 追偿案件列表/详情、进入复核、凭外部证据解决和异人审批豁免；提醒作业只报 SLA，不回写钱包或自动处置。
- 公共/管理 API 完整权限点和管理菜单；登记 `report.export/report.download`，实际异步导出在 P7 交付。

### 9.2 验收出口

客户端不能推进任务，重复事件/领取幂等；一次性 VIP 权益与中性任务进度同成败且任务永不阻断合法收益。Finance case 状态 CAS、权限、异人豁免、外部证据、幂等和只追加审计通过，任何处置不产生钱包流水。弹幕 total 与可见集合一致；Banner 时间边界和危险链接拦截正确。所有排除活动、`SUB_VIP`、AI 聊天、版权和付费 TaskPlan 的入口/配置/作业为零。

### 9.3 回滚

撤回任务/Banner/配置发布版本，关闭新弹幕；已领取奖励不撤销，已公开内容按审计状态处理。缓存信号丢失不影响版本读取。

## 11. 空库发布步骤

1. 冻结应用、Proto、迁移和首发规则版本；记录制品 hash。
2. 创建 primary、slave 只读账号、Redis 命名空间和最小权限供应商凭证。
3. 运行 `migrate` 建新 Schema，执行约束/索引/角色/Schema diff 检查。
4. 部署 `workerd` 但暂不领取业务作业；部署 `apid/mand` 为不可公开状态。
5. 发布 RBAC、业务时钟、收益类型、资产、等级、商品、渠道、任务和 Banner 首发规则；双人复核资金配置。
6. 运行幂等 `InitializeFinanceBootstrap`，在一个事务创建首个 ACTIVE calc/segment、唯一 genesis anchor 和 launch day OPEN 行；复验 singleton、launch-1、规范空向量、无 shard/publication/ledger 引用和重复执行 contract hash 不变。
7. 创建合成用户执行注册、关系、双资产、内容授权和沙箱支付/提现烟测，随后按测试数据清理策略隔离该租户；生产财务表不直接删除烟测事实。
8. 启用 worker 领取，确认 primary sweep、首日封账预检、指标和告警；再开放公共流量。
9. 按 5%、25%、50%、100% 新系统流量观察错误、锁等待、对账和外部渠道；这里是新系统自身发布比例，不是 1.0 双写或割接。

## 12. 发布回滚与停止条件

立即停止新命令的条件：资产守恒差异、重复出款/入账、权限绕过、未知排除类型写入、无法重建的作业积压或数据库持续死锁。

回滚顺序：关闭新建命令 → 保持回调/回查/在途 worker → 回滚应用制品 → 回滚可逆配置为已审核版本 → 对账已提交事实 → 修复后重开。不得清库、删除流水、强制改终态或把未知渠道结果当失败。

因为没有 1.0 割接，回滚目标是“2.0 暂停服务并保护新库事实”，不是把新用户切回旧系统。

## 14. 变更控制和完成定义

阶段进行中如需改变资产单位、关系真源、等级门槛、返佣、外部命令可靠性或排除范围，先更新 ADR 和本文依赖/门禁，再编码。不得为赶期创建两套实现。

单个领域“完成”需同时满足：

- 文档、Proto、迁移、实现和权限点一致；
- 主流程、失败、并发、幂等、回滚和对账均有自动化测试；
- dashboard、告警、作业重试和诊断入口可用；
- 参考/改造/拒绝项经评审，没有从 `splay` 粘贴的耦合分支；
- 不得以未完成标记代替已确认的 2.0 正式规则。
