# 98 测试与性能验收

## 1. 目标与门禁原则

本章是 P0–P7 的硬验收合同。资金守恒、权限、并发、故障恢复或排除项检查不通过时不得以“后续补测”放行；性能结果必须来自固定数据集和保存的 SQL/计划证据。

测试层级：纯函数单元测试 → PostgreSQL 集成测试 → API/鉴权契约测试 → 并发/属性测试 → worker 与故障注入 → 固定数据集性能 → 空库发布演练。

## 2. 测试环境

- PostgreSQL 主库 + 可人为暂停回放的只读副本；约束、扩展和参数与生产一致。
- Redis 可独立断网、清空信号和注入超时；缓存不可预置为正确答案。
- 支付、出款、KYC、视频供应商使用可编排的原始 HTTP 签名沙箱，支持 raw-body 篡改、超时、乱序、重复、错误金额、provider ACK 和未知状态。
- SMS/Email 使用锁定 Forge `message v0.4.1` 的可编排 sender，能在 claim/发送/finalize 之间杀 worker；WhatsApp 渠道不存在。
- 时钟可固定在 `Asia/Jakarta` 的日/周/月边界，不修改操作系统全局时间。
- 每个集成用例从迁移创建的空 Schema 开始，不导入 1.0 数据。

## 3. 资产硬门禁

### 3.1 六种操作 × 两种资产

| 操作 | available delta | frozen delta | 必测结果 |
| --- | ---: | ---: | --- |
| 可用入账 | `+amount` | `0` | 累计入账、流水 before/after 正确 |
| 可用出账 | `-amount` | `0` | 不得透支 |
| 可用转冻结 | `-amount` | `+amount` | 同一流水双桶变化、ACTIVE 冻结明细一致 |
| 冻结转可用 | `+amount` | `-amount` | 只允许 ACTIVE 冻结，终态 RELEASED |
| 直接入冻结 | `0` | `+amount` | 有明确外部来源；ACTIVE 明细一致 |
| 冻结最终扣除 | `0` | `-amount` | 只允许 ACTIVE 冻结，终态 SETTLED |

对 `COMMON` 和 `EXPERIENCE` 分别执行成功、余额不足、非法金额、超精度、重复、冲突和中途失败。EXPERIENCE 的提现和非白名单消费必须失败。

逐笔冻结 DDL 门禁还必须把 opening/terminal ledger 的 `freeze_id/user_id/asset_type/amount/kind` 与 freeze 明细做 exact composite FK + 延迟约束验证：跨用户、跨资产、少开/多开、部分金额终结、RELEASED 配 SETTLE 或 SETTLED 配 UNFREEZE 均不可提交；合法 Open→Release/Settle 可在一个事务提交且两个 partial unique 各只有一行。

### 3.2 守恒断言

对每个 `(user_id, asset_type)`：

```text
available_now = opening_available + SUM(available_delta)
frozen_now    = opening_frozen    + SUM(frozen_delta)
frozen_now    = SUM(asset_freezes.amount WHERE status = ACTIVE)
total_in - total_out = available_now + frozen_now - opening_total
```

不同资产绝不相加验证。每个业务命令还必须证明业务单、冻结、余额、流水、任务和审计同成败。

### 3.3 并发随机测试

固定随机种子创建 100 个用户和两种资产，发起 10,000 次并发随机合法/非法操作，包含同键重放、同键异义、交叉转冻/释放/扣除、多用户批量入账和故障注入。验收结果：

- 无负 available/frozen，无重复入账，无丢流水；
- PostgreSQL 未报告死锁；超时重试仍满足幂等；
- 每用户每资产通过全部守恒公式；
- 每个 ACTIVE 冻结有且仅有一笔明细，终态只能发生一次；
- 全局锁等级“命令幂等/外部事件→`rollup_roots('income')` rank 40 SHARE→账务日 fence rank 50 SHARE→`BusinessRootLockKey(rank,type_code,normalized_id)`→closure prelock→既有 freeze→用户/关系/资格/聚合 gate→资产→追加事实”和各等级内部排序日志始终单调；首发 rank/type_code 注册表逐项覆盖，未登记业务根、异构表无 type_code 或序列回退由测试立即失败。现金机器人购买必须记录 product/holding→rank 350 `user_robot_product_stats(robot_product_id,user_id)`→来源结算/月根→closure/user 的单调轨迹，券路径不伪造或反锁该现金限额根。
- 异步任务来源 writer 固定记录“命令/外部事件→rank 90 source stream shard→来源业务根→closure/user/task”，consumer 固定“rank 90 claim→closure/user/task”；period barrier 只按规范顺序锁 64 个 rank 90 根。三者正反并发 10 分钟无死锁，任何来源业务根后补锁 stream root 或跨 shard 逆序均由静态/运行轨迹测试拒绝。

### 3.4 EXPERIENCE 兑换

为 `asset_exchange_rule_settings` 的启停、汇率、舍入、单笔/业务日上下限逐个做边界测试。两笔并发争抢当日最后额度只有一笔成功；同一业务日切换规则版本仍复用同一 `user_limit_usages`，不能重置额度。一次兑换必须原子生成 usage、一条 `asset_exchanges`、一笔 EXPERIENCE 出账和一笔 COMMON 入账；相同键重放返回原结果，同键改金额冲突，任一写点失败全回滚。冲正引用原 exchange 并产生唯一反向事实，同时对称更新 usage；余额不足时不得让任一资产为负，也不得把兑换隐式塞进提现。

### 3.5 人工调整与自然唯一纠错

`asset_adjustments` 分别覆盖 `DISCRETIONARY` 与 `REVERSAL`。后者必须引用原 ledger，用户、金额、资产与 INCOME/EXPENSE 对称方向完全匹配；一条原流水只允许一次全额冲正，不支持部分冲正，换 100 个客户端幂等键也不能多冲。`PRE_CLOSURE_SOURCE_CORRECTION` 还必须带稳定 `source_domain/source_kind/source_id/source_component`，数据库自然唯一约束与 command dedupe 双层生效。同键异义、错原流水、跨资产、非对称方向、非等额金额、CLOSING 后运营赠送和 CLOSED 钱包写均失败；每个注入点要求 adjustment、approval、余额、流水与审计同成败。

## 4. 事务与故障注入

对下列每个注入点强制返回错误，并比较事务前后快照：

| 流程 | 注入点 |
| --- | --- |
| 注册 | 用户后、双资产第一行后、关系边后、等级后、审计前 |
| 剧集购买 | EXPERIENCE 扣款后、COMMON 补差后、订单/权益前、第 N 个返佣/freeze 后、任务前 |
| Playlet Backing / Robot Purchase | 容量后、资产后、持仓后、一次性 partner pool 后、活跃聚合后 |
| 一次性 VIP 履约 | 权益后、第 N 个冻结返佣后、任务进度后、订单 PAID 前 |
| 每日结算 | 直接收益后、第 N 个返佣后、游标前；断言不得新增 partner pool |
| 任务领取/纠错 | 状态更新后、资产入账后、领取事实/`task_compensations` 前；同一来源换幂等键不得重复补偿 |
| 提现 | 条件 TOTP 验证/`last_accepted_step` 推进前后、业务单后、冻结后、审核后、终态释放/扣除后 |

任一点失败都要求订单、资产、流水、冻结、持仓、任务、关系/等级聚合和审计全部回滚。测试同时用静态规则检查事务闭包内没有裸 `*bun.DB`、slave、HTTP、Forge SMS/Email、支付商或 Redis Publish。

并发锁序门禁同时运行剧集购买/退款/返佣释放、现金/券机器人购买、日结/到期、关系绑定/等级刷新、合伙人来源/领取、任务领取/补偿、人工资产调整、提现创建/审核/终态、注销清退，以及收益资产写入/`income_calc_dirty` rollup 的正反组合。每条可能新增 COMMON/权益/blocker 的路径都必须显示 `PrelockUserClosures` 先于 freeze/user state，再以 `LockUsersAndValidateClosureGate` 在 user 锁内复核 generation/status；测试注入 prelock 后并发 CLOSING，证明旧 generation 不能提交。关系拓扑分别构造祖先 ID 全小于、全大于和交错于来源用户三组数据，证明实现先收齐再排序，而非默认“来源用户先锁”。至少连续 10 分钟无 PostgreSQL deadlock；故意注入“券或用户后锁商品”“用户后锁 partner month”“资产后锁等级”“统计投影后锁资产”和“只预读 closure 不锁内复核”五种测试实现，必须被静态规则或锁序断言捕获，证明门禁不是空测。

## 5. 提现与外部回调

1. 空、非法、0、负数、超精度、低于/高于限额、手续费后净额不正均在冻结前失败。
2. 同幂等键重复申请返回原单；同键改金额/银行卡冲突。
3. `AWAIT_REVIEW` 取消/拒绝只释放一次；批准后不能用户取消。
4. 出款成功只能 `SettleFreeze` 一次；`CANCELED/REJECTED/FAILED` 三类释放终态各自及互相乱序都只能 `ReleaseFreeze` 一次；加上 ARRIVED 共四个业务终态。
5. 对成功→失败、失败→成功、重复成功、未知→成功和延迟回调做全排列；钱包冻结只按首次合法业务终态结算一次，后续有财务最终证据的矛盾必须进入类型化 Finance case/disposition，而不是只记人工备注或改资产。
6. 支付、出款、KYC、广告和视频 callback 逐个使用已登记 provider/kind 固定字面量路由；先基于限长 raw body/headers 验签，验签失败、event 重复、金额/币种/订单不匹配都不推进状态，响应符合 provider ACK。路由/query/body 均不得动态选择验签算法，descriptor 无 callback Proto。
7. 渠道请求超时保持 UNKNOWN/待回查，不立即释放或重复出款。
8. payout attempt 以 CREATED 提交后立刻杀死 worker，再由多个 worker 重领；活动 partial unique 覆盖 CREATED，最终始终复用同一 attempt/商户号且只有一个外部出款意图。
9. 充值/VIP 每个订单的 COLLECT 和 REFUND 各只有一个全生命周期 attempt；换 attempt_no/merchant key、FAILED 后另建和 UNKNOWN 并发重试均由数据库拒绝，迟付纠正仍落回 `:collect:1`。
10. 提现不存在专用人脸检查表、API、callback target、context 或锁层。从未成功确认 TOTP（包括仅有未确认 PENDING/EXPIRED）的 `NEVER_BOUND` 可跳过；ACTIVE 绑定在提现事务中必须验证 code 并原子推进 `last_accepted_step`，缺 code、错 code、同 step 重放都在冻结前拒绝；曾确认但当前 REVOKED（含 reset）且未重绑/恢复时不得提现。同幂等请求已成功时先返回原结果，不要求新 OTP。
11. ACTIVE 用户只能普通提现；CLOSING 用户只能通过 closure endpoint 清退服务端计算的本批最大合法正额。同一 closure 最多一笔非终态，前批终结后按连续 sequence 创建下一批；DAY/WEEK 用尽则等下一窗口。构造余额分别等于/超过单笔、渠道、日、周上限，验证每批不绕限且最终归零。ACCOUNT_CLOSURE 渠道发布分别以 0、1、32、33 个 slot 验收：0/33、断号、重复和错误 set hash 均不能发布，1/32 合法；dust 事务最多锁 32 条 slot/对应渠道根，只有完整集合全部不可支付才允许 dust-to-PAYABLE。既有持仓后来再入账时可新做 quote 并继续清退，不能充值/购买/Backing 或隐式处置 EXPERIENCE。
12. 充值成功退款从 PAID→REFUND_PENDING→REFUNDED 始终只有一条原 credit，REFUNDED 恰有一条等额 refund settle；外部超时/临时失败始终保持同一 PENDING attempt 和 ACTIVE freeze。仅在证明未受理后可显式转 REFUND_CANCELED 并唯一 release，之后不可再退款；取消/成功乱序只产生一个冻结终态，迟到矛盾进入人工追偿。
13. FAILED/EXPIRED COLLECT 即使退出普通 attempt sweep，finality OPEN 仍由独立索引/lease 扫到。停 worker、丢 Redis、认领后崩溃再恢复，最终权威 PAID 原子履约并唤醒 closure，NOT_PAID 保存证据并解除不确定性；未知绝不因重试耗尽误判。历史 CONFIRMED_PAID 在资产/权益清退后不永久阻塞注销。
14. 新 COLLECT 缺 risk_until/finality_next_run、以非 OPEN 初始化或 REFUND 偷填 finality 字段均由 CHECK 拒绝；订单 EXPIRED/attempt FAILED 不清除 OPEN，CONFIRMED_* 没有检查时间/证据或仍持 lease 也无法提交。
15. PAID 充值退款时把 COMMON 消费到低于原 credit：`StartDepositRefund` 稳定返回 `REFUND_BALANCE_INSUFFICIENT`，订单仍 PAID，freeze、REFUND attempt、Finance case 和渠道请求均为零；余额恢复后原语义重试才可进入 REFUND_PENDING。

16. VIP REFUND attempt 对 UNKNOWN/临时失败始终复用同一商户号；只有权威 NOT_ACCEPTED evidence/time 且无未知请求时，attempt 与订单同事务进入 REFUND_NOT_ACCEPTED，entitlement、返佣、任务和资产完全不变并退出 closure blocker。NOT_ACCEPTED 与成功并发只得一个本地终态；终结后迟到外部成功只创建一条 `VIP_REFUND_SUCCESS_AFTER_NOT_ACCEPTED` EXTERNAL/RECEIVABLE case，重放不多建案。
17. payout attempt 1..8 边界、旧 lease、Switch 与 `FinalizeNotAcceptedPayoutFailure` 正反并发逐项验证：同一 NOT_ACCEPTED attempt 只能存在 switch 或 failure resolution；无候选/第 8 次由 attempt-level primary sweep 在 Redis 丢失及认领崩溃后自动恢复，原子把 withdrawal FAILED、DAY/WEEK 两 reservation RELEASED、两个 usage 回退且 freeze 只释放一次。第 9 次、错证据、错 version、旧 owner、串单 STOP cause 和自引 cause 均由 DDL/CAS 拒绝；有可用渠道时 worker 不擅自选路。
18. withdrawal 已 ARRIVED 后仍有 STOP_CONFIRMING attempt 时，独立 attempt 索引/lease 必须继续查单；旧 owner 迟到影响 0 行。分别从 FAILED、NOT_ACCEPTED、STOPPED 注入完全匹配的已验签成功或封存 reconciliation，必须只走证据化 `-> SUCCEEDED` 纠正边、保留旧终态证据并退出活动索引；相同成功重放无第二次效果，错 provider/merchant/金额/币种拒绝，STOPPED_BEFORE_SUBMIT 永远不能转成功。枚举最多 8 个 attempt 的成功/反转排列并验证 canonical 永远是最小未反转 `attempt_no`：A1 canonical、A2 duplicate 后，A2 反转要取消其 OPEN/IN_REVIEW RECEIVABLE；A1 反转而 A2 仍成功要提升 A2 并取消其旧 duplicate 案，不能建 missing-payout PAYABLE；全部反转才建唯一 `PAYOUT_FAILURE_AFTER_LOCAL_ARRIVED`。原案 WAIVED 时无反向金额，原案 RESOLVED 时分别创建唯一 `DUPLICATE_PAYOUT_REVERSED_AFTER_RECOVERY` PAYABLE 或 `PAYOUT_SUCCESS_AFTER_FAILURE_COMPENSATED` RECEIVABLE。故障注入任一点必须让 attempt operation/financial status、canonical、全部 disposition/event、原案取消/反向案和 provider event 同成败；任一时刻“真实净出款－唯一已结冻结－未结/已外部结算 Finance 案件”守恒。

## 6. 用户、关系与安全

| 场景 | 验收 |
| --- | --- |
| 注册确定上级 | 用户、两资产行、祖先链、1–5 层边、等级行和审计同事务 |
| 注册人口 barrier | 注册在分配 `registration_seq` 前持 population root SHARE；月度统计 UPDATE cutoff 与在途/新注册并发后，cutoff 前成员不漏、新注册只落到更大 seq，普通注册彼此不串行。NORMAL 的 seq 非空/唯一/不可更新，非 NORMAL 必须为空；回滚 gap 不复用且不被计作成员。百万用户 INPUT/VALIDATE 的 `EXPLAIN` 必须命中 seq partial unique 的固定 N keyset，不得全表 sort/offset |
| 百分位 head 锁序 | publication create/publish 与并发注册、前驱换代、同月重复协调持续混跑 10 分钟无死锁；锁轨迹必须按前驱/current head 升序（rank 20）→ population UPDATE（rank 30），捕获 upper 的事务不扫描用户且持 population 排他锁在 deadline 内完成 |
| 无上级注册 | parent/祖先链为空，后绑定资格明确 |
| 合法后绑定 | 仅“无 parent 且无任何下级”成功一次 |
| 自邀/循环/禁用上级/错误类型 | 全部拒绝且无部分边 |
| 并发绑定不同上级 | 最多一个成功，完整链和边对应同一上级 |
| 已有下级晚绑定 | 即使自己无 parent 也拒绝 |
| 祖先链深度边界 | `RELATION_PATH_MAX_DEPTH=128` 恰好成功，129 拒绝且不能截断写入；128 层 key 的唯一/前缀 B-tree 插入、后绑定和百万队列查询均命中目标索引 |
| 五层重建 | `referral_edges` 可从 `inviter_ids` 重建且逐边一致 |
| 边唯一防线 | 同一 `(descendant_user_id,depth)` 插入第二祖先、并发绑定造成同层竞争时由数据库唯一约束拒绝，事务不残留半条链 |
| 关系统计 | `user_relation_stats` 的直属/五层 NORMAL 成员数与边表重算一致；允许邀请的非 NORMAL 祖先也预建并更新 stats，但不创建 `user_levels`、返佣资格或普通用户权益 |
| 标识扫描 | 热路径无 F 码、字符串关系数组或子树全表扫描 |

安全测试覆盖登录枚举防护、密码 hash、OTP 绑定/重放/恢复、refresh 轮换、会话撤销、CSRF/Origin、权限点、数据范围、KYC/银行卡脱敏、`user_security_audits` 只追加、审计不可删和超级密码不存在。Token 的 `auth_version/family_generation` 必须与 primary 当前值一致；改密、风险封禁或注销只递增 `users.auth_version` 即在 O(1) 内使全部历史 token 失效，不允许扫描会话才能完成安全终态。每用户活动 family 和待返回 issuance 均有数据库硬上限，超过时确定性撤最旧或拒绝新登录；用十倍上限历史数据证明 closure/安全变更的锁行数、耗时不随历史增长。`CompleteLogin`/`RefreshSession` 在 session/issuance 提交后、响应前杀进程；相同 nonce/request hash/device proof 重试必须返回逐字节相同 token pair，不建第二个 session、不撤销 family。ROTATED 旧 token 换 nonce/设备重放只条件撤销对应 family generation；相同请求在密文销毁后返回明确重新登录错误而不误报盗用。

注销还需验证 blocker 注册表完整覆盖失败提现释放、退款回补、冻结返佣释放、持仓结算/返本、ASSIGNED 未使用机器人激活券及既有任务/合伙人领取；合伙人 OPEN→CALCULATING→SEALED→CLAIMABLE 全程不得出现可关闭空窗，closure cutoff 前已归属收益在成熟后仍可领取清退。EXPIRED/FAILED COLLECT 在迟付风险窗或未取得 CONFIRMED_NOT_PAID 证据时持续阻塞，迟付确认与 closure 完成并发只能先入账待清退或先证明未收款，绝不 CLOSED 后静默入账。任一未来 COMMON 来源且无清退能力时不得进入 CLOSING。CLOSING 可做窄用途 KYC/补卡、COMMON 重复清退、EXPERIENCE 显式兑换/放弃和券 VOID；提现仍执行本文条件 TOTP 规则，不建专用人脸。最终 CLOSED 同事务递增 `auth_version` 且不删除用户/关系/账务事实。

在 challenge 提交后、Forge 调用前、调用中、返回后和 finalize 前杀进程：明确未调用/未接受的路径可按同一应用级 `delivery_dedupe_key` 重试；无法证明是否接受的过期 SENDING 必须转 `UNKNOWN` 且不自动重发，用户冷却期后显式创建新 challenge。`PROVIDER_ACCEPTED`/UNKNOWN/过期/消费后按既定时点 crypto-shred，transport 接受不记为 delivered。银行卡核名在提交、调用、响应和 finalize 各点崩溃时，按 `provider_request_key`/lease 重领且不重复建单，旧 lease owner 不能覆盖新结果。

注销完成与充值迟付、新收入、退款释放、出款回调、持仓到期/返本正反并发时，worker 必须先预收齐 business root/freeze/user/asset 集合，再严格按 dedup/event→income rollup root SHARE→finance day fence SHARE（涉及 ledger）→attempt→产品/订单/withdrawal/持仓→返佣/月/settlement→closure prelock→freeze→user gate→asset 的注册 rank 锁定；提现专用人脸锁层不存在。锁内出现集合外 blocker 就回滚扩集，不得从 closure 反向锁 attempt/order、从业务根反向补锁 root/day 或在资产后晚锁业务根。持续 10 分钟无死锁，且 CLOSED 绝不遗留可产生 COMMON 的未终结事实。

人工 `INCOME/EXPENSE`、任务正常领取和 `CompensateUserTask` 分别与注销请求/完成做正反并发：ACTIVE 路径先提交时注销锁内复检看到余额或未来领取；注销先转 CLOSING 时仅 cutoff 前既得领取/来源纠错可成功并同事务推进 blocker，运营赠送失败；CLOSED 后所有钱包 mutation、换键重放和管理员强制参数均失败且账户 version 不变。历史 CLOSED 纠错只生成外部 Finance case 证据，不得重开账号或伪造钱包流水。

安全并发另记录 `UserStateLockKey(type_code,user_id,id)` 轨迹：refresh/logout/改密/OTP 与 closure 完成双向混跑时必须保持 users→credentials→bindings→challenges→session family roots→有界当前 sessions/issuances→KYC→bank→risk/limit→关系/等级/任务/VIP 的全序。KYC 回调与 `ReviewKyc` 必须先锁 user，再按 ID 锁全部当前/候选 case 并原子切换 current；`ReviewBank` 和提现必须同样按 user→current KYC→bank→risk/limit。注入 case→user、bank→KYC、session→user 或 challenge→credential 的反向实现必须稳定触发门禁，而生产实现持续 10 分钟无死锁、无漏撤销会话或双 current KYC。

银行目录测试覆盖未知/下架 bank_code、错币种/用途、缺 provider mapping、同版本重复 code 和版本发布并发；新绑卡拒绝失效目录项，既有提现仍按快照完成。CLOSING 等待期间 KYC/卡失效后，仅 closure-purpose 重新 KYC/窄补卡可用，提现仍执行条件 TOTP，无人脸路径或普通业务权限复活。

| L2 | 50 | 0 | 1 | 0 | 0 |

注册事务先建 L0 聚合行，再以全零输入运行首发规则并以 L1 提交；提交后仍为 L0 属于失败。L3+ 的持仓条件以已发布首发规则为输入，测试不得把它们硬编码在前端或 evaluator 外部；L2 必须同时满足个人活跃值 50 和至少一笔有效 COMMON 持仓。

必测：每档差一个最小单位/刚好/超过、升降级、历史最高不降、规则版本切换、持仓暂停/恢复、关系新增引发五层聚合、并发增减不丢更新、dirty 强制同步刷新。纯 evaluator 在无数据库情况下遍历规则表。

活跃值来源自然键必须独立于客户端幂等键：同一持仓换 100 个键重放仍只有一条 GRANT；到期/取消正反并发最多一条引用原 GRANT 的 REVERSAL，用户及五层祖先聚合最终与源事实重算完全一致。

资格传播构造深度大于同步波预算的合法链和宽团队，令多名成员连续跨过/跌破 qualified 门槛。每个 worker/sync 波只能锁本人和前五层、最多 6 个用户；旧 lease/dirty generation 不能清新变化。目标资金命令从 `level_recalc_queue(relation_path_key,user_id)` 的 B-tree 前缀半开区间发现任意深度潜在影响，预算内可同步排水，预算耗尽返回 `LEVEL_PROPAGATION_PENDING` 而非使用旧等级；一个目标有百万 dirty descendants 时计划仍为 Index Scan + keyset LIMIT N，实际读取不超过 `N+O(1)`，禁止 bitmap/top-N/递归扫描。另装载百万条同时到期 queue，worker 的 `ORDER BY next_run_at,lease_due_at,user_id LIMIT N` 必须命中完全同序 partial B-tree，plan 无 Sort 且 actual rows 不超过 `N+O(1)`。同步排水每波是业务事务前的独立短 Tx，锁轨迹不得同时持有 product/month/day/asset 等资金锁；真正业务 Tx 只用 runtime root、queue `LIMIT 1` 和目标等级行复验 fresh token。Redis 丢失后后台波最终与全量规范重算一致。规则换版另验证 runtime root 的 SEEDING/DRAINING/VERIFYING 全程注册、关系/等级指标写、等级展示与资金资格失败关闭，百万用户 seed/verify 每 Tx 固定 N，缺行/混合版本/错误 proof 不能切 serving，成功只用短事务恢复入口。

规则 fixture 还要让 `current_level` 数值保持不变但 `qualified_level` 先升后降；old flag 必须来自行上历史 `is_qualified/qualified_level_snapshot/rule_version`，new flag 来自 candidate，前五层合格计数精确 -1/+1。审计和 proof 缺任一前后门槛、用新门槛反推 old flag 或队列 generation 不匹配都拒绝切 serving。

构造目标用户 ID 大于/小于/交错于单波本人和前五层祖先；`EnsureLevelFresh` 与 dirty worker 每波都必须先收齐至多 6 个 ID 再升序锁。锁内发现这五层集合变化时只回滚重读该波，禁止追加晚锁或扩成全链闭包；并发刷新持续 10 分钟无死锁、不丢合格计数，过期 lease 可重领。

返佣测试保存来源、层级、基数、结算时等级/比例/规则版本；后续关系/等级变化不得改历史。来源矩阵逐项验证：短剧/机器人日收益为最多五层 DIFFERENTIAL 可用入账；剧集仅以 `paid_common`、一次性 VIP 仅以 `rebate_base_common` 做最多两层 FLAT COMMON 冻结返佣。非 ACTIVE DIFFERENTIAL 候选的 forfeiture 必须 `previous_after=previous_before` 且 `not_granted_amount=0`，后续合格候选继续按旧 previous 计算；FLAT 必须先舍入，ZERO_DIFF/ZERO_ROUNDED 不建 forfeiture，只有 rounded>0 且非 ACTIVE 才保存精确正未授予金额。冻结到期只释放一次，退款前取消 freeze；退款后钱包可安全扣回则 REVERSAL 一次 POSTED，余额不足或账号 CLOSED 则一次 EXTERNAL_RECOVERY 并引用唯一 Finance case，GRANT/REVERSAL 均不覆盖原金额或快照。POSTED 钱包冲正必须进入 Income overview/day/month/year/export/对账；EXTERNAL_RECOVERY 无 asset ledger，不能改变这些用户收益结果，只进入 Finance case 管理统计。

对最小合法来源基数构造 `candidate_diff>0` 但舍入金额为 0：DIFFERENTIAL 必须记录 `ZERO_ROUNDED`、按 entitlement 推进 previous，且不写零额 settlement/freeze/ledger；FLAT 无论候选 ACTIVE 与否都只记录 ZERO_ROUNDED，不建 forfeiture。两种模式都不得把该比例/槽位转给远层，并与 `ZERO_DIFF`、正常正额 GRANT、正额非 ACTIVE FORFEIT 的 trace/hash 可确定性区分。所有返佣/合伙人金额事实保持严格正数。

LEVEL_AGNOSTIC 购买返佣只在规则 rate 行以 `beneficiary_level IS NULL` 表达，并受独立唯一约束；实际 settlement 仍保存受益人当时真实 L0–L7 与等级版本。任何 `UNSPECIFIED=0` 写入 rate、settlement 或其他业务事实都由 API/数据库拒绝。

合伙人对 30%/50%/70%/100% 系数、基础 5% 池、月份边界、第 5 日领取、并发领取唯一和重放逐项验证。每个现金 `Playlet Backing` / `Robot Purchase` 来源只生成一条正额 GRANT，`pool_base_amount` 与当时本金一致；pool fact 的 allocation/trace/hash 与后续冲正、封账和 adjustment 依 06 章守恒，连续 N 天日结仍不新增 pool。

PARTNER 规则非 Jakarta 月初生效、重复 source/tier、tier 门槛非严格递增或权益系数向后下降均发布失败；相邻 tier 系数相等合法。月封账分别在 source staging、逐 adjustment 应用、聚合、验证、标记 SUCCEEDED 和最终发布前注入崩溃；`partner_month_shards(month,calc_version,shard_id)` 不重不漏，每个阶段只按稳定 `beneficiary_hash` 范围和固定 N keyset 读取，cursor/carry/证明与结果同事务，过期租约重领不重复累计。专门让同一受益人的多条 ALLOCATION 使用空 `adjustment_id`，并让批界横跨最后一条 ALLOCATION 与第一条 ADJUSTMENT；全非空 `adjustment_sort_id` keyset 重启后必须不漏不重，nullable row-value 游标实现必须由测试击穿。构造单一热点受益人百万来源及百万 adjustment，再构造 N 行分属 N 个用户的批次，证明任何事务读取/锁行不超过 N + 固定标量 carry，N 条输入总计至多写 `3N+O(1)` 条 application/head/settlement 输出，用户组闭合绝不集中遍历或插入百万行；`EXPLAIN (ANALYZE, BUFFERS)` 命中 hash/cursor 索引且无全月 sort/scan。分别配置 shard_count=0、257 和伪造 shard_id/range，应用与数据库均拒绝；1 和 256 可完成且协调/发布最多锁 256 行。伪造 `processed_shards`、`job_runs`、count/sum/hash 或断裂 cursor/application/head 链均不能封账。确定性代码/证明缺陷时，普通 retry 不得沿坏 cursor 继续；`RestartPartnerMonthGeneration` 必须校验 expected version/contract、活动租约和异人审批，在一个短事务最多 ABANDON 256 旧 shard并创建 256 新 shard。旧 generation 的部分 source/application/head/settlement 永不可见且旧 owner 写 0 行，新 generation 保持同 cutoff/规则/seed/前驱证明并从零重建。`partner_months` 保持可恢复 CALCULATING，迟到 GRANT/adjustment 不得越过各自 cutoff；只有全部唯一分片源/结果证明及 adjustment application 连续性验证通过才短事务 SEALED。相邻两个月同时封账时，后月必须等待前月 SEALED 的 predecessor hash/carry 证明，不能重复应用同一 adjustment；月根未 CLAIMABLE 的请求全部拒绝，进入后 claim 按 root 选中的 calc version 并发仍只入账一次。

合伙人 source keyset 还必须验证生成式 `phase_rank`：ALLOCATION=0、ADJUSTMENT=1，错误 rank/未知 phase 由 DDL 拒绝；测试数据跨越最后一条 ALLOCATION 到第一条 ADJUSTMENT 并崩溃重领，`ORDER BY`/cursor/hash 全部只使用 phase_rank，证明 PostgreSQL 字符串词法顺序不会把 ADJUSTMENT 排在 ALLOCATION 前。首发 tier 门槛严格递增、权益系数仅非递减；Sultan/Envoy 同为 1.00 必须可发布，任何后档系数下降必须失败。

合伙人来源的最小合法 COMMON 基数必须使 5% pool 舍入后为正，否则产品发布失败。构造 pool 为正但某一层 diff 舍入为 0：pool fact 必须在 `decision_trace` 保存 `ZERO_ROUNDED`，`allocation_count/allocation_sum/unallocated_amount/allocation_hash` 只匹配正额行，`decision_trace_hash` 独立匹配完整逐层裁决且 `allocation_sum<=pool_amount`；篡改任一 hash、trace 与 allocation 的 depth/用户/金额映射都不能提交。重放、来源 REVERSAL 和月封账均不得伪造零额 allocation 或把未分配舍入尾差记入用户收益。

- 机器人售价扣款、本金返本/活跃值分别按快照；等级不合格日必须原子写唯一零金额 `SKIPPED_LEVEL` 日裁决、资格/规则快照并推进 settlement cursor，且没有 ledger/返佣/pool。崩溃重试仍只有一行，恢复等级后从首个合格业务日继续，历史 SKIPPED_LEVEL 永不回补。
- 机器人现金商品的 sale/principal/cash limit 为 0 均禁止发布；同一用户对限购 N 的商品并发 N+1 次只成功 N 次，`user_robot_product_stats` 条件占位、holding、容量和扣款同成败。券核销不占现金次数但仍占总容量。停机跨多个结算日后，`Playlet Backing` 和机器人都只从最早 cursor 逐日补齐。
- 两张机器人券并发首持仓最多一张成功；现金购买与券核销正反并发统一按 product→coupon→user，只产生一条 `robot_qualification_consumptions(FIRST_ROBOT_HOLDING)`，最后一份商品容量只生成一个 holding，现金购买仍按规则完成。券分发必须按 code/root→closure prelock→user gate 执行，只有 ACTIVE 可获券；与注销正反并发时只能先 ASSIGNED 并成为 blocker/由 disposition VOID，或先 CLOSING 后拒绝，CLOSED 永无新映射。预读后商品下架/售罄、券换归属/作废/过期均在锁内拒绝且不消费资格；券不返本金、不产生团队返佣/pool。
- 直接伪造 code=A 用户、mapping=B 用户、redemption/holding/disposition=C 用户的组合时，`(code_id,user_id)` 与 `(user_coupon_id,code_id,user_id)` composite FK 必须在数据库拒绝；合法转 ASSIGNED、核销和注销 VOID 全链始终引用同一用户与 code。
- 任务只由真实服务端事实推进；一次性 VIP 只以 `ONE_TIME_VIP_ENTITLEMENT_CREATED` 推进 `PURCHASE_ONE_TIME_VIP`，全仓无 `SUB_VIP`；重复/乱序去重，奖励并发领取一次，客户端无手工进度入口。PROGRESS_CORRECTION 只允许未领取的 IN_PROGRESS/CLAIMABLE，验证 `raw=before+delta>=0`、`after=min(target,raw)` 和 `0<=after<=target`，跨目标时双向切换 IN_PROGRESS/CLAIMABLE；CLAIMED 或已存在 reward claim 必须拒绝。纠正与领取并发先锁同一 user_task，只能一个成功，纠正事实、before/raw/after、进度、状态和审计同 Tx。REWARD_CORRECTION 只有在 CLAIMABLE 且无 claim 时原子创建 compensation/claim/ledger 并转 CLAIMED；任一写点失败全回滚，重放不得出现“已入账但仍 CLAIMABLE”。`CompensateUserTask` 必须引用唯一 reward claim 或稳定业务来源，`task_compensations` 自然键使换 100 个幂等键也只有一条纠错；错来源、超原奖励、同键异义和 CLOSED 用户钱包补偿全部拒绝。
- 任务规则 reward asset 非 COMMON/EXPERIENCE、金额 0/负数/超精度/超上限、舍入为 0 或异步来源漏 registry/root/分片映射时发布失败；user task/claim 的非法快照也被 DDL 拒绝。制造周期结束前已持久化、结束后才被消费的异步事实：64 个 writer root 的 period barrier 未捕获或任一 consumed seq 未到 upper 时不得 EXPIRED，全部 APPLIED/IGNORED 后才可裁决。另让来源事务先取得 root 并分配 seq、暂停在提交前，再并发捕获 cutoff；协调器必须等待它提交/回滚，提交事实被 upper 覆盖且不会被后续 keyset 跳过。批中崩溃、Redis 丢失、旧 lease、回滚序号和重复消费均不越稳定 upper、不漏进度。伪造 APPLIED 的空/错 user_task、rule、user、definition 或 `period_identity` composite FK 必须失败；尤其 ONCE 的原始 period 为 NULL 时仍必须由非空 `ONCE` identity 拒绝错用户/定义/规则拼接。VIP 订单在 cutoff 前创建、支付在 CLOSING 后完成时，任务 `source_persisted_at` 必须仍等于 order.created_at 并被接受；cutoff 后新订单被拒绝。
- VIP 分别退款 ACTIVE、队首/中段 QUEUED 权益，验证后续队列连续前移、每份购买期限不缩短、区间不重叠且 schedule audit 完整；与新购/到期并发仍最多一条 ACTIVE。创建订单先在 `user_vip_stats` 预占，支付履约把 reservation 原子转为 entitlement，明确未支付/过期释放；并发创建第 64 个成功、第 65 个稳定拒绝，任何退款/Ensure/重排最多访问 64 条非终态权益，计数始终等于 reservation + ACTIVE/QUEUED。充值和 VIP 各自每单全生命周期只有一个 REFUND attempt/稳定商户号，UNKNOWN、拒绝、重启或人工重试不得创建第二个渠道退款意图。
- 剧集/VIP 付款人退款时，把一名已收返佣受益人预先关为 CLOSED 或耗尽可追回余额；渠道成功、付款人退款/权益撤销仍必须终态完成。第三方钱包不得在 CLOSED 后 mutation，也不得成为主退款 veto；不足或关闭部分按 `(source_type,source_id,source_component,subject_user_id,direction)` 只创建一条 `finance_recovery_cases`，重复与乱序不得多记债权。管理状态只允许 `OPEN -> IN_REVIEW -> RESOLVED|WAIVED`；另验证只有带唯一权威来源反转事实的内部事务可把未结案转 `CANCELED_BY_SOURCE_REVERSAL`，已 RESOLVED 必须建 registry 指定的反向案，客户端/管理员不能直接取消。旧 version、缺外部处置/反转证据、同键异义、越权和同人豁免审批均失败；成功命令只追加审计，不改钱包/原返佣。新返佣计算在五层每个位置分别注入不合格/CLOSING/CLOSED 候选，断言跳过者不推进 `previous_effective_rate`，后续合格祖先按正常差额公式结算，forfeiture 的规范 trace hash 重跑一致。
- 对 ASSET、EXTERNAL、BOTH 三类 Finance case 分别尝试用错方向、错 basis、错资产/金额、错币种/外币金额和合法 NULL 组拼 settlement；数据库生成的 `value_fingerprint` 与 `(case_id,fingerprint)` composite FK 必须只允许全额完全一致的一行，ASSET/EXTERNAL 不得因 MATCH SIMPLE 的 NULL 跳过校验，同一外部凭据并发仍只解决一案。
- 弹幕保存实际发送语言并覆盖默认回落，敏感命中仅本人可见待审；本人举报拒绝，举报选择隐藏单条/作者时 block 同事务，过滤后 total 与 items 一致。管理限制作者阻止新发并可查询时隐藏既有内容，恢复单条/作者全局状态不删除用户 block。Banner 使用不可变 revision，按语言/区域/平台/app build、`effective_from/effective_to/clickable_from`、priority 和位置上限由服务端决定；响应稳定不可点击原因，点击在 primary 复验 current revision，危险跳转无法发布。

## 9. 主从、缓存与作业恢复

### 9.1 slave 延迟

暂停副本回放，执行充值、购买、绑定、等级更新、任务领取和提现。余额、冻结、资格、幂等、终态、播放授权和读己之写必须从 primary 返回正确结果；允许延迟的列表需标明一致性并最终收敛。

生产数据库角色测试：slave DSN 对 INSERT、UPDATE、DELETE、DDL、`SELECT ... FOR UPDATE` 均被拒绝。

### 9.2 Redis 丢失

丢弃全部提交后信号、清空缓存并让 Redis 短时不可用。等级 dirty、结算 status、购买返佣释放/追偿、支付/出款 `next_run_at`、任务待办、报表导出和通知生成/投递必须由 primary sweep 在 SLA 内恢复，重复执行仍幂等。通知按 `(user_id,dedupe_key)` 唯一，站内信写失败或外围 DEAD 不得回滚/改变来源业务。

### 9.3 作业竞争

至少启动 4 个 worker 并发处理同一批到期对象，验证 `FOR UPDATE SKIP LOCKED` 不重领、不饿死；worker 崩溃后未提交行可重新领取，已提交行按唯一键跳过。

### 9.4 跨日封账屏障

在 Jakarta 23:59 开启资产事务并持有昨日 `finance_business_days FOR SHARE` 到 00:10 之后，OPEN→CLOSING 协调事务的 `FOR UPDATE` 必须等待；事务提交后冻结的 source upper bound 和最终 count/amount/hash 必须包含该流水。反向场景中，协调器先把日置为 CLOSING，携带昨日预计算时间但尚未取得 fence 的 writer 必须整体收到 `BUSINESS_DAY_ROLLED`，以原幂等键和重新采样的今日时间重试；已返回 `provisional=false` 的昨日结果永不变化。尝试让应用锁今日 fence 却插入昨日 `occurred_at/business_date`、显式写 generated date 或绕过 FK 均必须被原语/数据库拒绝。完全没有流水且未预创建 day row 的日期也必须由协调器 Ensure，所有唯一 shard 收敛后生成 `0/0/CANONICAL_EMPTY_HASH` 的 FINALIZED 事实并供月 rollup 使用。

在 `V2-PERF-1` 单日峰值上验证封账严格采用短协调事务、多笔有界构建/验证事务和短发布事务；任何事务不得扫描整日。对 shard 领取、carry group、正代 upsert、cursor/hash 推进和发布逐写点杀进程/注入回滚，过期 generation 重领后结果与规范源 SQL 完全一致且没有重复累计。分别配置 shard_count=0、257、非法 shard_id/范围，应用和 DDL 均拒绝；1 与 256 可完成，协调/发布/restart 最多插入或锁 256 行。缺 shard、重复 shard、错误 generation、cursor 跳跃或任一 source/result count/amount/hash 不等都必须拒绝 FINALIZED。CLOSING 期间日序列只能在一条 primary SQL 的 statement snapshot 内直接按用户/业务日聚合源流水并返回 `provisional=true`；暂停查询并让 dirty worker 推进累计 cursor 后仍不得漏计/重复，最后一片完成也不能提前暴露正代。发布提交后一次切换，月表只消费 day 指针指向的正代。测试同时断言 30 秒应用 deadline、statement/idle timeout、错误连接参数 readiness，以及所有资产路径的锁轨迹都是“事件/幂等→income root→day fence→业务根”，不存在业务根后补锁 root/day row。

空库 bootstrap 必须在一个事务创建唯一 income root、首个 ACTIVE calc 及其完整 segment contract、`business_date=finance_launch_date-1` 的唯一 genesis anchor 和 launch day OPEN 行。分别伪造第二个 anchor、错误日期、非 FINALIZED、`build_generation/shard_count/source_upper` 非 0、非空 calc/policy/vector、空 finalized_at，数据库均拒绝；任何 `asset_ledgers`、`income_day_publications`、`finance_day_shards` 对 anchor 的引用也必须失败。用 launch day 零流水和有流水两组 fixture 完成首日 OPEN→FINALIZED，再完成首个 earning month 的无前驱月代，证明 genesis 只承担首日前驱且不会进入 API、publication、月份 source 或 activation leaf。

### 9.5 计算版本屏障与代次恢复

为 ACTIVE 与 BUILDING/CATCHING_UP/PROVING/VALIDATED candidate 并发写入充值、提现冻解、兑换、退款、收益等全部 COMMON `(biz_type,ledger_kind)`；每一条都必须为两个版本登记 dirty，worker 即使判为 EXCLUDED 也推进连续 `cursor_account_seq`。制造一百万条连续排除流水尾后，下一次处理仍只从上次账户 seq keyset 读取固定 N 行，不得反复扫描旧 tail；策略发布时缺失/重复任一六种 kind 组合、UNKNOWN 类型或错误 amount_source 必须失败。热点账户每批处理 N 条并保存 first/latest/cursor 证明，不能把账户 seq 与全局 ledger ID 比较。

在 candidate baseline 各 shard、转 CATCHING_UP/PROVING、activation leaf/shard 构建、增量领取、日/月 publication、VALIDATED 与 root 激活每个写点并发注册零流水用户、插入新流水和杀进程。构造 1,000 万用户、十年 FINALIZED 日/月覆盖和一个热点 proof shard；每个证明事务只按 keyset 读取 N 行，遗漏任一零账户/用户 stats/day/month leaf、伪造 hash、旧 lease/generation 或 mutation 后未重验都不能 VALIDATED。分别给 `proof_shard_count` 和 activation shard 的 `shard_count/shard_id/hash range` 注入 0、257、缺号、重复、重叠和空洞，应用与 DDL/发布全部拒绝；1 与 256 可完成。Start proof、进入 QUIESCING 和最终激活都必须在 root 锁内用索引 `LIMIT 1` 证明不存在 CLOSING 日；制造任一 CLOSING 日时三者稳定失败、root/代次不变，绝不读取、比较或接管该日任一旧 ACTIVE/candidate shard。无 CLOSING 时激活事务只读取最多 256 条当前 proof shard，不扫描用户、leaf、日期或月份，锁持有时间和读取行数不随用户/历史日增长。旧 ACTIVE 在切换前始终可读，切换后所有 writer 只登记新 ACTIVE，任何 A/B 日代次混读失败。

`RestartFinanceDayGeneration` 对期望 generation/calc/contract/source upper、双人审批和命令 hash 做正反测试。在旧 shard 活租约、非 CLOSING、期望不符或任一证明不完整时不得改变 day；分别在旧代 ABANDON、generation 递增、新 publication/shard 创建和审计后故障，事务回滚必须完整。成功后旧 owner 的任意迟到 batch/validate/finalize 更新影响 0 行，新代沿用完全相同 cutoff、calc 与契约并可续跑至发布。RESTATED candidate 不得接管任何 CLOSING 日；须等待该日按原 calc 完成 FINALIZED，之后以不可变 publication 进入 segment/scope 证明。

RESTATED segment 合同做连续两次重述：先以 I1 替换 ACTIVE 时间线中的 `[d1,d3)`，再以 I2 替换 I1 内 `[d2,d3)`；I2 必须得到一次扁平化的全时间线，`[d1,d2)` 仍引用 I1、`[d2,d3)` 引用 I2，其余继承原 EVENT_TIME 段，运行时不得递归读取 base。对 segment_no 断号、首尾非无穷、相邻 gap/overlap、模式列形状错误、封存后增删改、`segment_contract_hash` 篡改逐项验证，任一情况都不得进入 CATCHING_UP/PROVING。

RESTATED scope 使用独立 ledger/freeze 双 cutoff fixture：冻结 opening 在 ledger upper 以内且 terminal 也在 upper 以内时为终结；opening 在 upper 以内而 terminal ID 超过 upper 时按 cutoff ACTIVE；freeze ID 超 freeze upper 或 opening ledger 超 ledger upper 时不属于成员。分别构造区间左 crossing、右 crossing、区间内仍 ACTIVE、完整闭合四类生命周期，只有 `left_crossing_count=right_crossing_count=0` 且 source/result vectors、scope contract 全等的代次可选中。scope shard 数 0/257、非法 shard/range、漏片/重复、旧 lease/generation、错误 selected generation/proof hash/calc、篡改双 cutoff或 partition hash 均必须被 DDL/CAS/延迟约束拒绝；崩溃重领后规范成员、count/amount/hash 与独立重扫完全一致。

进入 PROVING 和最终 `ActivateIncomeRestatement` 必须同时复验不可变 `segment_contract_hash`、`scope_contract_hash`、所选 VALIDATED scope generation/proof、zero-crossing，以及 USER_ACCOUNT/DAY_PUBLICATION/MONTH_PUBLICATION 三类 activation proof。任一 scope/segment 或 activation proof 在验证后发生 mutation，candidate 必须回到 PROVING；旧证明、错 hash、非零 crossing、缺任一时间段/日/月/账户 leaf 或任一 CLOSING 日都使激活事务影响 0 行，ACTIVE 指针保持原值。

月发布另做独立硬门禁：在同一 user/date/category 下制造两个 `stream_kind/policy_version_id` 日行，跨批 source cursor 必须按完整六元 `(user_partition_hash,user_id,category,stream_kind,business_date,policy_version_id)` 逐行覆盖，月 amount/count/hash 与规范 SQL 完全一致。`EXPLAIN` 必须显示一个 predecessor carry 与最多 31 个 selected DAY 索引分支的 `Merge Append + global LIMIT N`，即每批 `N+O(32)`，不能先全月 sort/hash/scan。分别配置 month generation/shard 的 shard_count=0、257、非法 shard_id、缺号、重复、范围重叠/空洞，应用与 DDL/发布均拒绝；1 与 256 可完成，协调/发布最多插入或锁 256 行。更高 current 构建、FAILED 或 ABANDONED 时旧 selected generation 继续可见；自动换代只允许不同 `calculator_build_id` 且 source contract/hash 完全相同，旧 owner 的任意迟到写影响 0 行。

| 收益月发布/百分位 | 月源最多 31 路 Merge Append 且每批固定 N；百万样本的 INPUT/RANK/两类 VALIDATE 都走登记索引，单事务耗时不随历史月数增长 |

每个目标保存：完整 SQL（脱敏参数）、表统计、索引 DDL、`EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS)`、执行次数、p50/p95/p99、锁等待、CPU/IO/WAL 和结果行数。禁止仅展示 ORM 总耗时或一次最佳值。

团队查询计划不得出现对 `users` 的递归子树扫描或无条件全表扫描；等级重算必须使用边表/聚合和 dirty partial index。

Schema exact-key 反例必须在真实 PostgreSQL migration test 中执行：把 A 用户 freeze/closure/VIP order、A 授权 request、A partner adjustment 或 A payment order 与 B 用户/另一资产/correlation/attempt/head/entitlement 子行拼接，所有组合均由 exact composite FK 拒绝；合法同主体组合可提交。迁移还必须实际创建并 introspect 父 `UNIQUE` 与子列顺序，不能以两个单列 FK、应用 CHECK 或触发器说明代替。补偿 shape 另覆盖 Backing/Robot net>0 必有且仅有一条同用户 COMMON/INCOME 等额 ledger，net=0/机器人激活券必须无 ledger，任何零额流水都失败。

payout 成功 fixture 必须原子得到 `status=SUCCEEDED/financial_status=SUCCESS_CONFIRMED`、空 lease/next_run，并退出活动 partial index；权威反转只把 financial status 置 REVERSED，操作状态仍 SUCCEEDED。DDL/迁移测试证明 `status=SUCCEEDED <=> financial_status IN (SUCCESS_CONFIRMED,SUCCESS_REVERSED)`，并逐条接受 FAILED/NOT_ACCEPTED/STOPPED 的合法证据纠正、拒绝 STOPPED_BEFORE_SUBMIT 纠正和无权威证据的跨边。ARRIVED active set 才允许 CANONICAL/DUPLICATE 与 `settled_by_attempt_id`，FAILED/REJECTED/CANCELED active set 只能 LATE_AFTER_LOCAL_FAILURE 且 settled_by 为空。`finance_case_source_reversals.outcome` 只接受 `CANCELED_UNSETTLED|NO_EFFECT_WAIVED|COUNTER_CASE_CREATED` 三个字面量及对应 counter-case NULL shape；PAYMENT/PAYOUT/RECONCILIATION 三种 trigger ID 必须判别 XOR 并真实引用能消除原差异的证据。迟到成功应收已结后又反转，只能创建 `PAYOUT_LATE_SUCCESS_REVERSED_AFTER_RECOVERY` PAYABLE，不能冒充 duplicate reason。

百分位链替换时，把前月 selected publication 从 VALIDATED 推为 SUPERSEDED，并发布新代：旧后继的六列不可变 predecessor composite FK 必须继续可读、不 cascade、不因父 status 变化失败；dependency sweep 只把 head 标脏并构建新后继。任何错 window/month/calc/generation/proof 或以 NULL 截断非首月前驱都必须拒绝。

## 12. API、权限与安全测试

- Proto lint、breaking、HTTP 路由冲突、OpenAPI、枚举/数据库约束比对和权限注解完整性；枚举 Gateway/OpenAPI 路由证明没有动态路径参数，GET selector 只在 query，POST selector 只在 Proto body。
- 遍历全部非零业务错误码，验证 Forge `errkit` code name、Encoder/Decoder、gRPC code 与 HTTP status 全映射；故意返回 SQL/供应商裸错误时对外只有安全 INTERNAL，对内 cause 可追踪且已脱敏，Domain 依赖图无 Forge。
- Forge `message` 的 SMS、SMTP Email、SendGrid Email 各跑成功、明确未接受、明确永久失败和不确定超时；provider registry 必须让每个 Manager 仅含一个 sender，配置试图把两个可兼容 sender 装进同一 Manager 时启动失败。只有明确未接受可进入 RETRY_WAIT；超时、响应丢失和返回后未 finalize 在无可靠幂等/查单证据时必须转 UNKNOWN，既不自动重发也不切换 provider。捕获应用日志、Forge 调用 context、持久化错误和 API 错误，均不得出现完整手机号、邮箱、OTP、模板敏感参数或 Forge 返回的 recipient-bearing 原始错误。
- 自助 API 注入其他 user_id、越权读取、IDOR、管理员权限组合和全链数据范围。
- 回调签名、固定 domain 路由、nonce/时间窗、原始体、证书轮换、重放和日志脱敏。
- SQL 注入、XSS 弹幕/Banner、危险 URL、上传内容类型、敏感日志和导出过期。
- 限流、验证码轰炸、登录撞库、refresh 重放和高风险操作近期认证。
- 后台从 INVITED 接受单次邀请、设置密码、确认 MFA 后才能 ACTIVE；密码正确但未过 MFA 无 token。Accept invite、CompleteAdminLogin、RefreshAdminSession 分别在 issuance/session 提交后响应前杀进程；相同 nonce/hash/device proof 必须返回逐字节相同 activation context/token pair，不建第二 session、不误判盗用，换 nonce/设备重放已轮换 refresh 才撤销 family。Admin logout、禁用、凭据/MFA 恢复均使旧 session version 立即失效且不影响 public session；invite 重放/过期、OTP 尝试耗尽、登录枚举和十倍活动会话上限逐项覆盖。bootstrap 激活只经部署 secret/bounded local command，仓库、迁移、镜像和日志扫描不得出现凭据/token。
- `admin_action_approvals` 的创建人/审批人分离、目标/请求 hash 绑定、一次性消费；普通 `user_id` 不能填入 admin actor/reviewer 字段。
- 单用户创建百万历史通知后，`MarkAllNotificationsRead` 只锁/更新一条 `notification_roots` 并把 `read_through_seq` 推至锁内 last；并发后插入的更大 seq 保持未读，单条 read、全读与 `ArchiveNotification` 乱序结果一致，归档只写本人一行，执行计划/写行数不随历史量增长。
- `report_exports` 只接受注册类型/过滤，不接受 SQL；创建和下载分别检查当前权限/数据范围，权限撤销、文件过期或 SHA-256 不符均拒绝并审计。
- 同一 domain 首版并发发布、未来区间交叠和边界相接时，`rule_domains` 行锁 + exclusion constraint 只允许合法半开区间；开放尾发布后继必须在一个事务把前版 `expires_at: NULL -> successor.effective_at` 并插入后继，故障时二者一起回滚，hash 不变。对尚未生效尾版本执行 `ReplaceScheduledRuleVersion`，分别在防重、domain、前驱、目标、审批、RETIRED、恢复前驱/插入替代版和审计后杀事务：每次都必须保持旧时间线完整；成功只能得到“前驱重新开放”或“同一生效点的已复核替代版”，不得出现空洞、重叠或双候选。已有任一事实引用后替换必须失败，RETIRED 历史仍能按 ID 回放。用客户端时间伪造昨日/本月初的 backdated successor、回滚发布和中段插版全部失败；INCOME_ACCOUNTING 只能选严格未来 Jakarta 日界，PARTNER 只能选严格未来 Jakarta 月界，历史变化只能创建 RESTATED calc version。deposit/VIP 商品 code 的开放尾执行同型测试。
- 同一 rollup_name 两个 VALIDATED 版本并发激活只能一个 ACTIVE；失败版本进入 FAILED，切换事务失败时旧 ACTIVE 不丢失。
- 收益策略在统计区间中途切版时，EVENT_TIME 结果按发生时点命中且响应返回完整有序 `policy_version_ids`；仅发布新策略不改历史。RESTATED 必须绑定新 calc version/策略/区间，重建校验并原子激活，不能让单一 policy 字段误解释跨版本累计值。
- 同一 task definition 的并发首版、重复 version、交叠区间被数据库拒绝；相接区间按 `period_start` 恰选一个版本，后继发布只原子收口开放尾且不改已生成任务快照。
- 导出在领取后、生成中、对象写后、finalize 前逐点杀 worker；过期 RUNNING 由新 owner/generation 重领，旧 generation 不能 finalize，临时对象不可下载且最终只有一个 SUCCEEDED 文件。
