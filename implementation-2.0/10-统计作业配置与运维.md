# 10 统计、作业、配置与运维

> 状态：2.0 实施约束。本篇定义收益口径、统计投影、配置发布、领域待办、缓存、主从路由和生产运维。资产、订单、持仓等领域事实仍以各自文档为准。

## 1. 目标与非目标

### 1.1 目标

1. APP、后台、账单、导出和对账使用同一份收益定义，同一个金额能够追到具体 `asset_ledgers`。
2. 热接口不重复扫描用户全历史流水；日/月汇总、累计快照和事实尾巴形成可重建、可校验的读模型。
3. 所有作业都可重入、可追赶、可并行、可观测；Redis 唤醒丢失或 `workerd` 重启不会丢工作。
4. 资金、资格和权益配置有不可变版本、复核、定时生效、审计和安全回滚，既有订单/持仓/结算不被新配置追溯改写。
5. `database.default` 与 `database.slave` 的路由可由接口名和指标审计，复制延迟不会进入资金或状态迁移决策。
6. `migrate` 能从空 PostgreSQL Schema 创建完整 2.0 结构；线上服务不自动建表。

### 1.2 非目标

- 不搬运 1.0 统计快照，不回放 1.0 流水，不提供历史迁移、双写、CDC、新旧表切换或割接开关。
- 不把 Redis、日志平台、从库、搜索索引或报表文件当成业务真源。
- 不建通用 Outbox，也不建可以承载任意 JSON 业务命令的通用任务队列。
- 不承诺外部供应商 exactly-once；只承诺本库业务事实、幂等请求和可恢复重试的可证明一致性。
- 不把展示 heat、运营手填数或客户端上报数混进真实财务、用户、订单和播放指标。

## 2. 时间、期间与一致性契约

### 2.1 核心对象

| 对象 | 作用 | 不变量 |
| --- | --- | --- |
| `BusinessClock` | 生成业务日/周/月/年半开区间 | 全系统固定 `Asia/Jakarta`，周一 00:00 起算，同一请求只固定一次 `as_of` |
| 收益策略/计算版本 | 解释何种 COMMON 流水以哪个 delta 进入哪个分类 | 已发布策略不可改；在线读取只使用 root 指向的 ACTIVE 版本 |
| 日/月/年度投影 | 加速已确认收益的期间查询 | 可重建，不创造资产；年度是同口径月/当前尾巴组合而非另一套分类 |
| 百分位 publication | 固定样本、窗口、as_of 和计算版本的展示排名 | 只读 VALIDATED generation；不影响余额、等级、奖励或资格 |
| 领域待办/作业租约 | 从业务状态重建后台工作 | `status/dirty_at/next_run_at` 是真源，Redis 只加速 |
| 配置发布 | 类型化规则的草稿、复核、生效与回滚 | 版本不可变、时间线连续、发布与审计同事务 |
| 报表导出/通知 | 可恢复的派生文件与用户消息 | 来源业务终态不依赖外围成功；均不是通用 Outbox |

### 2.2 `BusinessClock`

全系统只允许一个业务时钟实现：

| 项目 | 固定约束 |
| --- | --- |
| IANA 时区 | `Asia/Jakarta` |
| 业务日 | 当地 `[00:00, next 00:00)` |
| 业务周 | 周一 00:00 开始，下一周周一 00:00 结束 |
| 业务月/年 | 当地自然月/自然年，全部左闭右开 |
| 数据库存储 | 时间点为 `timestamptz`，业务日期为 `date` |
| API 时间点 | Unix 秒；响应同时返回业务区间和 `timezone` |
| 作业时间 | 每次执行固定一个 `as_of`，同一批次不得反复取系统当前时间 |

- 服务器进程所在操作系统时区不参与业务计算；不得用 `time.Local`、字符串截日期或固定 `+07:00` 代替 IANA 时区。
- 进程启动时加载时区数据库并验证 `Asia/Jakarta`；数据库连接建立后验证会话时区和时间函数。失败时 readiness 不通过。
- SQL 范围只写 `occurred_at >= start_at AND occurred_at < end_at`，不使用右端也包含的 `BETWEEN`。
- 财务流水的 `occurred_at` 是服务端确认该资产变化的业务发生时间；客户端时间和供应商事件时间另存来源事实，不允许用它们回填或倒写已封账期间。

### 2.3 响应一致性

统计响应必须携带：`timezone`、`start_at`、`end_at`、`as_of`、`generated_at`、`provisional`、有序去重的 `policy_version_ids` 和 `calc_version_id`。其语义为：

- `provisional=false`：指定区间已封账，且使用返回的策略集合/计算版本；同版本内结果不可原地覆盖。即使只有一个策略版本也返回单元素集合，不切换字段形态。
- `provisional=true`：包含尚未封账的当前期间或 primary tail；结果精确到 `as_of`，但后续合法新事实会继续变化。
- 相同分页/导出请求必须固定同一个 `as_of` 和版本，不能翻页时跨版本。
- 需要绝对精确的当前余额、累计收益和本期收益走 `default`；允许短暂陈旧的已封账历史和大报表才走命名 Replica Query。

## 3. 收益口径唯一真源

### 3.1 事实来源和确认金额

收益统计只读取 `asset_ledgers`，并同时满足：

1. `asset_type = COMMON`；`EXPERIENCE` 无论 `kind` 或名称多像奖励，都不进入可提现收益。
2. 生效策略必须精确命中一条 `(biz_type,ledger_kind)` 登记；“属于哪类收益”和“从哪个 delta 桶取数”由该登记共同决定，禁止从 `ref_type`、接口名或正负号猜测。
3. 每条登记同时保存 confirmed 口径 `included/category/amount_source=AVAILABLE_DELTA|FROZEN_DELTA|ZERO` 和 pending 口径 `pending_effect=NONE|ADD|RELEASE|CANCEL/pending_amount_source=ZERO|ABS_FROZEN_DELTA`。confirmed 规范函数固定为 `AVAILABLE_DELTA -> available_delta`、`FROZEN_DELTA -> frozen_delta`、`ZERO -> 0`；included 行不得选择 ZERO，excluded 行必须选择 ZERO。pending NONE 必须选择 ZERO，其他 pending effect 必须选择 ABS_FROZEN_DELTA 并返回三个互斥的正数效果之一。正数确认收益，合法冲正为负数，不能只加正数而忽略更正。
4. 冻结收益在 `INCOME_FROZEN` 原始业务日登记为 `EXCLUDED/ZERO + ADD/ABS_FROZEN_DELTA`，只增加 `pending_income`。到期 `UNFREEZE` 必须保留原收益 `biz_type/ref`，登记为 `INCLUDED/AVAILABLE_DELTA + RELEASE/ABS_FROZEN_DELTA`，在释放业务日确认一次并减少 pending。释放前 `SETTLE_FROZEN` 登记为 `EXCLUDED/ZERO + CANCEL/ABS_FROZEN_DELTA`，只取消 pending；对应返佣 REVERSAL 终态必须是 CANCELED_FROZEN，不能成为 confirmed reversal。普通冻结/解冻/最终扣除等非收益 biz type 全部显式登记 `EXCLUDED/ZERO + NONE/ZERO`；释放后的受控 `EXPENSE` 以负 `available_delta` 冲减原分类。发布校验逐个 biz type/kind 证明 confirmed 与 pending 两套字段，不能只凭 kind 猜测。
5. `occurred_at` 决定业务期间；`created_at` 只用于入库顺序、审计和排障。

`ledger_kind` 只参与选择版本化登记，不能单独决定业务分类。`total_income` 只表达已经释放/可用的已确认收益，不包含仍冻结部分；钱包 `available` 表达全部可用资金，ACTIVE 收益冻结另展示为 `pending_income`。三者字段名和帮助文案不得互相冒充。

### 3.2 首发收入分类

具体 Proto 数值由枚举登记表生成，本文固定业务语义：

| 统计分类 | 可进入白名单的 `biz_type` | 说明 |
| --- | --- | --- |
| 短剧直接收益 | `Playlet Backing` 日结直接收益 | 参与用户自己的 COMMON 收益 |
| 短剧团队返佣 | `Playlet Backing` 产生的五层返佣 | 受益人为祖先用户 |
| 机器人直接收益 | 普通/券持仓按规则确认的直接收益 | 券持仓只允许直接收益 |
| 机器人团队返佣 | 普通 COMMON 机器人持仓产生的五层返佣 | 券持仓不得产生 |
| 合伙人分红 | 已结算且已领取/释放的合伙人分红；`PARTNER_CLOSURE_ADJUSTMENT_REVERSAL` | 资格快照与收益月份在来源结算表；注销清退负调整以受控 EXPENSE 冲减同一分类 |
| 剧集购买返佣 | 下级单次购买剧集产生的返佣 | 必须引用购买事实 |
| 一次性 VIP 返佣 | 下级购买一次性 VIP 产生的返佣 | 不存在自动续订收入类型 |
| 任务奖励 | 产品明确保留且以 COMMON 发放的任务奖励 | EXPERIENCE 任务奖励仍排除 |
| 人工收益补偿 | 经专门审批、明确标记为收益补偿的流水 | 普通资产纠偏不自动算收益 |

下列项目明确不算收益：充值本金、充值赠送、本金返还、资产兑换、提现申请/解冻/退回、退款回补、普通人工调账、体验资产、活动/抽奖/祈福/团队房奖励、自动续订、VIP 邀请活动，以及 2.0 已删除的任何旧类型。

首发 registry 对 `biz_type=PARTNER_CLOSURE_ADJUSTMENT_REVERSAL` 固定：只有 `ledger_kind=EXPENSE` 登记为 `INCLUDED/category=PARTNER_DIVIDEND/amount_source=AVAILABLE_DELTA + pending NONE/ZERO`，且业务流水的 available delta 必须为负；其余五种 ledger kind 均显式 `EXCLUDED/ZERO + NONE/ZERO` 且领域代码不得生成。该行与 06 章注销 disposition 共用种子和 CI 枚举，不允许查询层临时补 CASE。

### 3.3 策略与防漂移

- `rule_versions(domain='INCOME_ACCOUNTING')` 是收益策略版本；`income_policy_items` 对每个 `(biz_type,ledger_kind)` 唯一登记统计分类、confirmed 的 `included/amount_source`、pending 的 `pending_effect/pending_amount_source`、展示顺序和说明。同一收入 `biz_type` 的 confirmed/pending 行必须映射到同一分类。
- 首发策略只允许在 Jakarta 业务日边界生效。发布校验要求所有收入型 `biz_type` 恰好出现一次、所有排除项显式登记理由、不存在未知枚举。任何存在 ADD/RELEASE/CANCEL 生命周期的 `biz_type` 在普通 EVENT_TIME 后继版本中必须保持同一 category；若要重分类，必须用 RESTATED 对该冻结生命周期的 open/terminal 全部事实一起重述，或引入新的 biz_type，禁止 open 在 X 类、release/cancel 在 Y 类。
- 结算/奖励代码新增 `biz_type` 时，CI 同时检查 Proto、数据库 CHECK/六种 kind 完整登记、收益策略种子、索引和口径测试；漏任一处不能合并。
- 已发布策略不可修改。将既有 `biz_type` 从排除改为计入属于财务口径变更，必须新建策略版本、选择仅未来生效或显式重建新 `calc_version`，不能静默覆盖历史。
- 默认 `EVENT_TIME` 模式按每条流水 `occurred_at` 命中的唯一策略版本分类；未来发布只影响其生效后的事实，当前 ACTIVE calc version 可继续累计，并把新版本加入有序 `policy_version_set`。若要重述历史，必须创建 `RESTATED` calc version，显式固定重述策略和半开区间，完整重建/对账/审批后原子激活；仅发布策略绝不自动改历史结果。
- APP、后台、导出、对账不各自维护 `IN (...)`；它们调用同一个 Income Query/Policy 组件。

## 4. 统计与运维数据表

### 4.0 表层级与唯一真源

本篇沿用并细化数据模型总览中的正式统计投影：`income_hourly_rollups`、`income_daily_rollups`、`income_monthly_rollups`、`operation_daily_rollups` 和 `rollup_reconciliations`。为实现“累计快照 + 实时尾巴”、小时曲线、有界日/月发布和无竞态版本切换，本篇补充 `rollup_roots`、`income_calc_dirty`、`user_income_stats`、日/月 publication 与 shards、百分位 publication/input、`rollup_versions`、`rollup_watermarks` 等控制元数据；它们与正式投影的关系是：

| 层级 | 表 | 是否业务真源 |
| --- | --- | --- |
| 不可变资金事实 | `asset_ledgers` 及各领域结算事实 | 是；收益金额最终从这里证明 |
| 正式查询投影 | `income_hourly_rollups`、`income_daily_rollups`、`income_monthly_rollups`、`operation_daily_rollups` | 否；均可从事实重建 |
| 投影校验事实 | `rollup_reconciliations` | 是审计事实，但不创造收益/运营金额 |
| 发布屏障 / 账务日证明 | `rollup_roots`、`finance_business_days`、`income_day_publications`、`finance_day_shards` | root 串行化版本激活和日封账；day 阻止倒写；按 calc 的 publication 与 shard 证明决定可见性，`job_runs` 不可替代 |
| 投影加速/控制元数据 | `income_calc_dirty`、`user_income_stats`、`rollup_versions`、`rollup_watermarks` | 否；丢失时只影响性能/重建进度，不改变业务事实 |

`user_income_stats` 加速累计与来源拆分，日/月账单仍由对应 rollup 提供；它们不能彼此回填成资金事实。每次对账直接以 `asset_ledgers` 为源分别校验累计、日表和月表，防止两个派生表“互相证明”。上述补充表必须先纳入数据模型总览和空库 migration 评审，才允许实现，不能成为文档外的影子 Schema。

### 4.1 配置与审计

| 表 | 关键字段/约束 | 责任 |
| --- | --- | --- |
| `rule_domains` | `code,status,version,updated_at`；code 唯一 | 每个规则域永远存在的发布锁根；首版发布也有行可锁 |
| `rule_versions` | `id, domain, version, status, effective_at, expires_at, content_hash, created_by_admin_id, reviewed_by_admin_id, published_at, created_at`；`(domain, version)` 唯一；PUBLISHED 区间按 domain exclusion 不重叠 | 所有领域不可变规则版本头及生效区间；内容落领域结构化子表 |
| `income_policy_items` | `rule_version_id,biz_type,ledger_kind,category,included,amount_source,pending_effect,pending_amount_source,display_order,description`；`(rule_version_id,biz_type,ledger_kind)` 唯一；confirmed/pending 字段交叉 CHECK | 收益口径的可查询明细；共享 registry 同时返回 confirmed 与三个 pending 正向效果，查询中不得散落 kind/符号分支 |
| `income_calc_policy_segments` | `calc_version_id,segment_no,valid_from/valid_until nullable,application_mode=EVENT_TIME_TIMELINE|FIXED_RESTATED,rule_domain nullable,fixed_policy_version_id nullable,source_calc_version_id nullable,segment_hash`；同 calc 区间 exclusion、序号唯一 | 每 calc 扁平全时间线；EVENT_TIME 动态选事件时规则，首发 FIXED 段恰好一个完整 policy version，事实选择无歧义 |
| `income_calc_segment_policy_versions` | 不在首发 Schema 建表 | 多 fixed policy 若未来需要，必须先 ADR 设计互斥子时间段/selector；禁止用“有序集合”暗示取首/末 |
| `income_restatement_scope_proofs` | `calc_version_id,current_generation,selected_generation,shard_count,source_upper_ledger_id,source_upper_freeze_id,scope_contract_hash,status=BUILDING|VALIDATED|FAILED,source/result vectors,left/right_crossing_count/hash,proof_hash,validated_at`；calc 唯一 | 稳定 scope head；双 cutoff与谓词是不可变 contract，selected/proof是异步结果；最多256 shard完整验证且 crossing=0 才能被 calc 引用 |
| `income_restatement_scope_proof_shards` | `calc_version_id,scope_generation,shard_id,shard_count,hash_start/hash_end,status=PENDING|RUNNING|VALIDATING|SUCCEEDED|FAILED,build_cursor,validation_cursor,source/result vectors,left/right crossing vectors,lease_owner/until/generation,next_run_at`；代次/shard 唯一 | 按 `asset_freezes.scope_partition_hash,id` 固定 N 构建与复验；游标、items、vector 同事务，崩溃/旧 owner 可恢复 fencing |
| `income_restatement_scope_items` | `calc_version_id,scope_generation,freeze_id,classification=INSIDE|OUTSIDE|CROSS_LEFT|CROSS_RIGHT,lifecycle_hash,built_at`；版本/代次/freeze 唯一 | 可重建的逐生命周期判定；验证阶段重扫规范事实与该结果集合，不靠单次无界聚合 |
| `config_releases` | `id, domain, rule_version_id, action, expected_version, status, reason, ticket_no, actor_admin_id, request_id, created_at` | 草稿复核、发布、退休和回滚发布事实 |
| `admin_audit_logs` | `actor_admin_id, permission, action, target_type/id, request_id, idem_key, reason, ticket_no, before/after_redacted, result, ip, user_agent, created_at`；只追加 | 人工操作的唯一审计入口 |

秘密、密码、私钥和供应商凭据不进入规则结构化子表；只保存 secret manager 引用。`content_hash` 基于不可变业务头（domain/version/effective_at 等，明确排除 status、开放尾 `expires_at` 和发布审计时间）及全部结构化子表的规范化内容计算，用于复核和防止审批后被替换；后继发布收口 `expires_at` 不改变已复核 hash。

### 4.2 收益投影

文中 `source_vector/result_vector` 是 DDL 生成器展开的固定强类型列组，不是 JSON：`confirmed_count/amount/hash`、`pending_add_count/amount/hash`、`pending_release_count/amount/hash`、`pending_cancel_count/amount/hash`；月级再增加 `pending_opening_count/amount/hash` 和 `pending_closing_count/amount/hash`。规范 hash 协议覆盖分量名称、顺序、category、规则版本和事实键，发布必须逐分量比较，禁止只比较净和后让 ADD 与 CANCEL 互相抵消。

所有 ledger cutoff 共用规范零锚点 `CANONICAL_EMPTY_LEDGER_UPPER=0`：`asset_ledgers.id` 必须大于 0，day、RESTATED baseline 和 cutover 的 source upper 均非负；索引取不到任何 COMMON 行时使用 0，而不是 NULL。空源的 count/amount/hash 固定为 `0/0/CANONICAL_EMPTY_HASH`。

`rollup_versions` 另建 `UNIQUE(rollup_name,id)`；root 的 `(rollup_name,active_calc_version_id)`、`(rollup_name,candidate_calc_version_id)`、`(rollup_name,cutover_candidate_id)` 都以相同列序 composite FK 指向它。延迟约束触发器要求 active 指针只指 ACTIVE、candidate 只指 BUILDING/CATCHING_UP/PROVING/VALIDATED、二者不同；NORMAL 时 cutover candidate 为空，QUIESCING 时 `cutover_candidate_id=candidate_calc_version_id`。版本状态与 root 指针只可在同一事务合法跃迁，不能把 income root 指到其他 rollup、FAILED 或已 RETIRED 版本。

genesis 由空库初始化事务创建且只允许一条 partial unique `finance_business_days((true)) WHERE is_genesis_anchor`。CHECK 把它与普通日完全分支：anchor 必须 `business_date=rollup_roots.finance_launch_date-1`（跨表关系由延迟约束触发器核对）、`status=FINALIZED/build_generation=0/shard_count=0/source_upper=0/calc_version_id IS NULL/policy_version_set=CANONICAL_EMPTY_SET/source_vector=result_vector=CANONICAL_EMPTY_VECTOR/closing_started_at IS NULL/finalized_at IS NOT NULL`；普通日必须 `is_genesis_anchor=false` 并沿用 1..256 shard/发布合同。`asset_ledgers`、`income_day_publications`、`finance_day_shards` 的写入约束触发器均要求目标 day 非 anchor；所有查询视图固定过滤 anchor。不得用普通 publication 伪造 genesis，也不得用 NULL 绕过普通 FINALIZED 合同。

`by_category/pending_by_category` 只保存小而稳定的分类金额映射，明细展示仍查日汇总或流水。它们不是独立口径：任意时点必须满足 `total_income = Σ by_category`、`pending_income = Σ pending_by_category >= 0`，并分别等于全历史规范 confirmed 净额与尚未终结的收益 freeze 金额，由同一对账作业校验；提现等普通冻结永不进入 pending 映射。

热索引至少包括：

- `income_calc_dirty(calc_version_id,dirty_at,user_id)` 和 `(lease_until,calc_version_id,user_id) WHERE lease_owner IS NOT NULL`；`user_income_stats.dirty_at` 只作诊断兼容，不再是版本切换的唯一待办。
- `income_daily_rollups(user_id,business_date DESC,calc_version_id,close_generation,category,policy_version_id)`；日封账构建用 `(business_date,calc_version_id,close_generation,user_id,category,policy_version_id)`；月构建必须有 `(business_date,calc_version_id,close_generation,user_partition_hash,user_id,category,policy_version_id)`，供最多 31 个选中日代次做索引 `Merge Append + global LIMIT N`。月 source cursor、排序和 hash 都使用完整唯一 tuple `(user_partition_hash,user_id,category,stream_kind,business_date,policy_version_id)`；DAY 分支把 stream kind 作为常量投影，禁止省略任何列后跳行，也禁止全月 sort/scan。
- `income_hourly_rollups(user_id,business_date,business_hour,calc_version_id,close_generation,category)`；日封账构建键顺序与 daily 相同并包含 hour。
- `income_day_publications(calc_version_id,status,business_date)`；`finance_day_shards(status,next_run_at,business_date,calc_version_id,shard_id)` 与 `(lease_until,business_date,calc_version_id,shard_id) WHERE status IN ('RUNNING','VALIDATING')`。
- `rollup_activation_leaves(calc_version_id,proof_generation,partition_hash,object_type,object_key)`；`rollup_activation_shards(calc_version_id,proof_generation,status,shard_id)` 和过期租约局部索引。

`job_runs` 记录“某次执行怎样”，`job_failures` 记录“哪个对象还没完成”；二者都不得保存可执行的任意业务 payload。真正欠下的工作仍在所属业务表的 `status/dirty_at/next_run_at`。

运营指标必须列出事实来源和去重键。例如注册读 `users.created_at`，成功充值读 `deposit_orders` 终态，真实播放读已授权 `play_events`；展示 heat 只能作为独立指标，不能冒充播放量。

`report_exports.filters_snapshot` 使用按 `report_type` 注册的强类型 schema，固定 `as_of/policy_version_set/calc_version`，禁止任意 SQL、任意表名或任意 JSON 作业 payload。文件写对象存储，数据库只保存不可枚举 object key、SHA-256、行数、过期时间和下载审计关联；生成/下载时都重新检查当前管理员仍拥有 `report.export/report.download` 及数据范围，权限已撤销时失败关闭。

### 4.4 站内通知与外部投递

`notification_roots` 按 `user_id` 一行保存 `last_user_seq/read_through_seq/version/updated_at`，满足 `0<=read_through_seq<=last_user_seq`。创建通知先在既定用户层顺序锁 root、令 `last_user_seq+=1`，再把新值固化为 `notifications.user_seq`；`notifications` 保存 `id/notification_no/user_id/user_seq/type/source_type/source_id/dedupe_key/template_version/title_snapshot/body_snapshot/read_at/archived_at/created_at`，`notification_no NOT NULL UNIQUE`、`UNIQUE(user_id,user_seq)`、`UNIQUE(user_id,dedupe_key)`。有效未读定义为 `user_seq > root.read_through_seq AND read_at IS NULL AND archived_at IS NULL`，索引 `(user_id,user_seq DESC) WHERE read_at IS NULL AND archived_at IS NULL`；单条已读只写该行，全读不批量改历史行。来源类型/ID 必须来自注册白名单，正文快照不能包含密码、OTP、完整卡号或任意业务 payload。

`notification_deliveries` 保存一条具体通知到具体 `channel=EMAIL/SMS/PUSH` 的尝试状态，字段含 `notification_id/channel/provider/delivery_dedupe_key/status=PENDING/SENDING/RETRY_WAIT/PROVIDER_ACCEPTED/UNKNOWN/DEAD/attempt_count/next_run_at/lease_owner/lease_until/lease_generation/last_error_code/provider_accepted_at`；`UNIQUE(notification_id,channel)`，待办部分索引覆盖 `status/next_run_at` 和过期租约。领取、续租和 finalize 都匹配 owner + generation + 未过期 lease。它只表达可从 notification/source 重建的外围提醒，绝不被支付、权益或资金命令当作成功条件；`PROVIDER_ACCEPTED` 不是已送达证明，`UNKNOWN` 表示没有证据可安全重发。Forge `message` 负责 EMAIL/SMS，PUSH 若启用则使用独立适配器，不能伪装成 Forge channel。

## 5. 状态机

### 5.1 配置版本

```text
DRAFT -> REVIEWED -> PUBLISHED -> RETIRED
```

- 资金/权益配置必须由不同主体完成创建/修改与复核；发布者不能绕过 `REVIEWED`。
- `PUBLISHED` 表示已发布且按半开区间等待/进入生效。普通 PUBLISH/SUPERSEDE/ROLLBACK 的 `effective_at` 必须不早于事务内数据库时间，并满足 domain 的下一允许边界；不允许把已过去时点补进正式时间线。
- 已发布内容、hash、版本号和 `effective_at` 不可改。发布时间线尾部的后继版本时，允许在同一 `rule_domains` 锁事务中把开放尾前版的 `expires_at` 从 `NULL` 一次性改为后继 `effective_at`；该 `SUPERSEDE` 元数据变化与后继插入、审计同成败，禁止中段插版、覆盖或单独收口。
- 回滚不是把旧行改回 `PUBLISHED`，而是复制已验证内容为更高版本，重新复核/发布，并记录 `ROLLBACK_RELEASE`。
- 历史口径变化只通过显式 `RESTATED` calc version 表达，不修改规则时间线，也不能借“回滚”绕过禁止倒填生效时间。
- 已产生业务事实的版本只能 `RETIRED`，不能删除。
- 已发布但尚未生效的尾版本不得通过通用退役命令单独退出。唯一入口 `ReplaceScheduledRuleVersion` 在锁定 `rule_domains`、前驱、目标和命令防重后校验：目标仍是时间线尾、`effective_at > database now()`、没有任何业务/投影引用且 `expected_version/request_hash` 匹配；随后只能在一个事务内执行两种完整变换之一：`RESTORE_PREDECESSOR` 将前驱 `expires_at` 恢复为 `NULL` 并把目标置 RETIRED，或 `REPLACE_SAME_BOUNDARY` 把目标置 RETIRED 并在完全相同 `effective_at` 发布一条已 REVIEWED 的新版本。审批消费、时间线变换、domain version 和审计同成败，任一写点失败仍保留原连续时间线。
- `RETIRED` 只表示不再被事件时间选择器用于新事实，不代表不可读；已落事实、导出、审计与重算继续按 `rule_version_id` 读取不可变头和结构化子表。已有引用的版本不可物理删除，也不可使用 scheduled replacement。

### 5.2 投影计算版本

```text
BUILDING -> CATCHING_UP -> PROVING -> VALIDATED -> ACTIVE -> RETIRED
    |             |          |    ^       |
    |             |          |    +-------+  (新事实：VALIDATED -> PROVING)
    +-------------+----------+----------> FAILED
```

- 在线查询每种 rollup 只读取 `rollup_roots.active_calc_version_id` 指向的一个版本；不能按 `MAX(version)` 或状态查询猜指针。
- 每个 calc version 都有一套扁平、全覆盖的口径 segments。初始版本以 `[-infinity,+infinity)` 的 `EVENT_TIME_TIMELINE(rule_domain=INCOME_ACCOUNTING)` 一段起步；它不枚举未来 policy ID，而是在事实 `occurred_at` 上选择无重叠的不可变规则版本，所以未来发布无需修改 calc contract，`policy_version_set` 只是已观察版本的 append-only 审计集合。创建 RESTATED 时，以当时 ACTIVE 为 base复制扁平 segments，把 `[from,to)` 替换为 `FIXED_RESTATED(fixed_policy_version_id)`；2.0 只接受一个完整 policy version，不接受无 selector 的多版本集合。CHECK 要求 EVENT_TIME 只有 rule domain且 fixed ID空，FIXED反之。exclusion/触发器要求首尾无穷、相邻无缝、序号连续。Create 事务一次写全并封存 segments；应用角色无 UPDATE/DELETE/后续 INSERT 权限，约束触发器禁止离开 BUILDING 后改变行数/hash。每个 baseline/dirty/day/month/proof batch 都匹配原 `segment_contract_hash`，篡改或不一致影响0行并令构建失败。运行时不递归 base，因此 I2保留I1，未来 EVENT_TIME 段仍采用届时规则。
- RESTATED 区间必须 `from<to`、两端为 Jakarta 00:00，`to` 不晚于当前 OPEN 日起点。Create 在持 root UPDATE、等待既有 COMMON writer 后同时固定 `source_upper_ledger_id` 与当前最大 income-freeze ID（无则0），把区间、双 cutoff、`asset_type=COMMON AND open_kind=INCOME_FROZEN`、opening/terminal as-of规则及 hash协议写入 `scope_contract_hash`；该字段不是异步 proof。规范成员仅含 `freeze.id<=freeze_upper` 且其唯一 opening ledger `id<=ledger_upper`；terminal只有唯一 terminal ledger存在且 `id<=ledger_upper` 才视为已终结，否则按 cutoff时 ACTIVE。新 writer只能得到更大 ledger/freeze ID，不能改变集合；build/validate都用同双 cutoff。open/terminal跨边界或区间内仍 ACTIVE计 crossing。短 combine后才写 selected scope generation/proof hash；CATCHING_UP→PROVING必须 composite引用 VALIDATED、zero-crossing head并复验 scope/segment contract。ADD 与 RELEASE/CANCEL必须全部重述或全部继承。
- 创建重建时先用短事务锁 root，确认没有 candidate，把新 `calc_version_id` 登记为 `candidate_calc_version_id` 并置 BUILDING，同时冻结初始 source cutoff；然后才允许任何全量 shard开始。自该提交起，所有 COMMON 流水 writer 在 root SHARE 锁内同时为 ACTIVE 和任一非终态 candidate upsert `income_calc_dirty(reason_mask|=LEDGER_APPENDED)`，无论该类型在当前版本中计入或排除，因此不存在“先扫完用户、后挂 candidate”而漏掉中间事实的窗口。upsert 若旧 mask 不含 LEDGER_APPENDED，则首笔流水把 `first_account_seq/latest_account_seq` 都设为本次 seq；否则用 `LEAST(old_first,new_seq)/GREATEST(old_latest,new_seq)`，最后按位合并 reason，绝不能对 ACCOUNT_CREATED 的 0 cursor 直接 LEAST。BUILDING candidate 的 dirty 只积累、不得被增量 worker领取；baseline builder只写到冻结 cutoff，完整 baseline 后才转 CATCHING_UP。注册零流水 COMMON 账户在 BUILDING/CATCHING_UP 只登记 `ACCOUNT_CREATED,first=latest=0` 和账户源集合，不写不存在的 proof leaf；CATCHING_UP worker 对 ACCOUNT_CREATED 先从 primary 验证账户并 upsert 零额 `user_income_stats(cursor_account_seq=0)`，即使没有 ledger也可清 dirty。worker 清创建 dirty 与并发首笔 ledger 使用 row lease/generation + reason/seq CAS；若新 ledger 已合并，旧 worker 不能清掉 LEDGER_APPENDED。
- CATCHING_UP 完成首轮日/月/累计和 dirty 追赶后，在短 root 事务递增 `proof_generation`、固定 `proof_shard_count<=256`、创建全套 DIRTY activation shards 并转 PROVING。此后注册或候选 stats、日/月 publication 变化才针对当前 proof generation upsert相应 USER_ACCOUNT/DAY_PUBLICATION/MONTH_PUBLICATION leaf、把对应 shard 的 `mutation_generation` 加一并置 DIRTY；proof worker 分批枚举独立源集合与候选投影并验证，只有 generation 未变化才写 `validated_generation=mutation_generation`。因此 pre-PROVING 不会写入未来/旧代 leaf，PROVING 后也不会让遗漏对象伪装成完整。
- 全部固定 shard VALIDATED、四分量 source/result 证明一致且 candidate dirty 为空时，短事务转 VALIDATED，并在首次成功时写不可回退的 `proof_validated_once_at`；仍保留 candidate 指针并继续接收 writer dirty，后续写会把 candidate 退回 PROVING并使相应 proof shard DIRTY。任一时刻最多一个 candidate；失败/放弃先清 root candidate 和 cutover token，再转 FAILED（`failure_reason=ABANDONED_BY_ADMIN` 表达人工放弃，不新增 rollup-version ABANDONED 枚举）。
- 激活使用 6.4 的数据库维护屏障而不是等待自然静默。获批命令只接受曾完整 VALIDATED（`proof_validated_once_at` 非空）且当前为 VALIDATED/因后续写退回 PROVING 的 candidate；在 root UPDATE 内要求无 CLOSING 日，并用有界 `LIMIT threshold+1` 检查 dirty 用户和 DIRTY shard 分别不超过压测固化的 `CUTOVER_MAX_DIRTY_USERS/CUTOVER_MAX_DIRTY_SHARDS`，超限不改变 root。通过后写 QUIESCING token；随后所有 COMMON writer 在任何业务事实前可重试失败。专用 primary worker用可接管 root lease 在无新写窗口排空有限 backlog、重验 proof 并原子切 ACTIVE。`INCOME_CUTOVER_SLO`、两个 backlog 常量和 worker 容量在 `V2-PERF-1` 固定，超 SLA 保持挡写并 P0 告警，只能由获批 Abandon 清屏障；不得让从未完成一次证明的 BUILDING/初次 PROVING 版本接管全站写入口。
- `FAILED` 版本保留运行记录后可清理其纯派生行；不得影响当前 ACTIVE 结果。

### 5.3 领域待办与运行记录

业务对象标准状态：

```text
PENDING/READY -> PROCESSING -> SUCCEEDED
       ^              |
       |              +-> RETRY_WAIT --(next_run_at)--> PENDING
       |              +-> BLOCKED --(人工修复/审计)----+
       +--------------(租约过期恢复)-------------------+
```

脏标型对象使用 `CLEAN -> DIRTY -> CLEAN`，不强行增加业务 status。`dirty_at` 保留最早未处理时间；worker 只在确认已覆盖该时间之前的事实后清除。

`job_runs` 自身使用 `RUNNING -> SUCCEEDED | FAILED | CANCELED`。它是观察记录，不是领取业务对象的真源；删除或丢失一条运行记录不能导致业务工作永久消失。

`rollup_reconciliations` 使用 `OPEN -> ACKNOWLEDGED -> RESOLVED`；仅误报可在双人复核后 `IGNORED`，且必须保留理由。非零财务差异不得因重跑而物理删除。

### 5.4 报表导出

```text
PENDING -> RUNNING -> SUCCEEDED -> EXPIRED
             |
             +-----> FAILED --显式重试--> PENDING
             +--lease 过期--> RUNNING（换 owner/generation 重领）
```

SUCCEEDED 必须有 `object_key/file_sha256/row_count/finished_at/expires_at`；其他状态不得返回下载地址。`RUNNING AND lease_until<now()` 可由 primary 原子换 owner、增加 `lease_generation/attempt_count` 重领，旧 generation 永远不能 finalize。索引同时覆盖 `(status,next_run_at,id)` 和 `(lease_until,id) WHERE status='RUNNING'`。EXPIRED 只撤销下载并按保留策略删除派生文件，不删除 `report_exports` 和下载审计。

### 5.5 通知状态

```text
站内信：UNREAD -> READ
          |        |
          +-------> ARCHIVED

投递：PENDING -> SENDING -> PROVIDER_ACCEPTED
                       |\-> RETRY_WAIT --到期--> PENDING（仅已证明未接受）
                       |\-> UNKNOWN（超时/响应丢失/调用后未 finalize；终态，不自动重发）
                       \--> DEAD（确定不可重试或明确失败超过上限）
```

标记已读/归档只允许本人按旧状态条件推进，重复调用返回原终态。过期 `SENDING` 只有在 provider profile 提供可靠幂等/查单证据时才允许查询并收敛；否则 primary sweep 条件转 `UNKNOWN`，不得因复用应用级 `delivery_dedupe_key` 就再次发送。`PROVIDER_ACCEPTED` 后不再发送且不解释为 delivered；UNKNOWN/DEAD 都不回滚站内信或来源业务。

`ArchiveNotification` 使用本人 token、`notification_no` 与命令幂等键，在 primary 条件设置单行 `archived_at`；未读或已读都可归档，已归档同语义重放返回原结果。归档不倒退 `notification_roots.read_through_seq`，也不影响其他通知。

### 5.6 百分位 publication

```text
BUILDING(INPUT -> INPUT_VALIDATE -> RANK -> RANK_VALIDATE) --证明通过--> VALIDATED
          |                                                       |--同窗口新代发布--> SUPERSEDED
          +--不可恢复契约错误------------------------------------> ABANDONED
```

每个窗口/as_of/calc 有一条稳定 `income_percentile_heads`。同一 as_of 可重建更高 generation，旧 selected VALIDATED 继续服务到新 generation 的短发布事务；该事务锁 head 与同窗口新旧代，复验新代全部证明及依赖 hash 后原子执行旧 `VALIDATED -> SUPERSEDED`、新 `BUILDING -> VALIDATED` 并切换 `selected_publication_id/selected_proof_hash`，任何失败都保留旧指针可见。partial unique 和 head 外键共同保证至多一个 selected VALIDATED。BUILDING/SUPERSEDED/ABANDONED 行和部分用户结果永不可见。

依赖不是一次性触发：primary sweep 分批比较每个 head 当前 selected publication 保存的 `current_month_publication_hash/predecessor_proof_hash` 与月 head、前月百分位 head 的当前 selected proof。发现不一致时条件设置 `dirty_at/dirty_reason`，从该窗口最早脏月开始顺序重建；月份 M 只有在 M-1 新代已 VALIDATED 且 head 已切换后才能固定新前驱，M 发布后再使 M+1 的比较自然失配并继续传播，直至当前月。月 publication 换 selected、过去月份重述或前驱换代即使 Redis 信号全丢也会被该 sweep 收敛；构建期间整条旧链继续以 `stale=true` 可读，绝不把新旧前驱拼接。`dependency_hash` 规范覆盖样本协议、人口 upper、前驱 ID/proof 和当前月 selected hash，验证与发布都重新计算。

publication 失败不影响收益金额，只令 `GetIncomePercentile` 返回 head 当前 selected 的最近有效月度快照及其 `as_of/stale=true`，或在从未成功、样本不足时返回 null 和稳定原因。每个 window/calc/as_of 只保留当前与前一个已成功 publication 的 input/rank 行和 1 个 BUILDING generation；更旧 SUPERSEDED/ABANDONED 大表行在新版本稳定 7 天后按 user_id 每批 N 删除，publication 头、proof、dependency hash、版本和清理审计永久保留。删除是纯派生保留策略，不改变当前可见代或收益事实。

## 6. 主流程与事务边界

### 6.1 收益事实写入

1. 顶层 Use Case 在事务外从本地缓存取得候选规则版本；不访问外部网络。
2. 在 `database.default` 开启一次事务，重新验证生效版本、业务资格和金额。凡可能写入任意 `asset_ledgers`，先锁 `rollup_roots('income') FOR SHARE`；COMMON writer 还从 token 读取 ACTIVE 与可空 candidate calc ID并保持到提交。这是 rank 40，必须早于 day fence，不能用当前“是否计入收益”作为是否加锁的分支。
3. 对所有会写 `asset_ledgers` 的命令，事务内重新采样服务端确认时点 `occurred_at`，随后调用 `AcquireFinanceDayFence(tx,occurred_at)`；该原语由 PostgreSQL 执行与 `asset_ledgers.business_date` generated column 完全相同的 Jakarta 日期表达式，Ensure 唯一 day row 后以 `SELECT ... FOR SHARE` 确认 OPEN，并把共享锁保持到业务事务提交。若日期已封账，返回可重试 `BUSINESS_DAY_ROLLED`，顶层用原幂等键重开事务并重新采样当前时点，不能倒写旧日。
4. 锁住来源业务根和全部业务裁决聚合后，按固定顺序锁 `user_assets` 并完成资产变动；不得在取得资产锁后补锁等级、资格或额度行。
5. 每一笔 COMMON 流水，不论当前策略把其 `(biz_type,ledger_kind)` 判为“计入”还是“排除”，都必须在资产层之后为 root token 中的 ACTIVE 和可空 candidate 分别 upsert `income_calc_dirty(user_id,calc_version_id)`，并用这些流水 `account_seq` 的最小/最大值更新 `first_account_seq=LEAST(...)`、`latest_account_seq=GREATEST(...)`；可同时更新 `user_income_stats.dirty_at` 作为观测字段。worker 按该计算版本的共享 registry 一次取得 confirmed amount、pending_added、pending_released、pending_canceled 四个结果，但两类都推进连续 `cursor_account_seq`，因此不会在账户尾部留下永久 gap，未来 RESTATED 也能重新解释历史排除项。策略发布门禁要求每个可产生 COMMON 流水的 `(biz_type,ledger_kind)` 在每个版本中恰有一个显式 confirmed+pending 条目，未知组合 fail closed。事实、流水、dirty 和幂等结果仍在一个事务；writer 不得在未持 root SHARE 时缓存 candidate 列表。
6. 事务提交后才尝试 Redis 唤醒和缓存失效；发送失败不改变入账成功结果。

资产写和 ACTIVE/candidate 收益置脏必须由同一个顶层 Use Case 编排并有静态/集成测试覆盖。禁止“先入账，提交后再尽力写 dirty”，否则 Redis 丢失或版本切换时无法恢复。

### 6.2 用户收益增量 rollup

每个用户游标使用资产账户锁内分配的 `account_seq`，避免 PostgreSQL 全局 sequence 分配与事务提交顺序不同造成跳行，并强制每批有界：

1. `workerd` 在一个短 `default` 事务中按 `(calc_version_id,dirty_at,user_id)` 用 `FOR UPDATE SKIP LOCKED` 领取 ACTIVE/CATCHING_UP/PROVING/VALIDATED calc 的一批 `income_calc_dirty`，BUILDING candidate 明确排除；只写 `lease_owner/lease_until/lease_generation`，立即提交，领取时不同时获取 root、day 或资产锁。
2. 对每个用户/calc 先从 primary 按 `(user_id,COMMON,account_seq)` 索引无锁预读 `cursor_account_seq < account_seq <= dirty.latest_account_seq` 的最多 N 条，固定本批 `batch_upper_account_seq` 并只收集这 N 条涉及的 `business_date`。真正的独立 `default` 事务先取得 `rollup_roots('income') FOR SHARE` 并确认该 calc 仍为 ACTIVE 或状态至少 CATCHING_UP 的 candidate，再按日期升序锁这些 day；这是 rank 40→50，不能在 asset/stats 后补锁。
3. 随后锁 `(user_id,COMMON)` 的 `user_assets`，再按固定 type 顺序锁对应 `income_calc_dirty` 与 `user_income_stats`；锁内仍只重读 `cursor_account_seq < account_seq <= batch_upper_account_seq` 的最多 N 条并推进到 batch upper。若日期集合变化，整事务回滚并扩集，绝不晚锁 day row。热点用户积压由多笔事务消化，单笔不追到 dirty 最新端；所有 COMMON writer 同样先持 root/day fence、再锁资产/投影。
4. EVENT_TIME 按 `occurred_at/business_date` 命中的唯一策略，RESTATED 按 calc version 固定的策略/区间分类。共享 registry 对每条流水同时产出 confirmed 与 pending 三效果；只有状态仍为 OPEN 的日期才条件 upsert `close_generation=0` 的 `confirmed_amount/pending_added/pending_released/pending_canceled`，CLOSING/FINALIZED 的权威正代由日封账从源流水构建，普通 worker 不再写该日。无论日期状态如何，用户累计 `total_income/by_category/pending_income/pending_by_category` 都按尚未覆盖事实推进，并合并有序 `policy_version_set`/hash 和 cursor；若 pending 将为负，作为 P0 数据不一致整体回滚，不能 clamp 为 0。
5. 每批把 stats cursor 推到 `batch_upper_account_seq`，并把 dirty `first_account_seq` 条件推进到下一序号；只有租约/generation 仍归当前 worker且 cursor 已覆盖锁内最新 `latest_account_seq` 时才删除 dirty。处理期间 writer 提高 latest 或旧 owner 迟到时条件删除影响 0 行，下一轮继续。0 代条件 upsert 影响 0 行时必须确认 day 已进入 CLOSING/FINALIZED，否则按并发异常回滚。
6. 提交后记录信号延迟；进程在任何一步崩溃，租约到期后可重领。唯一键和 cursor 使重复执行不重复累计。

不使用“全局 `MAX(asset_ledgers.id)` 就代表此前全部事务已提交”的假设。累计 cursor 只走账户锁内连续的 `account_seq`；日封账的全局 ID upper 只有在 root 排他锁已等待全部 writer 提交后才冻结。

### 6.3 精确读取：汇总 + primary tail

累计收益使用 primary 上的一条 SQL/CTE，在同一 statement snapshot 读取 `total_income/by_category/pending_income/pending_by_category/cursor_account_seq/policy_version_set` 并以该行 cursor 汇总 COMMON 事实尾巴；不得用两个 READ COMMITTED 语句在中间允许 worker 提交，也不得另扫 `asset_freezes` 猜收益 pending。该查询按 ACTIVE calc version 的 EVENT_TIME/RESTATED 契约计算：

```text
canonical_income_amount = CASE policy.amount_source
  WHEN AVAILABLE_DELTA THEN ledger.available_delta
  WHEN FROZEN_DELTA    THEN ledger.frozen_delta
  WHEN ZERO            THEN 0
END
canonical_pending_amount = CASE policy.pending_amount_source
  WHEN ABS_FROZEN_DELTA THEN abs(ledger.frozen_delta)
  WHEN ZERO             THEN 0
END
pending_added    = CASE policy.pending_effect WHEN ADD     THEN canonical_pending_amount ELSE 0 END
pending_released = CASE policy.pending_effect WHEN RELEASE THEN canonical_pending_amount ELSE 0 END
pending_canceled = CASE policy.pending_effect WHEN CANCEL  THEN canonical_pending_amount ELSE 0 END
exact_total = user_income_stats.total_income + SUM(eligible_tail.canonical_income_amount)
exact_pending = user_income_stats.pending_income
  + SUM(tail.pending_added - tail.pending_released - tail.pending_canceled)
```

这段逻辑由一个版本化 registry join/SQL function 返回，不允许 overview、账单、rollup、导出或对账分别写 `CASE ledger_kind`。函数还校验三种 pending 效果均为非负且单行至多命中一种，最终 exact pending 也必须非负；任何未登记组合直接报错，不按 0 静默吞掉。

- 同一共享 SQL/registry 同时供增量 worker、小时/日/月/年构建、exact tail、导出和对账计算 `canonical_income_amount`；禁止任一消费者另写 CASE。组件同时计算 today/week/month/year/total 和分类，所有过滤都来自 calc version 的策略应用契约；响应 `policy_version_ids` 是快照集合与 tail 命中集合的有序并集。
- 没有快照行时 cursor 视为 0，结果仍正确，只是首次查询较慢；空库上线无需历史回填或读写切换。
- 汇总更新不删除源流水，所以读取旧快照 + 旧 cursor + 全尾巴仍精确；不能只读 `total_income` 裸列。
- 当前期间、累计值和写后回读不从 replica 拼接；从库只服务已封账的版本化历史。日序列对 OPEN/CLOSING 日不使用累计 cursor，也不把“0 代一次查询 + tail 另一次查询”拼接，而是在 primary 用一条 SQL 按 `(user_id,business_date)` 直接聚合源流水并返回 statement `as_of/provisional=true`；专用索引保证范围有界。对 FINALIZED 日必须先读 `rollup_roots.active_calc_version_id`，再 join 同 calc 的 VALIDATED `income_day_publications.selected_generation`，绝不读 day 首次封账版本、0 代或正在构建的正代来猜当前口径。

#### 6.3.1 年度汇总与超过用户百分比

`GetAnnualIncomeSummary(year)` 使用 BusinessClock 生成自然年半开区间，返回 12 个固定月份槽位、分类和年度合计。完整历史年只读取 root ACTIVE calc 下已 VALIDATED 的月投影；包含当前月时在 primary 用一条固定 `as_of` 的 SQL/CTE 合并已封账月份、当月已封账日和 OPEN/CLOSING 日源流水，返回 `provisional=true`。年度合计必须等于同响应 12 月槽位之和，分类、冲正、策略集合与概览/月账单共用规范 SQL，不能维护独立“年度类型映射”。

`GetIncomeSeries` 不接受任意 SQL 粒度，只允许固定组合：`window=DAY,granularity=HOUR` 返回 24 个 Jakarta 小时槽；`WEEK|MONTH + DAY` 返回自然日槽；`CUMULATIVE + MONTH` 从空库首个合法收益月返回月槽并使用 `offset + limit + total`，单次最多 120 点。FINALIZED 日内曲线读取同 calc/publication generation 的 `income_hourly_rollups`；OPEN/CLOSING 当日由 primary 在一个 statement snapshot 直接聚合源流水。周/月读日投影，累计读月投影；缺槽显式补 0，所有点之和等于同 `as_of`/范围的卡片总额。非法组合、跨日 HOUR、超过 120 点或客户端自定义 timezone 均拒绝。

月账单返回两组守恒字段：

```text
closing_confirmed_total = opening_confirmed_total + confirmed_income + confirmed_reversals
closing_pending = opening_pending + pending_added - pending_released - pending_canceled
```

`confirmed_income/reversals` 按分类只来自规范收益策略返回的 confirmed amount；已释放返佣能从钱包全额扣回时，POSTED REVERSAL 对应的 EXPENSE 流水进入 reversals。`CANCELED_FROZEN` 只由其 `SETTLE_FROZEN` 流水产生 `pending_canceled`，绝不进入 confirmed reversal。EXTERNAL_RECOVERY REVERSAL 没有钱包流水，是 Finance 余额外应收，不能改变用户 overview、日/月/年序列、账单、导出或收益对账；它只进入 Finance case 管理报表，案件 RESOLVED 或 RECEIVABLE 的 WAIVED 也不补造历史用户收益流水。`pending_added/released/canceled` 只能取同一个 registry 返回的 ADD/RELEASE/CANCEL 正数效果，不能在查询中另按 kind 推断。opening/closing pending 必须分别等于区间边界时 ACTIVE 收益冻结的可重放和；提现/普通资产冻结不混入。当前月用 primary 固定 as_of 并标 provisional，已封账月从版本化投影/冻结动作事实读取。月账单、概览 pending、冻结列表和资产流水的同一 freeze 必须双向追溯。

“超过用户百分比”只是一份每个自然月封账后异步发布的展示快照，更新时间和样本协议固定如下：

1. `window_type=YEAR` 使用当年 `[Jan 1, month_end next day)`，`CUMULATIVE` 使用空库首个业务日至同一月末；`as_of_month_end` 必须是已 FINALIZED 自然月，固定 ACTIVE calc、月 publication hash 和有序 policy set。当前未封账月不进入排名，API 明示月末 as_of。
2. 首发样本协议是代码/DDL/测试共同登记的不可配置常量 `INCOME_PERCENTILE_SAMPLE_V1`：包含 `type=NORMAL` 且 `registered_at < window_end` 的全部普通用户，不按当前 ACTIVE/CLOSING/CLOSED 状态变化，明确排除后台、系统、机器人和测试主体；`min_sample_count=100`。因此同一 cutoff 可重放，不需要伪造历史账号状态；改变样本语义必须另立 ADR 和 V2 协议常量，不能借普通配置热改。
3. 创建 publication 的短事务预收集同 window 的前月与当前 `income_percentile_heads`，按 `(calc_version_id,window_type,as_of_month_end)` 升序锁定（首月只有当前），再持 `user_population_roots('normal_users') FOR UPDATE`，等待已经取得 SHARE 的注册提交，捕获 `registration_seq_upper` 后立即结束该短事务；新注册取得更大 seq，不会进入本 publication。它同时固定前月 head 当前 selected publication ID 与 proof hash（首月为空），以及当前月 selected rollup hash，计算不可变 `dependency_hash`。前驱为 dirty、没有 selected 或 proof 不匹配时只延期，不跨越前驱创建新链；worker 构建阶段不再持人口锁。
4. INPUT worker 按 `users(registration_seq)` partial unique 索引每次最多 N 行枚举规范成员。NORMAL 用户 sequence 由数据库单调序列分配，允许回滚留下 gap 但禁止复用、NULL 或重复；gap 不代表成员。每个用户金额只读取“前月同窗口 input 的一个索引点 + 当前月固定分类数的 `income_monthly_rollups`”，YEAR 在一月从 0 重置，CUMULATIVE 从上月延续；新 calc 的重建也严格逐月追赶。因此单事务读取/锁/写为 `O(N * 固定分类数)`，与用户历史年数无关，不逐用户扫描日/月全历史。input 行、cursor、member/value count/amount/hash 同事务推进。
5. INPUT_VALIDATE 使用独立 validator 和独立 cursor，从规范 `users(registration_seq<=upper,registered_at<window_end,type=NORMAL)`、前月 input 和当月 rollup 重新逐行计算，不读取 input 作为成员真源；逐行比较 user/registration_seq/amount/input_hash，并独立组合 member/value 证明。漏用户、多用户、错金额、cursor 跳跃、前驱或月 hash 不同都不能进入 RANK。
6. RANK 按 input 的 `(income_amount,user_id)` 索引每次最多 N 行，持久保存 tie carry；`strictly_lower_count` 只在金额变化时推进，因此同金额同排名。RANK_VALIDATE 再以独立 cursor/tie carry 重算每个 tie group，逐行比较 `income_amount/strictly_lower_count/sample_count/exceeded_ratio/decision_hash`，并把全部排名字段纳入独立 rank decision hash；全员 rank=0 等伪结果无法通过。
7. `exceeded_ratio = strictly_lower_count / sample_count`，API 用十进制定点比率字符串返回；样本 `<100`、本人不在样本、没有 VALIDATED publication 时返回 null 及 `INSUFFICIENT_SAMPLE/NOT_IN_SAMPLE/NOT_READY`，不得伪造 0 或随机百分比。只有 input build/validate 与 rank build/validate 四套游标都到尾、成员/金额/rank count/hash 两两相等，且锁内重读前驱 proof、当月 selected hash 与 `dependency_hash` 仍一致，短发布事务才生成 `proof_hash`、切 head 指针并置新代 VALIDATED。

百分位不会参与钱包、返佣、等级、任务、推荐或权限，也不与实时 tail 拼接。Redis 只缓存 `publication_id + user_id` 的展示结果；缓存丢失回查数据库，绝不能影响任何收益金额。

### 6.4 日/月封账与重建

日封账采用“短协调事务 + 可恢复分片 + 短发布事务”，禁止在一笔事务里扫描并覆盖整天数据：

1. 日 rollup 持续增量更新 OPEN 日的 0 代。空库初始化事务在创建 income root/首个 ACTIVE calc 时固定不可变 `finance_launch_date/first_earning_month`，同时创建 `business_date=launch_date-1` 的唯一 `is_genesis_anchor=true,FINALIZED,source_upper=0,source/result=CANONICAL_EMPTY` 行和 launch day OPEN 行；anchor 不允许 ledger 外键、publication/月表/API读取，也不能另建第二条。每日 Jakarta 00:10，协调器先做 readiness fast-fail；正式短事务按 root UPDATE → 前一业务日 → 目标 day 顺序锁定。除 launch day 的前驱恰为 genesis anchor 外，前一日必须是普通 FINALIZED；因此首日可启动且任一时刻仍最多一个 CLOSING 日。root 排他锁等待收益 writer SHARE，超时只回滚重试。
2. 锁取得后，从 root 固定 ACTIVE `calc_version_id`，从 primary 固定策略集合、`INCOME_HASH_V1` 协议、分片数，并用 `(SELECT ... WHERE asset_type='COMMON' ORDER BY id DESC LIMIT 1)` 的结果 `COALESCE(...,CANONICAL_EMPTY_LEDGER_UPPER=0)` 固定此刻 source upper；应用常量与 DDL 共同强制 `FINANCE_DAY_SHARD_COUNT_MAX=256`，只有 `1<=shard_count<=256` 才令 `build_generation += 1`，原子执行 `OPEN -> CLOSING`、创建该 day/calc 的完整 shard 集。shard 把 64 位 `user_partition_hash` 空间切成连续无空洞范围。协调事务最多插入 256 行，不扫描流水、不生成日表；以后旧日 writer 在 root→day 锁序中读到 CLOSING 后整体失败。
3. worker 用短事务领取当前 publication `current_generation` 下的 PENDING/可重试 FAILED/租约过期 RUNNING shard并递增 `lease_generation`。每个构建事务锁 publication `FOR SHARE` 和一条 shard，校验 publication=BUILDING、current generation、owner/generation/lease，只从 `(business_date,asset_type,user_partition_hash,user_id,id)` 索引按自身 hash 范围及真实 keyset 读取 `id<=source_upper_ledger_id` 的最多 N 条 COMMON 流水。分类在取出 N 行后按该 calc 的 EVENT_TIME/RESTATED 契约执行；不能先全日 hash、join、filter 或 sort 再 LIMIT。
4. 源序固定为 `(user_partition_hash,user_id,ledger_id)`；carry 保存一个跨批用户的小型 category map，其中每类同时累计 confirmed、pending added/released/canceled、count/first/last ID/hash。用户组闭合时才以本正 generation 确定性 upsert 各 category 日行。日行、source cursor/carry 和累计证明同事务提交；热点用户可跨任意批次，但每笔事务仍只读 N 条索引记录。
5. 源扫描结束后 shard 转 VALIDATING。验证也以固定 N keyset 扫描本 generation 日行，重算 confirmed 与三种 pending effect 的 result count/amount/hash 并同事务推进 validation cursor。只有四套 source/result 证明相等、cursor 到尾且 owner/generation 仍匹配才转 SUCCEEDED；否则 FAILED 并保留错误。`job_runs`、内存计数和缓存进度不能替代证明。
6. 普通日发布事务依次锁 root→day→publication→固定 shard 集，只读 `shard_count<=256` 条 SUCCEEDED 证明，确认 generation、hash 范围连续、无活动旧租约及全日 confirmed/pending count/amount/hash；空日四组均规范为 `0/CANONICAL_EMPTY_HASH`。通过后把 publication 置 VALIDATED，并把 day 置 FINALIZED、保存不可变源证明；不扫描流水、不批量更新日行。在线历史读取由 root ACTIVE calc + VALIDATED publication 选 generation，而不是把 day 的首次 calc 当永久口径。
7. 崩溃时 day/publication 留在 CLOSING/BUILDING，worker 从持久 cursor/carry 续跑，绝不回到 OPEN。普通代码缺陷恢复只能走下面的强类型命令；旧 generation 结果保留为不可见派生证据，旧 owner 迟到写由 generation 条件拒绝。
8. 所有业务事务有应用硬 deadline 30 秒、数据库 `statement_timeout <= 25s` 和 `idle_in_transaction_session_timeout <= 5s`。每个构建/验证批次按实测选择 N，使 p99 小于 statement timeout 的一半；协调、批次、发布任何一步都不得无界扫描。`EXPLAIN` 必须证明 Index Scan 的读取行数受 N/hash 范围约束，稀疏/空 shard 也不能全日排序。
9. 账务事务跨日提交时，`occurred_at` 以服务端确认时点为准。已持 root/day 共享锁的旧日事务可先提交并被封账纳入；尚未取得 fence 而发现旧日 CLOSING/FINALIZED 的事务用原幂等键整体重试，并按当前确认时点记入今日。迟到事件或人工更正在当前业务日追加引用原事实的调整流水。
10. 月 rollup 只读取 root ACTIVE/candidate calc 下、目标自然月每个 FINALIZED day 对应的 VALIDATED selected publication，以及同 calc 前月 selected 月行中 `pending_closing<>0` 的 carry stream；genesis anchor、0 代和其他 calc/generation 不得混入。每个 calc 的不可变 `first_earning_month` 由 launch date 固定并由 RESTATED 继承；仅 `earning_month=first_earning_month` 可以把四个 predecessor 列全置空并使用规范零锚点，任何后续月必须完整指向前一自然月同 calc 的 generation/proof，不能用 NULL 截断 carry。协调短事务固定最多 31 个日 publication 的集合 hash、前驱四列、`shard_count<=256` 和 calculator build，以 composite FK 指向不可变 generation proof，锁稳定 head 后创建 BUILDING generation/shards而不改变 selected。worker 对每个 shard把 `pending_closing<>0` partial-index 前驱流与最多31个 DAY 流做 `Merge Append + global LIMIT N`；完整 source key/cursor 为 `(user_partition_hash,user_id,category,stream_kind,business_date,policy_version_id)`，前驱用固定哨兵 date/policy。静默月仍携带 opening→closing，三月 release 不会丢；数千万零 closing 行也不被扫描。source vector/hash覆盖完整键与 confirmed/pending，执行计划上界 `N+O(32)`。独立验证守恒/predecessor proof 后才短发布；前月 selected 换代从直接后继起按月置 dirty顺序重建，旧链 stale 可读。最终发布只锁 head/current generation/最多256 shard，原子 SUPERSEDE 旧代并切 validated selected；失败不动旧 selected。
11. 月代次是纯派生恢复，不提供人工 RPC，也不使用 `stats.rebuild` 权限分支。瞬时失败在同 generation 从持久 cursor续跑；验证/确定性失败把 generation/shards 标 FAILED。只有部署了不同 `calculator_build_id` 且旧代无活动 lease时，`build_income_month` 才以原日集合 hash、calc、shard_count 创建更高 current generation并把旧 FAILED 代 ABANDONED；旧 owner 被 head current + generation status + lease generation fencing。任何新代仍须完整证明后才能切 selected，因此自动恢复不能改资金、规则、cutoff或掩盖差异。候选日/月结果完成时更新 activation leaf 并把 proof shard置 DIRTY，激活事务不逐月扫描。
12. RESTATED 重建先锁 root，以当前 ACTIVE 为 base，物化/封存 segments、继承 first month，并在同一无在途 writer快照固定 ledger/freeze双 upper与 scope contract后登记 BUILDING；不可变 contract与后续 selected proof分列。baseline各批匹配 segment/scope contract。scope创建完整 `[0,count)` 最多256 shards；worker用 partial `(scope_partition_hash,id) WHERE asset_type='COMMON' AND open_kind='INCOME_FROZEN'` 且 `freeze.id<=source_upper_freeze_id` 每 Tx 读最多 N 个候选，再通过 freeze_id 唯一 opening/terminal ledger 按 `ledger.id<=source_upper_ledger_id` 重建 as-of 生命周期，写/核 item/vector/cursor并匹配 contract+lease generation。每片独立重扫，短 combine最多256片；成功才设置 head selected/proof，crossing非零不可PROVING。BUILDING/CATCHING_UP不写 activation leaf；重建覆盖launch起普通FINALIZED日与连续月份。
13. `StartIncomeRestatementProof` 只在 candidate CATCHING_UP、dirty 为空、scope crossing count 为零、segment/scope hash 与 contract 一致且没有 CLOSING 日时，用短 root 事务递增 proof generation、创建恰好 `proof_shard_count<=256` 条 DIRTY shard并转 PROVING。proof worker 按固定 hash range/真实 keyset/最多 N 行验证 COMMON账户、从 launch 起 FINALIZED day、从 `first_earning_month` 起无空洞月份；leaf/vector同时覆盖 confirmed、ADD/RELEASE/CANCEL、月 opening/closing、segment contract 与 scope proof。PROVING 后变化才写当前代 leaf并 bump mutation；只有扫描到尾且 mutation 未变才 VALIDATED。叶缺失/额外、月份断链、后续月 NULL predecessor、scope/segment/predecessor hash漂移都保持 DIRTY。
14. `ActivateIncomeRestatement` 的首个短事务遵守全局 rank：命令防重→rank 40 root→rank 100 approval。锁内重验 expected candidate/root version/proof generation/contract hash，要求 candidate `proof_validated_once_at IS NOT NULL` 且状态为 VALIDATED 或后续写导致的 PROVING；分别用 dirty/dirty-shard 索引 `LIMIT CUTOVER_MAX_*+1` 证明 backlog 未超过压测固化上限，并用 partial index `LIMIT 1` 证明没有 `finance_business_days.status='CLOSING'`。任一条件失败都不改 root；CLOSING 先由普通封账或 Restart 命令完成。通过后等待既有 root SHARE writer 退出，用 `(asset_type,id DESC)` 取最后 COMMON ID并 `COALESCE(...,0)` 固定 cutover upper，递增 cutover generation，写 QUIESCING candidate/request/approval/started/next-run，清 owner/until并保留单调 lease generation；审批消费与 root 变更同事务。事务不扫描账户、leaf、日期或月份。
15. QUIESCING 提交后，所有新 COMMON writer 在 root SHARE 锁内、任何业务状态变更前返回 `INCOME_CUTOVER_RETRY`；日封账协调器也不得创建新 CLOSING 日。`sweep_rollup_cutover` 先用只锁 root 的短 claim 事务，候选满足 QUIESCING、`next_run_at<=now` 且生成式 `cutover_claim_due_at<=now`，条件写 owner/lease-until、令 `cutover_lease_generation+=1` 后提交。之后每个固定 N 处理/续租事务都锁 root，并同时匹配 `(cutover_generation,owner,cutover_lease_generation,lease_until)` 与 `lease_until>clock_timestamp()`，再以既有 account_seq/day/month keyset 排空 candidate dirty或重验一片 proof；同事务 CAS 续租/推进 next-run。owner 崩溃后新 worker 从已提交 cursor接管；即使过期旧 owner先抢到 root，也因未过期谓词影响 0 行，不能自续租，Redis 丢失不影响新 owner领取。
16. 最终激活短事务仍由当前 cutover owner 发起，按 root→approval/版本/固定 proof shard 的顺序加锁并匹配完整双 generation lease token以及 `lease_until>clock_timestamp()`；只做有界检查：request hash/expected versions/审批仍匹配，仍无 CLOSING 日，`LIMIT 1` candidate dirty 为空，恰好 `proof_shard_count<=256` 条当前代 shard 全部 VALIDATED、validated=mutation、范围连续、四分量组合 proof 等于 candidate 头；当前最后 COMMON ID 的 `COALESCE(...,0)` 仍等于 cutover upper。条件成立才同事务旧 ACTIVE→RETIRED、candidate→ACTIVE、切 root 指针并递增 activation generation，清 candidate及所有 nullable cutover/lease字段；两个 generation 保留不回退。过期 owner不能激活，即使尚无新 owner；空库 upper=0 走同一路径。
17. QUIESCING 期间任何证明失败都保持 root 挡写、退避 next-run并告警，不能自动切半套结果或静默开放 writer。`AbandonIncomeRestatement` 同样按命令防重→root→approval加锁，绑定 candidate/cutover generation/request hash；它在锁内递增 cutover lease generation以 fence 当前/旧 owner，清 candidate及 nullable cutover字段，把非 ACTIVE 版本置 FAILED(ABANDONED_BY_ADMIN)并恢复 writer，不删除证据。禁止 truncate 在线版本、逐日切指针或让 A/B publication 混读。财务事实错误只能追加冲正；历史分类错误只能用完整 RESTATED 版本修复。

#### 6.4.1 `RestartFinanceDayGeneration`

这是恢复 CLOSING 日失败构建的唯一命令，不等同于泛化 `RetryJobFailure`。外部请求必须包含 `business_date/expected_build_generation/expected_calc_version_id/expected_contract_hash/reason/ticket_no/idempotency_key/approval_no`；`request_hash` 覆盖全部字段，要求异人审批及 `stats.day.restart`。Use Case 在事务内以 `approval_no` 解析并锁定唯一审批行，内部 `approval_id` 不暴露给客户端。

正式短事务按命令防重→root→day→approval→publication→固定 shard ID 加锁，仅当 day=CLOSING、期望 generation/calc/策略/hash/source upper 全匹配、`1<=shard_count<=256`、旧 shard 全部 FAILED/终态或租约已过期且无活 owner 时执行。它把旧 generation 最多 256 条 shard 标记 ABANDONED，递增 generation，以完全相同的 source cutoff/calc/策略/hash 契约创建新 publication generation 和完整 shard 集；不得重开 day、改变 shard_count/金额口径或借此采用未审核策略。审批消费、generation 变更和审计同事务；旧 worker 的 owner/generation 写全部失败。若旧策略本身无法解释历史事实，使用上面的 RESTATED candidate/barrier，不允许把普通未来规则硬塞进 restart。

### 6.5 运营 rollup

运营统计按“一个事实来源 + 一个去重键 + 一个业务时间字段”登记。增量作业锁 `rollup_watermarks`，在同一 `default` 事务内 upsert 当前批结果并推进 cursor；外部导入的供应商报表先落自身渠道对账表，不能直接加总到运营 rollup。

候选大扫描可从 replica 读取，但写入前必须在 primary 按主键重新确认；如果候选集依赖精确截止水位，则整个该批直接从 primary 读取。replica 结果不能直接推动 primary 水位。

### 6.6 外部工作

支付、出款、SMS、Email 等网络调用使用对应业务表（如 `payment_attempts`、`payout_attempts`、`security_challenges`、`notification_deliveries`）的 `status/next_run_at/attempt_count`：

1. primary 短事务 claim 并提交。
2. 事务外调用供应商；支付/出款必须使用渠道支持的稳定供应商幂等键，SMS/Email 只复用应用级 `delivery_dedupe_key`，不得声称 Forge 会把它传给供应商。
3. primary 新事务条件更新结果、业务终态和审计。
4. 不确定结果进入回查而非再次创建新业务命令。

这些表表达具体领域的未完成动作，不是 Outbox。供应商原始回调审计表也不是消息投递队列。

SMS/Email transport 统一使用精确锁定的 Forge `message v0.4.1`，不实现 WhatsApp。Forge 只在事务外调用；challenge/delivery 状态、lease、sweep、retry 和应用级 `delivery_dedupe_key` 继续以 primary 为真源。Forge 返回成功只推进为 `PROVIDER_ACCEPTED`，不表示 `DELIVERED`；只有已证明未接受的临时失败才进入 RETRY_WAIT，超时/响应丢失/调用后未 finalize 在无可靠供应商幂等或查单能力时转 `UNKNOWN`，不盲目重发或切换 sender。应用 registry 在调用前选定 provider，每个 Forge Manager 只装配一个 sender，从构造上禁用 `v0.4.1` 的自动跨 sender fallback。Twilio/BytePlus/Aliyun 可使用内置 SMS sender，Kirim 若纳入则由 Infrastructure 实现受限 custom `message.SmsSender`；Email 使用 Forge SMTP/SendGrid sender 与启动期编译模板。调用 context 隔离 Forge 内部可能包含完整收件人的失败日志，适配器丢弃或安全分类原始错误，只记录脱敏手机号/邮箱、归一化错误码和 key hash；禁止记录 OTP、模板敏感参数或向上透传带收件人的错误字符串。

### 6.7 异步报表导出

1. 管理命令在 primary 校验 `report.export`、数据范围和注册的 report/filter schema，固定 `as_of/source_watermark/policy_version/calc_version/required_replay_lsn`，并把 `report_exports(PENDING)`、命令幂等结果和 `admin_audit_logs` 同事务提交。
2. worker 在 primary 以 `FOR UPDATE SKIP LOCKED` 领取 PENDING，或重领租约已过期的 RUNNING，写 owner/until 并递增 generation；事务外等待专用只读 replica 达到 required LSN，再按注册的参数化查询、固定水位和版本流式生成 `temp/<export_no>/<generation>`。replica 超 lag 不回落 primary 扫大表。
3. 生成过程计算 SHA-256 和行数。对象写成功后新开 primary 事务，只有 owner/generation/lease 仍匹配才能把最终 object key/hash/row count 写入并转 SUCCEEDED；数据库 finalize 失败或旧 worker 迟到时临时对象不可下载，由保留期清理。重领始终复用固定 as_of/版本，不创建第二个 export 事实。
4. 下载命令每次重新校验当前 `report.download`、数据范围、SUCCEEDED、未过期和对象 hash，再签发短期凭证并写审计。权限快照只解释“当时为何允许创建”，不能覆盖当前已撤销权限。

导出不是跨系统业务命令，不需要 Outbox；`report_exports.status/next_run_at/lease` 足以重建工作，派生文件丢失可按同一固定水位重建。

### 6.8 通知生成与投递

1. 需要站内信的来源在同一业务事务直接插入，或由其 `status/dirty_at` 的 primary sweep 重建；两条路径必须使用同一 `dedupe_key=<source_type>:<source_id>:<event>`，唯一冲突读回原通知。
2. `ListNotifications` 只读当前 token 用户；未读数和写后读取走 primary。`MarkNotificationRead` 条件设置单行 `read_at`。`MarkAllNotificationsRead` 以命令幂等键锁当前用户 `notification_roots`，执行 `read_through_seq = last_user_seq` 的 O(1) 条件更新并返回该水位；随后分配的更大 `user_seq` 仍为未读，百万历史通知也不产生批量 UPDATE、持久 cursor 或长事务。
3. 外部渠道 worker 短事务领取 delivery，事务外调用供应商，再用稳定 key 条件 finalize；未知结果先查询，不换 key 重发。
4. Redis 信号只加速。通知或 delivery 行丢失可从注册的来源状态补建；外围发送失败永远不能改变订单、资产、权益、任务或审核终态，因此该表不是通用 Outbox。

## 7. 幂等与并发控制

| 场景 | 幂等键/约束 | 并发方式 |
| --- | --- | --- |
| 自动作业实例 | `(job_name, shard_id, scheduled_for, calc_version_id)` | 唯一约束；重复调度复用同一 run |
| 领域对象处理 | 业务自然唯一键 + 旧状态条件 | `FOR UPDATE SKIP LOCKED` 领取，固定锁序处理 |
| 收益日 rollup | `(user_id,business_date,category,policy_version_id,calc_version_id,close_generation)` + 用户 cursor | 0/正代并存；同一事务累计并推进 cursor，DDL 以 §4.2 为准 |
| 收益月 rollup | `(user_id,earning_month,category,calc_version_id,build_generation)` | 旧构建代不可见保留；同代来源日 hash 相同则 no-op，DDL 以 §4.2 为准 |
| 配置发布/回滚/未生效替换 | `command_deduplications` + `expected_version` + 内容 hash/目标时间线 hash | primary 锁 domain；同键异内容冲突；scheduled replacement 原子保持连续区间 |
| 人工重跑/解阻塞 | 管理幂等键 + 目标/原因 hash | 业务变更和审计同事务 |
| 创建报表导出 | 管理 actor + RPC + Idempotency-Key；hash 固定类型/过滤/as_of/版本 | primary 创建唯一 PENDING；worker `SKIP LOCKED` 领取 |
| 缓存失效/Redis 唤醒 | `object_id + version` | 重复删除/重复唤醒无副作用 |

- 不用 Redis 锁保证财务或作业唯一性；Redis 失效时数据库约束仍成立。
- worker 的批量大小、租约和退避都配置上限。网络任务租约过期只允许进入“查询供应商结果”，不能盲目重发不可判定的付款。
- 可重试错误使用带抖动的指数退避并受 `max_attempts`/最大间隔约束；业务不合法、配置缺失、权限/账号待修复进入 `BLOCKED`。

## 8. 配置管理

### 8.1 类型化登记

每个配置 domain 在代码中登记 schema、默认值、范围、是否影响资金、允许的生效粒度、兼容版本和验证器。首发至少包括：

- `INCOME_ACCOUNTING`：`biz_type` 白名单与分类，只能在发布事务数据库时间之后的下一个 Jakarta 业务日边界生效。
- 等级、返佣、合伙人、`Playlet Backing`、机器人商品/收益、任务/`Robot Activation Voucher`、充值/VIP/提现和内容投放规则。
- 作业批量、租约、重试和缓存 TTL；这些运维参数也必须有边界，不能用配置制造无界事务或关闭财务对账。

不存在的 key、未知字段、重复 `biz_type`、交叉生效区间、比例总和越界、负金额、循环引用和不兼容应用版本都在发布前拒绝。

### 8.2 发布流程

1. `mand` 创建 DRAFT，规范化内容并计算 hash；只做 schema/引用预检。
2. 第二位有权限的管理员复核，写 REVIEWED 和审计；复核后内容改变会自动退回 DRAFT。
3. 发布 Use Case 在 `database.default` 的一个事务中先锁预置 `rule_domains(domain)` 根，再按版本号锁定时间线尾行并校验 `expected_version`、应用兼容和引用。它用同一事务的数据库 `now()` 计算 `earliest_allowed_effective_at`：普通 domain 不早于 DB now，INCOME_ACCOUNTING 必须是严格晚于 now 的下一个 Jakarta 日界，PARTNER 必须是严格晚于 now 的下一个 Jakarta 月界；回滚发布也不例外。新版本只能追加到尾部：若尾行 `expires_at IS NULL`，要求新 `effective_at` 同时满足最早边界并严格晚于尾行起点，再把尾行仅此一次收口；若尾行已有终点，新版本必须从该终点开始且该终点仍未过去。收口、写 PUBLISHED、`config_releases(action=SUPERSEDE/PUBLISH/ROLLBACK_RELEASE)` 与 `admin_audit_logs` 同成败。数据库对可被事件时间选择的 PUBLISHED 行用 `(domain WITH =, tstzrange(effective_at,COALESCE(expires_at,'infinity'),'[)') WITH &&)` exclusion constraint 兜底；同域首版和并发未来发布也不能覆盖同一时点，禁止中段插版或任何 backdated successor。错误的未生效尾版本必须走 `ReplaceScheduledRuleVersion` 的恢复前驱/同边界替换协议，不能先 Retire 再另行 Publish。
4. 提交后广播 `domain + version + content_hash` 失效信号。各实例收到后删除旧缓存并从 primary 加载；信号丢失由短 TTL 和版本校验恢复。
5. 未来生效版本由解析器按时间选择，不依赖某一秒 cron 改“当前”布尔值。

资金写路径可在事务前读取本地不可变快照，但事务内必须从 primary 验证该版本在业务时点仍生效；不匹配就回滚、刷新、有限次重试。事务内不访问 Redis，也不执行配置 HTTP/RPC。

订单、持仓、权益、结算和返佣事实保存实际使用的 `rule_version_id` 与关键数值快照。配置回滚只影响回滚版本生效后的新事实，除非产品规则明确创建新的补偿事实。

### 8.3 管理能力

`mand` 提供：配置列表/详情、草稿校验、差异预览、复核、定时发布、历史版本、回滚发布和引用影响分析。所有高风险动作要求 `reason`、`ticket_no`、`Idempotency-Key` 与细粒度权限；接口不提供直接修改 PUBLISHED payload 或删除历史版本的能力。

## 9. 缓存策略

### 9.1 可缓存对象

| 数据 | L1/Redis 策略 | 真源与回退 |
| --- | --- | --- |
| 已发布不可变规则版本 | 版本化 key，L1 + Redis；发布后失效 | primary `rule_versions`；资金事务内复核版本 |
| 已封账日/月账单 | key 含 user、期间、policy/calc version；可长 TTL | 版本化 rollup；版本变化自然换 key |
| 内容/后台弱一致列表 | 短 TTL、单飞回源 | 命名 Replica Query，超延迟停用 |
| 当前收益/累计收益 | 不缓存事实尾巴；可在一次请求内单飞合并 | primary 汇总 + tail |
| 余额、冻结、权限、幂等、订单/任务可迁移状态 | 不作为缓存真值 | primary/当前 Tx |

- key 必须包含 schema 版本、业务时区、业务区间和规则/计算版本，禁止只用 `user_id` 缓存一份无版本“收益首页”。
- 提交后优先删除而不是在写路径回填；写请求不得因 Redis 删除失败而回滚数据库事务。
- Redis Pub/Sub 只广播失效/唤醒。没有信号时 TTL 和 primary sweep 恢复；缓存中不得保存唯一待办。
- 缓存命中率不能以牺牲一致性换取。对当前数据的精确读取慢时先优化索引、rollup 和尾巴，而不是延长不透明 TTL。

## 10. 主从路由与降级

| 能力 | 正常路由 | 从库异常时 |
| --- | --- | --- |
| 资产/订单/资格/权限、当前累计收益 | `default` 或当前 Tx | 失败关闭，不改走缓存 |
| dirty claim、领域状态迁移、rollup 写/水位/对账结论 | `default` Tx | 暂停并告警 |
| 已封账个人日/月账单 | 命名 Replica Query，可按版本缓存 | 轻查询在熔断+限流下最多一次回落 default |
| 后台列表/内容统计 | 命名 Replica Query | 返回可重试错误或受限回落 |
| 大报表、导出、全量扫描 | replica | 不回落 default，避免拖垮主库 |
| 候选扫描 | replica 可选，claim/复核必须 default | 直接改为小批 primary sweep 或暂停 |

- replica 连接在生产使用数据库只读角色和 `default_transaction_read_only=on`；进程启动进行写失败探针/权限校验。
- 每个 Replica 响应记录观测到的复制延迟和源版本。延迟超过允许值时路由层停止新重查询，不允许业务仓储悄悄切库。
- `default` 与 `slave` 即使配置成同一 DSN 也是两个连接池；事务内不得用 slave 或裸 default DB 读取。
- migrations、worker claim、配置发布和人工纠偏从不连接 slave。

### 12.2 管理与运维接口

`mand` 提供以下能力，均有审计：

- 统计：查看 ACTIVE/candidate、lag、水位、四分量来源与 rollup 差异、抽样明细；收益重述只能使用 02 章登记的 `CreateIncomeRestatement/GetIncomeRestatement/StartIncomeRestatementProof/ActivateIncomeRestatement/AbandonIncomeRestatement`，不得用通用 job retry 或直接 UPDATE 版本/root。
- 对账：查看/确认差异、下载受控证据、修复后重跑；不能用“忽略”直接让非零财务差异消失。
- 作业：按状态/owner/时间查看 runs 和 failures，重试 RETRY_WAIT、修复后解除 BLOCKED、调整受限并发；不能上传任意 payload 执行。
- 日封账恢复：`RestartFinanceDayGeneration` 只处理一条 CLOSING day 的失败 generation，使用独立 `stats.day.restart`、异人审批、期望版本/hash 和完整审计；通用 `RetryJobFailure` 无权创建 generation。
- 配置：草稿、diff、校验、复核、发布、历史、回滚和影响分析。
- 缓存：按对象 ID + 版本失效，禁止生产“全库清缓存”无范围按钮。
- 审计：按 actor、权限、目标、request_id、ticket 和结果检索；财务证据导出额外授权。
- 导出：`POST /v2/admin/report-exports` 创建固定版本异步任务；`GET /v2/admin/report-exports` 列表，`GET /v2/admin/report-exports/detail?export_no=...` 查询；`POST /v2/admin/report-exports/retry` 仅让 FAILED/PENDING 或已过期 RUNNING 按原固定快照重试；`POST /v2/admin/report-exports/download` 在复核当前权限、数据范围、状态、hash 和过期时间后签发短期下载凭证。两个 POST 的 `export_no` 均放 Proto body；列表使用 `offset + limit + total`。

建议权限点：`report.read`、`report.export`、`report.retry`、`report.download`、`stats.reconcile`、`stats.rebuild`、`stats.activate`、`stats.abandon`、`config.read`、`config.write`、`config.review`、`config.publish`、`config.rollback`、`job.read`、`job.retry`、`job.unblock`、`cache.invalidate`、`audit.read`。激活与放弃 candidate 均使用目标/hash 精确匹配的异人审批；人工资产补偿使用独立权限和双人审批，不包含在统计权限内。

## 13. 审计、指标与告警

### 13.1 审计要求

- 管理业务变更与 `admin_audit_logs` 在同一 `default` 事务；审计写失败则操作回滚。
- before/after 只保存必要且脱敏的差异，不记录密码、OTP、令牌、密钥、完整卡号、供应商原始敏感体或流水 `extras` 全量。
- 自动行为写 `job_runs`；对象失败写 `job_failures`；人工重试/解阻塞另写 `admin_audit_logs` 并关联原 run/failure。
- 审计、资产流水、配置发布和对账结论只追加；更正以新的反向/解决记录表达。

### 13.2 指标

- 收益：dirty 数、最老 dirty 年龄、rollup 吞吐/耗时、tail 行数分布、ACTIVE/candidate 状态、activation proof DIRTY/VALIDATED 数、mutation lag、单批/激活锁行数、日/月封账延迟、年度/月槽差异、百分位 publication 年龄/样本数/构建进度/证明差异、按分类金额。
- 作业：scheduled/run/success/fail/skip、claim 冲突、lease 过期、重试次数、BLOCKED 数、每对象耗时和追赶天数。
- 配置：各 domain 当前/未来版本、发布失败、事务内版本冲突、实例缓存版本分布、失效广播失败。
- 数据库：default/slave 各自池使用率/等待、慢 SQL、事务时长、锁等待、死锁、回滚、复制 lag、fallback 次数和重报表拒绝数。
- 缓存：L1/L2 命中、回源、单飞合并、陈旧版本拒绝、Redis 错误和删除/广播失败。
- 对账：source/rollup 金额与行数差、资产桶守恒差异、未解决差异年龄和受影响用户数。
- 导出：PENDING/RUNNING 数、最老等待、生成耗时/行数/字节、失败原因、过期清理、权限撤销拒绝和下载审计数。
- 通知：UNREAD 数/年龄、生成去重冲突、SMS/Email/PUSH delivery pending/retry/unknown/dead/`PROVIDER_ACCEPTED`、租约回收、Forge sender/供应商延迟、不确定结果与手机号/邮箱脱敏扫描；PUSH 指标来自独立适配器。

### 13.3 首发告警阈值

| 告警 | Warning | Critical |
| --- | --- | --- |
| 收益最老 dirty / rollup lag | `> 5m` | `> 30m` |
| 日封账延迟 | `> 30m` | `> 2h` |
| 财务对账金额差 | 任意非 0 立即告警 | 持续两轮或影响多个用户立即升级 |
| `BLOCKED` 财务对象 | 任意新增 | 超过 owner SLO 或持续增长 |
| replica replay lag | `> 10s` | `> 60s`，停用重查询 |
| primary 事务 | p99 超预算或单 Tx `> 2s` | 锁等待/死锁或单 Tx `> 5s` |
| lease 过期率 | `> 1%/15m` | `> 5%/15m` |
| tail 扫描 | p95 `> 100` 行 | p95 `> 1000` 行或持续增长 |
| Redis 信号/失效失败 | `> 1%/5m` | 持续 15m 且 sweep lag 上升 |

阈值上线后按容量压测和 SLO 调整，但“财务差异非零”“生产 slave 可写”“未知收益枚举”“Schema 不兼容”始终为零容忍。

## 14. 失败模式与恢复

| 故障 | 系统行为 | 恢复动作 |
| --- | --- | --- |
| Redis 全部不可用 | 核心事务继续；配置走本地短缓存/primary，唤醒和失效变慢 | primary sweep 追赶；监控 dirty/TTL；恢复后不补发业务 payload |
| replica 不可用/延迟 | 强一致路径不受影响；停重报表，轻查询受控回落 | 熔断探测恢复，确认 lag 后再开放 |
| workerd 批中崩溃 | 当前 DB Tx 回滚；已 claim 对象等待租约到期 | 其他副本重领，cursor/唯一键保证幂等 |
| rollup 更新成功但水位失败 | 同一事务整体回滚 | 重跑同批，不重复累计 |
| activation proof 构建中新增用户/流水/日/月结果 | 对应 shard mutation generation 同事务推进并重新 DIRTY；旧 validator 条件更新 0 行 | 有界重验该 shard；root 激活只等当前 1..256 条证明，不降级为全表扫描 |
| 百分位构建崩溃/Redis 丢失、过去月份依赖换代 | BUILDING 部分结果不可见，收益金额不受影响；API 由稳定 head 使用旧 selected 并标 stale 或返回 null | 租约到期按 generation/cursor/tie carry 续跑；primary dependency sweep 从最早失配月顺序重建后继链，缓存从 head/publication 回源 |
| Redis 信号发出但 DB 回滚 | 信号必须提交后发送；若误发，消费者回查不到待办即 no-op | 记录违规指标并修正调用点 |
| 错误配置已发布未生效 | 仅执行 `ReplaceScheduledRuleVersion`：原子恢复前版开放尾，或在相同生效点换入已复核版本 | 禁止独立 RETIRE 造成区间空洞；审计关联事故 |
| 错误配置已产生事实 | 不修改历史事实 | 停止新写；发布新版本；需要时生成审批补偿和新 calc version |
| 收益策略遗漏/未知枚举 | 不猜测归类；相关封账保持 provisional/失败并告警 | 修复登记与策略，CI/启动校验通过后重建新版本 |
| 对账差异 | 不自动改资产或覆盖 ACTIVE rollup | 隔离影响范围，查源事实，追加冲正或新版本重建 |
| 导出 worker/对象存储失败 | report 保持 PENDING/FAILED 且数据库没有伪 SUCCEEDED；临时对象不可下载 | 原任务按稳定 object key 重试或清理临时对象，成功后 primary 原子 finalize |
| 导出期间 replica lag/权限撤销 | 停止或失败关闭，不回落 primary 扫大表，不继续使用旧权限快照授权下载 | lag 恢复后重试；重新授权后必须新建/显式重试并再校验当前范围 |
| 主库不可用 | 写、强一致读和 claim 失败关闭 | 数据库层完成选主/恢复；确认 timeline 和复制一致后应用重连 |
| 时区资源/DB 时区错误 | readiness 失败，不运行结算/封账 | 修复镜像/连接设置，通过边界测试后启用 |

每个 Critical 告警必须链接 runbook，至少写清：如何确认影响、怎样停止扩大、只读取证 SQL、恢复前置、是否需要财务复核和恢复后对账。禁止在故障中直接改余额、删流水、手工推进水位或跳过未验证版本。

## 15. 部署、Schema 与日常运维

### 15.1 空库首次部署

1. 创建 `default` 业务角色、生产只读 `slave` 角色和独立 `migrate` 角色；确认 `slave` DML/DDL 失败。
2. 用目标发布包执行 `migrate default init`、`migrate default up` 和 `migrate default status`；只连接 `database.default`。
3. 运行空库 Schema 校验：表/外键/CHECK/唯一/部分索引、种子规则 hash、枚举对齐、时区和角色权限。
4. 启动 `workerd` 但先保持外部投递暂停，确认 sweep、job registry 和空队列健康；再启动 `mand` 和 `apid`。
5. 通过 smoke test 创建新用户、两类资产行、一次收益事实、一次 rollup、一次配置发布和一次审计，再开放流量/外部投递。

这是 2.0 新 Schema 的 greenfield 部署，不含 1.0 数据搬迁、影子读、双写、CDC、历史回填和流量割接步骤。空库没有 `user_income_stats` 行时 exact tail 自动从 0 计算，功能不依赖预热。

### 15.2 后续发布

- 在线进程只检查 Schema 兼容区间，不自动迁移。先运行前向兼容 migration，再滚动 `workerd/mand/apid`；破坏性 contract 仅在所有旧版本退出并经评审后执行。
- 生产禁用 `migrate down`；不可逆财务 DDL 没有伪回滚。应用回滚依赖 expand 阶段兼容和配置新版本，不删除新事实。
- 新索引以登记 SQL、目标数据集 `EXPLAIN (ANALYZE, BUFFERS)`、构建空间和写放大预算为准；大表索引并发创建并独立监控。
- 部署 readiness 包含：Schema 版本、BusinessClock、default 可写、slave 只读/lag、规则版本可解析和 job registry 完整。

### 15.3 备份、恢复与演练

- 上线产生数据后，主库执行持续归档/PITR 与加密备份；恢复演练使用隔离环境，验证资产守恒、配置版本、作业水位和审计链。
- Redis、rollup 和缓存可重建，但 PostgreSQL 不可变事实、当前状态、幂等记录和审计必须进入恢复点目标。
- 恢复到旧时间线后先暂停外部投递，核对供应商幂等键/状态，再逐个开放 payout/payment/notification worker，避免重复外部动作。
- 演练至少每季度进行一次，记录 RPO/RTO、数据差异、缺失 runbook 和修复 owner。

### 15.4 日常检查

- 每日：财务对账差异、封账状态、dirty/blocked、replica lag、备份结果。
- 每周：慢查询与索引命中、tail 分布、作业容量、失败类型、配置版本分布和权限审计。
- 每月：恢复演练抽查、角色权限 diff、过期 secret 引用、规则/Proto/DDL 枚举一致性和容量预测。
- 纯派生失败版本和过期缓存可按保留策略清理；资产、订单、支付事件、结算、发布、对账和审计事实不物理删除。

## 16. 验收用例

### 16.1 收益口径

1. 同时写入允许的 COMMON/EXPERIENCE、充值、机器人直接收益、团队返佣、本金返还、冻结收益、释放、提现解冻、任务奖励和人工调账；断言只有策略 INCLUDED 的 COMMON `(biz_type,ledger_kind)` 按登记 delta 桶进入正确分类。另尝试写未知组合和充值赠送/活动收入类型，必须 fail closed 且无事实残留。
2. 对 registry 的四组规则逐一做正反测试：收益 `INCOME_FROZEN=EXCLUDED/ZERO+ADD/ABS_FROZEN_DELTA`，对应 `UNFREEZE=INCLUDED/AVAILABLE_DELTA+RELEASE/ABS_FROZEN_DELTA`，释放前 `SETTLE_FROZEN=EXCLUDED/ZERO+CANCEL/ABS_FROZEN_DELTA`，所有非收益冻解均为 `EXCLUDED/ZERO+NONE/ZERO`。释放前退款必须得到 CANCELED_FROZEN，只有 pending canceled；释放后受控 EXPENSE 才冲减 confirmed 原分类。另对 `PARTNER_CLOSURE_ADJUSTMENT_REVERSAL+EXPENSE` 断言负 available delta 进入合伙人分红 confirmed，其他五 kind 显式排除且不能生成，并验证 overview/day/month/year/admin/export/reconcile 全链守恒。再让 open 与 release/cancel 跨普通策略版本：发布若改变 pending lifecycle category 必须失败；RESTATED 重分类必须同时重述全生命周期。错配字段、负 pending、同一行多效果、未知组合和查询内自建 CASE 均失败。
3. 合法负向冲正降低原分类，且引用原流水；总收益等于所有分类之和。
4. APP 概览、详情合计、月账单、年度汇总、后台用户详情、导出和对账对同一 `as_of/policy/calc version` 完全一致；年度 12 月槽之和、分类之和与年度总额分别守恒。
5. Jakarta 日/月边界、周一 00:00、跨年、闰日和服务器运行在 UTC/其他时区均得到相同半开区间。
6. 百分位样本分别构造 0、99、100 人、同分和负冲正；少于 100 返回 null，100 人起严格按 `strictly_lower/sample_count` 计算且同金额同值。构建中杀 worker、旧 generation 迟到、Redis 清空或 replica 延迟都不改变收益金额，部分 generation 永不可见，回源结果携带固定 as_of/规则/计算版本。过去月份月 selected 换代后，从该月开始的 YEAR/CUMULATIVE 后继链按月收敛；每一月发布前必须引用当前前驱 proof，过程中 head 继续返回完整旧链并标 stale，失败不得切走旧 selected。
7. DAY/HOUR 固定 24 槽，WEEK/MONTH 的 DAY 槽和 CUMULATIVE/MONTH 槽分别补零；非法粒度组合拒绝。各曲线点之和与同范围卡片一致，累计超过 120 月按标准分页稳定返回。
8. 月账单的 confirmed 与 pending 两条公式逐字段守恒；分别覆盖月初已有 freeze、月内新增/释放/取消、跨月释放和释放后冲正，opening/closing pending 与冻结明细回放一致。

### 16.2 rollup、幂等与并发

1. 汇总前、汇总事务中和汇总后插入收益，`summary + tail` 始终等于 primary 源流水；模拟 sequence 小 ID 迟提交也不漏计。
2. 在 Jakarta 23:59 开启并持有昨日 day fence 共享锁，跨过 00:10 后才提交；OPEN→CLOSING 协调事务必须等待，随后冻结的 source upper bound 包含该流水。另让事务在 day 已 CLOSING 后携带昨日预计算时间继续，必须收到 `BUSINESS_DAY_ROLLED`、整笔回滚并以原幂等键在今日重试；昨日 `provisional=false` 发布后永不变化。
3. 让 rollup worker 读到旧 cursor 后暂停：若它先持昨日 FOR SHARE，协调器必须等待并在其提交后转 CLOSING；若协调器先转 CLOSING，worker 必须跳过昨日 0 代 upsert、只推进尚未覆盖的用户累计。两种交错都不能修改正在构建的正代；锁内 tail 新增跨日时必须回滚扩集。
4. 在 `V2-PERF-1` 的 5,000 万流水规模和单日峰值数据上运行日封账：协调/发布事务不允许出现流水或日表全扫描；每个构建/验证事务都受 N 条上限和 25 秒 statement timeout 约束。随机杀死 worker、让租约过期、重复领取、在 source upsert 与 cursor 更新的每个写点注入失败，恢复后每个正代 group 只累计一次。
5. 构造单一热点用户超过一个批次、空日、全负向冲正日和多个 policy version：carry 跨批结果必须与一次性规范 SQL 相同；空日发布 `0/0/CANONICAL_EMPTY_HASH`。篡改任一 shard 的 cursor、amount、count、hash、generation 或制造缺号/重复 shard 时，FINALIZED 发布全部失败关闭。
6. 在 CLOSING 期间持续读取日序列，只能由一条 primary SQL 直接聚合该用户/日源流水并返回 `provisional=true`，不能复用累计 cursor、拼接不同 statement snapshot 或看到部分正代。让 dirty worker 在查询的潜在“读快照/读 tail”间提交并越过该日，结果仍与同一 statement snapshot 的规范源 SQL 相等；最后一个 shard 成功但发布事务未提交时正代仍不可见。发布事务提交后一次切换到完整正代，月 rollup 只消费该代次。失败 generation 重启不得重开旧日或把旧正代变为指针。
7. 把应用事务挂起超过 30 秒、违反 statement/idle timeout 或伪造不获取 day fence 的 ledger 写；前两者被取消并告警，后者被静态/集成约束拒绝。封账可延迟但不得漏账，readiness 对错误连接参数失败。
8. 同一 dirty 用户被两个 workerd 领取，只有一个有效 lease；租约过期、崩溃重跑和同批重复执行不重复累计。分别注册零流水用户于 BUILDING、CATCHING_UP、PROVING 和无 candidate：前两者只产生 `ACCOUNT_CREATED,seq=0` dirty，worker 必须创建零 stats 后清理；PROVING 同时更新当代 USER_ACCOUNT leaf；之后首笔 ledger 合并原因并只累计一次。rollup upsert 后故意让 cursor 更新失败时事务整体回滚。
9. 丢弃全部 Redis 信号，primary sweep 仍完成收益、等级、结算、冻结释放、支付/出款回查和 CLOSING 日续跑/发布。
10. 重建写 BUILDING 版本时在线仍读旧 ACTIVE；验证失败不切换，验证成功一次事务切换且旧版本可审计。非零对账差异生成 OPEN 记录和告警，不自动改钱包或删除差异。
11. 同一来源通知由事务直写和 sweep 并发生成时只保留一行；本人已读/全读与新通知并发不误读他人或越过固定 as_of。投递 worker 崩溃、租约过期和供应商响应丢失均保留应用级 `delivery_dedupe_key`，但没有可靠幂等/查单证据时必须转 UNKNOWN 而不是重发；业务终态不受 `PROVIDER_ACCEPTED`/UNKNOWN/DEAD 影响，且 transport 接受不得冒充 delivered。
12. 月构建在同一用户、业务日、分类下放入两个不同 `policy_version_id` 的日行，跨批六元 cursor 必须逐行覆盖且月金额/hash 与规范 SQL 一致；索引计划只能是一个 `pending_closing<>0` partial-index 前驱流加最多 31 个选中日分支的有界 `Merge Append + global LIMIT N`。在前月数千万行且仅极少 closing 非零时，`EXPLAIN (ANALYZE,BUFFERS)` 的前驱读取仍受 N 与 hash range 约束，禁止过滤后无界扫描零行。篡改 predecessor month/calc/generation/proof 任一列或让 composite FK/前月 selected 依赖漂移都不得发布。分别配置月 generation/shard_count 为 0、257、非法 shard_id、重叠/空洞范围和缺片，应用与 DDL/发布全部拒绝；1 与 256 可完成，协调/发布最多写锁 256 片。更高 current 构建失败时旧 selected 持续可读；只有不同 calculator build 且相同 contract 才可换代，旧 owner迟到写为 0。
13. RESTATED candidate 从未完整证明、dirty 用户或 DIRTY shard 超过任一 `CUTOVER_MAX_*` 时 Activate 必须不改 root；满足上限后才能进入 QUIESCING。分别在设置屏障后、处理批中和最终激活前杀死 owner，过期 lease 必须被更高 `cutover_lease_generation` 接管；再让过期旧 owner在新 owner尚未 claim 前先锁 root，处理、续租和激活都必须因 `lease_until<=database now()` 影响 0 行。超 SLO 维持挡写/P0，获批 Abandon 以相同锁序 fence worker 后恢复。空库或尚无 COMMON ledger 时 day 封账、baseline 与 cutover upper 均为 0，空 proof 可正常发布/激活；不得出现 NULL cutoff。

### 16.3 配置、权限与缓存

1. 同一人不能创建并复核资金配置；未知字段、错区间、比例越界、未知 `biz_type` 和不兼容应用版本发布失败。
2. 同 Idempotency-Key 同内容返回原发布结果，不同内容冲突；并发 `expected_version` 只有一个成功。
3. 发布后故意丢失 Redis 失效，TTL/事务内 primary 版本校验仍阻止旧规则产生新财务事实。
4. 回滚生成更高新版本，旧订单/持仓/结算保持原规则快照；PUBLISHED 历史不可编辑/删除。
5. 无 `stats.activate/job.unblock/config.publish/cache.invalidate/audit.read` 权限的管理员分别被拒绝，失败尝试也有安全审计。
6. 同键同过滤创建导出返回原任务，同键改过滤/as_of/版本冲突；两个 worker 只生成一个 SUCCEEDED 文件，hash/行数与固定版本查询一致。
7. 创建后撤销管理员权限、缩小数据范围、文件过期、对象被篡改和重复下载逐项测试；均不能越权下载，所有成功下载都有审计。
8. SMS 与 Email 各在 claim/调 Forge/finalize 三个边界杀 worker，验证 primary sweep 保留原 `delivery_dedupe_key` 并把无可靠证据的不确定调用收敛为 `UNKNOWN`，不得自动重发；nil 只得到 `PROVIDER_ACCEPTED`。扫描全部日志/指标/作业失败证明无完整手机号、邮箱、OTP 或模板敏感参数；无 WhatsApp provider/config/route。

### 16.4 主从、故障和部署

1. 生产 slave 角色执行 DML、DDL 和写事务失败；事务内静态扫描不存在 slave/裸 DB 调用。
2. 模拟 60 秒复制延迟，当前累计与写后回读仍精确，重报表停止，轻查询回落受限且有指标。
3. Redis、slave、单个 worker 和整个 workerd 依次中断/恢复，核心事实不丢、待办可追赶、无重复外部付款。
4. 从空 PostgreSQL 执行 `migrate default init/up/status` 后四进程通过 readiness 和 smoke test；`migrate slave up`、生产 `down`、应用自动建表全部失败。
5. 仓库和发布包不含 1.0 历史迁移、双写、CDC、旧表查询或割接开关。
