# 08 机器人持仓、激活凭证与任务

## 1. 目标与范围

本域提供机器人商品、购买、持仓、逐日收益、到期返本、等级资格、机器人激活凭证（Robot Activation Voucher）和任务奖励。产品对外使用“智能收益机器人”等中性名称；“AI”不是模型调用能力。

保留 Robot Activation Voucher，完全排除普通短剧支持券、双倍券、FlashSale、订阅机器人、活动机会、付费 TaskPlan 和客户端伪任务。

## 2. 对象与业务不变量

| 对象 | 定义 | 不变量 |
| --- | --- | --- |
| 机器人商品 | 售价、本金、周期、每日收益、额度和等级要求的已发布版本 | 扣款按售价；返本/活跃值/业绩按本金快照 |
| 机器人持仓 | 用户购买或核销 Robot Activation Voucher 后形成的合约 | 规则发布后不改写持仓快照 |
| 持仓日结算 | 每业务日直接收益事实 | `(holding_id, business_date)` 唯一 |
| Robot Activation Voucher | 可核销为指定规则持仓的激活凭证 | 不返名义本金、不产生团队返佣 |
| 资格消费事实 | 统一裁决现金购买与激活凭证核销的“首持仓”竞争 | `(user_id, qualification_type)` 唯一，所有持仓创建入口共用 |
| 任务定义/版本 | 目标、真实事件来源、周期和奖励 | 客户端不能任意推进进度 |
| 用户任务/领取 | 某用户某周期的进度与奖励事实 | 任务奖励与机器人持仓/Playlet Backing 收益解耦 |

机器人普通购买只使用 `COMMON`。`EXPERIENCE` 不可购买机器人，除非未来通过新规则版本和 ADR 明确开放；不能沿用剧集消费的默认策略。

## 3. 状态机

### 3.1 商品与持仓

```text
商品：DRAFT --复核发布--> PUBLISHED --下架--> OFFLINE --归档--> ARCHIVED

持仓：ACTIVE --等级不足--> PAUSED_LEVEL --等级恢复--> ACTIVE
       ACTIVE/PAUSED_LEVEL --到期处理成功--> MATURED
       ACTIVE/PAUSED_LEVEL --受控取消--> CANCELLED
```

- 普通商品 `required_level` 可为空；等级商品要求当前等级 `>= required_level`。
- 降级只暂停等级商品未来收益，不追回已结算收入；恢复后从恢复后的首个合格业务日继续，不补发暂停日。
- 首发 COMMON 购买商品的 `principal_amount` 必须严格大于 0，到期按该快照返本一次；零本金只允许 `ROBOT_VOUCHER`，其永不返本。
- 激活凭证持仓到期不返任何名义本金。
- 商品下架阻止新购，既有持仓继续按快照履约。

### 3.2 激活凭证

```text
CREATED --分配用户--> ASSIGNED --核销--> REDEEMED
                         |  \--人工/关户处置--> VOID
                         +--到期--------> EXPIRED
```

请求时必须同时检查状态和 `expires_at`，不能等待分钟任务改变状态。凭证码只保存安全 hash；查询响应不回传完整可用凭证码。

### 3.3 任务

```text
用户任务：IN_PROGRESS --真实进度达到目标--> CLAIMABLE --领取事务--> CLAIMED
             |                                  |
             +--周期结束未完成-----------------> EXPIRED
```

任务定义版本使用 `DRAFT -> REVIEWED -> PUBLISHED -> RETIRED`。发布事务先锁稳定 `task_definitions` 根，同一 definition 的版本单调且 PUBLISHED 半开区间不重叠；新版本只能追加到时间线尾部，开放尾只允许在发布后继的同一事务收口。发布后不改写已生成用户任务的目标和奖励快照。

## 4. 数据表与索引

### 4.1 机器人

- `robot_products`：严格正 `sale_price/principal_amount`、`duration_days`、`required_level`、正 `cash_purchase_limit`、`capacity`、`sold_count`、`rule_version_id`、状态和投放条件。首发现金本金为 0、售价为 0、限购为 0，或 `round(principal_amount*partner_pool_rate)` 不为正都不能发布；激活凭证的零本金语义只在 voucher rule/holding 表达。
- `user_robot_product_stats`：每个 `(user_id,robot_product_id)` 一行，保存 `successful_cash_purchase_count/version/updated_at`，计数非负且不超过首次创建时固化的 `cash_purchase_limit_snapshot`；联合主键。现金购买在 product 之后、user 之前锁该 O(1) 根并用条件 UPDATE 占一个名额，事务回滚时计数也回滚；禁止在资金事务 COUNT 历史 holdings。激活凭证核销不占现金限购，仍受 voucher rule、首持仓资格与商品总容量约束。
- `robot_product_rule_settings`：与 `rule_versions(domain=ROBOT_PRODUCT)` 一对一，保存必填正 `default_daily_rate`、收益金额 scale/舍入，以及 `cancel_enabled/cancel_refund_basis=SALE_PRICE/cancel_refund_rate/cancel_fee_rate/settled_income_policy=KEEP`；DDL CHECK 与发布器共同强制两种取消比例都在 `[0,1]`，并验证每个可售商品快照满足 `gross<=sale_price`、`fee<=gross`、`net>=0`。发布拒绝缺 default、非正日收益率、会把任一最小合法收益基数舍入为 0 或未知策略，规范内容进入 rule hash。
- `robot_daily_rates`：商品、业务日/日序号、覆盖收益率和版本；覆盖率必须 `>0`，发布事务按对应商品所有可用 `yield_base` 下界、金额 scale/舍入验证 `round(base*rate)>0`。缺失日期使用持仓创建时快照的 `default_daily_rate`，绝不由代码默认为 0；负数、0 或小到舍入为 0 的 override 在发布前拒绝，不能让到期游标永久卡住。
- `robot_holdings`：`holding_no NOT NULL UNIQUE`、用户、商品、来源 `COMMON_PURCHASE/ROBOT_VOUCHER`、售价、本金、`yield_base_amount`、规则/default rate/收益 scale/舍入/取消策略快照、起止日期、当前等级门槛、累计收益、结算游标、状态和 `next_run_at`。COMMON_PURCHASE 强制 `yield_base_amount=principal_amount>0`；ROBOT_VOUCHER 强制 `principal_amount=0` 且 `yield_base_amount=robot_voucher_rules.yield_base_amount>0`，该基数只用于收益计算，绝不是可返本金。
- `robot_holding_settlements`：持仓、业务日、资格等级/规则版本快照、`yield_base_amount_snapshot/daily_rate_snapshot/rounding_snapshot`、直接收益、可空资产 ledger、`status=POSTED|SKIPPED_LEVEL` 和稳定 reason；持仓/业务日唯一。POSTED 强制 `direct_income=round(yield_base_amount_snapshot*daily_rate_snapshot,scale,rounding_mode)>0` 且 ledger 非空；SKIPPED_LEVEL 必须金额为 0、ledger 为空、reason=LEVEL_INELIGIBLE。
- `robot_qualification_consumptions`：`user_id/qualification_type/source_type/source_id/deduplication_id/created_at`；主键 `(user_id, qualification_type)`，来源事实和公共幂等引用唯一。首发唯一类型为 `FIRST_ROBOT_HOLDING`，任何成功创建的第一笔机器人持仓都必须在原事务占用。

`robot_holding_cancellations` 每 holding 最多一行，保存业务号、`user_id`、来源/规则快照、`gross_compensation_common/fee_common/net_compensation_common`、已结收益 KEEP、可空且唯一 `compensation_ledger_id`、非空且 CHECK 固定为 COMMON 的 `compensation_asset_type`、活跃值 reversal、pool reversal、审批/工单、幂等和时间。COMMON_PURCHASE 按固定公式 `gross=round(sale_price*cancel_refund_rate)`、`fee=round(gross*cancel_fee_rate)`、`net=gross-fee>=0`；ROBOT_VOUCHER 三者恒为 0。CHECK 强制 `net>0` 当且仅当 ledger 非空，net=0/凭证路径 ledger 必须空；实际子列 `(compensation_ledger_id,user_id,compensation_asset_type)` exact composite FK 回资产流水父键，ledger 非空时由固定资产列证明 COMMON，触发器再复验 kind=INCOME、amount=net 和 holding ref。已结直接收益/团队返佣保留，未来收益和到期本金返还取消，补偿是唯一终止资金效果。

本域复用 05/07 章的 `finance_recovery_cases` 和 `benefit_forfeiture_audits`。前者只在原受益已发放、来源冲正时第三方已 CLOSED 或锁内可追回余额不足而不能安全扣回时建立，方向为 RECEIVABLE；后者只记录新持仓/日结来源计算时不合格/CLOSING/CLOSED 候选受益人从未建立 GRANT/pool allocation 的裁决，差额算法按 06 章保持 previous 不变。两者都以来源事实+组件+受益用户为自然唯一键，与该持仓来源/结算/取消主事务同成败，不是 Outbox；Finance case 不改任何钱包，forfeiture 不创造资金事实。

热索引：`robot_products(status, priority, id)`、`robot_holdings(user_id, status, ends_at, id)` 和待结算 partial `(next_run_at, id)`。

### 4.2 Robot Activation Voucher

- `robot_voucher_rules` 保存必填 `robot_product_id`、显式正 `yield_base_amount`、持仓/收益规则、有效期和是否仅首持仓可用；收益率/scale/舍入从所指商品已发布规则固化到持仓。发布校验 `round(yield_base_amount*default_daily_rate)>0`；每次成功核销与现金购买共用该商品的 `capacity/sold_count`，计算基数不能作为本金、活跃值、返本或容量，也不能绕过商品下架。
- `robot_voucher_batches` 保存审批、数量、生成状态和规则版本。
- `robot_voucher_codes` 是凭证 lifecycle 唯一真源，保存 code hash、批次、`CREATED/ASSIGNED/REDEEMED/VOID/EXPIRED`、`assigned_user_id` 和核销引用；hash 唯一，并建立 `UNIQUE(id,assigned_user_id)` 供归属复合引用。
- `user_robot_vouchers` 只保存 `id/code_id UNIQUE/user_id/assigned_at/expires_at/source_type/source_id` 的归属与展示事实，不复制 status；建立 `UNIQUE(id,code_id,user_id)`，且 `(code_id,user_id)` composite FK 必须指向 code 的同一 `assigned_user_id`，查询状态 join code 真源。
- `robot_voucher_redemptions` 保存用户、`code_id`、`user_voucher_id`、持仓和幂等键；`code_id`、`user_voucher_id` 分别唯一，并以 `(user_voucher_id,code_id,user_id)` composite FK 指向同一归属。凭证来源 holding 使用相同三列引用，不能把 A 用户的 code、B 用户的 mapping 和 C 用户的 holding 拼接。
- `robot_voucher_dispositions` 是账号 CLOSING 时清理未核销凭证的只追加事实，保存 `closure_id/code_id/user_voucher_id/user_id/kind=VOID_ON_ACCOUNT_CLOSURE/before_status=ASSIGNED/after_status=VOID/reason/created_at`；`code_id`、`user_voucher_id` 分别唯一，并以完整三列 composite FK 回同一归属，不删除或改写历史。

分配事务按命令防重/审批→rule/code→`PrelockUserClosures`→`LockUsersAndValidateClosureGate` 固定顺序执行，锁内只允许目标用户 ACTIVE，再条件更新 code `CREATED -> ASSIGNED` 并插入唯一 user mapping；CLOSING/CLOSED 稳定拒绝且 code 仍 CREATED。批量发放凭证按 code ID 分成最多 N 行的独立事务，每批先收齐全部 rule/code/用户 ID 再排序锁定，不得在单事务扫完批次或边遍历边加锁。核销事务锁 code 和 mapping，条件转 `ASSIGNED -> REDEEMED` 并插入 redemption/holding；普通作废/过期只推进 code，mapping 永久保留审计。任一事务失败两表都不漂移，对账以 code 为真源验证映射/核销一一对应。

ASSIGNED 未核销凭证是明确的 closure blocker。CLOSING sweep 的 `DisposeClosureRobotActivationVoucher` 在一个短事务按 code/mapping→closure prelock→user gate 加锁，重验同用户、同未完成 closure 与 ASSIGNED 后，原子把 code 转 VOID、插入唯一 disposition 并推进 closure `next_check_at`；重复执行返回原 disposition。它不产生资产、本金、返佣或任务进度，也不允许把凭证转给其他用户。注销完成事务因此不需要扫描/锁定凭证历史，只需索引化 EXISTS 证明没有 ASSIGNED。

若 voucher rule 限制“首持仓”，在事务内锁定 `users` 行并读取 `robot_qualification_consumptions(FIRST_ROBOT_HOLDING)`；不能仅在事务前 COUNT。现金购买和激活凭证核销都调用同一个 `ClaimFirstRobotHolding` 原语：首个成功入口插入消费事实；若凭证核销发现已被任意来源占用则失败，普通现金购买发现凭证已先占用时仍可作为非首笔正常购买。并发先后以用户行锁及唯一约束裁决，事务回滚时资格占用也回滚。

### 4.3 任务

- `task_definitions`：稳定任务 code、类型、重复规则、状态。
- `task_rule_versions`：`task_definition_id/version/status/effective_at/expires_at`、目标值、合格事件、目标人群、`reward_asset/reward_amount/reward_scale`、异步来源 `expiration_grace_seconds` 和展示内容；`UNIQUE(task_definition_id,version)`，PUBLISHED 同 definition 区间由 exclusion constraint 禁止重叠。DDL 与发布器共同强制 `reward_asset IN (COMMON,EXPERIENCE)`、`reward_amount>0`、符合对应资产 scale/全局单次奖励上限且不会舍入为 0，目标值严格正；非法规则不能进入 PUBLISHED。`user_tasks` 和 claim 必须复制同一合法奖励快照并以 CHECK 再守门。
- `user_tasks`：用户、任务定义、规则版本、重复规则、目标/进度、状态、周期、非空生成列 `period_identity`，以及 `claim_source_count/claim_source_max_persisted_at/claim_source_multiset_hash/progress_version`。DAILY/WEEKLY 保存 Jakarta 半开周期，ONCE 的两个原始周期字段为空；`period_identity` 对 ONCE 固定为保留值 `ONCE`，周期任务由规范化起止时间生成，真实任务输入禁止使用该保留值。分别按 lifetime 或 period 唯一，并建立 `UNIQUE(id,user_id,task_definition_id,rule_version_id,period_identity)`。每条 APPLIED progress/受控 correction 与进度同事务锁 task 更新：max 取规范来源 `persisted_at` 最大值，count 和与插入顺序无关的固定 multiset hash 覆盖所有当前 claimability 输入；目标为正，因此 CLAIMABLE 必须 count>0/max/hash完整。它是关户 O(1) cutoff 证明，不替代追加事件。
- `task_progress_events`：`user_id/task_definition_id/user_task_id nullable/rule_version_id nullable/period_identity nullable`、来源领域/类型/事实 ID、事件时间、规范 `source_persisted_at`、正数 delta、`status=APPLIED/IGNORED`、稳定忽略原因和规则查找时间；`(source_domain,source_kind,source_id,task_definition_id)` 唯一。APPLIED 强制五个实例引用字段非空，并以 `(user_task_id,user_id,task_definition_id,rule_version_id,period_identity)` composite FK 指向同一实例/用户/定义/规则/周期身份；IGNORED 强制这些引用为空并要求 reason 非空。这样 ONCE 不会因 nullable period 让 PostgreSQL MATCH SIMPLE 跳过整条 FK。IGNORED 表示该真实事实发生时没有适用规则、用户不在目标人群或已进入不接受新任务的状态，不得在后来换版时追溯改为 APPLIED。
- `task_source_consumption_roots`：每个异步 `source_domain/source_kind/shard_id` 一行，首发固定 `TASK_SOURCE_SHARD_COUNT=64`，保存 `last_source_seq/target_source_seq/consumed_source_seq/lease_owner/lease_until/lease_generation/next_run_at/version`。来源事实以稳定 ID hash 选 shard；其写事务先锁该 root、执行 `last_source_seq += 1` 并把返回的连续 `task_source_seq` 与数据库生成的 `source_persisted_at` 写入事实，因此回滚不消费序号，迟提交也不能落在已捕获 upper 之前。consumer 短 claim 锁 root并把当时 `last_source_seq` 固定为 target，之后只按 `(shard_id,task_source_seq)` keyset 消费到 target；每条必须形成唯一 APPLIED/IGNORED 后才推进 consumed。owner/until 成对、generation fencing，旧 owner 影响 0 行。
- `task_period_source_barriers`：每个 `task_definition_id/period_start/source_domain/source_kind/shard_id` 一行。仅在数据库 now 到达 `period_end+expiration_grace_seconds` 后，协调事务按固定根序短暂锁齐该来源的 64 个 writer root，等待此前在途 writer 提交/回滚并捕获各自 `last_source_seq` 为不可变 upper；它不扫描来源事实。周期任务只有在全部登记来源分片 `consumed_source_seq>=source_upper_seq` 后才可 EXPIRED。同步来源无需 barrier；任何来源 registry、root 或分片映射漏登记都使规则发布/过期失败关闭。
- `task_reward_claims`：用户任务、奖励快照、`claim_source_count/max_persisted_at/multiset_hash/progress_version` 领取快照、资产 ledger 和幂等键；每个用户任务一次成功领取。
- `task_compensations`：`id/compensation_no/user_task_id/user_id/kind=PROGRESS_CORRECTION/REWARD_CORRECTION/delta/reward_asset/reward_amount/source_domain/source_kind/source_id/source_component/source_persisted_at/reason_code/ticket_no/approval_id/correction_mode/closure_id/deduplication_id/asset_ledger_id/created_at`；业务号、幂等和可空 ledger 唯一，同一 approval 只消费一次。五个 source 字段由强类型任务来源 registry 根据既有事实解析，管理员只能提交来源 selector，不能自报 `source_persisted_at`、用户、金额或组件。`(source_domain,source_kind,source_id,user_task_id,source_component)` 唯一，换 approval/幂等键不能对同一遗漏组件重复纠错。它只追加纠错事实，不改旧 progress event/claim。

`PROGRESS_CORRECTION` 只修复一个已登记来源组件的漏记/误记，锁内证明来源所属用户、任务定义和有符号 delta 与 registry 规则一致；只允许当前状态 IN_PROGRESS/CLAIMABLE 且不存在 `task_reward_claims`。先算 `raw_progress=before_progress+delta` 并要求 raw 非负，再固化 `after_progress=min(target_progress,raw_progress)`，因此数据库始终满足 `0<=progress<=target`；after 达到目标则转/保持 CLAIMABLE，低于目标则转/保持 IN_PROGRESS，尚未领取时允许 CLAIMABLE 因负纠正退回 IN_PROGRESS。compensation 同时保存 before/raw/after，纠正事实、progress、状态和审计同一事务；领取与纠正都先锁同一 `user_tasks`，CLAIMED 或已存在 reward claim 后一律拒绝 progress correction。`REWARD_CORRECTION` 只补齐已经 CLAIMABLE 但未生成领取事实的单次奖励：仅当条件更新 `user_tasks WHERE status=CLAIMABLE` 成功且尚无 claim 时，才能创建唯一 `task_reward_claims(user_task_id)` 并原子推进 `CLAIMABLE -> CLAIMED`，让 compensation、claim、任务终态与该 claim 的唯一 ledger 同事务提交；普通领取已经占用 claim 时，同语义重放读回原 claim/compensation，其他语义冲突，绝不能另写第二条奖励流水或留下“已入账但仍 CLAIMABLE”。已领取奖励的金额纠错改走 05 章对原流水的受审计 REVERSAL/新调整，不复用任务补偿旁路。

首发必须包含稳定任务 `task_definitions.code=PURCHASE_ONE_TIME_VIP`，其唯一进度来源是 `ONE_TIME_VIP_ENTITLEMENT_CREATED`，目标值为 1。一次性 VIP 权益、任务进度和来源唯一事件在同一购买事务写入；Proto、表和指标中不得出现 `SUB_VIP`、续订或订阅语义。任务是否完成不影响 VIP 权益或其他合法收益。

强类型任务来源 registry 同时定义“事件时间”和“来源登记时间”的取值列，调用方不能自填。`ONE_TIME_VIP_ENTITLEMENT_CREATED` 的 `event_time=vip_entitlements.activated_at`，但规范 `source_persisted_at=vip_orders.created_at`：订单在账号 ACTIVE 时已持久化，所以 closure cutoff 前订单的迟到支付可在 CLOSING 原事务创建权益和任务进度；cutoff 后新建订单仍被 user gate 拒绝。数据库触发器以 entitlement→order 的 composite FK 重算这两个值。异步来源还必须在其源表保存上述 root 分配的 shard/seq；没有 registry 映射的来源只能生成稳定 IGNORED，不能推进任务或过期水位。

任务实例只通过 `EnsureUserTask(tx,user_id,task_definition_id,event_time)` 创建。调用前必须已完成 01 章两阶段 closure gate 并持有目标 user/可空 closure；原语会断言 gate token，不能被裸 Tx 绕过。`DAILY/WEEKLY` 先由 `BusinessClock` 把 `event_time` 归一为 Jakarta 周期，以不可变 `period_start` 在 primary 唯一选择 `effective_at <= period_start < expires_at` 的 PUBLISHED 版本；`ONCE` 在首次成功 Ensure 时按该次 `event_time` 选版本，命中 lifetime 唯一实例后永远返回原快照。原语使用 `INSERT ... ON CONFLICT` 后锁定既有/新实例，把 rule ID、重复规则、目标、奖励、目标人群判断和展示快照固化；换版不重写既有实例。周期预生成器也必须调用同一 closure gate 和原语，且只为 ACTIVE 用户预热；它延迟或漏跑不影响进度正确性。

`RecordTaskProgress(tx, source_fact)` 是唯一进度入口。来源 Use Case 先锁业务根，再经 closure gate 锁用户，最后以来源自然键防重并调用 Ensure。ACTIVE 正常 APPLIED；CLOSING 只允许 `source_fact.persisted_at < requested_at` 的既有来源延迟消费并唤醒 closure，cutoff 后 IGNORED/整单拒绝；CLOSED 不建 task/奖励。适用时锁实例、插入 APPLIED、推进有界进度，并用固定 commutative hash 协议原子更新 `claim_source_count/max/hash/progress_version`；受控负 correction同样以唯一 correction fact更新该证明，不能只改 progress。若达到 CLAIMABLE，证明字段必须完整；任一写失败整体回滚。没有适用版本不阻断来源业务，多个适用版本视为 schema 损坏。

上段“先锁业务根”只适用于同步任务来源。异步来源 writer 必须在事务开始时先按 01 章 rank 90 锁唯一 `task_source_consumption_roots` shard并分配 seq，再进入其 event/session/业务根；consumer 同样先锁单个 root claim，再按 user/task 层处理。period barrier 只在一个短事务中按 `(domain,kind,shard_id)` 锁 64 个 rank 90 根、固定 upper 后提交，不同时持有 user/task/资产锁。两套轨迹不能混用或在业务根后反锁 source root。

重复规则首发只允许 `ONCE`、`DAILY`、`WEEKLY`；周一 00:00 为周起点。新增周期须扩展 `BusinessClock` 测试。

## 6. 主流程与事务边界

本章任何依赖等级的购买、核销、日结或返佣 Use Case，都必须在真正业务事务开始前调用 06 章 `EnsureLevelFresh` 做固定预算、多笔至多 6 用户的独立短事务排水；排水期间不得持有 finance day、商品、持仓、月份、用户或资产锁。随后业务事务取得 rank 35 runtime root SHARE/CLEAN，并以 queue path `LIMIT 1`、目标等级行 generation/version 复验一次性 fresh token；失败则整笔回滚并返回可重试，禁止在业务 Tx 内嵌套排水或持低 rank 锁跨波等待。

本章任何可能产生资产流水的现金购买、日结/返本、受控取消、任务奖励领取或 `REWARD_CORRECTION` 事务，都在 command/来源事件防重之后、取得任一商品/持仓/任务业务根之前调用 `AcquireIncomeWriteFences`，依次取得 income root SHARE 与当前 `business_date` 的 OPEN day fence；若同一路径依赖或改变等级，rank 35 runtime root 必须更早取得。来源/月份根锁齐后、用户层之前，对持仓用户、任务用户和候选收益人统一先 `PrelockUserClosures`，再锁既有 freeze，最后 `LockUsersAndValidateClosureGate`；无 freeze 时两阶段相邻。新购买/核销/任务来源及新受益资格只接受 ACTIVE，CLOSING 只终结 cutoff 前已登记来源并唤醒 blocker，CLOSED 不新增钱包/权益。激活凭证核销若本次严格不写资产流水可不取 root/day fence；资产原语不得在业务根之后懒获取 fence。

### 6.1 COMMON 购买机器人

1. primary 读取商品发布版本，计算售价、本金、容量、个人限额候选，并在业务事务外对购买者及返佣资格目标完成有界 `EnsureLevelFresh`。
2. 顶层 Use Case 开 default 事务，先锁命令防重行、rank 35 runtime root SHARE/CLEAN，再依次取得 income root/day fence，随后锁商品/既有持仓根与 `(user_id,robot_product_id)` 的 `user_robot_product_stats`；再从 primary 预读来源用户的 `parent_id/inviter_ids/version` 和受益集合，调用 `EnsurePartnerMonth` 取得 OPEN 月共享 fence，并按全局 rank ensure/锁齐本人/祖先的 `partner_monthly_qualifications` 与所有受益人的 `partner_settlements`。只有期间根闭包完整后，才收齐用户、等级、资格和任务 ID 并按 `UserStateLockKey` 加锁。
3. 锁内重读来源用户版本与祖先链；不一致则在取得资产锁前回滚并用原幂等键重试。随后复验 fresh token、调用 `ClaimFirstRobotHolding`、重查当前等级，以 `successful_cash_purchase_count < cash_purchase_limit_snapshot` 条件占用一个个人名额，再条件占用商品容量；任一影响行数不是 1 整体回滚。发现 dirty/queue/runtime generation 变化就回滚，绝不在此事务同步排水。
4. 按 `(user_id, COMMON)` 锁资产并使用 `ApplyMutations` 扣 `sale_price`，创建持仓并保存全部快照。
5. 按 `principal_amount` 增加个人/五层活跃聚合；只写步骤 2 已持锁的月份对象，以 `source_kind=CASH_ROBOT_PURCHASE, source_fact_id=holding_id` 和 `pool_base_amount=principal_amount` 创建唯一 `partner_pool_facts`，按当时规则一次计算 5% 基础池与分配。该来源以后不得在日结算重复入池。
6. 写任务进度、资产流水、审计和幂等结果；任一步失败全部回滚。

扣款售价和本金快照可以不同；差异必须在商品发布审核中明确显示，不能由代码推断。

### 6.2 核销 Robot Activation Voucher

1. 事务外按凭证 hash 从 primary 只读定位 `code -> rule -> robot_product_id`，只做格式/展示预检并形成候选根集合；预读不预留容量或资格。若 voucher rule 依赖等级，先完成固定预算 `EnsureLevelFresh`。
2. 正式事务先锁命令防重行和 rank 35 runtime root，再严格按 rank/type_code 锁 `robot_products -> robot_voucher_rules -> robot_voucher_codes -> user_robot_vouchers`，锁内重验 code 仍指向同 rule/product/mapping、归属当前用户、状态 ASSIGNED、未过期且商品可售。随后才收齐并锁本人及所需用户、等级、资格和任务行，复验 fresh token，通过 `ClaimFirstRobotHolding` 原子裁决首持仓；候选 product/binding、用户集合或等级 generation 变化时整体回滚扩集，禁止 user 后回锁 product。
3. 对商品执行与现金购买相同的容量条件占用；凭证持仓也占一个真实 holding capacity，售罄时整笔失败。随后以条件更新把 code 真源转 `REDEEMED`，创建 `robot_voucher_redemptions` 与来源为凭证的持仓；user mapping 保持不可变归属记录，不另写第二份状态。
4. 激活凭证持仓的 `principal_amount=0`，不创建本金返还、活跃值、团队返佣或合伙人池事实；按 voucher rule 产生直接收益。
5. 写任务进度和审计后提交。

两张不同激活凭证或现金购买与凭证核销并发时，所有路径先锁同一商品、再锁 voucher 根（如有）、最后锁用户/资格，因而不会形成 product↔user 反向环；资格唯一键使首持仓凭证最多成功一次。现金购买不会被错误拒绝，但它若先提交会使并发首持仓凭证失败；最后一份容量只能由一个入口占用。

### 6.3 日收益与返本

worker 在 primary 按 `next_run_at` 使用 `FOR UPDATE SKIP LOCKED` 领取持仓：

1. 领取事务外确定业务日和已发布到持仓的收益快照；等级商品先按固定预算执行 `EnsureLevelFresh`，不持有 holding/day/month 锁。真正结算事务再检查日结算唯一键并复验 fresh token。
2. 不达标时在同一事务写唯一 `robot_holding_settlements(status=SKIPPED_LEVEL,amount=0,ledger_id=NULL)`，保存当日等级/规则/reason，转/保持 `PAUSED_LEVEL`，并原子推进结算游标与 `next_run_at`；不得创建资产流水、返佣或 pool，也不得仅改状态而漏掉该日裁决。
3. 合格时选择该业务日显式 `robot_daily_rates`，缺失则取持仓 `default_daily_rate_snapshot`，再以持仓不可变 `yield_base_amount_snapshot` 计算 `direct_income=round(base*rate,scale,rounding_mode)>0`；同一事务创建 `POSTED` 日结算与 COMMON 直接收益。仅普通 COMMON 购买且规则允许时创建五层返佣；凭证虽可产生直接收益，但本金恒 0 且永无团队返佣。合伙人池已在现金购买成功时按本金快照创建一次，日结绝不新增或累加 pool fact。恢复后每个短事务只处理首个尚无日裁决的业务日（合格写 POSTED，不合格写 SKIPPED_LEVEL）并把 `settlement_cursor_date` 精确推进一天；既有 SKIPPED_LEVEL 永不回补。
4. 到期只表示不再生成新的应结日，不能绕过积压日直接成熟。仅当锁内证明 `[starts_on,ends_on)` 每个 Jakarta 业务日都恰有一条 `POSTED|SKIPPED_LEVEL` 裁决、`settlement_cursor_date=ends_on` 且不存在缺口时，后续有界终结事务才可对普通购买持仓入账本金快照、减少活跃值、更新五层聚合并转 `MATURED`；否则只推进 `next_run_at` 继续补齐最早缺口。
5. 激活凭证持仓终结只改状态，不返本、不返佣。

日结算、返佣、资产流水和持仓累计任一失败全部回滚，可按唯一键重试。任务状态不参与收益资格。

受控取消只对规则启用的 ACTIVE/PAUSED_LEVEL 开放，不接受管理员传入金额。事务只锁持仓并读取持仓内已固化的不可变产品/取消规则快照，不再回锁 rank 更低的产品行；随后锁现金来源原 partner pool GRANT，并在进入用户层前按 rank 锁原月份 month/qualification/settlement。若需要后续 OPEN 月 SOURCE_REVERSAL adjustment，也先 Ensure 并锁齐该月及 adjustment/application，最后才锁用户状态和资产。按 cancellation 表公式写唯一补偿（凭证为 0）、移除剩余活跃值并阻止未来日结/到期返本，再创建唯一 pool REVERSAL：原月份 OPEN 时对称冲减月资格和原 allocation，已封账时为各受益人创建后续 OPEN 月 SOURCE_REVERSAL 负调整。已结直接收益/团队返佣 KEEP；激活凭证持仓没有本金、活跃值、团队返佣或 pool GRANT，只转 CANCELLED 并保留核销历史。任一补偿、冲正、终态或审计失败全部回滚。

### 6.4 任务进度和奖励

- 同一业务 Use Case 能确认的事实（注册、购买、Playlet Backing、弹幕等）在其原事务中先走 closure→user gate，再调用 `RecordTaskProgress`。即使周期生成器尚未运行，原语也会懒创建或取得唯一 `user_tasks` 后原子写事件与进度，不允许先把事实提交、再依赖内存消息补任务。
- 一次性 VIP 履约使用 `source_domain=VIP, source_kind=ONE_TIME_VIP_ENTITLEMENT_CREATED, source_id=vip_entitlement_id` 推进 `PURCHASE_ONE_TIME_VIP`；`source_persisted_at` 必须由 registry 复制原 VIP 订单 `created_at`，VIP 订单、权益和进度同事务，重复回调命中来源唯一键。
- 异步可验证事实（例如达到视频观看阈值）由 primary 按源事实保存的 `(task_source_shard,task_source_seq)` 真实索引扫描，在自己的短事务调用同一原语；来源唯一键保证 worker 崩溃、Redis 信号丢失或重跑都不重复。每批只在目标 seq 内全部事实形成 APPLIED/IGNORED 终态后推进对应分片 consumed cursor；周期过期必须等待 grace、稳定 period barrier 和全部分片达到 upper，不能因为在途迟提交、消费者延迟或裸时间水位永久漏掉周期内事实。
- 客户端上报只提供候选证据，必须由播放事件、订单或其他服务端事实验证。
- 奖励领取在事务外预读 task/closure，正式事务按“命令防重 → day fence → closure → users → user_tasks → assets”加锁并复核集合。ACTIVE 正常领取；CLOSING 不扫描海量 progress events，而是要求 `claim_source_count>0`、proof hash完整、`claim_source_max_persisted_at < requested_at`，并核对 task progress_version 未变；不满足即不是 cutoff 前既得任务。通过后把新资产写成 blocker并唤醒 closure。随后条件 `CLAIMABLE -> CLAIMED`，把同一 source proof/version 快照复制到 `task_reward_claims`，调用 ApplyMutations并写审计；CLOSED拒绝，任一步失败全回滚。
- `CompensateUserTask` 事务外只做展示预检。正式事务按“命令防重 → REWARD_CORRECTION 时 income root SHARE → day fence → 异人审批 → 被纠正的稳定任务来源 → `PrelockUserClosures` → 既有 freeze（如有）→ `LockUsersAndValidateClosureGate` → user_tasks → assets（如有）”加锁；纯 PROGRESS_CORRECTION 同时跳过 root/day 和资产。预读无 closure 时取得 user 锁后再确认仍无 closure。ACTIVE 可追加经审批的 progress/reward correction；CLOSING 只接受能引用 cutoff 前已登记遗漏来源的 `PRE_CLOSURE_SOURCE_CORRECTION`，并同事务把 closure `next_check_at` 提前；CLOSED 一律拒绝，不创建 task compensation、钱包或 Finance case。补偿、审批消费、closure 唤醒和审计必须同成败。
- “任务不阻断合法收益”指没有适用规则、目标人群不匹配或任务未完成时分别记 IGNORED/保持未完成，不能拿任务资格阻断 Playlet Backing、机器人持仓、直接收益、返佣或提现；如果本应原子写入的任务事实发生数据库错误，则遵守全局事务不变量，来源业务与任务事实一起回滚，不能制造已成功业务但丢进度的半状态。

## 7. 幂等与锁顺序

| 命令 | 唯一键 | 固定锁顺序 |
| --- | --- | --- |
| 发放激活凭证 | actor/RPC/key；code/mapping 唯一 | 防重/审批 → voucher rule/code → closure gates → 目标用户 → 条件 ASSIGNED/追加 mapping |
| 关户作废激活凭证 | closure/code；disposition 对 code/mapping 唯一 | voucher code/mapping → closure gates → 用户 → 条件 VOID/追加 disposition |
| 购买机器人 | actor/RPC/key；用户/商品/购买序号业务唯一；首持仓资格唯一 | 防重 → level root(35) → income root(40) → day fence(50) → 商品/持仓 → OPEN month/qualification/settlement → closure gates → 用户/资格/关系/等级/任务 → 资产 → 追加持仓/pool/流水 |
| 核销激活凭证 | actor/RPC/key；voucher/redemption 唯一；首持仓资格唯一 | 防重 → level root(35，规则依赖时) → 商品 → voucher rule/code/mapping → closure gate → 用户/资格/等级/任务 → 条件占容量 → 追加 redemption/持仓 |
| 日结算 | holding/business_date | level root(35) → income root(40) → day fence(50) → 持仓 → closure gates → 用户/关系/资格/等级聚合 → 受益账户按 user/asset → 追加结算/流水 |
| 到期返本 | holding/terminal_operation | level root(35) → income root(40) → day fence(50) → 持仓 → closure gates → 用户/关系/资格/等级聚合 → 用户资产 → 追加终态/流水 |
| 现金持仓取消 | holding/terminal_operation；pool reversal 唯一 | level root(35) → income root(40) → day fence(50) → 持仓/原 pool GRANT → 原/后续 month、qualification、settlement、adjustment → closure gates → 用户状态 → 资产 → 追加补偿/REVERSAL/adjustment |
| 任务进度 | source_domain/source_kind/source_id/task_definition；ONCE lifetime 唯一 | 来源业务根 → closure → 用户 → 任务定义/规则 → 用户任务按 ID |
| 奖励领取 | user_task 唯一；actor/RPC/key | 防重 → income root(40) → day fence(50) → closure → 用户 → 用户任务 → 用户资产 |
| 任务补偿 | actor/RPC/key；compensation_no/approval 唯一 | 防重 → REWARD 时 income root(40)/day fence(50) → 审批/来源/recovery root → closure gate → 用户/任务 → 可选资产 → 追加 compensation/流水/审计 |

## 8. 失败模式

| 失败 | 行为 |
| --- | --- |
| 商品并发售罄 | 条件更新失败，资产和持仓全回滚 |
| 等级在购买前变脏 | 业务 Tx 外按固定波预算排水；真正 Tx 复验 fresh token，变化则可重试失败，不用 slave/缓存旧等级或在资金 Tx 内嵌套重算 |
| 某日收益率缺失 | 使用持仓快照内必填 default；持仓竟缺 default 属数据损坏，整体暂停并 P0 告警，不按 0 静默结算 |
| 结算进程崩溃 | 事务回滚或唯一事实已提交；按 `next_run_at` 重跑 |
| 凭证到期任务延迟 | 核销入口直接比较 `expires_at`，仍拒绝使用 |
| 凭证发放与注销并发 | code→closure→user 同序；先发放则成为 blocker 并由 disposition VOID，先 CLOSING/CLOSED 则不建立 mapping |
| 不同激活凭证并发首持仓 | 用户级锁 + 资格唯一键只允许一次 |
| 现金购买与首持仓凭证并发 | 共用 `ClaimFirstRobotHolding`；若现金先提交则凭证失败，若凭证先提交则现金作为非首笔继续，绝不产生两个首持仓事实 |
| 现金购买与凭证核销争最后容量 | 两条路径都先锁商品并做同一容量条件更新；只能成功一个，凭证路径不得先持 user/code 后等待商品 |
| 现金持仓取消重复/与日结并发 | 持仓行锁决定结算或取消顺序；补偿、活跃值、pool REVERSAL/adjustment 和终态同成败，重复只返回原结果 |
| 任务事件重复/乱序 | 来源唯一键去重，进度上限为目标值，已领取不回退 |
| 周期生成器延迟/与来源并发 | 两者共用 `EnsureUserTask`；唯一索引只产生一个实例，来源事实在原事务懒创建后立即计入 |
| ONCE 规则换版/重复生成 | lifetime partial unique 返回历史实例；已完成/已领取后永不创建第二份奖励 |
| 任务补偿与注销并发 | user 锁决定先后；普通补偿在 CLOSING/CLOSED 失败，cutoff 前来源纠错只在 CLOSING 白名单内成功并留下 blocker 唤醒 |
| Redis 信号丢失 | primary sweep 发现到期持仓/任务待办 |

## 9. 缓存与作业

- 商品列表、任务定义可缓存，键包含发布版本和定向条件；最终购买资格在 primary 重查。
- 激活凭证状态、持仓收益资格、任务可领取和资产余额不以缓存为真源。
- 作业：持仓日结算、到期返本、等级暂停/恢复校验、激活凭证过期标记、CLOSING 用户 ASSIGNED 凭证的有界 disposition sweep、任务周期预生成/到期、64 分片 source root 认领/连续 seq 消费、grace 后 period barrier 捕获与过期裁决、结算/任务对账。周期预生成与 Redis 都不是进度消费的正确性前提。
- Redis 提交后信号仅缩短等待；全部作业能从 `status/next_run_at` 或源事实恢复。

## 10. 指标与告警

- 商品：浏览/购买成功率、售罄竞争、售价与本金差异分布、等级拒绝原因。
- 持仓：待结算数、结算延迟、吞吐、暂停等级数、收益/返本/返佣金额、每来源 pool fact 数和重试次数。
- 激活凭证：生成、分配、可用、过期、核销、closure VOID/disposition、CLOSED 后发放拒绝、并发冲突、首持仓拒绝和资格消费来源分布。
- 任务：真实事件消费延迟、各 source shard 的 `last/target/consumed_source_seq` lag、最老 root lease、周期 barrier 未捕获/未覆盖分片数、grace 后过期延迟、进度去重、`PURCHASE_ONE_TIME_VIP` 完成数、可领未领、领取成功/冲突和伪证据拒绝数。

告警包括：激活凭证持仓产生返本或团队返佣、任务阻断业务收益、日结算重复、本金返还与快照不符、活动/订阅机器人类型出现、客户端手工推进任务成功。

## 11. 验收用例

1. 商品售价扣款、本金返本/活跃值/业绩分别按快照执行；现金 `yield_base=principal`，凭证 `yield_base=voucher rule snapshot` 且 principal=0，每日都按 `round(base*rate)` 与持仓 scale/舍入重算一致，运营改配置不改变既有持仓。
2. 等级刚好低于/等于/高于门槛的购买和每日收益正确；降级暂停、不补发暂停日、恢复后继续且历史不改。
3. 并发购买最后容量只有合法请求成功；余额、持仓、活跃值、任务和审计同成败。
4. 普通现金持仓购买成功时只创建一条 `pool_amount=principal_amount*5%` 的基础合伙人池事实；连续 N 日结算仍只有该一条，逐日收益、五层返佣和到期返本可重复执行而不重复入账。
5. 激活凭证持仓有直接收益但永不返名义本金、不增加活跃值、不产生团队返佣/合伙人池。
6. 两张激活凭证并发触发首持仓条件最多一张成功；现金购买和凭证核销正反并发顺序均只产生一条 `FIRST_ROBOT_HOLDING` 消费事实，且现金购买按规则正常完成；已过期但任务未标记的凭证仍无法使用。
7. 激活凭证分配/核销/作废/到期/关户处置正反并发后，code lifecycle 唯一真源与 user mapping/redemption/disposition 一一一致；不得出现两个 user mapping、一个 code 两次核销、CLOSED 后新 ASSIGNED 或两张表状态漂移。先发放后注销时 ASSIGNED 必须阻塞直至唯一 VOID disposition，注销先赢时发放完整失败。
8. 现金持仓在规则允许时取消：未结算补偿、活跃值回退、唯一 pool REVERSAL/封账后 adjustment 与 CANCELLED 同事务；重复取消以及取消/日结/到期乱序没有第二次资产或池效果。激活凭证持仓取消仍不返本/返佣。
9. 任务进度只能来自真实唯一事实；一次性 VIP 只通过 `ONE_TIME_VIP_ENTITLEMENT_CREATED` 完成 `PURCHASE_ONE_TIME_VIP`，全链没有 `SUB_VIP`；重复、乱序和伪造事件不多加，奖励并发领取只入账一次。暂停周期生成器后来源事务仍会懒创建并计入，生成器与来源并发也只有一个实例。
10. 同一任务定义的重复 version、交叠 PUBLISHED 区间和并发首版发布由行锁/唯一/exclusion 拒绝；边界相接时，每个 `period_start` 恰选一个版本，开放尾后继发布原子收口前版且不改既有用户任务。
11. ONCE 使用用户/定义 lifetime 唯一约束；完成、领取、规则换版和生成器重跑均不能创建第二个实例或第二笔奖励。DAILY/WEEKLY 在 Jakarta 周期边界前后归属唯一、无遗漏。
12. 任务无适用规则、目标人群不匹配或未完成时，机器人和短剧合法收益仍正常结算；应写 APPLIED 的任务 SQL 故障则与来源事实一起回滚。
13. Redis 信号全部丢弃后，持仓、激活凭证和任务 sweep 在 SLA 内恢复。
14. 全仓无 FlashSale、订阅机器人、普通支持券、双倍券、付费 TaskPlan 或活动机会写入口。
15. 现金购买与凭证核销对同一商品做 product→voucher→user 正反并发，最后一份容量只能生成一个 holding；核销事务外预读后把凭证切到另一规则/使商品下架/售罄，锁内重验必须完整失败且 code 仍 ASSIGNED、资格未消费。锁轨迹出现 code/user→product 的实现由门禁拒绝。
16. 任务进度/奖励补偿与注销请求正反并发遵守 05 章账号门禁：ACTIVE 先补偿则注销锁内复检看到未来资产能力，注销先进入 CLOSING 则普通补偿失败；只有 cutoff 前遗漏来源纠错可留下 `task_compensations` 并唤醒 blocker，CLOSED 后任务、钱包和版本均不变。
