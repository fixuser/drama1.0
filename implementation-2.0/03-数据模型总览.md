# 03 数据模型总览

## 1. 目标

本章给出 2.0 新库的逻辑 Schema、表归属、真源层级、公共约束和索引原则。字段细节以迁移 DDL 为最终可执行表达，但 DDL 不得偏离本章及领域文档。

数据库为 PostgreSQL。所有业务写、Schema 迁移和强一致读使用 `database.default`；`database.slave` 是同一业务库的延迟只读副本，不拥有单独业务事实。

## 2. 真源分层

| 层级 | 定义 | 示例 | 恢复方式 |
| --- | --- | --- | --- |
| A：不可变事实 | 已发生且不可覆盖的财务/业务事件 | `asset_ledgers`、结算明细、支付回调事件、审计 | 只追加；错误用反向事实 |
| B：当前事实 | 对象当前合法状态 | `users`、订单、持仓、冻结、权益 | 条件状态迁移；保留审计 |
| C：同步派生 | 与业务事实同事务维护的热路径数据 | `user_assets`、`referral_edges`、`user_levels` 聚合字段 | 可从 A/B 重建，并定期校验 |
| D：异步派生 | 允许延迟的查询加速 | 日 rollup、榜单、搜索索引、缓存 | primary sweep/全量重算 |

Redis、slave、日志平台和外部供应商响应都不属于数据库事实层级。

## 3. 公共字段与类型

### 3.1 标识与审计

- 业务表使用 `bigint generated by default as identity` 主键，或使用明确的自然唯一键；`users.id` 即业务 `user_id`。
- 所有外键字段用被引用对象单数名 + `_id`，用户外键一律为 `user_id`、`source_user_id`、`beneficiary_user_id` 等，不出现 code。
- 可变表至少有 `created_at timestamptz not null`、`updated_at timestamptz not null`、`version bigint not null default 0`。
- 软删除仅用于允许隐藏的配置/内容，字段为 `deleted_at`；订单、资产、结算、回调和审计不允许物理删除或软删后复用唯一键。
- 管理写入保存 `created_by_admin_id/updated_by_admin_id` 或关联 `admin_audit_logs`，不能只存昵称。

### 3.2 金额和数值

- 资产金额沿用 `shortmax` 的定点格式，统一为 `numeric(30,8)`；余额和冻结使用 `CHECK (value >= 0)`。
- 流水 delta 允许正负，但 before/after 非负且满足 `after = before + delta`。
- 业务提交的金额必须为正；方向由操作枚举决定。
- 比率使用 `numeric(18,8)`，在具体字段上限制范围，如 `[0,1]`。
- 活跃值使用 `numeric(30,8)`，它不是资产，不进入 `user_assets`。
- 数量和层级使用整数；关系深度为 `smallint` 且 `>=1`。

### 3.3 时间与状态

- 时间点用 `timestamptz`；业务日期用 `date`，均按 `Asia/Jakarta` 的 `BusinessClock` 生成。
- 周期用左闭右开 `[starts_at, ends_at)`；数据库比较不使用 `BETWEEN` 表达右开区间。
- 状态列使用稳定字符串并加 CHECK，或使用小整数 + 集中映射；不使用 PostgreSQL 原生 enum，以便受控扩展。
- 状态改变使用 `UPDATE ... WHERE id=? AND status IN (...)` 并检查影响行数。
- 可重建作业对象统一使用需要的 `dirty_at`、`next_run_at`、`attempt_count`、`last_error_code`，但不强迫所有表都具有这些字段。

WHERE status='APPROVED' AND expires_at>now() AND request_hash/action/target/permission 全匹配` 一次消费，且消费、目标业务变更、命令幂等与 `admin_audit_logs` 同一事务；审批行不保存或代为执行 payload。

## 6. 关键唯一约束

`users.registration_seq` 由数据库 sequence 单调分配且不可更新：CHECK 要求 `type='NORMAL'` 时 `registration_seq/registered_at NOT NULL`，其他主体 `registration_seq IS NULL`；partial unique `users(registration_seq) WHERE type='NORMAL'` 防止复用。sequence 回滚产生的 gap 合法且永久保留，任何统计都不得把 gap 当用户或使用 `COUNT(seq range)` 代替枚举真实行。`users.closure_generation` 非空、初始 0 且只允许在账号 `ACTIVE -> CLOSING` 时与唯一 closure 创建同事务加一；2.0 不提供取消注销或重开路径。`users.relation_path_key` 由 root→self 的固定 8 字节大端 user ID 段组成，平台常量 `RELATION_PATH_MAX_DEPTH=128`；CHECK 强制 `relation_depth BETWEEN 0 AND 128`、字节长恰为 `8*(depth+1)` 且不超过 1032，并复核末段。REFERRAL 规则的 `max_relation_depth` 发布约束必须在 `[1,128]`，注册或无下级的一次后绑定同事务更新 path；它可由 inviter 链重建，不是关系真源。

22. `finance_recovery_case_roots(source_type,source_id,source_component,subject_user_id,direction)` 唯一，`case_id` 非空时唯一且不可改回空；`finance_recovery_cases(case_no)`、`root_id` 分别唯一，并重复保存/约束校验同一自然键供审计。案件保存 `value_basis=ASSET|EXTERNAL|BOTH`、可空 `asset_type/amount`、可空 `external_currency/external_amount`、`available_snapshot/account_status_snapshot/provider_event_id/reconciliation_id/source_terminal_snapshot/reviewed_by/reviewed_at/waiver_approval_id/resolution_id/resolved_by/resolved_at/waived_by/waived_at/canceled_at`。ASSET 只允许正 asset 组且 external 组空，EXTERNAL 反之，BOTH 两组都正；纯法币 VIP 矛盾必须用 EXTERNAL，不能把可为 0 的返佣基数伪装为会计资产额。原因枚举固定含 `CLOSED_ACCOUNT|INSUFFICIENT_AVAILABLE|ACCOUNT_CLOSURE_COMMON_DUST|EPISODE_REFUND_AFTER_ACCOUNT_CLOSED|COLLECT_SUCCESS_AFTER_CONFIRMED_NOT_PAID|COLLECT_FAILURE_AFTER_LOCAL_PAID|REFUND_SUCCESS_AFTER_LOCAL_CANCELED|VIP_REFUND_SUCCESS_AFTER_NOT_ACCEPTED|REFUND_FAILURE_AFTER_LOCAL_REFUNDED|PAYOUT_SUCCESS_AFTER_LOCAL_FAILED|PAYOUT_FAILURE_AFTER_LOCAL_ARRIVED|DUPLICATE_PAYOUT_AFTER_CHANNEL_SWITCH|DUPLICATE_PAYOUT_REVERSED_AFTER_RECOVERY|PAYOUT_LATE_SUCCESS_REVERSED_AFTER_RECOVERY|PAYOUT_SUCCESS_AFTER_FAILURE_COMPENSATED`。前两项约束账号/余额快照；COMMON_DUST 要求 PAYABLE+ASSET(COMMON) 并引用同用户 closure disposition；EPISODE reason 要求 PAYABLE+ASSET、source=`EPISODE_REFUND_REQUEST`、component 为 `COMMON|EXPERIENCE` 且引用同用户、窗口内唯一请求及对应正订单实付组件；支付/出款类必须引用已验签 provider event 或已封存 reconciliation discrepancy。reason registry 统一约束方向、强类型 source/component、原本地终态和价值快照。案件 `version` 只增，状态允许 `OPEN -> IN_REVIEW -> RESOLVED`，仅 RECEIVABLE 的 `IN_REVIEW -> WAIVED`，以及仅通过唯一 `finance_case_source_reversals` 从 OPEN/IN_REVIEW 转 `CANCELED_BY_SOURCE_REVERSAL`；CANCELED 要求没有 settlement/waiver、保存取消证据且不能重开。WAIVED 必须满足 RECEIVABLE、消费目标/hash 匹配的异人审批、记录 waived actor/time 且 resolution 为空，PAYABLE+WAIVED 由 CHECK/触发器共同拒绝，所有终态不可重开。
   `finance_recovery_cases.value_fingerprint` 是 NOT NULL 生成列，按版本化规范编码 `direction/value_basis/asset_type/amount/external_currency/external_amount`，对不适用的 nullable 组使用域外类型哨兵而不是 SQL NULL，并建立 `UNIQUE(id,value_fingerprint)`。`finance_external_settlements` 保存 `id/case_id/provider/settlement_type/external_reference/direction/value_basis/asset_type/amount/external_currency/external_amount/value_fingerprint generated/evidence_hash/settled_at/recorded_by/created_at`；`case_id` 唯一，非空 `(provider,settlement_type,external_reference)` 全局唯一，并以 `(case_id,value_fingerprint)` composite FK 引用案件。CHECK 仍分别验证 ASSET/EXTERNAL/BOTH 的原始列形状；生成函数从 settlement 原始列重算，调用方不能直接提供 fingerprint，因此 nullable 组不能利用 MATCH SIMPLE 绕过全额匹配。证据来自受信 Finance 渠道；case 只有在同事务插入该行并回填唯一 resolution_id 后才能 RESOLVED。同一凭据并发用于两案最多一案成功。首发一笔 settlement 只对应一案；批量收付必须另立 ADR，引入 settlement allocation 与 sum 守恒，不能放宽唯一键。

   `team_rebate_settlements.finance_recovery_case_id` 可空、非空时 UNIQUE/FK；GRANT 仅允许 `FROZEN|POSTED|RELEASED|CANCELED`，REVERSAL 只允许 `CANCELED_FROZEN|POSTED|EXTERNAL_RECOVERY`。REVERSAL=CANCELED_FROZEN 必须引用原 FROZEN→CANCELED GRANT、非空 terminal freeze ledger 且 case 为空；REVERSAL=EXTERNAL_RECOVERY 当且仅当 case 非空并引用原 RELEASED GRANT；POSTED 引用原 RELEASED GRANT且 case 为空。约束触发器验证 REVERSAL 与原 GRANT 的来源组件、受益人、资产与全额金额一致；POSTED 与 EXTERNAL_RECOVERY 都保持原 GRANT RELEASED，只有 CANCELED_FROZEN 把原 GRANT 从 FROZEN 推进为 CANCELED。

   `benefit_forfeiture_audits(source_type,source_id,source_component,beneficiary_user_id)` 唯一，并保存 `calculation_mode/previous_effective_rate_before/previous_effective_rate_after/entitlement_rate/candidate_diff/not_granted_amount` 和规范 trace hash。DIFFERENTIAL 不合格/非 ACTIVE 候选必须 `previous_after=previous_before AND not_granted_amount=0`；FLAT 先计算规范未舍入值和 rounded amount：base/rate 为零记 ZERO_DIFF，未舍入正但 rounded=0 记 ZERO_ROUNDED，这两种只进入 `team_rebate_calculation_audits`，不创建 forfeiture；只有 rounded>0 且候选非 ACTIVE 时才建立精确正 `not_granted_amount` 的 forfeiture。案件/forfeiture 都是业务结果事实，必须与来源退款/返佣结算同一事务插入；不得换幂等键重复建案，也不得由后续 worker 伪造钱包补记。`robot_voucher_codes` 建 `UNIQUE(id,assigned_user_id)`，`user_robot_vouchers` 建 `UNIQUE(id,code_id,user_id)` 并以 `(code_id,user_id)` composite FK 回 code 真源；redemption、holding 的凭证来源和 disposition 均以完整 `(user_voucher_id,code_id,user_id)` composite FK 回同一映射。`robot_voucher_dispositions(code_id)`、`robot_voucher_dispositions(user_voucher_id)` 分别唯一，且只允许引用同用户、同 code 的 ASSIGNED 归属事实。
23. `income_percentile_heads(window_type,as_of_month_end,calc_version_id)` 唯一，`current_generation` 只增；selected 的 publication ID/generation/proof 三字段同空同非空。publication 除业务唯一键外显式建立 `UNIQUE(id,window_type,as_of_month_end,calc_version_id,generation)`；head 以列序完全一致的 `(selected_publication_id,window_type,as_of_month_end,calc_version_id,selected_generation)` composite FK 引用它，不能假设 `id` 单列唯一会自动支持复合 FK。延迟约束触发器再保证切 head 的提交时 selected publication 为 VALIDATED、generation 不大于 current 且 `selected_proof_hash=publication.proof_hash`。head 有 selected 时不得将 dirty 置空，除非锁内比较的前驱 selected proof 与当月 selected hash 都等于 publication dependency；无 selected 时 API 只能 NOT_READY。`income_percentile_publications(window_type,window_start,window_end,as_of_month_end,calc_version_id,sample_protocol_version,generation)` 唯一，同一 head 最多一个当前 VALIDATED generation；`income_percentile_inputs(publication_id,generation,user_id)`、`user_income_percentiles(publication_id,generation,user_id)` 分别唯一。只有固定人口 cutoff 的规范用户重扫与 input 清单、input 与 rank 结果的成员/金额/rank count/hash 分别相等、依赖 hash 仍匹配且所有游标到尾，publication 才可 VALIDATED；发布替代代次时同事务把旧 VALIDATED 转 SUPERSEDED、新代转 VALIDATED并切 head，BUILDING/SUPERSEDED/ABANDONED 行永不被用户查询。
   `income_percentile_publications` 还保存六个同空同非空前驱身份列：`predecessor_publication_id/predecessor_window_type/predecessor_as_of_month_end/predecessor_calc_version_id/predecessor_generation/predecessor_proof_hash`。目标建立不含可变 status 的 `UNIQUE(id,window_type,as_of_month_end,calc_version_id,generation,proof_hash)`；子列按完全同序 composite FK 引用该不可变身份。CUMULATIVE 只有 `as_of_month_end=first_earning_month` 的首月允许空前驱；YEAR 只有 `as_of_month_end=max(该年一月,first_earning_month)` 的首月允许空前驱。其余 publication 必须指向同 window/calc 的前一自然月；创建/发布时延迟触发器复验前月 head 当时仍选中该 generation/proof 且目标状态为 VALIDATED，YEAR 不得跨年。目标后来被 SUPERSEDED 不修改身份键，也不级联子行；旧后继继续作为 stale 旧链可读并由依赖 sweep 重建。这样后继用 NULL 截断累计链、引用错月份/窗口/calc/proof 都无法提交。
24. `team_rebate_calculation_audits(source_kind,source_fact_id,source_component)` 唯一，保存完整规范五层输入/裁决 hash；所有对应 GRANT/forfeiture 必须引用同一 audit。即使五层均无正金额也必须存在一行，重放只能命中原 hash。
25. `income_month_publications(earning_month,calc_version_id)` 唯一且 `current_generation` 只增；`income_month_generations(earning_month,calc_version_id,build_generation)`、`income_month_shards(earning_month,calc_version_id,build_generation,shard_id)`、`income_monthly_rollups(user_id,earning_month,category,calc_version_id,build_generation)` 唯一。generation 与 shard 都由 DDL CHECK 强制 `shard_count BETWEEN 1 AND 256`，shard 还要求 `0<=shard_id<shard_count`，范围必须连续、无空洞/重叠；应用配置不得突破硬上限。只有恰好 1..256 个范围连续的 SUCCEEDED shard 且 daily source/result 证明相等，generation 才可 VALIDATED 并被 head 原子选中；新 current 构建/失败时旧 selected 仍可读，部分/FAILED/ABANDONED/SUPERSEDED generation 永不可读。
26. `level_rule_runtime_roots(domain)` 唯一，serving/effective candidate 不得相同，状态 CLEAN 时 candidate/seed cursor 必为空，非 CLEAN 时 candidate 与 generation 必填；所有等级读写入口在非 CLEAN 时失败关闭，serving 只可在完整 seed、dirty 波清零和独立 proof 通过的短事务切换。`user_levels.dirty_at` 非空时 `dirty_generation>calculated_dirty_generation`；`is_qualified` 必须是 `level_rule_version_id/qualified_level_snapshot` 下最后成功结果。`level_recalc_queue(user_id)` 唯一并与 dirty 行 generation 一致，relation path 必须等于同用户当前 path；lease owner/until/generation 成组出现。清 dirty/删 queue 必须同时匹配 metrics、dirty 和 lease generation；任何合格状态变化只更新前五层并为实际输入变化的祖先创建下一波。

27. 跨表“同主体/同业务根”一律使用可由 PostgreSQL 直接建立的 exact composite key：`asset_freezes UNIQUE(id,user_id,asset_type)` ← `asset_ledgers(freeze_id,user_id,asset_type)`；`play_authorization_requests UNIQUE(user_id,request_id,correlation_id)` ← issuance 同序三列；`partner_settlement_adjustments UNIQUE(id,user_id,beneficiary_hash)` ← head 的 `(adjustment_id,beneficiary_user_id,beneficiary_hash)`；`account_closures UNIQUE(id,user_id)` ← 所有 closure 子事实的 `(closure_id,user_id)`；`vip_orders UNIQUE(id,user_id)` ← entitlement 的 `(vip_order_id,user_id)`。必选引用的整组子列均 NOT NULL；可选引用（例如普通 INCOME/EXPENSE 的 `freeze_id`、NORMAL 兑换的 `closure_id`）由判别 CHECK 约束为“不适用时引用 ID 为空、适用时完整非空”，再建立可空 composite FK，不能把所有场景一刀切成 NOT NULL。触发器只验证状态/hash，不得假装替代父 UNIQUE/FK。
28. 收款 current pointer 防串单：`payment_attempts` 建 `UNIQUE(id,deposit_order_id)`、`UNIQUE(id,vip_order_id)`，`deposit_orders(current_attempt_id,id)` 与 `vip_orders(current_attempt_id,id)` 分别同序引用对应父键；current 为空时允许无 attempt，非空时必须同单，kind/status 再由延迟约束验证。提现不存在专用人脸表或引用。`otp_bindings` 另建 `UNIQUE(id,user_id)`，withdrawal 的 `(otp_binding_id,user_id)` composite FK 同序指向它；`otp_mode=NOT_REQUIRED` 时 `otp_binding_id/otp_accepted_step` 必须全空，`TOTP` 时必须完整非空，延迟约束只校验创建时复制的 binding 身份和 step，不因后续合法重置改写已提交 withdrawal。
29. `account_closure_rule_settings(rule_version_id)` 唯一，`closure_channel_count CHECK BETWEEN 1 AND 32`；`account_closure_channel_slots` 建 `UNIQUE(rule_version_id,slot_no)`、`UNIQUE(rule_version_id,payment_channel_id,fiat_currency,channel_rule_version_id)`，slot CHECK 1..32，全部列非空并真实 FK 到规则/渠道版本。PUBLISHED 延迟约束验证实际 `COUNT(*)=closure_channel_count`、slot 恰为连续 1..count、canonical set hash 相等且发布后无 UPDATE/DELETE；因此 dust 事务最多锁 32 个槽而不是历史全部渠道。

唯一约束是并发正确性的最终防线，不能只靠查询后插入或 Redis 锁。

## 8. 枚举真源

Proto 是跨进程枚举真源，数据库约束与 Go 映射由同一登记表生成或在 CI 比对。首发核心枚举：

- `AssetType`: `UNSPECIFIED, COMMON, EXPERIENCE`。
- `AssetMutationKind`: 六种资产操作，见资产文档。
- `FreezeStatus`: `UNSPECIFIED, ACTIVE, RELEASED, SETTLED`。
- `UserLevel`: `UNSPECIFIED, L0, L1, L2, L3, L4, L5, L6, L7`。
- `RobotHoldingSource`: `UNSPECIFIED, COMMON_PURCHASE, ROBOT_VOUCHER`；现金合伙人池来源独立使用 `CASH_ROBOT_PURCHASE`。
- 支付、提现、持仓、任务和内容状态均使用领域前缀，禁止通用 `Status` 混用。
- `DepositOrderStatus`: `UNSPECIFIED, PENDING, EXPIRED, FAILED, PAID, REFUND_PENDING, REFUNDED, REFUND_CANCELED`；REFUND_CANCELED 只用于充值退款明确未受理后的不可逆释放终态。
- `VipOrderStatus`: `UNSPECIFIED, PENDING, EXPIRED, FAILED, PAID, REFUND_PENDING, REFUNDED, REFUND_NOT_ACCEPTED`；最后一项必须引用唯一退款 attempt 的权威未受理证据，且保留原 entitlement、返佣、任务和资金效果。
- `VipSlotReservationState`: `UNSPECIFIED, RESERVED, CONSUMED, RELEASED`；RESERVED 仅可单向转为支付履约的 CONSUMED 或财务确认未支付的 RELEASED，权益后续到期/退款不回写该历史状态。
- `EpisodePurchaseRefundFinality`: `UNSPECIFIED, NOT_ELIGIBLE, ELIGIBLE, REQUESTED, REFUNDED, REJECTED, EXPIRED`；`EpisodeRefundRequestStatus`: `UNSPECIFIED, REQUESTED, SUCCEEDED, REJECTED, EXPIRED`，不存在可持久化 APPROVED。
- `PaymentAttemptStatus`: `UNSPECIFIED, CREATED, PENDING, UNKNOWN, SUCCEEDED, FAILED, NOT_ACCEPTED`；NOT_ACCEPTED 只允许 REFUND 且要求权威未受理证据。`PayoutFailureResolutionKind`: `UNSPECIFIED, NO_ELIGIBLE_CHANNEL, OPERATOR_ABORT, ATTEMPT_LIMIT_REACHED`。
- `PayoutFinancialStatus`: `UNSPECIFIED, NO_SUCCESS, SUCCESS_CONFIRMED, SUCCESS_REVERSED`；`PayoutSuccessDisposition`: `UNSPECIFIED, CANONICAL, DUPLICATE, LATE_AFTER_LOCAL_FAILURE, REVERSED`；二者按 09 章有界集合协议生成，不由 API 客户端填写。
- `FinanceRecoveryCaseStatus`: `UNSPECIFIED, OPEN, IN_REVIEW, RESOLVED, WAIVED, CANCELED_BY_SOURCE_REVERSAL`；最后一项没有管理写接口，只能由有权威证据的来源反转事务生成。

禁止创建支持值、普通支持券、旧等级名、自动续订、活动或旧订单类型的枚举值。

## 9. 配置版本

影响资金/权益的配置采用 `DRAFT -> REVIEWED -> PUBLISHED -> RETIRED`：

- 已发布结构化内容、`content_hash`、版本号和 `effective_at` 不可原地修改；修正生成新版本。唯一例外是发布紧邻后继版本时，在同一 domain 锁事务中把开放尾前版的 `expires_at` 从 `NULL` 一次性收口为后继 `effective_at`，并写 `SUPERSEDE` 发布审计；不得改为其他时间或再次修改。
- 发布事务只允许按版本号在已发布时间线尾部追加，校验生效区间不冲突、引用齐全、比率/金额合法，并写审计；禁止向已发布时间线中段插入或覆盖。开放尾收口和后继 PUBLISHED 插入必须原子完成，任一步失败全部回滚。
- 命令按 `effective_at <= now < next_effective_at` 从 primary 解析版本。
- 订单、持仓、权益、结算保存版本 ID 和必要数值快照，后续发布不重写历史。
- 缓存键包含版本，发布后的 Redis 失效只是加速。
- `rule_versions` 只保存版本头和 `content_hash`，不藏任意 JSON 业务规则。`REFERRAL`、`ACCOUNT_CLOSURE`、`ASSET_EXCHANGE`、`TEAM_LEVEL`、`TEAM_REBATE`、`PARTNER`、`DEPOSIT`、`WITHDRAWAL`、`BANK_DIRECTORY`、`ROBOT_PRODUCT` 等运行时值必须落在本章登记的结构化 settings/rates/sources 子表；发布事务校验子表齐全，并让 `content_hash` 覆盖规范化后的全部子表内容。
- 尚未生效且无任何引用的时间线尾版本只能由 `ReplaceScheduledRuleVersion` 处理：在 domain/前驱/目标全锁定且双人审批后，要么恢复前驱 `expires_at=NULL` 并退役目标，要么保持原边界、退役目标并发布已复核替代版。禁止把退役、恢复前驱和发布替代版拆成多次提交；失败时原时间线与 hash 完整保留。`RETIRED` 只退出新事实的事件时间选择，历史仍按 ID 回放。

## 10. Schema 迁移规范

1. 只有 `migrate` 进程可执行迁移，应用进程启动时只检查最低/最高兼容版本。
2. 迁移文件单调编号、代码评审、校验和固定；生产已执行文件不可修改。
3. P0 空库可一次创建基线 Schema；之后采用 expand → deploy → contract，避免长锁。
4. 新非空列先加 nullable/默认策略、回填、校验，再加约束；大索引使用并发创建并单独监控。
5. DDL 事务能力在迁移文件中显式声明；失败不得把版本标为完成。
6. 回滚优先回滚应用和配置；不可逆财务表 DDL 不提供破坏性 down。
7. 本项目不包含 1.0 数据迁移、旧表读取、双写、CDC 或割接脚本。

## 11. 数据保留、分区与归档

- 资产流水、订单、支付事件、提现、结算和审计按合规长期保存。
- 大表初始保持简单的非分区结构；以固定生产规模压测验证。只有单表规模、维护窗口或查询计划达到书面阈值后才通过 ADR 分区。
- 归档不得改变余额/冻结守恒和用户账单；归档前后均运行 hash、行数和金额对账。
- 隐私删除对可匿名化资料做不可逆脱敏，不删除法定财务事实。

## 12. 验收用例

1. 全部表、外键、CHECK、唯一约束和索引均能从迁移在空 PostgreSQL 一次构建。
2. Schema 扫描只出现 `COMMON/EXPERIENCE`，不存在支持值、F 码、普通支持券和旧等级枚举。
3. 删除/禁用用户不会级联删除关系、资产、订单、结算或审计。
4. 所有 `user_id` 外键类型一致；`referral_edges` 五层可从 `users` 祖先链重建并逐行一致。
5. 重复业务键、非法金额、负余额、无效状态和 unspecified 枚举由数据库拒绝。
6. 在目标数据集上执行热查询，计划命中预期索引且没有子树全表扫描。
7. `database.slave` 生产账号执行 INSERT/UPDATE/DELETE/DDL 必须失败。
8. 迁移 CI 完成空库 up、Schema diff、约束检查和应用兼容版本检查。
