# 00 设计决策与术语

## 1. 目的

本章把 2.0 已确认选择固化为不可被实现细节悄悄改写的决策，并统一领域语言。除非新增 ADR 明确替代，本文中的“必须/禁止”均是上线门禁。

## 2. 决策登记

| 编号 | 决策 | 直接后果 |
| --- | --- | --- |
| D-001 | 2.0 从空库开始 | 只建新 Schema；没有历史导入、双写、旧系统割接和兼容查询 |
| D-002 | 全新 `/v2` API | 不保留旧 Proto、旧 HTTP 路径、旧枚举 wire 值或代理层 |
| D-003 | 资产仅 `COMMON`、`EXPERIENCE` | 支持值和活动资产不进入模型；每种资产独立守恒 |
| D-004 | 关系只使用 `user_id` | 分享、请求、数据库外键和日志均使用 `user_id`；F 码完全不存在 |
| D-005 | 同库事实单事务 | 顶层 Use Case 在 `database.default` 开启一次事务，内部写原语只接收 `Tx` |
| D-006 | `slave` 只做可延迟查询 | 余额、资格、幂等、状态推进和读己之写全部访问 primary |
| D-007 | 不建通用 Outbox | 可重建工作使用业务状态 + primary sweep；Redis 通知只加速 |
| D-008 | L0–L7 规则保留、实现重做 | 使用顺序枚举、版本规则、聚合快照、纯函数和审计，不保留旧名映射 |
| D-009 | `requirements-1.0/91` 默认建议正式化 | 不再作为待确认项；其默认值是 2.0 初始业务规则 |
| D-010 | 业务时区固定 | `Asia/Jakarta`；业务周从周一 00:00 开始，区间统一为左闭右开 |
| D-011 | 错误边界使用 Forge `errkit` | Domain 只返回 sentinel/typed error；Service 统一映射为安全业务码，Transport 编解码 Proto/gRPC/HTTP |
| D-012 | Forge `message` 只作 SMS/Email 发送适配 | 固定版本，事务外发送；数据库保存 challenge/delivery、lease、retry 与 sweep；不实现 WhatsApp |
| D-013 | 外部 callback 保留原始 HTTP | 固定字面量路由先对 raw body/headers 验签，再映射内部 typed command；不规划 callback Proto |
| D-014 | HTTP 路径不含路径参数 | GET 选择器放 query，POST 命令标识放 Proto body，callback 只注册 provider/kind 固定路由 |
| D-015 | 提现不做专用人脸检查 | 保留基础 KYC 与已核验银行卡；TOTP 从未成功确认可跳过、ACTIVE 必验，曾确认但当前 REVOKED（含 reset）须重绑或受控恢复 |
| D-016 | 英文业务名不使用泛化 `Support` | 现金短剧参与为 `Playlet Backing`，现金机器人为 `Robot Purchase`，机器人券为 `Robot Activation Voucher` |

## 3. 正式化的产品规则

| 主题 | 2.0 正式规则 |
| --- | --- |
| 机器人售价/本金 | 实际扣款使用商品售价；返本、活跃值和业绩使用购买时的显式本金快照 |
| 等级机器人 | 当前等级不低于商品要求才产生后续收益；降级暂停，已结算历史不追溯 |
| 机器人激活券 | 英文规范名 `Robot Activation Voucher`；不返名义本金，不产生团队返佣 |
| 等级初始值 | L0 只作为注册事务内的初始化值；首次纯函数计算后普通用户以 L1 提交，L1 为零门槛基础等级 |
| 短剧参与份额 | 英文规范名 `Playlet Backing`；使用版本化的固定份额或最小金额配置，不硬编码“必须恰好 50” |
| 任务与收益 | 任务只控制任务奖励，不能阻断合法参与收益、机器人收益或返佣 |
| 一次性 VIP | 只按后台已发布商品的显式价格出售；无首购隐式价、优惠券或自动续订 |
| 一次性 VIP 任务 | 稳定 code 为 `PURCHASE_ONE_TIME_VIP`，只接受 `ONE_TIME_VIP_ENTITLEMENT_CREATED`；不使用 `SUB_VIP`/订阅语义 |
| 购买返佣 | 剧集和一次性 VIP 的直属/间接两层返佣先进入 COMMON 冻结；到期释放，退款按唯一 REVERSAL 取消或追偿 |
| 合伙人基础池 | 每笔合格 `Playlet Backing` / `Robot Purchase` 现金本金成功时只创建一次 5% pool fact；每日收益结算不得重复入池 |
| TaskPlan | 付费 TaskPlan 不进入 2.0 |
| 合伙人系数 | `0.3/0.5/0.7/1.0` 分别表示池的 30%/50%/70%/100% |
| 团队禁用 | 只限制团队相关能力；只有账号状态禁用才禁止登录 |
| 广告解锁 | 一次已验证广告完成事件永久解锁指定剧集，权益唯一且可审计 |
| 真实播放 | 凭证签发、续播进度和 heat 均不算真实播放；只接受服务端可验证 start/heartbeat/CDN/provider 事件 |
| Banner | 服务端按时间、位置、语言、区域、平台、优先级和数量上限过滤 |
| 敏感弹幕 | 保存为本人可见、待审核；不伪装成公开发布成功 |
| 展示放大值 | 只能称“热度”，不能作为真实人数、销量、播放量或资金统计 |
| 注销 | 先禁止新动作；COMMON 经注销用途提现清退，EXPERIENCE 只能显式兑换或留有处置事实后放弃；全部持仓、冻结、在途提现终结后完成 |
| 银行卡姓名 | 规范化比较 + 供应商核名；不确定结果进入人工复核 |

## 4. 统一术语

| 术语 | 定义 | 禁止混用 |
| --- | --- | --- |
| 用户 `user_id` | `users.id`，唯一业务身份编号 | 粉丝码、邀请码、外部身份 ID |
| 上级 `parent_id` | 用户唯一直属邀请人 | 任意五层祖先、后台数据范围 |
| 祖先链 `inviter_ids` | 从直属上级到根的完整 `bigint[]` 快照 | 字符串数组、五层边表 |
| 五层边 `referral_edges` | 为普通团队、等级和返佣派生的 1–5 层关系 | 权威关系源、全链后台权限 |
| 粉丝 | 产品展示用语，等同“某用户的下级成员” | 独立标识类型 |
| 团队 | 按关系和业务层数形成的统计/权益集合 | 账号登录权限 |
| `COMMON` | 可消费、可用于参与产品、可提现的通用资产 | 支持值、法币账户余额 |
| `EXPERIENCE` | 仅可用于指定消费和配置化兑换的体验资产 | 可提现资产、支持值 |
| 可用余额 | 当前可立即执行允许操作的金额 | 总资产、冻结金额 |
| 冻结总额 | 某用户某资产所有 ACTIVE 冻结明细之和 | 跨资产相加的“总冻结” |
| 冻结明细 | 解释冻结来源、状态和终结方式的事实 | 提现单或收益单的替代物 |
| 流水 | 余额桶每次变化的不可变前后快照 | 可编辑业务日志 |
| 活跃值 | 等级和团队规则使用的非货币指标 | `EXPERIENCE`、支持值、资产余额 |
| 持仓 | 用户购买/参与后按规则产生收益的业务合约快照 | 账户冻结明细 |
| 短剧参与 `Playlet Backing` | 用 `COMMON` 参与已发布短剧产品，形成可结算业务事实 | 客服 support、剧集购买、任务奖励 |
| 机器人购买 `Robot Purchase` | 用 `COMMON` 购买机器人商品并形成持仓 | 旧名 Robot Support、券核销 |
| 机器人激活券 `Robot Activation Voucher` | 仅用于激活零本金机器人持仓的券 | 普通短剧支持券、现金购买 |
| 直接收益 | 持仓归属用户自身的结算收入 | 五层返佣、合伙人分红 |
| 五层返佣 | 来源用户最多五层上级按等级差额获得的收入 | 完整祖先链、活动奖励 |
| 合伙人分红 | 按月、按家庭活跃值和系数分配的基础池收入 | 五层返佣、活动池 |
| 一次性 VIP | 明确期限的一次购买权益 | 支持等级 L1、自动订阅 |
| 业务日 | `Asia/Jakarta` 下的自然日 `[00:00, next 00:00)` | 服务器本地日、UTC 日 |
| 幂等键 | 命令语义和结果的唯一重放标识 | 仅 Redis 锁、随机日志 ID |

## 5. 全局不变量

1. 金额均为十进制定点值；API 使用字符串，数据库使用统一精度的 `numeric`，禁止浮点数。
2. 每个用户每种资产恰有一个账户行；两个资产的余额、冻结和流水分别守恒。
3. 资金事实、业务事实、幂等结果和审计要么在同一 primary 事务内全部成功，要么全部失败。
4. 所有状态迁移必须有允许边集合、条件更新和终态幂等；禁止“直接覆盖任意状态”。
5. 用户自助命令的主体只来自令牌，不能使用请求体传入的 `user_id`。
6. 所有业务规则都通过带版本的已发布配置解析；持仓、订单和结算保存所使用的规则快照或版本。
7. Redis、slave 和 rollup 均为可丢失或可延迟派生数据，不能作为资金、资格或权益事实。
8. 真实指标和展示热度分表或分字段；财务报表只消费白名单事实。
9. 删除采用业务状态或软删除；不可变流水、订单、结算和审计不得覆盖或物理删除。
10. 排除项没有表、Proto 枚举、API、任务、消费者、配置、缓存或统计写入口。
11. Domain 不依赖 Forge；裸 SQL/供应商错误必须在 Service 映射为稳定业务码，客户端不得收到密钥、SQL、内部路径或供应商原文。
12. HTTP binding 不得含动态路径参数；外部 callback 必须在解码前对受限长度的 raw body 与必需 headers 验签。
13. SMS/Email 的 challenge/delivery 事实、lease、重试和扫描都以 primary 为真源；Forge `message` 成功只表示 `PROVIDER_ACCEPTED`，不表示已送达。没有供应商幂等/查询证据时，超时或调用后崩溃必须收敛为 `UNKNOWN`，禁止自动重发制造重复消息。
14. 提现不存在专用人脸检查事实；已 ACTIVE 的 TOTP 绑定必须在提现事务原子校验防重放，曾确认后 reset/revoke 不能降级为“从未成功确认”；仅有未确认 PENDING/EXPIRED 历史仍属于 NEVER_BOUND。

## 6. 状态与时间约定

- Proto 枚举第一个值必须为 `*_UNSPECIFIED = 0`；业务写入拒绝 unspecified。
- 运行时依赖 `github.com/toolbelts/forge` 首发精确锁定 `v0.4.1`；升级必须重跑错误 wire 契约和 SMS/Email 投递故障矩阵，禁止漂移版本范围。
- 数据库保存稳定字符串枚举或受 CHECK 约束的小整数；映射只有一处，不依赖显示文案。
- 业务时间统一保存 Unix 秒或 PostgreSQL `timestamptz`；计算周期必须经过 `BusinessClock`。
- 日、周、月范围均使用 `[start_at, end_at)`，周一 00:00 是周起点。
- `created_at` 只表示创建；`updated_at` 表示事实最后变化；终态另有 `resolved_at/completed_at/ended_at`。
- 管理员更正通过冲正或新版本完成，不回写历史快照。

## 7. 决策变更流程

涉及资金单位、账户桶、关系真源、等级门槛、返佣、外部支付命令或一致性路径的变更，必须提交 ADR，至少回答：

1. 替代哪项决策，为什么当前不变量无法满足新需求；
2. 新状态机、Schema、API、事务、幂等和故障恢复如何工作；
3. 对既有新库数据如何处理；
4. 需要新增哪些守恒、并发、回滚和性能测试；
5. 如何回滚配置或版本。

只有出现“无法从数据库事实重建、且外部命令必须送达”的真实场景时，才允许单独 ADR 评估窄用途 Outbox；不得预先建立通用表、运行时开关或双路径。

## 8. 参考、改造与拒绝

| 分类 | 结论 |
| --- | --- |
| 参考 `shortmax` | 按领域组织工程、Proto 驱动接口、default/slave 分工、资产账户与流水分离 |
| 2.0 改造 | 增加冻结总额和通用冻结明细；收紧 Tx 参数；关系和等级改为显式聚合；为规则、状态和审计补版本 |
| 拒绝复制 `splay` | 用户宽表存余额、散落 SQL 更新、F 码关系、错位等级枚举、接口多版本并存、活动钩子、请求触发结算和客户端复制规则 |

## 9. 验收

- 任一 Proto、表、配置和页面使用本文术语且无同义漂移。
- 全仓扫描不存在 F 码算法、支持值、新旧 API 代理或通用 Outbox 实现。
- 任何资金或资格方案均能指出 primary 事务、幂等唯一键、锁顺序和恢复入口。
- `requirements-1.0/91` 的 Q-001 至 Q-024 均已在本文或对应领域文档转化为明确规则，不再留作运行时猜测。
