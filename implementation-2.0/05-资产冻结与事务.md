# 05 资产、冻结与事务

> 本章是资产域的实施真源。2.0 从空库开始，只实现 `COMMON` 与 `EXPERIENCE`，不迁移 1.0 余额、不保留 F 码、不建立支持值或活动资产，也不允许业务服务直接更新余额。

## 1. 目标

资产域只做三件事：保存每个用户每种资产的可用额与冻结总额、以不可变流水证明每次变化、以冻结明细解释冻结总额的来源和终结方式。收益、购买、提现等领域决定“为什么动钱”，资产域决定“怎样安全地动钱”。

实施完成后必须满足：

1. 全项目只有 `ApplyMutations` 能改变 `user_assets`；调用方只提交正数金额和操作类型，不自行拼正负号。
2. 同库业务事实、余额、流水、冻结明细和幂等结果在 `database.default` 的同一个事务中提交。
3. 每个用户在注册事务内创建两条资产行，热路径不再执行 `ensure row` 或宽表读改写。
4. `user_assets.frozen` 是快速判断和展示用的冻结总额；`asset_freezes` 是可审计、可终结、可扩展的冻结明细，二者始终可对账。
5. 扣款和冻结用单条条件更新完成“判断余额并扣减”，不采用“先查余额、再更新”，不依赖 Redis 锁保证资金正确性。
6. 多账户操作按固定顺序加锁；同一账户的批量变更合并为一次余额更新，减少数据库往返和热点行写放大。
7. primary 是资金事实唯一读写入口；slave 只服务允许延迟的流水和历史查询。

不在本章范围内：活跃值、等级、持仓本金、法币、银行卡余额、支持值、展示热度。它们不能借用 `EXPERIENCE` 或 `COMMON` 字段存储。

## 2. 对象与不变量

### 2.1 资产类型

| `asset_type` | 含义 | 可用范围 | 提现 |
| --- | --- | --- | --- |
| `COMMON` | 通用资产 | 内容消费、Playlet Backing、Robot Purchase、配置允许的兑换、提现 | 允许 |
| `EXPERIENCE` | 体验资产 | 指定内容消费及配置明确允许的体验资产兑换 | 禁止 |

两种资产使用相同账户结构和变动原语，但业务授权不同。统一结构是为了复用守恒、并发和对账能力，不表示 `EXPERIENCE` 自动获得 Playlet Backing、返佣或提现资格。任何新资产类型必须通过 ADR 增加；不能在 `extras` 中伪造第三种余额。

金额在 API 中使用十进制字符串，在数据库中统一使用 `numeric(30,8)`；业务配置可进一步限制小数位。所有变动命令的 `amount` 必须严格大于零，方向只能由 `kind` 决定。

### 2.2 六种对称操作

设正数金额为 `A`，六种操作对两个余额桶和累计值的影响如下：

| `kind` | `available_delta` | `frozen_delta` | `total_in` | `total_out` | 典型用途 |
| --- | ---: | ---: | ---: | ---: | --- |
| `INCOME` | `+A` | `0` | `+A` | `0` | 充值、立即可用收益、退款回补 |
| `EXPENSE` | `-A` | `0` | `0` | `+A` | 内容购买、Playlet Backing、Robot Purchase、兑换转出 |
| `FREEZE` | `-A` | `+A` | `0` | `0` | 提现申请、从可用额保留资金 |
| `UNFREEZE` | `+A` | `-A` | `0` | `0` | 提现拒绝、业务失败原路退回 |
| `SETTLE_FROZEN` | `0` | `-A` | `0` | `+A` | 提现成功、冻结资金正式离开账户 |
| `INCOME_FROZEN` | `0` | `+A` | `+A` | `0` | 先进入冻结期的收益或返佣 |

`FREEZE`/`UNFREEZE` 只在两个桶之间移动，不虚增累计流入流出；`INCOME_FROZEN` 补齐“直接产生冻结收入”这一方向，不能先入可用再冻结并制造两条无业务意义的流水。

### 2.3 守恒公式

对每个 `(user_id, asset_type)` 独立成立：

```text
available_after = available_before + available_delta
frozen_after    = frozen_before    + frozen_delta

available >= 0
frozen    >= 0
total_in  >= 0 且只增不减
total_out >= 0 且只增不减

available + frozen = total_in - total_out
available = Σ asset_ledgers.available_delta
frozen    = Σ asset_ledgers.frozen_delta
frozen    = Σ asset_freezes.amount WHERE status = ACTIVE
```

2.0 是空库，账户从零开始，因此不需要“期初差额”修正项。数据库中的每条流水还必须独立满足 `before + delta = after`；同一 `(user_id,asset_type)` 账户只按连续 `account_seq` 校验邻接，前一序号的 `after` 必须等于后一序号的 `before`。全局流水 `id` 只用于跨账户审计 cutoff，不代表账户提交顺序，禁止用它证明逐账户连续性。

冻结明细进一步满足：

```text
ACTIVE   冻结：只有一笔 FREEZE 或 INCOME_FROZEN 开启流水
RELEASED 冻结：开启金额 = UNFREEZE 终结金额
SETTLED  冻结：开启金额 = SETTLE_FROZEN 终结金额
```

任何跨资产“总余额”只允许在展示层分别列出，不得把 `COMMON` 与 `EXPERIENCE` 相加后用于额度、收益或财务报表。

## 3. 状态机

### 3.1 账户与流水

`user_assets` 没有业务状态：用户创建时即存在，注销后仍保留事实。`asset_ledgers` 创建后不可修改、不可删除；更正必须写一笔方向相反、指向原流水的新业务冲正。

### 3.2 冻结明细

```text
                         ReleaseFreeze / UNFREEZE
                       ┌──────────────────────────> RELEASED
OpenFreeze             │
FREEZE 或              │
INCOME_FROZEN ─────> ACTIVE
                       │
                       └──────────────────────────> SETTLED
                         SettleFreeze / SETTLE_FROZEN
```

规则：

- `ACTIVE -> RELEASED` 和 `ACTIVE -> SETTLED` 是仅有的合法迁移。
- `RELEASED`、`SETTLED` 都是不可逆终态；终态重放返回原结果，不能再次动余额。
- 同一冻结明细并发执行释放与结算时，只允许一个条件更新成功；失败方读取终态后按幂等或冲突处理。
- 2.0 首版一条冻结明细必须整体终结。需要分期终结的业务在开启时拆为多条独立明细；不得修改原 `amount` 或部分覆盖终态。
- `expected_release_at` 只表示业务预期，不自动决定释放还是结算；来源领域必须调用正确终结操作。

## 4. 数据表、关键字段、约束与索引

### 4.1 `user_assets`

一行代表一个用户的一种资产，是余额查询和条件扣减的热点表。

| 字段 | 设计 |
| --- | --- |
| `user_id` | `bigint`，外键到 `users.id`；禁止 F 码或其他编码身份 |
| `asset_type` | `smallint`/稳定枚举，仅允许 `COMMON`、`EXPERIENCE` |
| `available`、`frozen` | `numeric(30,8)`，默认 0 |
| `total_in`、`total_out` | `numeric(30,8)`，默认 0，只由变动原语累加 |
| `version` | `bigint`，每次账户写入加一；用于诊断和缓存版本，不用于“先读版本再写”的乐观扣款 |
| `last_ledger_seq` | `bigint`，默认 0；同一账户锁内为新流水连续分配，只增不减 |
| `updated_at` | `timestamptz`，使用数据库时间 |

约束与索引：

- 主键 `(user_id, asset_type)`，同时就是所有热路径的定位索引。
- `CHECK available >= 0 AND frozen >= 0 AND total_in >= 0 AND total_out >= 0`。
- 注册事务一次插入两种资产；缺行属于数据损坏，资金入口返回内部错误并告警，不能在热路径静默补行。
- 不为金额列建立普通索引；运营余额区间查询走离线/rollup，不扫描或拖慢热点表。

### 4.2 `asset_ledgers`

一行代表一次不可变资产变化，字段至少包括：

| 字段组 | 关键字段 |
| --- | --- |
| 主体 | `id`、`user_id`、`asset_type`、正数 `account_seq`、只读 `user_partition_hash` |
| 方向 | `kind`、正数 `amount`、`biz_type` |
| 双桶快照 | `available_delta/before/after`、`frozen_delta/before/after` |
| 关联 | `ref_type`、`ref_id`；两者必须同时为空或同时有值 |
| 冻结关联 | `freeze_id`，只有涉及冻结桶的四类流水必填 |
| 幂等 | `idem_key`、`request_hash` |
| 上下文 | 有版本 Schema 的 `extras`，只存检索非核心上下文，不存余额真值 |
| 时间 | `occurred_at` 为服务端确认的业务发生时间；`business_date date GENERATED ALWAYS AS ((occurred_at AT TIME ZONE 'Asia/Jakarta')::date) STORED`；`created_at` 为数据库入账时间 |

数据库约束必须覆盖：

- `amount > 0`；两个桶不能同时为零变化。
- 两组 `before + delta = after`，且两个 `after >= 0`。
- `kind` 与金额/增量严格匹配本章六种操作表，调用方不能存自定义符号组合。
- `idem_key` 非空且全局唯一；`request_hash` 非空。
- `(user_id,asset_type,account_seq)` 唯一；`ApplyMutations` 在锁住账户行后从 `last_ledger_seq+1` 为本批该账户流水分配连续区间。它不依赖全局 sequence 的提交顺序，供单用户增量 cursor 安全推进。
- 显式建立 `UNIQUE(id,user_id,asset_type)`，供业务补偿、冻结和其他保存冗余主体的子事实使用 exact composite FK；`id` 单列主键不能代替子表的同主体证明。
- `business_date` 由数据库从 `occurred_at` 唯一生成、调用方不可写，并以真实外键引用 `finance_business_days(business_date)`。顶层先调用 `AcquireIncomeWriteFences(tx,occurred_at)`：固定按 `rollup_roots('income') FOR SHARE` → `AcquireFinanceDayFence` 取得 OPEN day；后者必须使用与 generated column 完全相同的数据库表达式求日。应用本地时区计算值不参与裁决。
- `user_partition_hash` 由 immutable 数据库函数按 `hash64(user_id,INCOME_HASH_V1_SEED)` 生成/校验；seed 随 hash 协议在空库 bootstrap 固化，调用方不可写。它只用于有界分片和索引，不替代 `user_id` 关系。
- 涉及冻结桶的 `kind` 必须有 `freeze_id`，`INCOME`/`EXPENSE` 不得伪挂冻结明细。
- `asset_freezes` 显式建立 `UNIQUE(id,user_id,asset_type)`；每条带 `freeze_id` 的流水以 NOT NULL `(freeze_id,user_id,asset_type)` 完全同序 composite FK 引用它。DEFERRABLE 约束触发器在提交时再验证：唯一 opening 的 kind 等于 freeze.open_kind、amount 等于 freeze.amount；终态恰有唯一 UNFREEZE/SETTLE_FROZEN、amount 同样等于 freeze.amount，并与 RELEASED/SETTLED 一一对应。这样数据库同时拒绝跨用户/资产串接、部分开冻或部分终结。
- 流水表禁止 UPDATE/DELETE 权限，只授予应用角色 INSERT/SELECT。

索引保持面向已知查询：

- 唯一索引 `asset_ledgers(idem_key)`。
- `(user_id, asset_type, created_at DESC, id DESC)`：用户流水 `offset + limit + total` 分页及稳定排序。
- `(user_id,asset_type,account_seq)`：累计收益 worker 的真实 keyset；每批最多 N 条，迟提交事务不能在 cursor 之前插入更小序号。
- `(asset_type,id DESC)`：RESTATED cutover 以 `asset_type=COMMON ORDER BY id DESC LIMIT 1` 固定全局审计 upper；百万 EXPERIENCE 尾也必须只读 O(1) 索引项。
- `(ref_type, ref_id, id)`，条件为 `ref_id IS NOT NULL`：业务单反查。
- `(freeze_id, id)`，条件为 `freeze_id IS NOT NULL`：冻结生命周期审计。
- `(business_date, id)`：day fence 最终 tail/count/hash 与日对账；不能用 `created_at` 替代业务日。
- `(business_date, asset_type, user_partition_hash, user_id, id) INCLUDE (biz_type,available_delta,occurred_at)`：日封账按连续 hash 范围和 `(user_partition_hash,user_id,id)` 真 keyset 每批读取最多 N 条 COMMON 流水；不得先全日表达式 hash/分类/排序再 LIMIT。
- `(user_id, business_date, id)`：OPEN/CLOSING 日的单用户精确收益聚合；避免错误复用累计 cursor 造成日账漏计。
- 唯一 `(freeze_id) WHERE kind IN (FREEZE,INCOME_FROZEN)`，以及唯一 `(freeze_id) WHERE kind IN (UNFREEZE,SETTLE_FROZEN)`：一条明细只有一个开启和一个终结资金动作。
- `(biz_type, occurred_at, id)` 只在财务明细确有在线查询需求时建立；大范围统计使用 rollup，不能为每个筛选项堆索引。

2.0 首发保持单表，以确保 `idem_key` 由数据库直接全局唯一。达到容量阈值后必须先做独立 ADR；若按时间分区，方案必须在同一事务内保留全局幂等注册和唯一性，在此之前不得因 PostgreSQL 分区限制把幂等降级为“分区内唯一”。

### 4.3 `asset_freezes`

一行解释一笔仍在或曾经在冻结桶中的金额。

| 字段 | 设计 |
| --- | --- |
| `id`、`freeze_no` | 内部主键与不可猜测的外部编号，`freeze_no` 唯一 |
| `scope_partition_hash` | 由 `id` 通过版本化稳定 hash 数据库生成的只读值；仅供 RESTATED 收益冻结 scope 固定分片，不是业务字段 |
| `user_id`、`asset_type` | 必须与关联账户及流水一致 |
| `amount` | `numeric(30,8)` 且 `> 0`，创建后不可修改 |
| `open_kind` | 仅允许 `FREEZE` 或 `INCOME_FROZEN` |
| `status` | `ACTIVE`、`RELEASED`、`SETTLED` |
| `biz_type`、`business_type`、`business_id`、`operation` | 资金业务分类、来源单据类型/ID 和该单据内的稳定冻结动作；业务单不能用冻结明细替代 |
| `idem_key`、`request_hash` | 开启幂等键和规范化请求 hash，键全局唯一 |
| `terminal_idem_key`、`terminal_request_hash` | 终结幂等键/hash，ACTIVE 时为空，终态时非空且唯一 |
| `expected_release_at` | 可空；业务预计可处理时间，不是终态事实 |
| `released_at`、`settled_at` | 与状态互斥匹配 |
| `extras` | 规则版本、展示说明等非真值上下文 |
| `created_at`、`updated_at` | 创建与状态变化时间 |

约束与索引：

- `CHECK amount > 0`，`open_kind` 白名单，状态白名单。
- `biz_type/business_type/business_id/operation` 全部必填且 operation 非空；冻结不能没有可追溯来源。
- 状态/时间一致性：ACTIVE 没有终结键/hash 和终结时间；RELEASED 只有 `released_at`；SETTLED 只有 `settled_at`。
- 唯一索引 `idem_key`；`terminal_idem_key IS NOT NULL` 时唯一。
- 显式 `UNIQUE(id,user_id,asset_type)` 作为 `asset_ledgers(freeze_id,user_id,asset_type)` 的父键；父键和子 FK 都不可由单列 `freeze_id` 或应用 CHECK 替代。
- 唯一 `(business_type, business_id, operation)`；同一业务动作只能开启一笔冻结。需要拆分时，业务在创建前生成稳定且可审计的不同 operation/component，不能靠重试随机号绕过。
- `(user_id, asset_type, status, id DESC)`：用户冻结列表。
- `(business_type, business_id, id)`：来源单审计。
- `(expected_release_at, id) WHERE status = ACTIVE AND expected_release_at IS NOT NULL`：primary 到期扫描。
- `(scope_partition_hash,id) WHERE asset_type='COMMON' AND open_kind='INCOME_FROZEN'`：RESTATED scope 只枚举通用资产收益冻结；实际 as-of 成员还必须在固定 freeze upper 内，并通过 `asset_ledgers.freeze_id` 的唯一 opening/terminal 行按 ledger upper 判定。即使存在海量 EXPERIENCE 收益冻结噪声，计划也不得退化为过滤后的无界扫描。
- `(id DESC) WHERE asset_type='COMMON' AND open_kind='INCOME_FROZEN'`：RESTATED 创建在持统计 root 锁时以 `ORDER BY id DESC LIMIT 1` 有界捕获 freeze upper；不得反扫主键再过滤海量普通/EXPERIENCE 冻结。
- 开启/终结流水通过 `asset_ledgers.freeze_id` 的两个部分唯一索引定位，避免 `asset_freezes` 反向引用流水形成循环外键。
- 不能用跨行 CHECK 保证冻结总额；由同事务写原语保持，并由对账任务证明。

### 4.4 `asset_exchanges`

体验资产兑换必须有独立业务事实，不能仅凭两条流水反推。`asset_exchanges` 至少保存：`id/exchange_no/user_id`、`operation=EXCHANGE/REVERSAL`、`purpose=NORMAL/ACCOUNT_CLOSURE`、可空 `closure_id`、`reversal_of_exchange_id nullable`、固定源资产 `EXPERIENCE`、固定目标资产 `COMMON`、正数 `source_amount/target_amount`、汇率和舍入快照、`rule_version_id`、公共 `deduplication_id`、两条 `asset_ledger_id` 和 `created_at`。原 EXCHANGE 和 REVERSAL 都是不可变 POSTED 事实，方向由 operation 决定，不在原行上改一个模糊状态。NORMAL 要求 closure_id 为空；ACCOUNT_CLOSURE 必须引用同用户进行中的 closure。

约束包括：源/目标金额均大于零，`exchange_no`、`deduplication_id` 唯一。EXCHANGE 的两条流水必须分别对应 EXPERIENCE/EXPENSE 和 COMMON/INCOME；REVERSAL 必须引用同用户、同绝对金额/规则快照的原 EXCHANGE，两条流水方向相反。partial unique `reversal_of_exchange_id WHERE operation='REVERSAL'` 保证一张原单最多一个反向事实；仅换幂等键不能重复冲正。反向纠错不修改原兑换或原流水。

### 4.5 `asset_adjustments`

人工调整不能只留下通用流水和一条松散审计。`asset_adjustments` 是不可变命令事实，至少保存 `id/adjustment_no/user_id/asset_type/semantic=DISCRETIONARY/REVERSAL/kind=INCOME/EXPENSE/amount/biz_type`、可空 `original_ledger_id`、`correction_mode=ACTIVE_ONLY/PRE_CLOSURE_SOURCE_CORRECTION`、可空 `closure_id`、结构化 `source_domain/source_kind/source_id/source_component/source_persisted_at`、`reason_code/ticket_no/approval_id/deduplication_id/asset_ledger_id`、操作者和时间。`adjustment_no`、`deduplication_id`、`asset_ledger_id` 唯一；同一 approval 只能消费一次；金额为正，目标 kind 仅允许 INCOME/EXPENSE。

`semantic=REVERSAL` 时 `original_ledger_id` 必填且建立 partial unique，原流水必须属于同一 `user_id/asset_type`、kind 只能是 INCOME/EXPENSE，本次 kind 必须相反且金额完全相等；不允许把一条流水拆成多个“部分冲正”或换 approval/幂等键再冲。`DISCRETIONARY` 时 `original_ledger_id` 必须为空，明确表示该动作不是在篡改或撤销某条既有流水。

`PRE_CLOSURE_SOURCE_CORRECTION` 的五个 source 字段全部必填，`source_persisted_at` 必须由服务端通过强类型 blocker/source registry 回查既有来源事实取得，不能接受管理员请求体传值；来源必须早于 `account_closures.requested_at` 且确实属于同一用户/资产语义。数据库建立 `(source_domain,source_kind,source_id,source_component,user_id,asset_type,kind) WHERE correction_mode='PRE_CLOSURE_SOURCE_CORRECTION'` 唯一索引，使更换 approval、工单或幂等键也不能重复纠错。其他模式的 source 字段必须全空，不能把“运营赠送”伪装成历史纠错。CLOSING 时保存 `closure_id` 和锁内账号状态快照；ACTIVE_ONLY 时 closure_id 必须为空。CLOSED 不允许创建钱包 adjustment：历史应付或追偿进入独立 Finance case/线下支付与审计流程，不重开用户、不改 `user_assets`，也不伪造旧业务日流水。

## 5. 领域 API

### 5.1 内部写原语

这些方法属于资产领域，不直接暴露为公共 HTTP：

| 方法 | 输入要点 | 输出/约束 |
| --- | --- | --- |
| `ApplyMutations(tx, mutations...)` | 真正的 `Tx`、正数金额、六种 `kind`、业务引用、幂等键 | 原子应用一组变化并返回与请求顺序一致的流水；不能接收裸 `DB/IDB` |
| `OpenFreeze(tx, command)` | `open_kind=FREEZE/INCOME_FROZEN`、来源、预计时间、幂等键 | 同事务创建 ACTIVE 明细并增加冻结总额 |
| `ReleaseFreeze(tx, freeze_id, command)` | 终结幂等键、原因、发生时间 | 条件执行 ACTIVE→RELEASED 与 `UNFREEZE` |
| `SettleFreeze(tx, freeze_id, command)` | 终结幂等键、原因、发生时间 | 条件执行 ACTIVE→SETTLED 与 `SETTLE_FROZEN` |

`ApplyMutations` 完整理解六种操作，但业务服务不能直接调用四种涉及冻结桶的操作；它们只能通过三个冻结方法进入，以保证明细与总额不会分叉。普通 `INCOME`、`EXPENSE` 和跨资产组合可以由顶层 Use Case 调用 `ApplyMutations`。

### 5.2 查询 API

| HTTP | 说明 | 数据源 |
| --- | --- | --- |
| `GET /v2/me/assets/wallet` | 当前用户两种资产的可用、冻结、合计和版本 | primary，保证读己之写 |
| `GET /v2/me/assets/ledgers?asset_type=COMMON` | `asset_type` 是必填 query selector；流水 `offset + limit + total` 分页，支持业务类型/时间过滤，按 `created_at DESC, id DESC` 稳定排序 | 默认 slave；客户端接受延迟 |
| `GET /v2/me/assets/freezes?asset_type=COMMON` | `asset_type` 是必填 query selector；ACTIVE/历史冻结明细使用 `offset + limit + total` | ACTIVE 默认 primary；历史可用 slave |
| `GET /v2/me/assets/freezes/detail?freeze_no=...` | 冻结详情及关联流水/业务单；selector 位于 query | primary 或明确的历史查询 |
| `POST /v2/me/assets/exchange` | `ExchangeExperience`；只接收源金额和幂等键，服务端按已发布规则计算 COMMON | primary 单事务 |
| `GET /v2/admin/user-assets?user_id=...` | 管理端资产审计；selector 位于 query | 有权限时 primary |
| `POST /v2/admin/asset-adjustments` | 受控冲正/调整，必须有原因、工单、审批和幂等键 | 创建不可变 adjustment 并调用同一变动原语；受账号关闭门禁，不开放任意余额覆盖 |

用户自助接口不接收 `user_id`；主体只来自令牌。不存在“设置余额”“修改流水”“修改冻结状态”的 API。

## 6. 主流程

### 6.1 用户账户初始化

注册 Use Case 在创建 `users` 行的同一事务中批量插入 `COMMON`、`EXPERIENCE` 两行零余额账户。任何一步失败则注册整体回滚。资产行存在是用户聚合的创建后条件，而不是第一次用钱时补齐的副作用。

### 6.2 普通收入与支出

1. 来源领域先锁定并验证业务单，计算确定金额和规则版本。
2. 以业务单号和动作构造稳定幂等键。
3. 在当前顶层事务内调用 `ApplyMutations`。
4. 同事务写业务终态、权益/持仓/结算事实和必要审计。
5. 提交成功后再失效展示缓存；提交失败不留下余额或流水中间态。

余额不足由带下界的条件 UPDATE 返回业务错误，不以事务前的展示余额判断为事实。

### 6.3 跨资产兑换或混合消费

`ExchangeExperience` 只在已发布 `rule_versions(domain=ASSET_EXCHANGE)` 及其 `asset_exchange_rule_settings` 明确允许时开放。结构化规则保存源/目标资产、兑换率、舍入方式、单笔和业务日上下限；请求只提交源金额和幂等键，服务端计算目标金额并保存规则/数值快照。它不能被提现流程隐式调用。

顶层 Use Case 的正式顺序为：命令防重 → day fence → 既有 exchange/reversal 根（如有）→ `PrelockUserClosures` → `LockUsersAndValidateClosureGate` → `(user_id,ASSET_EXCHANGE_DAILY,Jakarta业务日)` 的 `user_limit_usages` → 两种 assets；本流程没有 freeze 中间锁，所以两阶段相邻。锁内 ACTIVE 接受 NORMAL，CLOSING 只接受 ACCOUNT_CLOSURE 并引用当前 closure，CLOSED 拒绝。随后以同窗既有 completed 对已发布规则做条件增量，创建 `asset_exchanges`，把 `EXPERIENCE/EXPENSE` 与 `COMMON/INCOME` 两个 mutation 一次交给 `ApplyMutations`；两笔流水共享兑换单引用但各自使用稳定幂等子键。CLOSING 兑换还要同事务推进 closure `next_check_at`，使新 COMMON 立即成为待清退 blocker。usage 唯一键不含规则版本，同日换版不能重获一整份额度；兑换冲正同事务对称扣减原 usage，不能低于零。同样地，剧集混合消费把两个资产 mutation 与购买权益放在一个事务。任一账号状态、余额、限额、流水冲突或业务事实失败，整个事务回滚。

### 6.4 开启冻结

`OpenFreeze` 按以下顺序在同一事务中完成：

1. 校验来源业务、资产类型、正数金额、幂等键和预计时间；已有同键时核对完整请求语义。
2. 创建 ACTIVE `asset_freezes`，获得 `freeze_id`。
3. 对从可用额冻结调用 `FREEZE`；对新产生的冻结收入调用 `INCOME_FROZEN`。
4. 写入带 `freeze_id` 的唯一开启流水；任一步失败全部回滚。

### 6.5 释放或结算冻结

`ReleaseFreeze`/`SettleFreeze` 先锁定冻结明细并校验用户、来源、ACTIVE 状态，再调用对应变动原语，最后用 `WHERE status=ACTIVE` 写终态、终结键/hash 和时间。条件更新影响 0 行时重新读取：同键同语义返回原结果，不同终态或不同语义返回冲突并告警。

冻结终结与来源业务终态必须在同一个顶层事务中。例如提现成功必须同时把提现单置为到账、冻结置为 SETTLED、冻结总额扣减并写流水；不能先改提现单后异步补钱包。

### 6.6 人工调整与关闭账户门禁

`CreateAssetAdjustment` 在事务外只做权限、格式、审批展示预检，并从 primary 预收集被纠正来源和潜在 Finance recovery 自然键。正式事务固定执行：命令防重 → `AcquireIncomeWriteFences` 的 income root/day → rank 100 `admin_action_approvals` → 将全部既有来源根、潜在 `finance_recovery_case_roots(rank=400,type=70)` 和期间/adjustment 根放入同一个 `BusinessRootLockKey` 计划，严格按 `(rank,type_code,normalized_id)` 单调取得 → `PrelockUserClosures` → `LockUsersAndValidateClosureGate` → 目标资产。尤其不能先锁 rank 500 的 partner month/adjustment 再回头 Ensure/锁 recovery root；来源存在性和集合在取得对应正式根后重验，变化即整体回滚扩集。本流程没有 freeze 中间锁，所以两阶段相邻。第二阶段会在 user 锁保护下复查第一阶段未命中 closure 的用户；因为 `RequestAccountClosure` 和所有会新增 blocker 的路径都锁同一 user，二者只有一个可先通过。普通 DISCRETIONARY 调整命中 CLOSED 只拒绝，不允许借 Finance case 变成无来源赠送；只有带稳定历史来源自然键的纠错才可在已预锁 root 下返回 PAYABLE/RECEIVABLE case 结果且不触碰钱包。

锁内规则如下：

- ACTIVE 可执行经审批的 ACTIVE_ONLY 调整；提交后若并发注销在等待，它会在自己的 user 锁内复检到新余额。
- CLOSING 拒绝运营赠送、善意补偿和其他可选新价值。只有能证明来源早于 closure cutoff 的 `PRE_CLOSURE_SOURCE_CORRECTION` 可继续，并且必须验证现有清退 KYC/卡/安全能力或明确的 closure-purpose 补办路径；adjustment、流水和把 closure `next_check_at` 提前/写入对应 blocker 同事务提交。
- CLOSED 一律拒绝钱包 mutation，包括换一个幂等键、管理员强制模式或任务奖励补偿。必须转为独立外部应付/追偿 case；该 case 不调用资产原语。
- 对 closure 前已登记来源的正常退款、冻结释放、结算和提现终态，不改造成“人工 adjustment”；它们继续走各自业务状态机、来源唯一键和 CLOSING 白名单。

命令同事务写 `asset_adjustments`、消费 request hash 完全匹配的异人审批、调用 `ApplyMutations`、写 `admin_audit_logs` 和幂等结果。任一步失败全部回滚。只追加一条流水而没有 adjustment/审批，或先入账再补 closure blocker，均属于 P0 实现缺陷。

### 6.7 `ApplyMutations` 批处理算法

首发硬常量为 `ASSET_MUTATION_BATCH_MAX=64`、`ASSET_ACCOUNT_LOCK_MAX=32`。顶层 Use Case 在开启事务前先验证，原语在取得任何账户/幂等行锁前再次断言；超限稳定返回 `ASSET_MUTATION_BATCH_TOO_LARGE` 或 `ASSET_ACCOUNT_SET_TOO_LARGE`，不做部分写。常量由同一代码生成源进入服务校验、测试 fixture 和运维指标，不能只藏在配置中运行时放大。上游只有在每项已有独立自然键、彼此不要求原子时才可拆成多个事务；一个业务动作若必须原子修改超过上限，必须重做有界业务模型并立 ADR，不能由 helper 静默分批破坏全成败。

为兼顾正确性和热点性能，实施顺序固定为：

1. 一次性校验所有命令，拒绝空幂等键、重复键、非法精度、零/负金额和不配对的引用。
2. 批量读取已有幂等流水；同键同 `request_hash` 返回原流水，同键不同请求立即报冲突。
3. 按 `(user_id, asset_type)` 排序并分组；同一组内保持调用方原始顺序。
4. 对每组计算两个桶的总增量、累计流入/流出和最小前缀余额要求；用一次条件 UPDATE 同时校验前缀下界、更新账户并把 `last_ledger_seq` 增加本组新流水数，通过 `RETURNING` 取得最终余额和序号上界。
5. 由最终余额/序号上界反推组内起点，再按原始顺序生成每条连续的 before/after 与 `account_seq`；批量 INSERT。
6. 结果映射回调用方请求顺序。任一唯一键冲突、余额不足或约束错误都让调用方事务整体回滚。

这样 N 条命令涉及 K 个不同账户行时，账户 UPDATE 次数是 K 而不是 N；正确性仍由数据库条件更新、约束、唯一索引和事务共同保证。

## 7. 事务边界

### 7.1 同库事实

- 顶层业务 Use Case 在 `database.default` 开启一次事务；内部 repository 和资产写原语只接收该 `Tx`，不能自行开启嵌套事务或偷偷使用全局 DB。
- 默认使用 PostgreSQL `READ COMMITTED` 加显式行锁/条件更新；资金正确性不要求把全局隔离级别提高到 SERIALIZABLE。
- 业务单、权益/持仓/结算、`user_assets`、`asset_ledgers`、`asset_freezes`、幂等结果和操作审计在同一事务提交。
- 事务内时间使用数据库 `now()` 或由顶层注入的一次性 `BusinessClock` 时间，不能每个 repository 各取一次系统时间。
- 提交结果不确定时，调用方不得凭网络异常猜测失败；必须在 primary 用幂等键查询并重放。

### 7.2 primary/slave 与外部边界

- 余额、冻结、资格、幂等、状态推进、回调履约、到期扫描和对账全部读取 primary。
- slave 只用于允许延迟的历史流水、历史终态冻结和离线报表；不得把 slave 读到的余额用于扣款或提示“已完成”。
- 资产域不调用支付商、消息平台或其他外部服务。其他领域需要外部调用时，先提交可恢复业务状态，再在事务外调用，随后开新事务收敛结果；SMS 与 Email 统一经 Forge `message` transport，发送成功最多表示 `PROVIDER_ACCEPTED`，WhatsApp 不在 2.0 范围内。
- 2.0 不建通用 Outbox。Redis 通知和进程内 after-commit hook 只用于加速缓存失效/唤醒，丢失后由业务状态的 primary sweep 恢复。

## 8. 幂等键

幂等键格式统一为带领域和动作的稳定字符串，例如：

```text
deposit:credit:<deposit_no>
drama:purchase:common:<purchase_no>
exchange:experience:out:<exchange_no>
exchange:common:in:<exchange_no>
withdraw:freeze:<withdrawal_no>
withdraw:release:<withdrawal_no>
withdraw:settle:<withdrawal_no>
income:frozen:<settlement_no>:<beneficiary_user_id>
```

规则：

1. 键由服务端业务唯一号构造，不使用时间戳、重试次数或随机日志 ID。
2. `request_hash` 对规范化后的 `user_id/asset_type/kind/amount/biz_type/ref/extras_schema_version` 计算；同键不同 hash 是调用错误，不能当作成功吞掉。
3. 同一批命令中不允许重复幂等键；跨用户也不能复用全局键。
4. 冻结开启键与终结键分开；释放与结算不能共享一个模糊的 `finish` 键。
5. Redis `SETNX` 或分布式锁可以削峰，但唯一索引才是最终防重依据。

## 9. 并发与锁顺序

所有涉及资产的事务遵守与 01 章一致的完整锁顺序；下列是资产路径的唯一规范展开，不是可跳过 closure 层的截断版：

```text
命令幂等/外部事件防重行（如有）
  -> rollup_roots('income')（会写 asset_ledgers 时 FOR SHARE）
  -> finance_business_days（会写 asset_ledgers 时按 business_date FOR SHARE）
  -> 来源业务聚合根：订单/产品/券/持仓/结算/返佣 GRANT（按 type/id；正反流程先收齐）
  -> account_closures（对全部参与用户执行 PrelockUserClosures；不存在也记录 gate token）
  -> asset_freezes（按 id，仅终结时；始终位于 rank 700 之后）
  -> 本事务参与业务裁决的用户/关系/资格/等级/任务/其他聚合行（按 user_id；如有）
  -> user_assets（按 user_id, asset_type）
  -> income_calc_dirty（每笔 COMMON 流水；按 calc_version_id,user_id）
  -> user_income_stats（同序；可重建统计投影）
  -> 插入业务子事实 / asset_ledgers / 审计
```

补充规则：

- 多账户/多资产 mutation 在资产域内部排序，不能要求业务调用方自己排序。
- `ApplyMutations/OpenFreeze/ReleaseFreeze/SettleFreeze` 写流水前必须断言顶层事务已通过 `AcquireIncomeWriteFences(tx,occurred_at)` 依次持有 income root SHARE token 和与数据库生成 `business_date` 对应的 OPEN day fence；资产原语不得在业务根之后自行补锁任一行。无 root token/fence、日期不匹配或 fence 非 OPEN 均直接失败，避免形成 day→root 与 root→day 两套路径。各领域锁序表中的“day fence”均是这个 root→day 组合的简写。
- 退款/冲正不得先锁 freeze 再回头锁其原返佣 GRANT；必须在事务前从 primary 预收集全部 GRANT/freeze ID，事务内按“业务根 GRANT → freeze”统一顺序锁定。集合在锁内扩大则回滚、扩集重试。
- 所有会新增、释放、减少注销 blocker 的路径都必须在 rank 500 及以前根锁齐后调用 `PrelockUserClosures`，再按需锁 freeze，最后调用 `LockUsersAndValidateClosureGate`；事务前未发现 closure 时也必须在 user 锁保护下复查不存在。禁止 freeze→closure、user→closure、asset→closure 的反向补锁，也禁止以“管理员命令”绕过用户状态锁。
- 禁止在锁住 `user_assets` 后回头锁来源订单、冻结明细、产品、关系、资格或等级等业务裁决行；发现需要更多业务数据时先退出事务重新组织流程。唯一列明的后置层是 `income_calc_dirty`→`user_income_stats`，统一按 01 章 `ProjectionLockKey`；它们只承载可重建收益投影，不能反向影响本次资金或资格判断，也禁止任何 rollup 先锁投影再锁资产。
- 同一冻结的释放/结算依赖行锁和 `WHERE status=ACTIVE`，不依赖进程锁。
- 死锁仍按数据库可重试错误处理，使用原幂等键做有限次数抖动重试；不能换键重试。
- 不为单用户余额使用全局互斥锁；热点账户由行级串行化，批量按账户分组减少持锁时间。

## 10. 失败模式与处理

| 失败模式 | 必须行为 |
| --- | --- |
| 金额为空、非法、零、负数或超精度 | 在开事务前拒绝；无业务单、余额、流水或冻结变化 |
| 可用/冻结余额不足 | 条件 UPDATE 影响 0 行，返回明确业务错误；不先查后扣 |
| 用户资产行缺失 | 视为 P0 数据损坏并告警；不得热路径自动创建掩盖注册问题 |
| 幂等键重放 | 同请求返回原流水/冻结结果；不同请求返回幂等冲突 |
| 并发重复首次请求 | 一个事务提交，其他事务命中唯一键并整体回滚，随后按原键重放 |
| 释放与结算竞态 | 仅一个 ACTIVE 条件更新成功；另一方不动余额并报告终态冲突 |
| 事务中途异常 | 同库事实全部回滚；禁止捕获流水插入错误后继续提交余额 |
| COMMIT 响应丢失 | primary 查询幂等键，不能创建新业务号或补写第二笔 |
| slave 延迟 | 不参与判断；查询页可显示“数据同步中”，不能因此重放资金命令 |
| 冻结总额与明细不平 | 禁止自动覆盖余额；生成 P0 对账事件，按流水定位缺陷并以受控冲正修复 |
| 缓存删除失败 | 资金已提交不回滚；依靠短 TTL/版本和重试失效，强一致读取绕过缓存 |
| 死锁/锁超时 | 整体回滚，有限重试并记录涉及账户键；超过阈值告警 |
| 人工入账与注销并发 | 同一 user 锁裁决；先入账则注销锁内复检看到余额，先进入 CLOSING 则可选补偿拒绝；CLOSED 后钱包永不变化 |

## 11. 缓存与作业

### 11.1 缓存

- 可缓存钱包总览展示，键包含 `user_id`，值携带两条账户的 `version`；任何资金决策都绕过缓存。
- 缓存失效只能在事务提交后执行。删除失败不反向回滚资金事务。
- 流水第一页可以短 TTL 缓存，但写后只做最佳努力失效；读己之写请求显式走 primary。
- 不缓存 ACTIVE 冻结作为终结依据，不用 Redis 保存剩余冻结金额。

### 11.2 作业

| 作业 | 数据源与行为 |
| --- | --- |
| 业务到期处理 | 来源领域表按自身 `status/releasable_at/next_run_at` 领取候选；候选扫描不持有 freeze 锁。每个对象新事务按防重/事件→income root/day fence（写 ledger 时）→来源业务根→`PrelockUserClosures`→既有 freeze→`LockUsersAndValidateClosureGate`→资产顺序执行；CLOSING 只终结 cutoff 前来源并唤醒 closure，CLOSED 为不变量破坏且失败关闭。资产域不从 `asset_freezes.expected_release_at` 自主猜终结方向 |
| 日常余额对账 | primary 比较账户余额与流水 delta 累计、冻结总额与 ACTIVE 明细之和 |
| 流水连续性检查 | 检查每条 before/delta/after 和相邻流水连续性 |
| 异常冻结扫描 | 告警超过业务 SLA 仍 ACTIVE、已终态但缺终结流水、来源单终态不匹配的记录 |
| 容量维护 | 分区创建、旧分区只读归档、索引膨胀与 autovacuum 监控 |

作业游标、批次、`status` 和下次运行时间保存在本库事实/作业表；调度通知可以丢失，primary sweep 必须能从数据库恢复。

## 12. 权限与审计

- 用户只能读取自己的余额、流水和冻结；服务端从令牌取得 `user_id`。
- 普通业务服务只能调用资产领域接口，数据库角色不得直接 UPDATE `user_assets` 或写伪造流水。
- 管理端拆分 `asset.read`、`asset.adjust`、`asset.reconcile` 权限；查看权限不包含调账。
- 人工调整必须保存 `operator_admin_id`、工单号、原因、IP、请求前后摘要、账号/closure 裁决和幂等键；消费 request hash 一致的异人 `admin_action_approvals`。调整通过 `INCOME`/`EXPENSE` 形成流水；具体冻结只能由来源状态机调用 Release/Settle，禁止用调账接口任意终结冻结或 SQL 覆盖余额。
- 银行、支付商和业务敏感信息不进入流水 `extras`；只存必要引用或脱敏快照。
- 资产、流水、冻结和操作审计均不物理删除；数据保留与脱敏服从财务合规策略。

### 12.1 Finance 追偿案件

本节 reason registry 的完整补充项还包括：`VIP_REFUND_SUCCESS_AFTER_NOT_ACCEPTED`（RECEIVABLE、EXTERNAL、必须引用已验签 refund success 或封存对账证据）、`EPISODE_REFUND_AFTER_ACCOUNT_CLOSED`（PAYABLE、ASSET、每个正 COMMON/EXPERIENCE 退款组件一案，必须引用窗口内唯一 refund request），以及出款差异已外部结案后才发生来源反转的 `DUPLICATE_PAYOUT_REVERSED_AFTER_RECOVERY`（PAYABLE、BOTH）、`PAYOUT_LATE_SUCCESS_REVERSED_AFTER_RECOVERY`（PAYABLE、BOTH）和 `PAYOUT_SUCCESS_AFTER_FAILURE_COMPENSATED`（RECEIVABLE、BOTH）。下述旧矩阵中的“完整”必须连同这些项理解；实现允许列表、迁移 CHECK、Proto、对账和测试必须使用同一 registry 生成，不能遗漏。

`finance_recovery_cases` 只承接已有稳定财务来源无法再由既定钱包终态安全表达的余额外处置。普通第三方冲正使用 `CLOSED_ACCOUNT` 或 `INSUFFICIENT_AVAILABLE`；注销中无渠道可支付的 COMMON dust 使用 `ACCOUNT_CLOSURE_COMMON_DUST` PAYABLE。支付相反终态包括：`COLLECT_SUCCESS_AFTER_CONFIRMED_NOT_PAID`、`REFUND_FAILURE_AFTER_LOCAL_REFUNDED`、`PAYOUT_FAILURE_AFTER_LOCAL_ARRIVED`、`DUPLICATE_PAYOUT_REVERSED_AFTER_RECOVERY` 和 `PAYOUT_LATE_SUCCESS_REVERSED_AFTER_RECOVERY` 为 PAYABLE；`COLLECT_FAILURE_AFTER_LOCAL_PAID`、`REFUND_SUCCESS_AFTER_LOCAL_CANCELED`、`VIP_REFUND_SUCCESS_AFTER_NOT_ACCEPTED`、`PAYOUT_SUCCESS_AFTER_LOCAL_FAILED`、`DUPLICATE_PAYOUT_AFTER_CHANNEL_SWITCH` 和 `PAYOUT_SUCCESS_AFTER_FAILURE_COMPENSATED` 为 RECEIVABLE。`EPISODE_REFUND_AFTER_ACCOUNT_CLOSED` 另为 PAYABLE。案件的 `value_basis=ASSET|EXTERNAL|BOTH` 决定必填正值组：钱包追偿/dust/剧集退款为 ASSET，纯法币 VIP 矛盾为 EXTERNAL，充值/提现等同时有规范 COMMON 与法币快照的矛盾为 BOTH。reason registry 同时限定 source type/component、方向、原本地终态、value basis 和必填 provider event/reconciliation/refund/case-reversal 证据，不能从自由字符串创建案件。顶层在取得用户/资产锁前，先为每个潜在来源组件按自然键调用 `EnsureFinanceRecoveryCaseRoot`，以 rank 400/type 70 的稳定顺序锁定轻量 `finance_recovery_case_roots`；即使最终正常走钱包，也只留下无 `case_id` 的协调根。锁内裁决命中条件时，才把全额案件作为该 root 的新子事实插入并一次设置 `case_id`。创建案件与来源终态同一 default 事务提交，不等待人工处理，也不反向改写已终结 freeze。它不能承接任意运营调账、无稳定来源赠送、可正常写钱包的扣款，也不能充当消息投递队列。

案件状态机固定为 `OPEN -> IN_REVIEW -> RESOLVED`，仅 `direction=RECEIVABLE` 的 `IN_REVIEW -> WAIVED`，以及来源差异已被新权威证据消除时由内部原语从 `OPEN|IN_REVIEW -> CANCELED_BY_SOURCE_REVERSAL`。取消不是管理 API：必须与唯一 `finance_case_source_reversals`、强类型 provider event/reconciliation 触发证据和来源 disposition 同事务；原案已 WAIVED 只记 `NO_EFFECT_WAIVED`，已 RESOLVED 则不能取消，而由 registry 以 `COUNTER_CASE_CREATED` 创建等额反向案件。`StartFinanceRecoveryReview` 只允许 OPEN，记录 reviewer 和 `expected_version`；`ResolveFinanceRecoveryCase` 只允许 IN_REVIEW，并在同一事务插入唯一 `finance_external_settlements`、以数据库生成的非空 `value_fingerprint` composite FK 证明方向、basis 及全部价值列与 case 完全一致后回填 resolution；ASSET/EXTERNAL 的不适用 NULL 组不能让 FK 跳过。`WaiveFinanceRecoveryCase` 只允许 IN_REVIEW 的 RECEIVABLE，并在同事务消费 request hash 完全一致的异人审批。外部凭据自然键 `(provider,settlement_type,external_reference)` 全局唯一，同一凭据并发用于两个案件时数据库只允许一个提交；一笔外部 settlement 首发不拆分多案。PAYABLE 是真实对外债务，只能凭完整外部付款证据 RESOLVED，通用 waive 必须拒绝；未来如需批量结算、债权人豁免或法定应付核销，另立 ADR 和专门会计事实。每个管理命令使用公共幂等事实、旧状态条件更新和 version CAS，命令结果与 `admin_audit_logs` 同事务；任一终态不可重开。任何处置都不得调用 `ApplyMutations`、重开 CLOSED 账号、覆盖原 GRANT/REVERSAL 或补写旧业务日流水。

读权限为 `finance.recovery.read`，进入复核/解决为 `finance.recovery.resolve`，RECEIVABLE 豁免为独立 `finance.recovery.waive` 加 `approval.approve`。列表可从 slave 读取并标记 `as_of/stale`，详情和全部状态命令走 primary。管理命令由 `case_no` 无锁定位 root，正式事务按 approval → `BusinessRootLockKey(rank=400,type_code=70,root_id)` → case 子行加锁；案件之后不得回头获取来源根。提醒 worker 只根据 `status/next_action_at` 产生可重建告警，不自动解决、豁免或修改钱包。

## 13. 指标与告警

至少提供以下维度和指标：

- 变动请求数、成功数、余额不足数、幂等重放数、幂等冲突数，按 `kind/asset_type/biz_type` 分组。
- `ApplyMutations` 事务耗时、锁等待、死锁、重试次数、每批 mutation 数、每批 distinct account 数、每账户 UPDATE 次数。
- `user_assets` 热点行 TopN、流水插入吞吐、索引/表膨胀、autovacuum 延迟。
- ACTIVE 冻结数量/金额/年龄，按 `asset_type/biz_type` 分组。
- 账户与流水差额、冻结总额与明细差额、相邻流水断裂数；任一非零立即 P0。
- slave 回放延迟只用于查询质量监控，不能降低资金告警等级。

日志必须携带 `trace_id`、业务单号、幂等键、`user_id`、`asset_type`、`kind` 和事务结果；金额日志按安全规范脱敏，不记录完整支付账号。

## 14. 验收用例

### 14.1 正确性与约束

1. 两种资产分别执行六种操作，逐项核对两个桶、累计值、流水快照和本章操作矩阵。
2. 任意生成合法操作序列，验证三条守恒公式、相邻流水连续和非负约束；非法序列必须在第一笔越界处整体失败。
3. 注册成功恰有两条零余额资产行；模拟漏建后所有资金入口失败并告警，不静默补行。
4. 同一幂等键相同请求重放 100 次只产生一条流水；改金额、用户、资产或引用后重放均返回冲突。
5. 任一流水 INSERT、冻结 INSERT、业务事实写入或审计写入故障，验证整个顶层事务无残留。
6. 跨资产兑换任一侧余额不足时两侧资产和业务单均不变化。
7. 兑换规则未发布、超单笔/日限额、舍入边界、同键异金额和并发重放均按预期失败或返回原结果；兑换单、两账户和两流水同成败。
8. EXPERIENCE 兑换与注销请求/完成正反并发：ACTIVE 兑换先提交时注销锁内看到结果；CLOSING 仅 ACCOUNT_CLOSURE purpose 成功并唤醒 COMMON blocker；CLOSED 失败且无 usage/exchange/ledger 变化。锁轨迹固定 closure→user→limit→asset，不得先锁 limit 再补 user。

### 14.2 冻结状态

1. `FREEZE` 与 `INCOME_FROZEN` 分别开启明细，账户冻结总额等于 ACTIVE 明细之和。
2. 对同一冻结并发执行 100 次 Release、100 次 Settle：只能出现一个终态、一次终结流水和一次余额变化。
3. 终态同键重放返回原结果；换终结键、换终结方向或换金额均冲突。
4. 到期扫描崩溃于取批次、锁定、写流水、提交响应丢失等位置，恢复后不重复终结。
5. 构造来源单已失败而冻结仍 ACTIVE、终态缺流水、总额不平，验证对账准确告警且不自动改钱。

### 14.3 并发与性能硬门禁

1. 使用 100 个用户、总计 10,000 次并发随机合法资产变动，覆盖两种资产和六种 `kind`；结束后账户、流水、冻结三方差额必须为零，余额不能为负。
2. 对同一热点用户并发收入、扣款、冻结、释放和结算，验证无丢更新；余额不足只影响对应事务。
3. 并发执行 A/B 用户相反方向的组合操作，持续压测不得出现不可恢复死锁；数据库死锁重试后结果唯一。
4. N 条 mutation 仅涉及 K 个账户时，通过 SQL 统计/trace 证明 `user_assets` UPDATE 次数为 K；禁止退化为每条 mutation 一次宽表更新。
5. 分别用 64/65 条 mutation 和 32/33 个 distinct `(user_id,asset_type)` 账户验证硬边界：上限值完整成功并保持一次顶层事务，超一条在任何锁/业务写前返回稳定错误且零残留。原子业务调用方不得把 65 条自动拆成两次提交。
6. 在相同数据库、数据量和压测模型下，与 1.0 散写基线比较：吞吐必须提升且 p95 事务时延不得回退；报告同时给出锁等待、SQL 次数和 CPU/IO，不能只报接口平均值。
7. 模拟 slave 延迟 60 秒，所有资金命令、读己之写、到期终结和对账仍只使用 primary 且结果正确。
8. 并发交叉运行购买/退款、日结/到期、返佣释放、提现创建/审核/终态和注销清退，trace 中全局锁等级只增不减；故意引入“资产后锁等级/产品”的测试替身必须被门禁捕获。
9. 暂停人工 INCOME/任务奖励补偿与 `RequestAccountClosure` 于各锁点：入账先提交时注销锁内能力复检必须看到余额；注销先转 CLOSING 时普通补偿无 adjustment/ledger 残留。只有引用 cutoff 前登记来源的纠错可在 CLOSING 入账并同事务唤醒 blocker；CLOSED 的 INCOME/EXPENSE、换键重试和管理员强制标志全部拒绝且钱包版本不变。
