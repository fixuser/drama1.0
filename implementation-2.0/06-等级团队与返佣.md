# 06 等级、团队与返佣

> 本章是 Drama 2.0 空库实现规范。团队关系依赖 [04-用户关系与安全.md](04-用户关系与安全.md) 的 `user_id`、`inviter_ids` 和五层 `referral_edges`。不实现历史等级保底、日期祖父分支、F 码兼容或旧数据迁移。

## 1. 目标与边界

本章覆盖团队等级 L0～L7、活跃值与持仓聚合、五层团队返佣、合伙人月度资格、奖池分配、结算和领取。

目标：

1. 等级枚举按业务顺序定义为 `UNSPECIFIED, L0, L1, ..., L7`，可直接比较，不再维护 rank map。
2. 保留现行等级数值门槛，但全部进入不可变规则版本；代码和前端不保存阈值副本。
3. 等级判定是只接收输入快照与规则版本的纯函数，不查询数据库、不写资产、不触发活动。
4. `user_levels` 物化判定所需的最小聚合；活跃值和人数变化在写时原子传播给最多五层祖先，读路径不再扫描团队子树。
5. 每次指标变化都在同一 primary 事务置 `dirty`；后台重算只读写 primary，并用 `FOR UPDATE SKIP LOCKED` 并行领取任务。
6. 凡购买资格、返佣、合伙人分配等资金/权益决策，必须先在 primary 有界排水 path-range 待办并取得 fresh token；超预算返回 retryable，不能消费旧等级或构造无界资格闭包。
7. 直接收益、五层返佣、关系/等级/比例快照和资产分录尽量作为一个结算事务提交，失败后按同一幂等键整体重试。
8. 合伙人月度统计、来源奖池、差额分配、封账和领取均有唯一事实和数据库并发防线。

不在本章范围内：

- 付费 VIP、个人 VIP 等另一条等级线；
- 升级补贴、邀请奖励、周年庆、AI-X、33 挑战、宝藏计划等活动等级副作用；
- 旧 `tips_level` 枚举兼容、历史 floor/cohort、硬编码日期分支；
- 用 Redis 排名、缓存或消息队列作为等级和结算真源；
- 为同库核心写入强制引入 outbox。跨系统通知未来确有不可重建且必须送达的需求时，另立 ADR 设计窄用途方案；本次不预留开关或表。

## 2. 对象、口径与不变量

### 2.1 等级枚举

| 枚举 | 数值 | 可落库 | 含义 |
| --- | ---: | --- | --- |
| `UNSPECIFIED` | 0 | 否 | 协议缺省/未知哨兵，不是业务等级 |
| `L0` | 1 | 是 | 新建行的初始化状态；注册事务必须完成首次计算 |
| `L1` | 2 | 是 | 无门槛基础等级，正常用户首次计算后的最低结果 |
| `L2` | 3 | 是 | 第一个有资格门槛的等级，也是“合格成员”默认门槛 |
| `L3` | 4 | 是 | 顺序等级 |
| `L4` | 5 | 是 | 合伙人资格的最低团队等级 |
| `L5` | 6 | 是 | 顺序等级 |
| `L6` | 7 | 是 | 顺序等级 |
| `L7` | 8 | 是 | 最高等级 |

代码、数据库、配置和协议都使用上述同一编号。`UNSPECIFIED` 不能写入 `user_levels`；任何未知枚举失败关闭，不按 L0 或 L1 猜测。

### 2.2 指标口径

| 指标 | 口径 |
| --- | --- |
| `personal_active_value` | 本人当前生效、按规则计活跃值的持仓本金合计 |
| `team_active_value` | 关系深度 1～5 的普通用户 `personal_active_value` 合计，不含本人 |
| `total_active_value` | 计算时派生：`personal_active_value + team_active_value`，不落第二份总额 |
| `active_holding_count` | 本人当前生效且满足等级口径的持仓条数 |
| `direct_qualified_count` | 深度 1 且当前等级 `>=L2` 的普通用户数量 |
| `team_qualified_count` | 深度 1～5 且当前等级 `>=L2` 的普通用户数量，包含直属 |
| `current_level` | 按当前指标和当前生效规则得出的等级，可升可降 |
| `highest_level` | 历史最高等级，只升不降 |

`Robot Activation Voucher` 持仓及其他未真实支付本金的持仓默认不增加活跃值、不增加 `active_holding_count`、不产生团队返佣和合伙人池。具体持仓创建时必须保存 `active_value_contribution` 和各收益资格快照，等级模块只应用该确定值，不根据产品名称猜测；2.0 不建模普通短剧支持券。

### 2.3 强制不变量

1. 每个参与团队等级的普通用户恰有一行 `user_levels`；后台账号不建等级行。
2. `current_level`、`highest_level` 均在 L0～L7 范围内，且 `highest_level >= current_level`。
3. 所有金额和计数非负；任何减量导致负数都使来源业务事务失败并告警。
4. `team_active_value` 永远不含本人，展示“团队总活跃值”时显式相加。
5. 合格成员门槛来自当前规则版本，初始版本固定为 L2；`direct_qualified_count` 与 `team_qualified_count` 使用同一门槛。
6. 一笔活跃值变化只应用一次，并对本人及前五层祖先对称增减。
7. 用户跨越合格门槛时，直属上级的 direct 计数和前五层祖先的 team 计数在同一重算事务原子调整。
8. 规则版本发布后不可修改；任何改动创建新版本，历史等级变更、返佣和合伙人记录继续引用旧版本。
9. 已结算返佣保存来源关系、受益人等级、比例和规则版本快照；后续等级、规则或账号状态变化不改历史。
10. 核心正确性只依赖 primary 中的持仓、关系、聚合、规则、资产流水和结算事实，不依赖缓存、Redis 队列或 slave。

## 3. 状态机

### 3.1 规则版本

```text
DRAFT --提交复核--> REVIEWED --发布--> PUBLISHED --> RETIRED
   └──────────────────删除未发布草稿
```

- `DRAFT` 可编辑，不可参与计算。
- `REVIEWED` 内容冻结，复核人与创建人不得相同。
- `PUBLISHED` 只能带满足 10 章发布门禁的当前/未来 `effective_at`；普通发布不得倒填过去，PARTNER 必须是严格晚于发布事务 DB now 的 Jakarta 月初。达到生效时间且未过 `expires_at` 才是“当前生效已发布版本”。
- 同一业务域任一时点最多一个 PUBLISHED 版本生效，生效区间不得重叠。
- 已发布版本只能退役，不能原地修值。
- 服务启动时没有当前生效的 PUBLISHED 版本则健康检查失败；禁止回退到 Go 硬编码默认值。

### 3.2 用户等级聚合

```text
CLEAN --指标/规则变化--> DIRTY --worker 或同步刷新锁定--> CALCULATING
CALCULATING --成功且版本未变化--> CLEAN
CALCULATING --失败或又有新变化--> DIRTY
```

`CALCULATING` 是数据库行锁期间的瞬时状态，不额外落枚举。持久状态由以下字段表达：

- `dirty_at IS NULL`、`calculated_metrics_version=metrics_version`、`calculated_dirty_generation=dirty_generation` 且规则版本为 runtime root 当前 active：`CLEAN`。
- 其他情况：`DIRTY`。

等级从 L1～L7 可双向变化；L0 只用于同一注册事务中的初始化，正常提交后应至少为 L1。`highest_level` 只在新等级更高时推进。

### 3.3 返佣事实

```text
五层即时返佣：ABSENT --来源结算成功--> POSTED --冲正成功--> REVERSED

购买冻结返佣：ABSENT --购买成功--> FROZEN --到期释放--> RELEASED
                                      └--退款取消--> CANCELED + REVERSAL(CANCELED_FROZEN)
RELEASED --退款--> 追加 REVERSAL(POSTED 钱包扣回 | EXTERNAL_RECOVERY 外部案件)
```

来源事实与首次返佣/冻结资产效果同事务提交，没有“业务成功但首次返佣待补”的半完成态。释放前退款时，原 GRANT 转 CANCELED，追加唯一 `REVERSAL(CANCELED_FROZEN)` 并用 `SettleFreeze` 取消 pending；该冲正没有可用余额流水、不得计作已确认收益冲正。已释放返佣遇到退款时，原 GRANT 保持 RELEASED，冲正追加唯一 REVERSAL 并引用它：钱包可安全扣回则 REVERSAL 终态为 POSTED；账号 CLOSED 或锁内可用额不足则同事务创建唯一 `finance_recovery_cases`，REVERSAL 终态为 EXTERNAL_RECOVERY。原 GRANT、金额和快照永不覆盖，也不存在提交后长期 PENDING 的第二套追偿路径。

### 3.4 合伙人月份与领取

```text
OPEN --月末截止--> CALCULATING --核对成功--> SEALED
SEALED --规则约定领取日到达--> CLAIMABLE
逐用户 settlement：CALCULATED --用户领取--> CLAIMED
```

- 月度来源事实在 `OPEN` 月写入，封账后禁止追加普通来源；迟到数据走下一期调整记录。
- `CALCULATING` 的瞬时/租约失败从当前持久 cursor 重试；若确定性计算器或证明协议有缺陷，必须用 `RestartPartnerMonthGeneration` 放弃整代并从零构建新代，旧代部分 settlement 永不可见。
- `SEALED` 金额不可直接修改；差异写入追加式 `partner_settlement_adjustments`，按 `apply_month` 进入后续开放月份。
- 月根停留在 CLAIMABLE；每个用户自己的 settlement 进入 CLAIMED，其他用户仍可领取。已 CLAIMED settlement 再次请求返回原领取结果，不重复入账。

## 4. 规则与现行阈值

### 4.1 初始等级规则版本

L2 的 50 使用本人活跃值并要求至少一个有效通用币持仓；L3～L7 的 200、1,200、7,000、40,000、300,000 延续现行计算使用的“五层总活跃值”，即本人加 1～5 层，不改变数值。直推和五层人数均统计等级 `>=L2` 的成员。

| 目标等级 | 本人活跃值下限 | 五层总活跃值下限 | 有效持仓条数下限 | 直属合格人数下限 | 1～5 层合格人数下限 |
| --- | ---: | ---: | ---: | ---: | ---: |
| L0 | — | — | — | — | — |
| L1 | 0 | 0 | 0 | 0 | 0 |
| L2 | 50 | 0 | 1 | 0 | 0 |
| L3 | 0 | 200 | 0 | 3 | 0 |
| L4 | 0 | 1,200 | 0 | 10 | 60 |
| L5 | 0 | 7,000 | 0 | 20 | 350 |
| L6 | 0 | 40,000 | 0 | 35 | 2,000 |
| L7 | 0 | 300,000 | 0 | 50 | 10,000 |

首发 `rule_versions(domain=TEAM_LEVEL)` 的结构化设置明确保存 `base_level=L1`、`qualified_level=L2`。纯函数从该版本的 `base_level` 开始，对 L2～L7 每一档独立执行五项 `>=` 判断，返回满足条件的最高等级。不能因为某一中间档未满足就提前 `break`；配置发布校验同时要求等级唯一、有序、金额/人数非负，并对可能跳档的配置输出影响预览。

L0/L1 首发分界不是运行时猜测：首发已发布版本的 `base_level=L1`，因此 L0 仅存在于注册事务写入等级行到首次纯计算之间，不能成为已提交普通用户的长期状态。如果未来改变 base 或 qualified level，必须新建规则版本并触发全量资格重算；不得只改枚举常量。

### 4.2 初始合伙人规则版本

合伙人要求来源时的 `current_level >= L4`，并按当月家庭活跃值确定档位：

| 合伙人档位 | 当月家庭活跃值下限 | 权益系数 |
| --- | ---: | ---: |
| Bronze | 5,000 | 0.30 |
| Silver | 50,000 | 0.50 |
| Gold | 500,000 | 0.70 |
| Sultan | 1,500,000 | 1.00 |
| Envoy | 5,000,000 | 1.00 |

系数统一使用 0～1 的小数，`0.30` 明确表示奖池的 30%，不是 0.3%。基础奖池率为 `0.05`。初始版本不包含周年庆翻倍、Envoy 额外溢出或其他活动加成。

## 5. 数据表、关键字段、约束与索引

### 5.1 通用 `rule_versions` 与等级结构化子表

等级、团队返佣和合伙人不各建一张版本主表，统一使用总览定义的 `rule_versions`：

| `domain` | 内容 |
| --- | --- |
| `TEAM_LEVEL` | base/qualified level 和 L2～L7 门槛 |
| `TEAM_REBATE` | 来源矩阵、计算模式、冻结/释放、舍入规则和等级×层级比例 |
| `PARTNER` | 时区、基础池率、最低团队等级、领取日、来源白名单和合伙人档位 |

`rule_versions` 统一保存 `id/domain/version/status/effective_at/expires_at/content_hash/created_by_admin_id/reviewed_by_admin_id/created_at/published_at`。其状态和时间约束遵循数据模型总览，三类规则只共享版本生命周期，不共享业务 payload。

`level_rule_settings` 是 `rule_versions(domain=TEAM_LEVEL)` 的一对一结构化子表：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `rule_version_id` | `bigint` | 主键、外键 `rule_versions(id)` |
| `base_level` | `smallint` | 首发明确为 L1；纯函数最低结果 |
| `qualified_level` | `smallint` | 首发明确为 L2；人数聚合门槛 |

`level_rule_tiers` 是同一版本的一对多结构化子表：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `rule_version_id` | `bigint` | 外键 |
| `level` | `smallint` | L2～L7；主键组成部分 |
| `min_personal_active_value` | `numeric(30,8)` | 非负 |
| `min_total_active_value` | `numeric(30,8)` | 非负 |
| `min_active_holding_count` | `integer` | 非负 |
| `min_direct_qualified_count` | `integer` | 非负 |
| `min_team_qualified_count` | `integer` | 非负 |

主键 `(rule_version_id, level)`。两个子表没有独立 status/version，不能脱离父 `rule_versions` 发布。规则发布事务锁定规则域，验证父子齐全、base/qualified 合法、档位完整、数值精度、时间不重叠、审批分离和 content hash 后再冻结。L1 由首发已发布版本的 `base_level` 明确决定，不依赖一条可能被误删的零门槛 tier。

### 5.2 `user_levels`

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `user_id` | `bigint` | 主键及外键 `users(id)` |
| `current_level` | `smallint` | `CHECK BETWEEN 1 AND 8` |
| `current_level_at` | `timestamptz` | 当前等级开始时间 |
| `highest_level` | `smallint` | `CHECK BETWEEN 1 AND 8`，只升不降 |
| `highest_level_at` | `timestamptz` | 首次达到最高等级时间 |
| `level_rule_version_id` | `bigint` | 最近成功计算使用的规则版本 |
| `is_qualified/qualified_level_snapshot` | `boolean/smallint` | 最近成功计算时按该历史规则得到的资格布尔值与门槛；切版时 old flag 直接读快照，new flag 按 candidate 规则计算，不能用新门槛反推旧状态 |
| `personal_active_value` | `numeric(30,8)` | 本人，非负 |
| `team_active_value` | `numeric(30,8)` | 1～5 层，不含本人，非负 |
| `active_holding_count` | `integer` | 非负 |
| `direct_qualified_count` | `integer` | 直属 `>= qualified_level`，非负 |
| `team_qualified_count` | `integer` | 1～5 层 `>= qualified_level`，非负 |
| `metrics_version` | `bigint` | 任一判定输入变化时原子加一 |
| `calculated_metrics_version` | `bigint` | 最近成功计算消费的版本 |
| `dirty_at` | `timestamptz null` | 持久脏标记 |
| `dirty_reason_mask` | `bigint` | ACTIVE_VALUE/HOLDING/RELATION/CHILD_LEVEL/RULE 等原因位 |
| `dirty_generation/calculated_dirty_generation` | `bigint/bigint` | 每次输入再变化 dirty generation 加一，成功波推进 calculated；worker 每波只处理本人和前五层 |
| `last_calculated_at` | `timestamptz` | 最近计算时间 |
| `version` | `bigint` | 任一行字段变化时加一，供缓存和诊断；与判定专用 metrics version 分离 |
| `updated_at` | `timestamptz` | 更新时间 |

约束：

- 金额、计数和全部版本号均不得为负。
- `highest_level >= current_level`。
- `calculated_metrics_version <= metrics_version`。
- `calculated_dirty_generation <= dirty_generation`；clean 时两种 metrics/generation 水位分别相等且祖先快照可清空。
- `dirty_at IS NULL` 时必须满足两个 metrics version 相等；规则版本是否仍是当前生效 PUBLISHED 版本由查询和 worker 共同校验。

索引：

- `(current_level, user_id)`：等级筛选与运营分页。
- `(level_rule_version_id, user_id)`：规则切换找旧版本行。
- 部分索引 `(dirty_at, user_id) WHERE dirty_at IS NOT NULL`：只供 queue 重建和对账；worker 领取租约只写 `level_recalc_queue`。
- `(user_id,dirty_generation)` 支撑单行 CAS；任意深度潜在影响查询只走下述规范化 queue 的路径前缀 B-tree，禁止用数组 GIN + top-N sort 冒充有界读取。
- 不给每个聚合列建索引；等级计算按主键读一行。

不保存所有等级人数数组。当前规则只需要固定 `>=L2` 的直属数和五层总数；旧页面如需逐等级分布，通过 `referral_edges JOIN user_levels` 的只读统计接口或独立报表投影提供，不能成为等级判定第二真源。

`level_recalc_queue` 是等级域的规范化持久待办索引，每个 dirty 用户一行：`user_id PK/relation_path_key/relation_depth/dirty_generation/status=PENDING|RUNNING/next_run_at/lease_owner/lease_until/lease_generation/lease_due_at/created_at/updated_at`。`relation_path_key` 复制 `users` 的 root→self 固定宽度二进制路径；B-tree `(relation_path_key,user_id)` 使任一目标的全部后代等于一个 `[target_path,prefix_upper(target_path))` 连续范围，强一致查询可真实 Index Scan + keyset + LIMIT N，不先物化全部匹配 TID。`lease_due_at` 是数据库维护的非空规范领取键：无租约时等于最小时间，持有租约时等于 `lease_until`；全局 worker 使用 partial B-tree `(next_run_at,lease_due_at,user_id) WHERE status IN ('PENDING','RUNNING')`。dirty 行与 queue upsert 同事务，generation 匹配清标时才删除 queue；它不携带业务命令、不是 Outbox，可从 `user_levels.dirty_at` 重建。

`level_rule_runtime_roots` 每个 `TEAM_LEVEL` domain 一行，保存 `serving_rule_version_id/effective_candidate_rule_version_id/status=CLEAN|SEEDING|DRAINING|VERIFYING/seed_cursor/proof_count/proof_hash/generation/dirty_at/version`。首发明确选择“受控维护 barrier + 单份 materialization”，不伪装成无 Schema 支撑的在线双缓冲：到达严格未来生效点时，短事务先把 root 从 CLEAN 置 SEEDING 并固定 candidate；从该提交起，所有注册/关系绑定、会改变活跃值/持仓/qualified 计数的写入口、等级/团队展示和任何资金/权益资格统一返回可重试 `LEVEL_RULE_ROLLOUT_PENDING`。这些入口都必须在用户/资产前持该 root SHARE 并要求 CLEAN；因此 worker 可在无并发指标写、无读者消费的条件下原地把 `user_levels` 从 serving 版本逐批转换为 candidate，按波次收敛并独立验证，最后短事务切 serving/清 candidate。不能返回混合版本或声称旧快照仍可读；失败只能从持久 cursor 续跑，规则缺陷则发布更正版本并在同一 barrier 内前向重算，不能把部分原地结果直接回滚为 CLEAN。该罕见维护窗口的 SLA、演练和告警是规则发布门禁，任何事务都不扫描全站。

### 5.3 `active_value_ledgers` 与 `level_change_audits`

`active_value_ledgers` 保存每次活跃值增加或对称移除，只有 `operation=GRANT/REVERSAL`：

- `user_id`、`delta`、`before`、`after`；
- `reason`、`source_type`、`source_id`、`grant_kind`、`reversal_of_id nullable`；
- `idempotency_key UNIQUE`；
- `created_at`；
- `CHECK (before + delta = after)`。

GRANT 的 `delta > 0` 且 partial unique `(source_type,source_id,grant_kind)`；REVERSAL 的 `delta < 0`、`reversal_of_id NOT NULL UNIQUE`，绝对值/用户/来源/规则必须与被冲正 GRANT 一致。管理纠错也必须先创建有审计和审批的显式来源事实，再走同一 GRANT/REVERSAL 模型，不能用新幂等键重复同源 delta。索引 `(user_id,id DESC)` 和 `(source_type,source_id)`。持仓事实、活跃值流水、本人聚合、五层祖先增量和 dirty 必须同事务提交。

`level_change_audits` 为追加式审计：

- `user_id`、`before_level`、`after_level`、`reason`；
- `rule_version_id`、`evaluated_metrics_version`；
- `before_is_qualified/before_qualified_level/before_rule_version_id` 与 `after_is_qualified/after_qualified_level`，证明切版时资格 delta 不是从新门槛反推旧状态；
- 五项输入快照及 `total_active_value`；
- `operator_admin_id`（仅人工纠错命令，外键指向 `admin_users.id`）；
- `created_at`；
- `UNIQUE(user_id, rule_version_id, evaluated_metrics_version)`。

当 `current_level`、`is_qualified`、`qualified_level_snapshot` 或所用规则版本任一变化时写日志；因此等级数值不变但资格门槛/flag 因切版变化也有完整前后审计。注册初始化使用独立 reason。人工不能直接改 `current_level`；纠错必须先修正可解释的来源指标或走带原因、审批和输入快照的专用命令。

### 5.4 返佣规则与 `team_rebate_settlements`

返佣版本主记录使用 `rule_versions(domain=TEAM_REBATE)`。一对一 `team_rebate_rule_settings` 保存金额 scale、舍入模式、默认入账方式和冲正策略；`team_rebate_rule_rates` 保存 `rate_scope=LEVEL_SPECIFIC/LEVEL_AGNOSTIC`、可空 `beneficiary_level`、`calculation_mode=DIFFERENTIAL/FLAT`、`depth=1..5`、`entitlement_rate numeric(18,8)`、`settlement_mode=AVAILABLE/FROZEN` 和 `release_after_days`。LEVEL_SPECIFIC 要求真实 L0–L7 且按 `(rule_version_id,source_kind,depth,beneficiary_level)` 唯一；LEVEL_AGNOSTIC 要求 `beneficiary_level IS NULL` 且按 `(rule_version_id,source_kind,depth) WHERE rate_scope='LEVEL_AGNOSTIC'` 唯一。直/间推购买使用 LEVEL_AGNOSTIC，数据库不把 Proto 零值 `UNSPECIFIED` 写成业务等级；发布校验禁止两个 scope 对同一来源/depth 重叠。

首发来源矩阵是计算器和 Schema 的正式白名单：

| `source_kind` | 来源事实 | 基数 | 层级/算法 | 初始资产效果 |
| --- | --- | --- | --- | --- |
| `PLAYLET_BACKING_DAILY` | 正额 POSTED `playlet_backing_settlements` | 当日直接收益基数 | 1～5 层等级差额 | COMMON `INCOME` |
| `ROBOT_HOLDING_DAILY` | `robot_holding_settlements` | 当日直接收益基数 | 1～5 层等级差额 | COMMON `INCOME` |
| `EPISODE_PURCHASE` | `episode_purchase_orders` | 仅订单 `paid_common`，EXPERIENCE 部分为 0 | 直属/间接 1～2 层 FLAT | COMMON `INCOME_FROZEN`，按规则释放 |
| `ONE_TIME_VIP_PURCHASE` | `vip_orders` | 订单按已发布规则换算并快照的 `rebate_base_common` | 直属/间接 1～2 层 FLAT | COMMON `INCOME_FROZEN`，按规则释放 |

`Robot Activation Voucher`、EXPERIENCE 支付部分、自动续订和活动来源不在矩阵中。新增来源必须同时扩展 Proto、结构化规则、事实外键校验、收益白名单、退款/冲正规则和测试。

`team_rebate_settlements` 保存：

| 字段 | 说明 |
| --- | --- |
| `id/business_no` | 内部主键和不可枚举业务号 |
| `operation/reversal_of_id` | `GRANT/REVERSAL`；REVERSAL 必须唯一引用原 GRANT |
| `source_kind/source_fact_id` | 严格对应上表事实主键 |
| `rebate_type` | `TEAM_DIFFERENTIAL/DIRECT_REFERRAL/INDIRECT_REFERRAL`；必须与 source/depth/calculation mode 匹配 |
| `business_date/source_user_id/beneficiary_user_id/depth` | 业务日、购买/收益用户、受益上级和真实层级 |
| `calculation_mode/base_amount` | DIFFERENTIAL 或 FLAT 及 COMMON 基数 |
| `beneficiary_level` | 结算时受益人的真实 L0–L7 等级快照；即使购买 FLAT 规则不依赖等级也必须保存，绝不落 NULL/UNSPECIFIED |
| `entitlement_rate/previous_effective_rate/diff_rate` | 比例快照；FLAT 的 previous 为 0、diff 等于 entitlement |
| `amount` | 正数返佣绝对额，方向由 operation 决定 |
| `ancestor_user_ids_snapshot` | 来源时关系快照，购买至少保存前两层 |
| `level_rule_version_id/team_rebate_rule_version_id` | 结算时等级及返佣规则快照；FLAT 也保存实际等级版本用于审计 |
| `status/releasable_at/next_run_at` | GRANT 为 `FROZEN/POSTED/RELEASED/CANCELED`；REVERSAL 提交终态为 `CANCELED_FROZEN/POSTED/EXTERNAL_RECOVERY`，不存在 PENDING/RECOVERY_REQUIRED 中间态；案件之后如何解决只改变案件状态，不改写返佣事实 |
| `finance_recovery_case_id` | 仅 REVERSAL=EXTERNAL_RECOVERY 时非空且唯一引用 Finance case；REVERSAL=CANCELED_FROZEN/POSTED 时必须为空 |
| `freeze_id/open_asset_ledger_id/terminal_asset_ledger_id` | 冻结明细、首次入账和释放/扣除/冲正流水引用 |
| `created_at/updated_at` | 创建和状态推进时间 |

原始事实使用 partial unique `(source_kind, source_fact_id, beneficiary_user_id, rebate_type) WHERE operation='GRANT'`；`source_fact_id` 已严格指向矩阵中的唯一日结算或订单事实，`business_date` 只是审计快照，不能用于绕过防重。冲正使用 `reversal_of_id UNIQUE WHERE operation='REVERSAL'`。REVERSAL 的用户、资产、绝对金额和来源必须与原 GRANT 一致，不能通过改日期或 `rebate_type` 绕过唯一键。索引 `(beneficiary_user_id,business_date DESC,id DESC)`、`(source_kind,source_fact_id)` 和待释放 partial `(releasable_at,id) WHERE operation='GRANT' AND status='FROZEN'`。

AVAILABLE GRANT 调用 `ApplyMutations(INCOME)`；FROZEN GRANT 调用 `OpenFreeze(INCOME_FROZEN)`。到期释放调用 `ReleaseFreeze`；来源退款在释放前创建唯一 `REVERSAL(CANCELED_FROZEN)` 并 `SettleFreeze`，原 GRANT 转 CANCELED，冻结终结流水只取消 pending，不形成 confirmed reversal。若已释放且受益人钱包仍允许写且可用额充足，REVERSAL 通过受控 `EXPENSE` 追偿并终态 POSTED；锁内可用额不足写 `reason_code=INSUFFICIENT_AVAILABLE`，账号已 CLOSED 写 `reason_code=CLOSED_ACCOUNT`，两者都不得部分扣回，而是在同一退款事务创建/命中唯一 `finance_recovery_cases` 并把 REVERSAL 终态记为 EXTERNAL_RECOVERY。原 GRANT 保持 RELEASED，案件状态协议见下述 §5.4.1；它绝不重开账号、写钱包或让第三方状态否决付款人退款。金额一律使用十进制定点数；API 比例用 0～1 字符串小数。

### 5.4.1 Finance 外部追偿案件

返佣子域只创建 `INSUFFICIENT_AVAILABLE` 或 `CLOSED_ACCOUNT` 两类 `finance_recovery_cases`；前者只允许 RECEIVABLE 且表示锁内可用额不足以全额扣回，后者表示 CLOSED 账号禁止任何钱包写。全局 Finance 模型还承接 05/09 章登记的支付渠道相反终态原因，不能据此向返佣入口开放任意 reason。创建时保存账号状态、可用额、应处置金额和强类型来源快照。返佣退款子类型还必须保存原 RELEASED GRANT 和 EXTERNAL_RECOVERY REVERSAL；CLOSED 后的稳定历史财务纠错则引用其获批纠错事实，不伪造返佣行。自然键由 `finance_recovery_case_roots(source_type,source_id,source_component,subject_user_id,direction)` 串行化；同一来源组件最多一案，换命令幂等键不能重复建案。

案件管理状态允许 `OPEN -> IN_REVIEW -> RESOLVED`，或仅当 `direction=RECEIVABLE` 时 `IN_REVIEW -> WAIVED`；全局支付域还允许受控来源反转把未结案转 `CANCELED_BY_SOURCE_REVERSAL`，但返佣 `CLOSED_ACCOUNT/INSUFFICIENT_AVAILABLE` 来源事实自身不可反转，因此返佣入口永不调用该分支。`RESOLVED` 必须在同事务创建一对一 `finance_external_settlements`；其 `(provider,settlement_type,external_reference)` 全局唯一，方向、资产、全额金额和外币快照必须与案件一致，同一凭据不能核销两案。`WAIVED` 仅表示债权经异人审批核销。`PAYABLE` 是对外真实债务，只能在完整外部付款证据下 RESOLVED，`WaiveFinanceRecoveryCase` 必须拒绝 PAYABLE；批量 settlement、债权人豁免或法定应付核销若未来需要，必须另立 ADR、独立动作和会计事实，不复用通用 waive。所有终态都不可重开，也不触发资产原语。REVERSAL 从退款事务提交起即保持 EXTERNAL_RECOVERY，原 GRANT 保持 RELEASED；案件解决或应收豁免不得把 REVERSAL 改为 POSTED，不得补写一条伪造钱包流水。用户收益只以 `asset_ledgers` 为规范来源：POSTED 钱包扣回进入 `confirmed_reversals`，EXTERNAL_RECOVERY 是余额外 Finance 应收，不改变用户收益、账单或钱包，只在 Finance 管理报表展示案件金额与处置进度。

退款创建路径必须先锁来源订单/attempt 和原 GRANT，再按规范键锁 `finance_recovery_case_roots`，随后才进入 closure/freeze/user/asset 层并决定 POSTED 或 EXTERNAL_RECOVERY；禁止先读余额再反向补 root。案件管理命令只用 `case_no` 无锁定位 root，正式按命令防重 → approval（仅 waive）→ recovery root → case → 审计加锁并重验映射；来源事实已经不可变，管理命令不得锁或 UPDATE 原订单、GRANT、REVERSAL、用户或资产，因而没有 case→来源的反向边。`start-review/resolve` 需要 `finance.recovery.resolve`；`waive` 需要 `finance.recovery.waive`、`direction=RECEIVABLE` 和目标/hash 完全一致的未消费异人审批。waive 的审批消费、案件条件更新、命令结果和审计同一 default 事务；接口契约见 [02-API与鉴权规范.md](02-API与鉴权规范.md) §8。

### 5.5 合伙人表

版本主记录使用 `rule_versions(domain=PARTNER)`；一对一 `partner_rule_settings` 保存 `business_timezone=Asia/Jakarta`、`base_pool_rate=0.05`、最低团队等级、领取日和舍入规则，`partner_rule_sources` 明确 `CASH_PLAYLET_BACKING/CASH_ROBOT_PURCHASE` 及其基数字段，`partner_rule_tiers` 保存 Bronze～Envoy 的月活跃值门槛和权益系数。`partner_rule_sources` 唯一 `(rule_version_id,source_kind)`，`partner_rule_tiers` 唯一 `(rule_version_id,partner_tier)`；发布拒绝重复来源/档位、非严格递增门槛和递减权益系数，允许相邻高档系数相等（首发 Sultan/Envoy 均为 1.00）。三类子表与父版本一起 hash、复核、发布，不允许把运行时必需值只写在文档或任意 JSON 中。

PARTNER 规则只允许在 `Asia/Jakarta` 自然月首日 00:00 生效/失效，且普通发布/回滚只能选择严格晚于事务 DB now 的月界；发布层拒绝月中时间和已经过去的月初。这样每个 `earning_month` 恰对应一个 `partner_rule_version_id`，不在同月拼接两套档位、领取日或舍入口径。

首发 `partner_rule_sources` 仅有两行：`CASH_PLAYLET_BACKING -> playlet_backings.actual_common_amount`，`CASH_ROBOT_PURCHASE -> robot_holdings.principal_amount`。两者都在来源成功事务创建一次 pool；日收益 settlement、EXPERIENCE、机器人激活券、任务、活动和人工调账不属于池基数。

`partner_monthly_qualifications`：

- 主键 `(user_id, earning_month)`；
- `family_active_value`，非负；口径为本人及关系深度 1～5 普通用户在该月新增的合格活跃值贡献；
- `partner_tier`；
- `metrics_version`、`rule_version_id`；
- `updated_at`；行没有独立 OPEN/SEALED 状态，可写性只由锁内 `partner_months.status` 裁决；
- 索引 `(earning_month, user_id)`。

`partner_calendar_roots` 只有一行 `code='PARTNER'`，保存不可变 `first_earning_month/version/created_at`。它在空库 bootstrap 事务中以业务上线日所在 Jakarta 自然月初始化；应用无 UPDATE/DELETE 权限。它不是可按环境漂移的“首发特例”：只有该自然月的 generation 可使用规范零前驱，任何更晚月份都必须引用前一自然月已发布证明。协调器必须从该月起逐月 Ensure/封账；没有 allocation 的静默月仍发布空 source、结转非零 adjustment head，从而形成无空洞链。

`partner_months` 是月级可锁聚合根，主键 `earning_month`，保存 `status=OPEN/CALCULATING/SEALED/CLAIMABLE`、唯一 `partner_rule_version_id`、可空 `current_calculation_version`、可空 `selected_calculation_version`、`next_run_at/sealed_at/claimable_at/version`。`EnsurePartnerMonth(tx,earning_month)` 先锁 `partner_calendar_roots`，拒绝早于 first month 或跳过尚未发布的前月，再按月唯一键 `INSERT ... ON CONFLICT`，从 primary 解析该月唯一 PARTNER 规则并创建 OPEN 根；来源事务随后用 `FOR SHARE` 取得 OPEN 月 fence，允许不同用户并发入池，封账则用 `FOR UPDATE` 等待所有来源后转 CALCULATING。OPEN 要求 current/selected 都空；CALCULATING 要求 current 指向 BUILDING 且 selected 仍为空；SEALED/CLAIMABLE 要求 current 为空、selected 指向 PUBLISHED。月界作业可预建本月/下月，但正确性不依赖 cron。来源 GRANT/OPEN 冲正必须持有该共享 fence；进入 CALCULATING 后旧月不接收新 GRANT/当前代 adjustment。所有分片完成且输入/输出/head 证明对账通过后，月根才能选择正 `calculation_version` 并发布为 SEALED；到领取日只推进月根为 CLAIMABLE，不批量更新用户行。查询和领取必须同时确认月根状态与 selected version。

`partner_month_generations` 保存每个 `(earning_month,calculation_version)` 的不可变构建契约：`status=BUILDING/ABANDONED/PUBLISHED`、`partner_rule_version_id/source_cutoff_at/adjustment_cutoff_at/shard_count/partition_seed/hash_protocol_version/calculator_build_id/contract_hash/predecessor_month/predecessor_calculation_version/predecessor_result_hash`、来源与 settlement/application/head 的 count/amount/hash、`created_at/abandoned_at/published_at/restart_reason/restart_ticket_no`。建立 `UNIQUE(earning_month,calculation_version,result_hash)`；三个 predecessor 列同空同非空，并以同列序 composite FK 指向 PUBLISHED generation。仅 `earning_month=partner_calendar_roots.first_earning_month` 允许三列全空且使用 `CANONICAL_EMPTY_PARTNER_PREDECESSOR_HASH`；其余月份由延迟约束触发器要求 predecessor month 恰为前一自然月、calc/hash 恰为该月 root selected 的 PUBLISHED generation。`shard_count` 数据库 CHECK 固定为 `1..256`，应用常量 `PARTNER_MONTH_SHARD_COUNT_MAX=256` 与 migration 同源生成；root 的非空 current 只能指向 BUILDING，非空 selected 只能指向 PUBLISHED，发布同事务把 current 清空并设置 selected。旧代一旦 ABANDONED 不可恢复或重新选中，派生 sources/settlements/applications/heads 保留为不可见证据并按保留策略有界清理。

`partner_month_shards` 是封账正确性事实，保存 `earning_month/calculation_version/shard_id/shard_count/hash_start/hash_end/status=PENDING/RUNNING/VALIDATING/SUCCEEDED/FAILED/ABANDONED/stage/lease_owner/lease_until/lease_generation/allocation_cursor/adjustment_stage_cursor/aggregate_cursor/adjustment_apply_cursor/validation_cursor/carry_user_id/carry_phase/carry_gross/carry_adjustment/carry_claimable/carry_previous_adjustment_id/carry_source_hash`、输入 allocation/adjustment/head count/amount/hash、期望输出 settlement/application/head count/amount/hash、验证结果 count/amount/hash、`next_run_at/attempt_count/started_at/finished_at`，唯一 `(earning_month,calculation_version,shard_id)`，并 CHECK `shard_count BETWEEN 1 AND 256`、`shard_id BETWEEN 0 AND shard_count-1`。月根进入 CALCULATING 的同一短事务创建 generation 和 `[0,shard_count)` 全部分片，并把无符号 64 位 hash 空间切成连续、无重叠、无空洞的范围；每个受益用户的稳定 `beneficiary_hash=hash64(user_id,PARTNER_HASH_V1_SEED)` 恰落入一个范围。所有 cursor 和固定大小 carry 与每批输出同事务推进；单个热点用户的百万来源或 adjustment 都能跨批，租约过期只能由递增 generation 的新 owner 重领，旧 lease 或非 current calculation version 不得写 cursor/SUCCEEDED。

`partner_month_sources` 是计算版本内不可见的规范化来源清单，保存 `earning_month/calculation_version/shard_id/beneficiary_hash/beneficiary_user_id/phase=ALLOCATION|ADJUSTMENT/phase_rank/adjustment_priority/adjustment_id nullable/adjustment_sort_id NOT NULL/source_kind/source_id/source_component/signed_amount/source_persisted_at/source_hash`，来源自然键在同版本唯一。`source_persisted_at` 必须从不可变 allocation 的持久化时间或 adjustment 的 approved/source provenance 复制，调用方不可填写；正数来源用它证明权益是否早于 closure cutoff，负数 correction 另在 hash 中保存原正来源引用。`phase_rank` 是数据库生成或触发器复核的规范序号，固定 `ALLOCATION=0、ADJUSTMENT=1`；CHECK 同时拒绝未知 phase、错误 rank 及直接改 rank，绝不能依赖枚举名或字符串的数据库排序。`adjustment_sort_id` 是不可变规范键：ALLOCATION 必须 `adjustment_id IS NULL AND adjustment_sort_id=0`，ADJUSTMENT 必须 `adjustment_id IS NOT NULL AND adjustment_sort_id=adjustment_id>0`；`phase/phase_rank/adjustment_priority/source_kind/source_id/source_component` 同样 NOT NULL。真实 keyset 索引、规范 hash 和 `aggregate_cursor` 都使用全非空元组 `(earning_month,calculation_version,shard_id,beneficiary_user_id,phase_rank,adjustment_priority,adjustment_sort_id,source_kind,source_id,source_component)`，翻页谓词固定为该 row-value 严格 `>`，初始游标使用各类型域外最小哨兵，绝不以 nullable 列比较。由 `phase_rank` 保证 ALLOCATION 物理排在 ADJUSTMENT 前，调整再按“前驱负 head、SOURCE_REVERSAL、其他负数、正数”和稳定 ID 排序。`PARTNER_HASH_V1_SEED` 是随 `hash_protocol_version` 固化的全局不可变常量，在空库 bootstrap 时写入配置真源；所有月份、allocation、adjustment 和 head 使用同一个 seed，不能在封账时随机生成。`partner_pool_allocations` 同步冗余不可变的 `earning_month/operation_sign/beneficiary_hash/source_persisted_at` 并建 `(earning_month,beneficiary_hash,beneficiary_user_id,id)` 索引；数值由同事务从 pool fact 复制并由约束触发器核对，不能由调用方填写。这样 source staging 每批最多读取 N 条真实索引记录，而不是对整月 join/hash 后再 LIMIT。

跨月调整使用版本化 `partner_adjustment_heads(adjustment_id,earning_month,calculation_version,beneficiary_user_id,beneficiary_hash,remaining_after,next_apply_month,source_hash)`；键为 `(adjustment_id,earning_month,calculation_version)`。`beneficiary_user_id/hash` 从 adjustment 复制，并由 composite FK/约束触发器核对两者及固定 hash 函数，支持按用户有界清退。首个适用月的候选来自 `partner_settlement_adjustments(first_apply_month,beneficiary_hash,id)` 索引，延续候选只来自上一收益月已 SEALED 根所指 generation 的非零 head，并以 `(earning_month,calculation_version,beneficiary_hash,adjustment_id) WHERE remaining_after<>0` 扫描。每个当前 generation 都写自己的 head，失败代次永不参与下一月。前驱契约保存在 generation 而非月根的可漂移字段中；除 `partner_calendar_roots.first_earning_month` 外，M 只有在 M-1 已 SEALED/CLAIMABLE 后才能 OPEN→CALCULATING，从结构上禁止相邻月份同时读取同一 remaining_before。静默月也必须读取并发布非零前驱 head。

`partner_settlements` 唯一键改为 `(user_id,earning_month,calculation_version)`，并显式建立 `UNIQUE(id,user_id,earning_month,calculation_version)` 供 application composite FK 使用：0 代是 OPEN/CALCULATING 期间的 provisional 累计；正代由 shard 构建且在月根发布前不可见，状态为 `BUILDING -> CALCULATED -> CLAIMED`。首条 application 前先插入或命中同用户/月/代 BUILDING 壳，全部 application 都以非空 `settlement_id` 引用它；用户组闭合时，只有持当前 shard owner/lease generation 的 worker 可用一次条件 UPDATE 固化金额/hash并转 CALCULATED。旧 owner、失败/ABANDONED 代和仍 BUILDING 的壳都不可发布或领取。SEALED/CLAIMABLE 由月根表达，避免封账或开放领取时批量 UPDATE 全月用户。`partner_adjustment_applications` 唯一键包含 `(adjustment_id,apply_month,calculation_version)`，只属于相应不可见代次。

`partner_pool_facts` 是追加式 GRANT/REVERSAL 事实：

- `operation=GRANT/REVERSAL`、`source_kind/source_fact_id`；GRANT 使用 partial unique `(source_kind,source_fact_id) WHERE operation='GRANT'`；
- REVERSAL 必须有唯一 `reversal_of_id` 指向同来源 GRANT，并保存终止业务事实类型/ID和原因；一个 GRANT 最多一条 REVERSAL；
- `source_user_id`、`earning_month`；
- `pool_base_amount`、`pool_rate`、`pool_amount`；`pool_base_amount` 是当时合格现金本金的通用名，不包含旧 `support` 语义；
- `ancestor_user_ids_snapshot`；
- `allocation_count`、`allocation_sum`、`unallocated_amount`、`allocation_hash`，只证明规范化正额 allocation 集合；
- `decision_trace jsonb`、`decision_trace_hash`、`trace_protocol_version`，独立证明最多五层的 `ALLOCATED|ZERO_DIFF|ZERO_ROUNDED|SKIPPED` 裁决、previous 前后值与金额快照；
- `partner_rule_version_id`、`reversal_apply_mode=OPEN_MONTH/NEXT_OPEN_ADJUSTMENT nullable`、`created_at`；
- `CHECK (allocation_count BETWEEN 0 AND 5 AND allocation_sum >= 0 AND allocation_sum <= pool_amount AND unallocated_amount = pool_amount-allocation_sum)`；`jsonb_array_length(decision_trace) BETWEEN 0 AND 5`。

`partner_pool_allocations` 规范化保存 `id/pool_fact_id/earning_month/operation_sign/beneficiary_hash/beneficiary_user_id/depth/team_level/partner_tier/self_rate/previous_effective_rate/diff_rate/amount/level_rule_version_id/partner_rule_version_id/reversal_of_allocation_id nullable/source_persisted_at/created_at`。`UNIQUE(pool_fact_id,beneficiary_user_id)`、`UNIQUE(pool_fact_id,depth)`；REVERSAL allocation 必须用唯一 `reversal_of_allocation_id` 一一引用原 GRANT allocation，并复制其全部绝对值快照。金额恒为正、depth 1～5、比例合法；同一来源的延迟约束验证 `COUNT/SUM/hash(正 allocation)` 恰等于 pool fact 的 `allocation_count/allocation_sum/allocation_hash`，并逐项验证每个 `ALLOCATED` trace 元素恰好对应同 depth、用户和金额的一条 allocation；`decision_trace_hash` 只覆盖完整逐层裁决，不与 allocation hash 混用。REVERSAL 复制原 GRANT 的上述证明字段且只为原正 allocation 建反向行。普通 JSON 不承担唯一性或金额真值。

`partner_pool_reversal_dispositions` 对每条 REVERSAL allocation 保存唯一处置：`id/pool_reversal_id/reversal_allocation_id/original_allocation_id/beneficiary_user_id/account_status_snapshot/outcome=ADJUSTMENT|RECEIVABLE/partner_adjustment_id/finance_recovery_case_id/source_persisted_at/deduplication_id/created_at`。`reversal_allocation_id`、`original_allocation_id`、deduplication 和两个非空结果引用分别唯一；ADJUSTMENT 要求仅 adjustment 非空，RECEIVABLE 要求仅 case 非空。composite FK/触发器验证三条 allocation、受益人、绝对金额和规则快照属于同一 GRANT/REVERSAL 对。该行是来源取消对第三方受益人的终态，不改变原 allocation。

所有金额列恒为正，正负语义只由 pool fact `operation` 决定。REVERSAL 复制原 GRANT 的来源金额、关系、分配、等级和规则快照，不能按取消时的新等级重算。GRANT allocations 按受益人累加、REVERSAL allocations 按相同快照冲减；这些行是不承担热余额查询的不可变解释事实。

`partner_settlements`：

- 唯一键 `(user_id, earning_month, calculation_version)`；0 代只供 OPEN/CALCULATING 预估，正代只由对应 shard 构建；
- `gross_amount`、`adjustment_amount`、`claimable_amount`；
- `status`：0 代为 OPEN，正代为 BUILDING/CALCULATED/CLAIMED；BUILDING 仅作同代 application 的不可见 FK 壳，可领取性读取 `partner_months.status=CLAIMABLE` 且 settlement=CALCULATED，不复制一套批量状态；
- `source_cutoff_at/positive_source_count/positive_source_max_persisted_at/positive_source_hash/closure_source_count/closure_source_max_persisted_at/closure_source_hash`、`calculated_at`、`claimed_at`；positive proof 只覆盖正权益，closure proof 覆盖所有决定该行金额的来源及其原始财务 provenance；
- `rule_version_id`、`claim_deduplication_id UNIQUE`、`claim_result_code=POSTED|ZERO_AMOUNT`、`asset_ledger_id UNIQUE`；CLAIMED 且 `claimable_amount>0` 时 ledger 必填/result=POSTED，CLAIMED 且金额为 0 时 ledger 必空/result=ZERO_AMOUNT；
- `calculation_hash`，确保相同来源集合得到相同结果。

`gross_amount/claimable_amount >= 0`，`adjustment_amount` 是 applications 的有符号和，并满足 `claimable_amount = max(gross_amount + adjustment_amount, 0)`；未能应用的负数只留在月根已发布 generation 的 `partner_adjustment_heads.remaining_after`，不能让 settlement 为负。

两个 proof 都使用统一空集合规范：`count=0` 时 `max_persisted_at IS NULL AND hash=CANONICAL_EMPTY_HASH`，`count>0` 时 max 非空且 hash 非空集合值；`claimable_amount>0` 还要求 `positive_source_count>0`。BUILDING 行的金额终值、proof、`calculated_at/claim_* /asset_ledger_id` 全空；CALCULATED 行金额、两类 proof、`calculated_at` 必填而 claim 字段全空；CLAIMED 行还要求 dedup、result、claimed_at 及上述金额分支完整。状态/时间/证明由 CHECK 与延迟触发器约束，不能用 NULL 绕过。

领取幂等结果由公共 `command_deduplications` 保存。正金额时 `claim_deduplication_id` 与月根当前指向的正代 settlement、`asset_ledgers` 入账同事务写入；零金额时同一命令不调用资产原语、不创建零流水，只把 CALCULATED→CLAIMED 并保存明确 `ZERO_AMOUNT` 幂等结果。无需另建领取事实表或依赖分布式锁。

`partner_adjustment_user_roots(user_id,last_approval_seq,version,updated_at)` 是每用户稳定分配根。`partner_settlement_adjustments` 是金额不可改的追加式财务事实，保存 `id/adjustment_business_no/origin=MANUAL/SOURCE_REVERSAL/original_earning_month/first_apply_month/user_id/beneficiary_hash/amount/reason/ticket_no/requested_by_admin_id/approved_by_admin_id/source_pool_reversal_id/status=PENDING_APPROVAL/APPROVED/REJECTED/approval_seq/reversal_of_id/correction_mode/closure_id/source_type/source_id/deduplication_id/approved_at/created_at`。`beneficiary_hash` 必须由服务端以全局固定 `PARTNER_HASH_V1_SEED` 从 `user_id` 生成并由数据库函数复核。MANUAL 审批成功或 SOURCE_REVERSAL 直接创建 APPROVED 的同一事务先按 rank 500/type45 锁 user root，执行 `last_approval_seq += 1` 并把返回值写入 adjustment；`(user_id,approval_seq)` 唯一，非 APPROVED 行 seq 为空。`amount` 可正可负但不可为零；`adjustment_business_no`、`deduplication_id` 唯一，人工冲正时 `reversal_of_id` 非空且唯一。`remaining_amount/PARTIALLY_APPLIED/APPLIED` 不再作为会被构建中代次提前改写的真源；剩余额只按已 SEALED 月根所指 generation 的 applications 求和得到，可另做可重建展示投影。

- `origin=MANUAL` 要求 `ticket_no/requested_by_admin_id`，APPROVED 时再要求不同的 `approved_by_admin_id`，走 `PENDING_APPROVAL -> APPROVED/REJECTED`。纠错必须新建引用原 adjustment 的人工冲正，不能改原金额。
- `origin=SOURCE_REVERSAL` 必须引用唯一 `(source_pool_reversal_id,user_id)`，金额严格等于原 allocation 的负值，管理员字段和 ticket 为空，由来源取消事务确定性创建为 APPROVED；它不是可传任意金额的“系统管理员”入口。
- MANUAL 创建和审批先在事务外从 primary 预收集 approval、稳定历史来源、潜在 Finance recovery 自然键及候选 month/adjustment 集合。正式事务进入 closure/user 层前，把这些根交给统一 `BusinessRootLockKey` 计划：rank 100 approval → rank 400 及以前的来源根 → `finance_recovery_case_roots(rank=400,type=70)` → rank 500 month/shard/qualification/settlement/adjustment/application；禁止先锁 month/adjustment 再反向补 recovery root。锁齐后才依次调用 `PrelockUserClosures` 与 `LockUsersAndValidateClosureGate`；本流程没有既有 freeze 中间锁，所以两阶段相邻。创建时 ACTIVE 可登记普通调整；CLOSING 只允许引用 cutoff 前既有财务来源的纠错；CLOSED 时普通 MANUAL 直接拒绝，只有该历史纠错可在预锁 root 下创建 PAYABLE/RECEIVABLE Finance case，且不创建未来 settlement adjustment。请求前已经 PENDING 的 adjustment 本身是 blocker，CLOSING 可审批或拒绝；任何批准/拒绝/应用都同事务推进 closure `next_check_at`。不得在 CLOSED 后新增或批准未来可领金额。
- 审批/来源冲正事务在上述预收集后，正式锁轨迹必须严格符合 registry 全序；同 rank/type 内按规范 key 排序。不得先锁 adjustment 再回头 Ensure month，也不得在用户或资产层扩大任一 root 集合；重验发现新键时整体回滚扩集。封账对月根转 CALCULATING 时固定 `adjustment_cutoff_at`，所以审批竞态只有“进入本月 cutoff”或“进入下一 OPEN 月”。正数 MANUAL 只在首个尚无已发布 application 的适用月全额应用一次；负调整按已发布历史 application 计算剩额并逐月抵扣，单月 `claimable_amount` 最低为 0。长期无可抵收入进入可重建 RECOVERY_REQUIRED 告警，不改已领取资产流水。
- `partner_adjustment_applications` 保存 `adjustment_id/user_id/apply_month/calculation_version/settlement_id NOT NULL/applied_amount/remaining_before/remaining_after/source_hash/created_at`，`UNIQUE(adjustment_id,apply_month,calculation_version)`；以 `(settlement_id,user_id,apply_month,calculation_version)` 引用同一受益人/月/代的 settlement composite unique，`user_id` 还必须与 adjustment/head 一致，金额带符号且不能为 0。构建中 application 属于不可见 generation，不更新 adjustment 本身；重跑由 shard cursor + generation 唯一键防重。只有月根 SEALED 指向的 applications 参与以后月份剩额计算，失败/旧 generation 不产生影响。历史已发布 settlement/application 永不回写。

`partner_closure_adjustment_dispositions` 是 CLOSING 用户对未抵完负 adjustment 的一次性终结事实，保存 `id/closure_id/adjustment_id/user_id/remaining_source=ORIGINAL_ADJUSTMENT|PUBLISHED_HEAD/head_earning_month/head_calculation_version/head_source_hash/remaining_amount/outcome=POSTED|RECEIVABLE/asset_ledger_id/finance_recovery_case_id/deduplication_id/created_at`；`remaining_amount` 保存待追回绝对正数，`(closure_id,adjustment_id)`、deduplication 和非空结果引用分别唯一。若从未产生已发布 head，source 必须 ORIGINAL_ADJUSTMENT、head 三字段全空且 remaining 等于原负 adjustment 绝对值；若已有历史，source 必须 PUBLISHED_HEAD、三字段全非空且引用最新 selected head 的负 `remaining_after`。最新 head=0、adjustment REJECTED 或正 adjustment 不允许 disposition。POSTED 要求仅 `asset_ledger_id` 非空，RECEIVABLE 要求仅 Finance case 非空。它不修改 adjustment/head/application，只让后续 staging 以唯一 anti-join 永久排除该 adjustment。

closure 行保存 `partner_adjustment_scan_after_seq/partner_adjustment_scan_upper_seq/partner_adjustment_scanned_seq`。Request 事务在取得 rank 500 user root 与 user 锁后才用 `clock_timestamp()` 固定 cutoff，并把当时 `last_approval_seq` 写为 upper。sweep 的每个处理事务先锁 user root、后锁 closure，完整匹配 `(closure version,lease_owner,lease_generation,lease_until,after,upper)` 且要求租约未过期；再按 partial 索引 `(user_id,approval_seq) WHERE status='APPROVED' AND amount<0` 每批最多 N 条继续严格 `>` 游标，对每条以 `(beneficiary_user_id,adjustment_id,earning_month DESC,calculation_version DESC)` `LIMIT 1` 定位最新已发布 head；无 head 用 ORIGINAL_ADJUSTMENT，负 head 用 PUBLISHED_HEAD，零 head直接跳过。批次提交同时 CAS 推进 after/version并续租；到 upper 时只有 root `last_approval_seq=upper` 才把 scanned 推到 upper，否则把新增区间并入下一窗口。过期/旧 owner 的游标、续租、READY 写均影响 0 行。所有审批序号都在该根锁内分配，所以不可能迟提交到已越过区间，也不会每批从头 anti-join 形成 O(n²)。若当前相关 `partner_months` 正处 CALCULATING，则该 adjustment 暂不越过游标，记录最小 blocked seq并等待该代 SEALED/CLAIMABLE 后重取；若为 OPEN，则正式事务锁住它后可先终结，后续封账 staging 必须看见 disposition。完成注销还必须按相同顺序锁 user root→closure，并证明 `last_approval_seq=scanned=upper`。

每条 disposition 正式事务先取得 income root/day fence，再按预收集计划锁潜在 RECEIVABLE recovery root、当前 month/generation、adjustment/head/disposition，证明 current generation 中不存在同 adjustment 的 staged source；发现已 staging、代次变化或集合扩大就回滚等待发布/重建，绝不边 ABANDON 边扣款。随后 `PrelockUserClosures`、锁 user 并复验同一 CLOSING/cutoff，最后锁 COMMON asset：可用额足以全额覆盖时用专用 `biz_type=PARTNER_CLOSURE_ADJUSTMENT_REVERSAL`、`ref=disposition/adjustment` 一次 `ApplyMutations(EXPENSE)`，该组合在 income registry 明确冲减合伙人分红分类并写 POSTED；不足时一分不扣，以 `INSUFFICIENT_AVAILABLE` 创建全额 RECEIVABLE Finance case 并写 RECEIVABLE。disposition、ledger/case、closure 游标/唤醒、幂等和审计同事务；发布证明反向拒绝任何同时存在 disposition 的 staged source。正 adjustment、已形成的正 claimable settlement 和其他既得权益仍必须按正常清退领取/归零，不能用 disposition 没收。

## 7. 主流程

本章任何可能调用资产原语的顶层事务，都在命令/来源事件防重之后、取得任一持仓/订单/返佣/月度等业务根之前，先调用 `AcquireIncomeWriteFences`，依次取得 `rollup_roots('income') FOR SHARE` 与当前 `business_date` 的 OPEN `finance_business_days FOR SHARE`。完成来源/月度根闭包后、取得任何 user 锁前，所有会新增、释放或清除用户收益 blocker 的路径统一先 `PrelockUserClosures`，再锁本次既有 freeze，最后 `LockUsersAndValidateClosureGate`；没有 freeze 的流程两阶段相邻。ACTIVE 才能获得新来源资格，CLOSING 仅处理 cutoff 前已登记事实并唤醒 closure，CLOSED 不写钱包或新可领事实。纯等级/关系计算不写流水且不改变收益 blocker 时不取 finance fence；资产原语只断言已有 root/day token，禁止在业务根之后懒获取。

返佣来源的业务所有者与候选第三方受益人必须在 gate metadata 中分角色裁决。已成立的购买、退款、持仓结算等主事实不能因某个祖先 CLOSING/CLOSED 而回滚：新 GRANT 只给同时满足返佣资格且账号 ACTIVE 的候选。DIFFERENTIAL 跳过候选写唯一 `benefit_forfeiture_audits`，令 `previous_effective_rate_after=previous_effective_rate_before` 且 `not_granted_amount=0`；这不是把固定层槽金额转给后续用户，后续合格候选仍按同一公式得到正常差额。FLAT 槽位必须先计算金额：ZERO_DIFF/ZERO_ROUNDED 只写 calculation audit，不因账号状态建零额 forfeiture；只有 rounded amount 正且候选非 ACTIVE 时才写精确正数 `not_granted_amount`，且不转给其他层。对历史已归属 GRANT 的退款冲正，CLOSED 或余额不足受益人创建唯一 `finance_recovery_cases`，其案件不是主业务终态的前置。只有业务所有者自身不满足对应 ACTIVE/既有来源白名单时，才拒绝整个命令。

### 7.1 注册初始化

1. 普通用户注册事务创建 `user_levels(current_level=L0, highest_level=L0)`。
2. 读取 primary 中当前生效的 `rule_versions(domain=TEAM_LEVEL,status=PUBLISHED)` 及其结构化子表；首发 `base_level=L1`，所以全零输入结果为 L1。
3. 同事务更新 current/highest 为 L1、记录规则和 metrics version，并写 `level_change_audits(reason=INITIALIZATION)`；该审计不产生“L0→L1”升级奖励或活动副作用。
4. 若注册同时绑定上级，关系边、`user_relation_stats` 与等级行同事务提交；普通成员总数由关系域更新，不写入 `user_levels`。新用户尚未合格且 active delta 为零时，不推进祖先判定专用 `metrics_version`，也不增加合格人数。

注册提交后仍停在 L0、缺 `user_levels` 或没有有效规则版本都属于阻断上线的不变量错误。

### 7.2 持仓生效、到期和纠错

1. 来源领域给出稳定事件键、`active_value_delta` 和 `holding_count_delta`，不让等级模块重新推断支付类型。
2. primary 顶层事务在任何 income/day/业务根之前先持 rank 35 `level_rule_runtime_roots('TEAM_LEVEL') FOR SHARE` 并要求 CLEAN，再按全局顺序锁定本人和前五层祖先的 `user_levels` 行；用户行统一按 `user_id` 升序。rollout 非 CLEAN 时来源业务尚未产生资产/持仓半状态就失败。
3. 生效时按来源自然键插入唯一 GRANT `active_value_ledgers`；到期/取消时插入唯一引用原 GRANT 的 REVERSAL。随后原子更新本人 personal/count 和最多五个祖先的 team active；仅换 idempotency key 不能重复应用同一来源。
4. 所有受影响行 `metrics_version += 1`，`dirty_at=COALESCE(dirty_at, now())`，合并 reason mask。
5. 同一命令若既按等级/资格分配本次收益、又写入会改变等级的活跃值，2.0 固定采用“来源发生前快照”：业务事务外先 `EnsureLevelFresh`，事务内复验 fresh token 后固化本次结算等级/资格，再应用 active delta 并标 dirty；本来源不得用自己刚增加的活跃值抬高自己的返佣/合伙人份额。新指标只影响提交后的下一来源；禁止在持有 income/day/商品/月/资产锁时嵌套多波刷新。只改变指标、不按等级付款的终结路径无需先排水，但仍先持 rank 35 CLEAN guard 并按步骤 4 建 queue。
6. 到期和取消只使用原 GRANT 的完全对称 REVERSAL；CHECK 或自然唯一键失败则来源持仓状态、返本和所有聚合一起回滚。

任意路径把等级行置 dirty 时，必须在同一事务执行统一 `MarkLevelDirty(tx,user_id,reason)`：推进 `dirty_generation`，读取用户当前 `relation_path_key` 并 upsert 同 generation 的 `level_recalc_queue`。只写 `dirty_at`、只发 Redis 或提交后补 queue 均为 P0；queue 可由 dirty 重建，但正常正确性不依赖修复作业。

一次性后绑定若用户已有有效持仓但没有下级，关系事务先在 `user_relation_stats` 增加新直属上级/前五层祖先的普通成员数并推进关系统计 `version`，再把该用户当前 `personal_active_value` 原子传播给新链的前五层祖先；若其已达到合格门槛，同时增加新直属上级的 direct qualified count 和前五层 team qualified count，并推进相关 `metrics_version/dirty`。绑定前发生的返佣和合伙人月度来源不追溯重算。

### 7.3 等级纯计算

纯函数输入固定为：

```text
LevelInput {
  personal_active_value
  team_active_value          // 不含本人
  active_holding_count
  direct_qualified_count
  team_qualified_count
}
```

函数内部只派生 `total_active_value` 并逐档比较，不接收当前等级，不加载配置，不读时间，不发送事件。它尤其不得发放奖励、不得更新任务、不得调用任何活动逻辑；这些副作用也不得通过回调偷偷注入。输出包含 `new_level` 和每档五项条件的判定明细，便于 API 与审计共用。

写服务负责：

1. 锁定 `user_levels`，读取指定的当前生效 PUBLISHED 规则版本和当前 metrics version。
2. 调用纯函数。
3. 若等级变化，更新 current/time；仅在新等级更高时更新 highest/time。
4. 写 `level_change_audits` 输入快照。
5. old flag 直接读取该行上次成功保存的 `is_qualified/qualified_level_snapshot/level_rule_version_id`，new flag 由本次规则纯函数返回；若二者变化，对直属上级 direct 计数、前五层祖先 team 计数做 `+1/-1`，并通过 `MarkLevelDirty` 为这些祖先建立下一波。即使 `current_level` 数值未变，规则的 qualified 门槛变化也必须传播。
6. 设置 calculated version；只有确认没有未消费变化时清空 dirty。

### 7.4 强一致资格刷新

`EnsureLevelFresh(user_ids, reason)` 是所有资格和资金消费者的统一前置，但绝不把任意深关系链扩成一笔固定点大事务。它使用“持久脏波 + 有界同步排水 + 最终快照线性化”：

1. 只使用 primary；先确认 `level_rule_runtime_roots.status=CLEAN` 且 active rule 与目标行一致。规则 rollout 未完成时资金/权益命令返回可重试 `LEVEL_RULE_ROLLOUT_PENDING`，不得混用新旧版本。
2. 在业务事务外按固定 `LEVEL_SYNC_WAVE_MAX` 排水。对每个目标先读其不可变 `relation_path_key`，再从 `level_recalc_queue(relation_path_key,user_id)` B-tree 的 `[target_path,prefix_upper(target_path))` 连续范围按 keyset 取剩余 N 行；多个目标数有接口硬上限并在内存去重。该 SQL 的物理读取上界为 `N + O(target_count)`，即使目标有百万 dirty 后代也不产生全量 bitmap/top-N sort，不枚举关系表。
3. 每个候选调用与 worker 相同的单波事务：事务外预收集“候选本人 + 当前前五层祖先”，去重按 `user_id` 升序锁齐并重验关系/metrics/dirty/queue/lease generation；只计算本人一次。old qualified flag 读取持久 `is_qualified + level_rule_version_id/qualified_level_snapshot`，new flag 按当前 serving（rollout 时为 effective candidate）规则计算，等级数值不变也可能产生资格 delta。若 flag 变化，同事务只对前五层祖先做计数增量，并为每个实际输入变化的祖先设置 `dirty_at`、`dirty_generation += 1`，以其当前二进制路径 upsert `level_recalc_queue`。该波最多锁/更新 6 个用户，不递归追加锁。
4. 候选只有在 `metrics_version/dirty_generation` 仍等于领取快照时才清 dirty/lease；并发新变化使条件更新 0 行并保留下一波。无论链多深，传播都由多笔至多 6 用户的事务向上推进，进程退出后 dirty 仍在。
5. 排水后，真正业务事务以 primary 的同一 statement snapshot 检查 runtime root CLEAN、目标行 clean/version 匹配，并对每个目标用上述路径范围索引 `LIMIT 1` 证明没有已提交的潜在影响 queue 行，再锁定目标等级行和记录资格快照。检查语句之后才提交的指标事件与本命令并发，资格判断线性化在该检查时点，只影响后续命令；此前已提交的 dirty 不可能越过检查。
6. 固定同步波数用尽但仍有潜在影响待办时返回可重试 `LEVEL_PROPAGATION_PENDING`，后台 worker 继续收敛；不能扩大单事务、返回 stale 资格或永久重试同一个超大闭包。关系不变量、负计数或 generation 冲突失败关闭并告警。

同步刷新和后台 worker 共用同一单波仓储与纯计算器，不能维护两套规则。普通展示可以返回旧值并明确 `stale/as_of`，资金决策只能取得第 5 步的 fresh token；token 绑定事务、目标集合、active rule、metrics/dirty generation 和检查时点，不能跨事务复用。

### 7.5 primary dirty worker

worker 分为不持有业务锁的领取事务和单波计算事务。领取事务在 primary 执行：

```sql
SELECT user_id
FROM level_recalc_queue
WHERE status IN ('PENDING','RUNNING')
  AND next_run_at <= :now
  AND (lease_until IS NULL OR lease_until <= :now)
ORDER BY next_run_at, lease_due_at, user_id
FOR UPDATE SKIP LOCKED
LIMIT :batch;
```

领取事务用同一条件写 queue 的 owner/until、递增 lease generation 后立即提交，不能覆盖未过期 lease，也不在持有候选行锁时动态锁祖先。随后执行上节同一个“本人 + 前五层祖先”单波事务；集合变化则回滚重读这一波，绝不扩大为递归闭包或晚锁。某波失败保留 `user_levels.dirty_at` 与 queue，租约过期后可重领；旧 owner/lease/dirty generation 的清标或删 queue 影响 0 行。多个 worker 通过 `SKIP LOCKED` 横向扩展，不需要 Redis 消费队列。每日 reconciliation 以固定 N keyset 查找 dirty 但缺 queue/queue generation 落后的行并修复索引，不能静默清业务 dirty。

规则切换由 `level_rule_runtime_roots` 的 SEEDING→DRAINING→VERIFYING 协议驱动：root 进入 SEEDING 后，所有可能改变等级输入的业务 writer 因 rank35 CLEAN guard 失败关闭。seed worker 按 `(user_id)` 每 Tx 最多 N 行设置 candidate dirty/generation并 upsert path queue；dirty worker 用 effective candidate 逐波原地计算；validator 以独立 keyset 证明所有普通用户均使用 candidate、`dirty_at IS NULL`、queue 为空、`calculated_metrics_version=metrics_version`，并核对资格人数分片 proof。只有 proof 完整且 root generation 未变，短事务才把 candidate 切为 serving 并回到 CLEAN；因此不存在 rollout 中的新指标写越过 validator，也不存在任何消费者读取混合版本。Redis 只加速。

### 7.6 五层团队返佣

1. 直接收益结算命令锁定来源事实，并用唯一键确认该业务日未结算。
2. 从 `referral_edges` 读取来源用户最近五层上级，按 depth 从近到远；同时保存 `ancestor_user_ids_snapshot`。
3. 对候选受益人执行 `EnsureLevelFresh`，再校验账号和团队收益资格。
4. 读取结算时当前生效的 `rule_versions(domain=TEAM_REBATE,status=PUBLISHED)`。`Robot Activation Voucher` 持仓及其他未真实支付本金的持仓明确排除；等级机器人等来源是否参与由已发布规则白名单决定。
5. 按 `calculation_mode` 走互斥分支。DIFFERENTIAL 以 `previous_effective_rate=0` 开始逐个处理 depth 1～5：每个候选先按等级和真实 depth 得到 `entitlement_rate`；候选不合格或账号非 ACTIVE 时直接记 FORFEIT、保持 previous 不变，合格 ACTIVE 才计算 `candidate_diff=max(entitlement_rate-previous,0)` 和 rounded amount。candidate diff 为 0 记 ZERO_DIFF，diff 正但舍入为 0 记 ZERO_ROUNDED，金额正才建 GRANT；三种合格裁决都把 previous 推进到 entitlement，ZERO_* 不建 settlement/freeze/ledger。FLAT 不读取或推进 previous，每个独立槽位必须先计算 base/rate、未舍入值和 rounded amount：ZERO_DIFF/ZERO_ROUNDED 只记 calculation audit；只有 rounded>0 后才按账号 ACTIVE 建 GRANT，否则建正额 FORFEIT。两种模式都不得把未授予或零舍入份额转给远层。
6. 每个来源组件无论最终有无正金额，都写唯一不可变 `team_rebate_calculation_audits`，保存五层完整规范候选与逐层 `GRANT|ZERO_DIFF|ZERO_ROUNDED|FORFEIT` 决定、账号裁决、未舍入值/舍入后值、previous 演进、舍入协议和 `calculation_trace_hash`。规范输入依次为来源种类/ID/组件、来源用户、规则版本、五层候选 `(depth,user_id,account_status,eligibility,level,entitlement_rate)`、各候选处理前后的 previous 与裁决；禁止把数据库行号、时间戳或 map 迭代顺序放入 hash。DIFFERENTIAL 的 forfeiture 保存 candidate diff rate 但 `not_granted_amount=0`；FLAT 每槽先裁决 ZERO_DIFF/ZERO_ROUNDED，只有 rounded>0 后才按 ACTIVE 建 GRANT或按非 ACTIVE 建正额 forfeiture。每个正金额 `team_rebate_settlements` 和实际 forfeiture 都引用该 audit；全为 ZERO_DIFF/ZERO_ROUNDED 时仍有一条可审计事实，重放必须命中相同 hash。
7. 直接收益事实、全部返佣事实及对应资产交易/分录同一 primary 事务提交。任一配置缺失、金额不守恒或资产写入失败，整体回滚并按原幂等键重试。

本方案明确选择同库原子结算，不保留“直接收益先成功、返佣进入异步异常账”的常态分支。批处理可把不同来源拆成多个事务，但单个来源事实不可拆。

### 7.7 合伙人来源分配

1. 合格的现金 `Playlet Backing` 或 `Robot Purchase` 成功时，在来源事务调用 `EnsurePartnerMonth(tx,earning_month)`，按月唯一键并发安全创建/读取根后以 `FOR SHARE` 确认 OPEN；`Robot Activation Voucher` 持仓及其他未真实支付本金的持仓不入池，2.0 不存在普通短剧支持券。
2. `pool_amount = round(pool_base_amount * 0.05)`，使用当时 partner rule version/金额 scale/舍入模式并保存关系前五层快照。`Playlet Backing` offer 和现金机器人商品发布时，必须以其最小合法 COMMON 基数验证 `pool_amount>0`；否则拒绝发布，来源事务绝不创建零金额 pool。
3. 在取得任何 user/asset 锁之前，按 `BusinessRootLockKey` 一次 ensure 并锁齐本次本人/五层祖先的 `partner_monthly_qualifications` 和全部受益人 `partner_settlements`；缺行也必须在月 fence 下按规范 key 顺序创建，不能在用户层之后因唯一冲突回头等待。对候选祖先在业务事务外完成强一致等级刷新，事务内复验 fresh token，并从已锁 qualification/level 行固化本来源发生前的 `family_active_value_before/partner_tier_before/level_snapshot`。
4. 以该来源前快照从近到远计算差额：只有 `current_level>=L4`、来源前已有合伙人档位且账号 ACTIVE 的候选参与；不合格或非 ACTIVE 候选不建 allocation，并令 `previous_effective_rate_after=previous_effective_rate_before`，更远的首个合格 ACTIVE 祖先仍从最近一次实际分配比例计算。合格候选的正 diff 若按快照舍入为 0，写入 pool fact 的规范 `ZERO_ROUNDED` trace 并推进 previous，但不写零金额 allocation；金额正才写 `partner_pool_allocations`。最多五项正分配，均强制保存 `family_active_value_before/partner_tier_before`；pool fact 的 `allocation_count/allocation_sum/allocation_hash` 仅证明全部正 allocation，`unallocated_amount=pool_amount-allocation_sum`；独立 `decision_trace/decision_trace_hash/trace_protocol_version` 保存逐层 `ALLOCATED|ZERO_DIFF|ZERO_ROUNDED|SKIPPED`，且 `0<=allocation_sum<=pool_amount`。本来源不得用自己刚增加的月活跃值提高本次档位或 allocation。
5. 完成本次 allocation 后，才对来源用户本人及前五层祖先原子增加当月 `family_active_value`，保存可对账的 `family_active_value_after`，并累加对应受益人的 OPEN `partner_settlements`；新的月活跃值只影响提交后的下一来源。来源撤销按 7.8 的唯一 REVERSAL 对称处理。
6. GRANT pool fact、monthly qualification、OPEN settlement 与 Backing/Purchase 来源事实同一 primary 事务提交；相同 source 重试返回原分配，不重复累加月活跃值或 settlement。来源用例的完整顺序必须是“来源订单/持仓根 → OPEN month 共享 fence → qualifications/settlements → users/levels/tasks → assets → 追加 pool/allocation”，不得在锁住用户或资产后才调用 Ensure。

### 7.8 合伙人来源冲正

1. `Playlet Backing` 提前终止或现金 `Robot Purchase` 持仓取消必须在该来源终态事务中锁原 GRANT，并以 `reversal_of_id` 创建唯一 REVERSAL；券持仓没有 GRANT，也不得伪造冲正。
2. REVERSAL 完整复制原 GRANT 的正数基数、池率、关系和规则快照，并为每条原 allocation 创建唯一反向 allocation；`operation` 提供负语义。重复/乱序取消命中同一 reversal；不得按取消时新等级或新关系重新分配。
3. 事务必须先锁原 `partner_months`，只以月根状态裁决。仅当 root=OPEN 时，才可按固定锁序把本人/五层 `family_active_value` 与各受益人的 0 代 `gross_amount` 按原快照精确减回，并写 `reversal_apply_mode=OPEN_MONTH`；任一结果为负说明数据不一致，整体回滚并触发 P0。qualification 或 0 代 settlement 即使字段仍显示 OPEN，也不能覆盖月根裁决。
4. root 为 CALCULATING/SEALED/CLAIMABLE 时一律不改原月 qualification、0 代/正代 settlement 或流水；REVERSAL 写 `NEXT_OPEN_ADJUSTMENT`。事务外按原 allocation 预收集全部受益人、稳定 adjustment 自然键和潜在 Finance recovery root，正式事务在用户层前锁齐；逐 allocation 执行两阶段 closure gate：ACTIVE，或原 allocation `source_persisted_at<=closure.requested_at` 的 CLOSING，创建唯一 `origin=SOURCE_REVERSAL/correction_mode=PRE_CLOSURE_SOURCE_CORRECTION` 负 adjustment 并在用户 adjustment root 分配 approval_seq；CLOSED 不创建 adjustment，而以 `reason=CLOSED_ACCOUNT/direction=RECEIVABLE` 建唯一 Finance recovery case。每条结果写对应 `partner_pool_reversal_dispositions`。来源终态、REVERSAL、全部 disposition 及 adjustment/case 必须同事务提交；第三方受益人的 CLOSING/CLOSED、余额或人工配合都不能否决付款人来源取消。没有 `CLAIMED` 月根状态，逐用户 CLAIMED 也不改变该分支。
5. 负调整不能令新月份可领金额小于 0；未抵完债务通过已发布 generation 的 `partner_adjustment_heads.remaining_after` 跨月携带，长期未清进入 RECOVERY_REQUIRED 告警。系统生成金额完全来自不可变原 allocation，因此不走人工双人审批；任何人工加减仍走 MANUAL 异人复核。

### 7.9 月度封账与领取

1. 统一 BusinessClock 确定 `earning_month` 半开区间。协调器先做无锁 readiness 预检，正式短事务依次锁前驱月和目标 `partner_months`；必须确认前驱已发布且没有活动旧代租约，再以 `WHERE status=OPEN` 转 CALCULATING。事务固定 source/adjustment cutoff、正 `calculation_version`、规则版本、分片数/seed/hash 协议、部署产物 `calculator_build_id` 及前驱 publication 证明，计算不可变 `contract_hash`，复验 `1<=shard_count<=256` 后创建 `partner_month_generations(BUILDING)` 和完整 shard 集并提交；它不扫描 allocation/adjustment，不生成用户结果。
2. worker 用短事务 `FOR UPDATE SKIP LOCKED` 领取 current generation 的 PENDING/可重试 FAILED/租约过期 RUNNING shard，写 owner/until 并递增 `lease_generation` 后立即提交。后续每笔事务都先锁 month `FOR SHARE`、再锁 generation `FOR SHARE`、最后锁该 shard，校验 month 仍 CALCULATING、root current version、generation=BUILDING 及 owner/lease_generation/lease，旧 owner 或旧 calculation version 的迟到写影响 0 行。
3. shard 先执行 STAGE_ALLOCATION：按自身 `[hash_start,hash_end)` 和冻结 cutoff，从 `partner_pool_allocations` 的月/hash keyset 索引每次读取最多 N 条，GRANT 写正、REVERSAL 写负的 `partner_month_sources`；来源行、count/amount/canonical hash 和 cursor 同事务推进。再执行 STAGE_ADJUSTMENT：只合并 `first_apply_month=本月` 的新 adjustment 与前驱月已发布 generation 的非零 head，两路各用独立 keyset cursor，并以 `NOT EXISTS partner_closure_adjustment_dispositions` 排除已终结 adjustment；为本 generation 写 ADJUSTMENT source 的同一事务再次锁/检查 disposition 唯一键。任何批次不得先全月 join/sort/hash 再 LIMIT。若 disposition 与 current generation 竞争，月/generation 锁令结果只能是“先 disposition，source 永不建立”或“先 source，disposition 回滚等待本代发布”，绝不两边都生效。
4. staging 完成后转 AGGREGATING。每笔事务按 sources 的真实 keyset 索引最多读取 N 行，以 `beneficiary_user_id` 分组；固定 carry 保存该用户累计 gross/adjustment/claimable、positive 与 closure 两组 source count/max/hash、阶段、最后 adjustment key、`settlement_id` 和 hash，不保存 ID 数组。首次读取某用户时，在当前 month/generation/shard owner fencing 下先插入或命中唯一 `partner_settlements(BUILDING)` 壳。ALLOCATION 行只累计 gross。进入 ADJUSTMENT 后按稳定优先级逐行应用：每读取一条 adjustment source，就立即在本事务为它至多写一条非零 application（非空 FK 指向该壳）和恰一条 head，更新标量 claimable/remaining 与证明后推进 `adjustment_apply_cursor`；因此 N 条输入最多产生 N 条 application、N 条 head 和至多 N 条首次 BUILDING 壳，即总输出不超过 `3N+O(1)`。每个用户组闭合只用 owner/lease/current generation CAS 把既有壳从 BUILDING 转 CALCULATED、写最终金额、两类 source proof 和 calculation hash并清 carry；不得遍历该用户历史 adjustment，也不得更新 adjustment 原行的 remaining/status。旧 owner 的 insert 命中同壳后仍不能越过 CAS。
5. 源 cursor 到尾且 carry 已冲刷后，shard 转 VALIDATING。验证事务以固定 N 分别 keyset 扫描本 generation 的 sources、settlements、applications 和 heads，重算 count/amount/canonical hash，并与各自 validation cursor 同事务推进。它还证明每条 ADJUSTMENT source 恰有一个 head、非零应用至多一条且 `remaining_before = applied_amount + remaining_after` 的有符号链连续，每条 application 的 settlement composite FK 指向同用户/月/代 CALCULATED 行，不存在 BUILDING 壳，也不存在与 closure disposition 重叠的 source。仅当全部 source/result/head 证明相等、没有悬空 application/head、owner/generation 仍匹配时条件转 SUCCEEDED；否则转 FAILED 并保留可恢复证据。一个 shard 至少由领取、若干 staging、若干 aggregate、若干 validate 事务组成，禁止“一 shard 一大事务”。
6. 发布事务按前驱月→目标 month→current generation→固定 shard ID 顺序加锁，只读取恰好 `shard_count<=256` 条 SUCCEEDED 证明，校验版本、范围连续、generation、租约、source/result/head count/amount/hash、contract hash 和前驱 publication hash。通过后同事务把 generation 置 PUBLISHED、month 写为 SEALED、`selected_calculation_version=原 current`、`current_calculation_version=NULL` 并设置 `sealed_at`；不扫描全月来源、不批量更新 settlement/application/head/qualification，因此仍是短事务。`processed_shards` 或 `job_runs` 不能替代证明；瞬时失败保持 CALCULATING 并从持久 cursor 恢复，绝不重开 OPEN。
7. 次月第 5 日达到规则定义的 `claimable_at` 后，单个短事务只锁月根并执行 `SEALED -> CLAIMABLE`；逐用户 settlement/qualification 不批量改状态。查询必须 join 月根所指 `calculation_version`，旧/失败/构建中 generation 永不可见。
8. 用户领取时先锁 command deduplication，再锁 month 根及其当前正 `calculation_version` 的唯一 settlement，执行两阶段 closure gate 后锁受益用户/资格行；仅 `claimable_amount>0` 才继续锁资产账户。锁内重查 month=CLAIMABLE、settlement=CALCULATED、账号裁决和 source cutoff。ACTIVE 正常领取；CLOSING 对 `closure_source_count>0` 必须验证 `closure_source_max_persisted_at <= account_closures.requested_at`，count=0 则必须是规范空 proof；两类 source hash/proof 均已由发布验证，不能扫描该用户海量 source，也不能用整月 cutoff 代替用户归属证明。正金额的资产入账与 settlement `CALCULATED -> CLAIMED`、幂等结果一起提交；纯负 adjustment 得到的零 settlement 可以 `positive_source_count=0`，但必须保留非空 closure proof，且不调用资产原语、不写 ledger，只原子转 CLAIMED并返回稳定 `ZERO_AMOUNT`。真正无来源的零行则两类 proof 都是规范空集合。两种分支均会解除 closure blocker。
9. 重复领取返回原 asset transaction；同键异语义冲突。封账后差异用 adjustment 进入后续月份，不改原 allocation/settlement。迟到来源、相邻月份并发封账、失败 generation 或并发 claim 均不能绕过 month publication pointer。

#### 7.9.1 `RestartPartnerMonthGeneration`

这是确定性计算器/证明缺陷导致当前代不能可信续跑时的唯一恢复命令，不等同于普通 `SealPartnerMonth` 或 `RetryJobFailure`。外部请求固定包含 `earning_month/expected_calculation_version/expected_contract_hash/replacement_calculator_build_id/reason/ticket_no/approval_no/idempotency_key`，完整进入 request hash，要求 `settlement.restart` 和异人审批；Use Case 在事务内以 `approval_no` 解析并锁定唯一审批行，内部 `approval_id` 不暴露给客户端。

短事务按命令防重→approval→前驱 month→目标 month→current generation→旧代最多 256 条 shard 加锁，仅当 month=CALCULATING、generation=BUILDING、期望版本/hash 完全匹配、旧 shard 全为 FAILED/终态或 lease 已过期且无活动 owner 时执行。它把旧 generation 及最多 256 条 shard 标为 ABANDONED并清 lease，令 root `current_calculation_version += 1`，以完全相同的规则、source/adjustment cutoff、shard_count、seed/hash 协议和前驱证明创建新 BUILDING generation/完整 shard 集；唯一允许变化的是已审批的 `calculator_build_id`，新 contract hash 显式包含它。审批消费、防重、旧代放弃、新代创建和审计同事务，任一点失败全部回滚。

旧代 sources/settlements/applications/heads 不 UPDATE、不进入后月 head、查询或领取；旧 worker 因 root current version + generation status + lease generation 三重 fencing 更新 0 行。新代从零 staging，不能沿用旧 cursor/carry/输出，也不能改变业务金额口径。若要改变规则、cutoff、前驱或 shard_count，必须修复来源/发布新规则并走显式后续 adjustment，不能滥用 restart。

### 7.10 剧集与一次性 VIP 直/间推返佣

1. 来源 Use Case 锁定 `episode_purchase_orders` 或 `vip_orders`，按 `referral_edges depth IN (1,2)` 取得当时直属/间接上级并保存快照。
2. 剧集基数严格等于 `paid_common`；EXPERIENCE 扣款不返佣。VIP 基数由已发布 TEAM_REBATE 规则从显式价/汇率快照确定并写回 `vip_orders.rebate_base_common`，不含优惠、赠送或自动续订。
3. 按 FLAT 规则对每个槽位先计算规范未舍入值和 rounded amount：base/rate 为零记 ZERO_DIFF，未舍入正但 rounded=0 记 ZERO_ROUNDED，两者只写 calculation audit；rounded>0 后才由账号 ACTIVE 建 GRANT，否则建正额 forfeiture。来源订单、权益/支付终态、所有 GRANT、`OpenFreeze(INCOME_FROZEN)`、任务进度和审计在同一 primary 事务提交。
4. `releasable_at` 到达后，worker 在 primary 小批量领取候选；正式事务按 GRANT → `PrelockUserClosures` → freeze → `LockUsersAndValidateClosureGate` → asset 锁定，确认来源早于 CLOSING cutoff 后调用 `ReleaseFreeze` 并转 RELEASED、唤醒 closure。CLOSED 前 blocker 会阻止未释放 GRANT，因此不能在 CLOSED 后入账；Redis 信号丢失不影响扫描。
5. 来源全额退款在同一退款收敛事务逐条创建唯一 REVERSAL：仍 FROZEN 的用 `SettleFreeze` 取消；已 RELEASED 且受益人钱包可写的走受控 EXPENSE；余额不足或受益人 CLOSED 时写唯一 Finance recovery 并终结该 REVERSAL 的本地处理，不得让它长期卡住付款人退款。重复/乱序退款只命中原 reversal/case，不会二次扣除或建案。
6. 用户通过 `ListRebates` 和 Income API 查看冻结/已释放/冲正状态；没有“手工领取返佣”命令。

| 合伙人来源取消 | 来源终态、唯一 pool REVERSAL、OPEN 月对称冲减或后续月 SOURCE_REVERSAL adjustments |
| 合伙人领取 | settlement 状态、claim、资产交易和分录 |
| 合伙人财务调整创建/审批 | approval、追加 adjustment、closure blocker 和目标开放月份标记；不改历史 settlement，CLOSED 不新增未来可领 |
| 合伙人构建代次重启 | 审批消费、旧 generation/shard ABANDONED、新 generation/shard、root current version、命令防重和审计 |

这些事务都在 default/primary。slave 只服务允许延迟的展示和报表，不能加入事务或提供锁前资格值。

### 8.2 可分批但不可丢失

- dirty 重算、规则切换、月度封账按小批事务推进，进度由数据库状态表达。
- 一个批次失败不影响已提交批次，但失败行仍满足可查询条件。
- 不用内存进度或 Redis LIST 作为唯一进度；进程重启后从数据库继续。
- 同库核心状态不写 outbox。提交后邮件、推送和埋点可消费普通通知；通知失败不影响等级或资金事实。

## 9. 幂等键

| 场景 | 幂等键/唯一键 |
| --- | --- |
| 活跃值增加 | `active:{holding_id}:activate` |
| 活跃值减少 | `active:{holding_id}:expire` 或明确 reversal ID |
| 等级重算 | `(user_id, rule_version_id, evaluated_metrics_version)` |
| 单来源日收益 | `(source_kind, source_fact_id, business_date, DIRECT)` |
| 单个受益人返佣 | `(source_kind, source_fact_id, beneficiary_user_id, rebate_type)`；business_date 只作快照，不进入唯一语义 |
| 返佣冲正 | `reversal:{original_rebate_id}` |
| 购买返佣释放 | `release:team_rebate:{grant_id}` |
| 合伙人入池 | `(source_kind, source_fact_id)` |
| 合伙人入池冲正 | `reversal_of_pool_fact_id UNIQUE`；每受益人 `(source_pool_reversal_id,user_id)` adjustment 唯一 |
| 合伙人分配 | `(pool_fact_id, beneficiary_user_id)`、`(pool_fact_id,depth)`；反向分配 `reversal_of_allocation_id UNIQUE` |
| 月度 settlement | `(user_id, earning_month, calculation_version)`；用户可见/领取只解析月根 selected version |

| 合伙人代次重启 | `(earning_month,new_calculation_version)` + 管理命令作用域 Idempotency-Key；expected old version/hash 全入 request hash |

每个 API 幂等记录保存请求摘要。相同键和相同语义返回原结果；相同键但月份、来源、金额或目标不同返回 `IDEMPOTENCY_CONFLICT`。数据库唯一约束始终是最终防线，分布式锁只能减轻热点。

## 10. 失败模式

| 失败模式 | 处理 |
| --- | --- |
| 没有当前生效的 PUBLISHED 规则或生效区间重叠 | 健康检查失败；等级/结算命令失败关闭 |
| 未知等级枚举、负门槛、档位重复 | 草稿校验拒绝，不能 schedule |
| 聚合减成负数 | CHECK 使来源事务回滚，触发 P0 数据告警 |
| `user_levels` 缺行 | 来源事务失败；禁止自动创建一行零值掩盖注册缺陷 |
| 活跃值事件重复 | 唯一键命中，返回第一次结果，不再传播 |
| worker 进程退出/Redis 丢消息 | `dirty_at` 或规则版本差仍在，下一 worker 继续 |
| worker 单行计算失败 | 保留 dirty、记录原因和重试次数，不清标记 |
| 同步波预算耗尽/规则 rollout 未完成 | 资金动作返回 `LEVEL_PROPAGATION_PENDING/LEVEL_RULE_ROLLOUT_PENDING`，保留 dirty；worker 仍按每波最多 6 用户继续，绝不永久重试一个超大闭包 |
| slave 落后 | 展示返回 stale/as_of；资格和资金改读 primary |
| 返佣规则缺层级或比例 | 单来源结算整体回滚，不按 0 静默跳过 |
| 返佣资产分录失败 | 直接收益与返佣整体回滚，原幂等键重试 |
| 合伙人来源冲正重复/乱序 | 原 GRANT 行锁 + reversal/adjustment 唯一约束返回原结果，不重复冲减 |
| 封账后来源冲正无足够未来收益 | 旧账不改；负 adjustment 跨 OPEN 月携带并进入 RECOVERY_REQUIRED 告警 |
| MANUAL adjustment 与注销并发 | 历史纠错先预锁潜在 Finance root，再由 closure/user gate 决定先后；CLOSING 只处理 cutoff 前登记事实并唤醒，CLOSED 普通调整拒绝、稳定历史来源才建外部 case |
| 冻结返佣释放 worker 中断 | GRANT 仍为 FROZEN 且 `releasable_at` 可扫；原释放幂等键继续执行 |
| 购买退款先于释放 | 唯一 REVERSAL 与 `SettleFreeze` 同事务，冻结额只最终扣除一次 |
| 购买退款晚于释放且余额不足/CLOSED | 原 GRANT 保持 RELEASED，唯一 REVERSAL 与唯一 Finance case 同事务提交并终态 EXTERNAL_RECOVERY；不产生部分扣回、负余额或静默核销 |
| Finance case 终结并发/豁免审批重放 | expected_version 只允许一个终态；waive 审批唯一消费，失败事务不改 case/source/审计，且全过程不取得来源、用户或资产锁 |
| 合伙人月封账对账不平 | 保持 CALCULATING，不进入 CLAIMABLE |
| 合伙人确定性计算器/证明缺陷 | 禁止从旧 cursor 继续；经 `RestartPartnerMonthGeneration` 放弃整代并以相同业务契约从零构建，旧代永不可见 |
| 并发领取 | 行锁和 `settlement_id UNIQUE` 保证仅一次入账 |
| 月封账后迟到来源 | 写下一期显式 adjustment，不重开历史 |
| 缓存失效失败 | 不影响真值；版本键/短 TTL 后自行收敛 |

## 11. 缓存与作业

### 11.1 缓存

- 当前生效的 PUBLISHED 规则按 `domain + version_id + content_hash` 缓存为不可变对象；生效指针短 TTL，发现新 ID 后原子切换。
- 等级资格、返佣和合伙人分配不得仅依赖缓存。强一致路径用 primary 行和明确 rule version。
- 团队 overview、level rules/gap 和返佣比例可短缓存，键包含 `user_id`、`user_levels.version`、`metrics_version`、`rule_version_id`；无法确认版本时不返回“新鲜”结果。
- 历史 rebate/settlement 列表可读 slave；领取状态和可领金额读 primary。
- Redis 队列可作为 worker 唤醒优化，但数据库 dirty 扫描是唯一可靠调度依据。

### 11.2 作业

| 作业 | 频率/触发 | 说明 |
| --- | --- | --- |
| `level_dirty_recalculate` | 持续 worker | primary + `SKIP LOCKED`，并行重算 |
| `level_dirty_sweep` | 每分钟 | 扫 dirty 和旧规则版本，确保不依赖队列 |
| `level_rule_rollout` | 规则到达生效点后持续 | runtime root 的 seed cursor、dirty wave 与 proof；每 Tx 固定 N，非 CLEAN 时资金资格失败关闭 |
| `level_metric_reconcile` | 每日 | 从有效持仓和五层边重算 personal/team/qualified count，并单独校验 `user_relation_stats` member count；只生成 diff |
| `level_rule_rollout_open` | 到达 effective_at | 只按 expected serving/version 把 runtime root 从 CLEAN 置为 SEEDING 并登记 candidate；绝不切 serving，最终切换仅由 `level_rule_rollout` 在 seed、drain、proof 全通过后的短事务完成 |
| `daily_income_rebate_settle` | 每业务日/追赶 | 按来源事实水位结算，幂等追赶漏跑日期 |
| `purchase_rebate_release` | 持续/分钟级 sweep | primary 扫到期 FROZEN GRANT，幂等释放冻结收益 |
| `finance_recovery_reminder` | 持续/人工协同 | 扫 Finance case 的 OPEN/IN_REVIEW 与 `next_action_at` 产生 SLA 告警；不自动扣钱包、解决或豁免 |
| `partner_month_close` | 月末后 | 冻结 cutoff，按稳定 hash/keyset 以固定 N 分阶段 staging/聚合/验证，短事务发布证明 |
| `partner_month_restart_sweep` | 只响应已审批人工命令 | 不自动创建代次；命令短事务最多放弃/创建各 256 shard，旧 owner fenced |
| `partner_claimable_open` | 每日 | 将达到领取时间且已 SEALED 的账单转 CLAIMABLE |
| `partner_closure_adjustment_dispose` | 连续/closure 唤醒 | primary 有界扫 CLOSING 用户最新已发布负 head；CALCULATING 时等待，OPEN 时先锁月阻止 staging 竞态；全额钱包扣回或全额 RECEIVABLE 终结，不做部分扣款 |
| `partner_reconcile` | 封账前后 | pool source、allocation、settlement、asset ledger 四方核对 |

对账发现漂移默认告警和生成差异清单，不直接覆盖聚合。修复必须通过有幂等键的纠错命令写 active ledger/change log/adjustment，保留为什么变动。

## 12. 权限与安全

1. 普通用户只能读取自己的等级、活跃值、返佣和 settlement；团队成员资料遵循关系篇五层权限。
2. 等级规则、返佣规则、合伙人规则分别需要配置权限和独立审批权限；创建人与审批人不得相同。
3. 财务 adjustment、月度封账、领取问题处理使用独立最小权限并记录 `operator_admin_id`、reason、ticket 和前后值。
4. 业务服务不能直接 UPDATE `user_levels` 聚合列，只能调用等级领域的幂等增量命令。
5. `workerd` 按部署 profile 注入最小仓储能力：等级重算 profile 只能更新等级域指定表；返佣释放 profile 额外获得统一资产原语所需权限。任何 profile 都不能直接 UPDATE 资产余额、用户身份或关系表。
6. 返佣和合伙人记录不可 UPDATE 金额或 DELETE；纠错使用 reversal/adjustment。
7. 所有资金决策先校验账号、团队收益能力和强一致等级；禁用只影响新权益，不删除历史记录。
8. API 不接受客户端提交等级、比例、depth、受益人或可领金额；这些全部由服务端关系和规则推导。
9. 日志不输出完整团队链或资产敏感信息；诊断使用业务号、user ID、rule version、metrics version 和 hash。

## 13. 指标、日志与告警

等级指标：

- `level_recalculate_total{mode=worker|sync,result,reason}`；
- `level_recalculate_seconds{mode}`、每批行数和 `SKIP LOCKED` 跳过数；
- `level_dirty_rows`、最老 dirty age、规则版本落后行数；
- `level_change_total{from,to,reason}` 和 `qualified_transition_total{up,down}`；
- `level_metric_delta_total{kind,sign}`、负数约束失败数；
- 等级分布、L0 提交后残留数、缺 `user_levels` 数；
- 强一致同步波次数、path-range queue 扫描/实际读取行数、预算耗尽数；单波锁行数超过 6 或一次范围读取超过 N 加固定 target 数立即告警。
- 规则 rollout 的 seed/drain/proof 进度、最老等待时间和资格命令受控失败数。

返佣和合伙人指标：

- 来源结算待处理数、最老业务日、成功/重试/失败数；
- 单来源受益人数、返佣总额/基数、零差额原因；
- 购买返佣 FROZEN/RELEASED/CANCELED、REVERSAL CANCELED_FROZEN/POSTED/EXTERNAL_RECOVERY 数量、最老待释放时长和 Finance case SLA；
- 幂等冲突和唯一键命中数；
- partner pool 来源额、池额、已分配额、未分配额；
- 月度 stats 行数、封账进度、calculation hash 冲突；
- CLAIMABLE 金额、领取成功/重复/失败、资产入账延迟；
- settlement BUILDING 壳数量/最老年龄、application 无父/跨用户 FK 拒绝数、CLOSING 负 adjustment disposition POSTED/RECEIVABLE/等待 CALCULATING 数及 source/disposition 重叠拒绝数；
- rebate/partner/asset 对账差异金额和记录数。

告警：

- 任何负聚合、缺等级行、未知规则版本、同域同一时点多条 PUBLISHED 版本生效立即 P0；
- dirty age 超过资格 SLA、同步刷新超限或规则切换长期未收敛告警；
- 来源事实已结算但直接收益/返佣/资产交易任一缺失立即告警；
- 合伙人封账不平、同用户同月多领取或 settlement 与资产金额不等立即 P0；
- worker 查询落到 slave、热路径出现五层子树聚合扫描应由运行时标签和 SQL 审计告警。

## 14. 验收用例

### 14.1 枚举、规则与纯函数

1. 验证 `UNSPECIFIED=0, L0=1, ..., L7=8`，数据库、Proto、配置逐值一致；未知值拒绝。
2. 全零输入首次计算得到 L1；已提交普通用户不存在长期 L0。
3. L2 在本人活跃值 49.99999999/50、有效持仓 0/1 的组合上边界正确。
4. L3～L7 对总活跃值、直属合格数、五层合格数逐项做阈值前一最小单位、等于阈值、超过阈值测试。
5. `team_active_value` 不含自己，纯函数只相加一次；展示总额与判定输入一致。
6. 纯函数在相同输入/规则下结果完全确定，不触发 SQL、时间读取、事件或活动写入。
7. current 可降级，highest 不下降；重复相同 metrics/rule 计算不重复写 change log。
8. 非单调但合法的测试配置仍逐档评估，不因中间档失败提前结束；发布界面产生风险警告。

### 14.2 原子增量与资格传播

1. 新持仓只增加本人 personal/count 和前五层 team active，第六层不直接增加。
2. 到期精确对称扣减；重复到期不重复扣，任意故障注入使持仓、资产、流水和聚合一起回滚。
3. 同一持仓来源即使更换 idempotency key 也只能有一条活跃值 GRANT 和一条引用它的 REVERSAL；重复生效、到期与取消乱序不改变最终聚合。
4. 两个下级并发增加同一祖先团队活跃值不丢更新，最终值等于两笔 delta 之和。
5. 用户从 L1→L2 时直属 direct 和五层 team 合格数各加一次；L2→L3 不重复加；L2→L1 精确减一次。
6. 多人同时跨 L2 时计数不丢失、不为负，并最终收敛到边表实时重算值。
7. 已有活跃值且无下级用户后绑定时，新增祖先立即得到正确 team active/qualified 增量；绑定前收益不追溯。
8. 注册绑定和后绑定都只在 `user_relation_stats` 增加一次 direct/team member count；与边表实时 COUNT 完全一致，`user_levels` 不出现这两个字段。
9. worker 被 kill、Redis 清空或节点重启后，dirty 行仍被 primary sweep 找回。
10. 两个 worker 使用 `SKIP LOCKED` 不重复处理同一 generation；计算中再发生指标变化时旧 owner 清标影响 0 行。
11. 构造深度大于 `LEVEL_SYNC_WAVE_MAX` 的合法链及宽团队，让最深成员变化触发多轮 qualified 跨线；每个传播事务只锁本人和前五层（最多 6 用户），同步预算耗尽时资金资格返回 retryable 而不误判，后台最终把所有波收敛到与规范重算一致。收敛前 target 的 path-range B-tree `LIMIT 1` 始终能发现潜在影响，收敛后资金命令成功；不得永久重领同一个超大闭包。

### 14.3 规则版本

1. DRAFT 可编辑，REVIEWED/PUBLISHED 不可编辑；创建人与复核人相同被拒绝。
2. 生效区间重叠、缺档、负值、重复等级、非法 qualified level 全部不能发布。
3. 切换新版本按 runtime root 执行 SEEDING→DRAINING→VERIFYING：百万用户只用固定 N keyset/单波事务，seed cursor、dirty generation 与 proof 可在任意写点崩溃后续跑；缺行、旧版本、未清 dirty 或 proof 不等均不能切 active。
4. 规则 rollout 期间等级/团队展示、注册、关系/等级指标写、购买资格、返佣和合伙人分配统一返回 retryable，不能读取或写入混合版本；不受等级影响的资产查询/认证仍可用。短事务切 serving 后才恢复。
5. 构造 `current_level` 数值不变但 candidate `qualified_level` 从 L2 升到 L3、再从 L3 降到 L2：old flag 必须取持久历史快照，new flag 取 candidate；前五层 direct/team qualified count 分别精确 -1/+1，审计保存前后门槛/规则，最终 proof 与规范重算一致。
5. 没有当前生效 PUBLISHED 版本时服务拒绝等级相关写入，绝不采用代码默认阈值。

### 14.4 五层返佣

1. 0～6 层关系分别验证只取前五层，depth 与 `referral_edges` 一致。
2. 未达等级、收益能力禁用、体验持仓和规则排除来源不获新返佣，原因可审计。
3. 同级/降序/升序受益链逐一核对 `previous_effective_rate`、`diff_rate` 和金额；在每个 depth 注入不合格、CLOSING、CLOSED 候选，断言 DIFFERENTIAL 跳过者的 previous before/after 相等、`not_granted_amount=0`，后续合格者只获得公式计算的正常差额，trace hash 重跑一致。FLAT 分别覆盖 ZERO_DIFF、正未舍入但 ZERO_ROUNDED、正额 ACTIVE GRANT 和正额非 ACTIVE FORFEIT：前两者不建 settlement/freeze/ledger/forfeiture，后者保存精确正 not_granted 且不转移。五层全部合格但 diff=0 时不产生零金额流水，仍有唯一 calculation audit 保存全部 ZERO_DIFF 决定。
4. 受益人结算前有 dirty 时强制 primary 刷新，不能使用 slave 或缓存旧等级。
5. 同一来源同一业务日重跑，直接收益、每个受益人返佣和资产分录均只有一份。
6. 在任一受益人记录或资产分录处注入失败，整个来源结算无部分提交。
7. 结算后改变等级或规则，历史的关系、等级、比例、金额和 rule version 不变。
8. 来源冲正产生等额反向事实和资产分录，原记录不可修改。

### 14.5 剧集与一次性 VIP 购买返佣

1. 剧集订单分别用全 COMMON、全 EXPERIENCE 和混合支付验证返佣基数只等于 `paid_common`；EXPERIENCE 部分不产生返佣。
2. 一次性 VIP 只按订单快照的 `rebate_base_common` 返佣；优惠、赠送、重复履约和任何自动续订入口都不能扩大基数。
3. 直属/间接两层分别命中 FLAT 比例，第三层及以后不生成 GRANT；同一订单重放只有一组冻结、流水和返佣事实。
4. 到期前收益仅存在于 COMMON frozen；到期 sweep 只释放一次，释放后 `user_assets.frozen` 与 ACTIVE freeze 求和一致。
5. 到期前退款取消冻结并创建唯一 `REVERSAL(CANCELED_FROZEN)`，只减少 pending、绝不进入 confirmed reversal；到期后退款能扣回时一次 POSTED，余额不足或账号 CLOSED 时不得部分扣回，只产生一次 EXTERNAL_RECOVERY 并引用唯一 Finance case，原 GRANT 保持 RELEASED；重复和乱序退款不重复扣款或建案。
6. 对同一 case 并发 start-review、resolve 和 waive：非法 OPEN→终态被拒绝，IN_REVIEW 只有一个匹配 expected_version 的终态成功；resolve 验证外部证据，waive 还必须验证 `direction=RECEIVABLE`、异人审批和 approval 唯一消费，PAYABLE waive 永远拒绝；两者都覆盖同键重放/异义冲突。管理锁轨迹只允许命令/可选 approval→recovery root→case，账号 CLOSED 时来源事实、`user_assets/version` 与 GRANT/REVERSAL 都不改变。
7. 在订单、权益、任务、任一 GRANT、freeze、余额或审计写入点注入失败，整笔购买无部分提交。

### 14.6 合伙人结算

1. Bronze～Envoy 在门槛前一最小单位、等于门槛和超过门槛时档位正确；系数明确按 30%/50%/70%/100%/100% 计算。
2. 当前等级 L3/L4 分界正确；不合格近层不占用 previous rate，较远合格层仍可取得正确差额。
3. 基础奖池恒为合格 `pool_base_amount` 的 5%，且每个 Backing/Purchase 来源在成功事务只创建一条 pool fact；连续 N 日收益结算仍只有这一条，不按日重复入池。体验/券/活动来源不入池。
4. 相同 source 重试不重复增加月家庭活跃值、pool source 或 allocation。
5. 月末封账按业务时区半开区间，不重不漏；pool、allocation、settlement 与资产对账一致。
6. 两个请求并发领取同一用户同一月份，只有一笔 claim、一笔资产交易，另一个返回原结果。
7. 未 SEALED、未到领取日、已领取、金额为零和账号收益禁用场景均有明确结果。
8. 封账后迟到来源和财务纠错只产生 adjustment，不覆盖已封账/已领取历史。
9. adjustment 创建人与审批人相同被拒绝；批准后只进入指定后续 OPEN 月份，冲正 adjustment 也只追加新事实。创建/审批与注销正反并发时，先登记的 PENDING 始终是 blocker，注销先转 CLOSING 后普通新调整失败；cutoff 前纠错会唤醒 closure，CLOSED 后 adjustment/settlement 不变且只允许外部 Finance case。
10. 在旧 generation 已提交部分 source/application/head/settlement 后模拟确定性缺陷：普通 retry 不得跳过坏输出；restart 的期望 version/hash、异人审批、活动 lease、0/257 shard 和同键异义逐项拒绝。合法 restart 最多锁/放弃 256 旧 shard并创建 256 新 shard，旧代输出永不可见、旧 owner 迟到写 0 行，新代从零得到与规范计算完全一致的唯一 PUBLISHED 结果。

### 14.7 性能与读写分离

1. 等级热读只按 `user_levels.user_id` 读取一行，不出现 `SUM(users.active_value)` 子树扫描。
2. 一笔指标变化最多直接更新本人加五层祖先；后续资格级联拆成同样最多 6 用户的持久波，普通写和单事务放大与关系总深度、团队宽度及全站用户量无关。
3. 五层返佣查找命中 `referral_edges` 主键/反向索引，不使用字符串码或数组切片。
4. dirty worker 只在 primary 锁行；slave 延迟测试不会造成错误资格、重复返佣或重复领取。
5. 用目标规模压测同步波排水、path-range queue、dirty backlog、规则 rollout、日结和月封账，记录 P50/P95/P99、锁等待、批次吞吐和追赶时间；一个目标有百万 dirty descendants 时 `EXPLAIN (ANALYZE,BUFFERS)` 仍必须是连续 B-tree range + keyset LIMIT N，实际读取不超过 `N+O(1)`，不得 bitmap/top-N/递归子树扫描；每个传播事务实际锁行上限为 6。
